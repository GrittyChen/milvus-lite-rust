## 问题

发行物目前由负责人在本机（macOS arm64 与本机 Docker 中的 Linux arm64）和一台远端原生 x86_64 主机上构建与验收。已发布的六个 RC（0.1.0rc1–rc3、0.2.0rc1、0.3.0rc1、0.3.0rc2）暴露出三类代价：

- **耗时与稳定性**：0.3.0rc2 候选端到端约 296 分钟，按 0019 并行后估计约 60 分钟；远端执行期间 SSH 断连、到 GitHub 的连接间歇超时，本机 Linux 容器遇到镜像站下载超时，本机还受合盖睡眠影响（见 [0.3.0rc2 验收](../testing/0.3.0rc2-acceptance.md)、[0019](0019-test-sharding.md)）。
- **证据层级**：Intel Mac 只有 Rosetta 上的构建与冒烟，0013 因此将其列为分层目标。
- **可复核性**：产物在个人机器上构建，第三方只能核对 Release 附件的哈希，无法核实它们由哪份源码、以何种方式构建。

0020 已在 GitHub 托管机器上完成三个标准平台的试点（[试点记录](../testing/0020-ci-pilot.md)），`main` 已启用必须通过 `ci-pass` 与 `compare-pass` 的分支保护。托管机器还提供原生 Intel Mac（`macos-15-intel`，4 vCPU / 14 GB），公开仓库的标准托管机器免费。

## 决策

在 CI 中从冻结提交构建全部发行物，并在托管机器上执行 0013 候选矩阵中可自动执行的部分；tag 与 Release 发布仍由负责人人工完成。Windows 不在本决策范围：首发构建期拒绝 Windows 目标是 0013 的产品决策，Windows 支持需要单独立项。

发行工作流只由 `workflow_dispatch` 触发，输入为冻结提交的完整 SHA、预期版本、演练开关（默认关闭，见「实施与试点」第 2 条），以及第 10 条要求引用的演练运行；运行标题固定为 `release v<版本>` 或 `dry-run v<版本>`。各阶段依次为：前置检查 → 冻结身份 → 构建 → 装配 → 验收 → 候选结果 → 正式来源证明。候选结果 job 依赖全部前序 job，只接受全部 success；正式来源证明 job 是最后一个 job，它成功才构成成功候选。

### 前置检查

1. **提交身份**：工作流必须从以冻结提交为最新提交的已推送分支触发。来源证明记录的是触发 ref 上的提交（`github.sha`），另行 checkout 其他提交会让证明指向错误的提交。前置 job 断言 `github.sha` 等于输入的 SHA、Cargo 与 Python 元数据的版本等于输入版本；全部 job 只 checkout `github.sha`。
2. **日常门槛**：`CI` 与 `Compare` 各自按工作流文件和 head SHA 列出同一 `github.sha` 的全部运行，不区分事件，取创建时间最新的一次（不是最新一次完成的）。该运行须 `status=completed`、`conclusion=success`，汇总 job（`ci-pass`、`compare-pass`）亦为 success，且该 attempt 的每个 job 都为 success：纯文档提交的运行会合法地跳过测试 job、汇总仍为 success（[0020](0020-continuous-integration.md) 公共约定 9），不能作为继承的证据，遇到时由负责人分别手动触发一次全量的 `CI` 与 `Compare`，待其完成后再触发发行工作流；queued、in_progress、cancelled、skipped、failure 均使前置检查失败。不按事件分开取，是因为任何事件触发的更新运行都是同一提交的新证据。选中运行的 ID 与 attempt 写入候选结果（第 12 条）；前置检查同时记录同一提交两个工作流全部运行的 ID 与最新 attempt；正式来源证明 job 在签发前重新查询一次，最新运行仍须是同一 ID 与 attempt，且全部运行的 ID 与 attempt 集合不变：此前有人启动新运行或重跑任何一次运行（包括较旧的运行，重跑不改变其创建时间），不论其排队、进行中还是已结束，即失败。该提交若出现过失败运行，按 0020「判定与流程」第 1 条须已写明根因，由负责人在触发前核对；有根因记录后可以手动重跑，但须等重跑完成并通过后再触发发行工作流。
   发行工作流以此继承源码级门槛：fmt、Clippy、MSRV、Windows 静态检查、工具自检与固定真值核验。差分与互通不在此列：`Compare` 用 `maturin develop` 或临时构建的 wheel 执行，与正式附件不是同一份字节，正式 wheel 上的差分与互通在第 9 条重新执行。
3. **版本唯一**：正式来源证明写入透明日志后不可撤回，因此版本在**正式签发步骤开始时即被消费**，不论该运行最终成功、失败还是结果不明；签发前失败的运行不消费版本，修复后可以用同一版本重试。演练不消费版本。前置检查拒绝已被消费的版本，判据为以下任一：
   - `v<版本>` tag 或同名 Release 已存在；
   - 本工作流中标题为 `release v<版本>` 的其他运行，其正式签发步骤已开始；
   - 版本台账（`docs/releases/consumed-versions.json`，按 main 最新提交读取）已登记该版本。
   只读 token 看不到草稿 Release；草稿只会在签发之后由负责人创建，此时版本已由前两项判据中的“签发步骤已开始”与台账覆盖。
   正式运行不得删除。删除权限无法由工作流阻止，因此另设台账：凡签发步骤已开始的运行，负责人在下一次正式运行前把版本、运行 ID / attempt 与结局提交到台账，透明日志中每组证明都能在仓库内找到对应记录。台账带格式版本，键集合固定；每条记录含版本、运行 ID、attempt 与结局（枚举：`candidate` 已签发待发布决定、`released`、`abandoned`、`signing-failed`），同一版本不得出现两次；签发步骤是否开始按该运行的每一个 attempt 判断，不只看最新 attempt；读取或校验失败都使前置检查失败，不当作空台账。工作流按版本设 `concurrency`，不取消进行中的运行，同版本的运行只能依次执行。成功候选若被放弃，下一个候选须换用新版本号；签发后的独立复审或发布授权仍可拒绝发布，但不会恢复该版本。
   **签发前与签发后的重跑**：签发步骤开始之前的任何失败（包括在签发门闩处拒绝、第 13 条的签发前复核失败、保全回执不符）都不消费版本，可以对同一运行「重跑全部 job」，或改开新运行；新 attempt 或新运行产生新的候选 ID，须重新保存并以新的审批行审批（第 20 条）。不得只重跑 attest 或只重跑失败的 job：前置检查与候选结果的 attempt 一致性守卫会拒绝。签发步骤一旦开始，该运行的任何 attempt 都不得重跑（第 20 条）。
4. 前置检查任一项失败（含第 19 条的签发环境预检），都在第一个构建开始前使工作流失败。只有前置 job 与正式来源证明 job 获得 `actions: read`，用于查询工作流运行。

### 冻结身份

5. 从 `github.sha` 生成 Git 归档及其 SHA256、完整源树清单（受版本管理的全部文件及软链身份）、产品 / 构建输入清单与工具版本（生成归档与清单所用的 Git 与 Python 版本，以固定键 `tool_versions` 记录），沿用 0013 候选阶段对每个冻结提交重新生成身份的要求。生成清单的工具迁入仓库，规则与过去候选使用的一致。普通测试日志、数据目录与构建缓存不进入这些清单；工作树出现未跟踪的构建输入即失败。生成工具纳入 0020 快速层的工具自检，覆盖软链、未跟踪输入、文件顺序与内容变化的变异用例，不只由发行工作流用自己的输出证明自己。

### 构建

6. 一次构建四个正式 wheel、sdist 与四个标准层的隔离 FI wheel。Linux 在按公开仓库摘要固定的 manylinux_2_28 镜像内构建（`quay.io/pypa/manylinux_2_28_x86_64@sha256:4131ddd7…` 与 `quay.io/pypa/manylinux_2_28_aarch64@sha256:abd1230a…`，见[首发准备验收](../testing/first-release-acceptance.md)）；两个 macOS 在各自原生架构上以 `MACOSX_DEPLOYMENT_TARGET=11.0` 构建；目标默认 CPU。wheel 以 `maturin build --release --locked` 构建；`maturin sdist` 没有 `--locked` 参数，作为唯一例外，由构建后的 `git diff --exit-code -- Cargo.lock` 与工作树洁净检查兜底。FI wheel 只用于验收，不发布。
7. 构建只发生一次。后续 job 下载同一组产物，先核对 SHA256 再使用，保证验收的就是将要发布的字节。

### 装配

8. 唯一的装配 job 核对正式集合恰为四个正式 wheel 与一个 sdist，FI wheel 不在其中；逐一计算 SHA256 并与各构建 job 记录的值对照，交出这份哈希清单供验收与候选结果使用。附件缺失、多出、混入 FI wheel 或哈希不符，均使工作流失败。

### 验收

9. 以下 0013 门槛在托管机器上执行，判据不变：
    - 归档与二进制检查（`check_artifacts.py`，正式与 FI 两类，含 glibc 2.28 动态库版本与 Mach-O 最低系统字段）；
    - 四个标准层：CPython 3.10 / 3.15 × 两条 SDK 的端到端全套，3.11–3.14 安装与联合冒烟，默认与完整 FI 的 Rust，FI wheel 恢复专项；
    - 四个标准层，正式 wheel 上的两条 SDK 完整差分与 Arrow 15 / 25 双向互通：沿用 0020 对照层的参照环境、分片与收集数，但 Python 侧改为安装装配 job 交出的正式 wheel（先核对 SHA256），安装后核对环境中原生模块的 SHA256 与正式 wheel 一致。互通用例另行调用的 Rust 示例与 FI 测试程序仍从冻结提交构建，属源码级组件，与过去候选相同；
    - Linux 的 LOCK、strace 与 PID 1（托管 Linux 机器自带 Docker；strace 需给容器 ptrace 权限）；
    - sdist：根与 `-m` 两种构建入口、PEP 517 安装，free-threaded / PyPy / Windows 的明确拒绝，以及在解包的 sdist 上执行 MSRV 检查（源码树上的 MSRV 已由前置条件继承，sdist 不含 `rust-toolchain.toml`，单独执行）；
    - 已发布上一版本读取新产物生成目录的兼容探针。
10. **PID 1 基础镜像**：0013 只记录了 `python:3.10-slim-bookworm` 两个架构的本地镜像 ID（arm64 没有仓库摘要），托管机器无法拉取，也不得改用可变的 tag。实施时为两个架构各固定一个可公开拉取的 `repo@sha256:...` 并写入本决策：amd64 为 `python@sha256:db6ee5170ebce0f4d165af242e8e77addc08bd9ffc37e8b1815752cf027aa4f8`，arm64 为 `python@sha256:f3902572f936b9e9a717644920d5c40d2c412d554625a9533bb1130f5afc1b8b`（`python:3.10-slim-bookworm` 于 2026-10-06 推送的两个平台清单，托管机器上可拉取待试点确认）；镜像内的 SDK 按固定依赖集合只用 wheel 安装；这是新的固定环境，不声称与 0013 的本地镜像等价。PID 1 结果记录镜像摘要、Docker 版本与内核。正式签发是最后一道门，签发后不再补跑人工候选门槛。因此两个架构的摘要固定并加入工作流之前，只运行诊断或演练；此后**每个**正式运行都须引用同一冻结提交上一次包含真实 PID 1 的成功演练，前置检查核对该演练的运行与 attempt 为同一 SHA、`mode=dry-run`、结论 success，且两个 PID 1 job 均成功，并写入候选结果。不从台账或其他状态推断“已做过”；正式运行自身的阶段矩阵也包含两个架构的 PID 1。
11. **运行环境沿用 0020 的公共约定**：完整历史 checkout 与 `persist-credentials: false`、完整 constraints（0020 只固定了 CPython 3.12 × pymilvus 3.0.2 与 3.10 × 2.6.17；本工作流新增的解释器与 SDK 组合各自生成固定的完整依赖集合）、不缓存 `target`、每个 job 的超时、锁文件与工作树洁净检查；判定同样沿用：显式 bash（pipefail）、零跳过、不加 retry、候选结果 job 只接受全部 success。测试与工具均取自冻结提交。兼容探针所用的上一版本及其附件哈希写入工作流，不在运行时取最新版本。
    完整依赖集合只用 wheel 安装，唯一例外是 Linux 上的 CPython 3.15：`orjson` 的 cp315 Linux wheel 只有 `manylinux_2_39`，无法在 glibc 2.28 的测试环境安装，而两条 SDK 都依赖它。为保持“CPython 3.15 + glibc 2.28 + 正式 wheel + 真实 SDK”的组合在目标用户态环境中执行，按以下约束处理，不扩大为允许其他依赖现场编译：
    - 只允许 `orjson==3.13.0` 从 sdist 构建，其余依赖仍来自固定 wheel；
    - 在独立 job 中分别针对 Linux x86_64 与 arm64，于固定摘要的 manylinux_2_28 镜像内用 CPython 3.15 构建；该 job 没有 `id-token`、`attestations` 或任何写权限；
    - 固定并记录 orjson sdist 的版本与 SHA256、maturin、Rust 工具链及其他构建依赖，以及生成 wheel 的 SHA256、ELF 架构与最高 GLIBC 依赖；
    - 同一平台两条 SDK 的环境安装同一份已构建的 orjson wheel，不在各环境中重复编译，结果写入该平台的环境与阶段证据。
    orjson 是被测试的客户端依赖，不进入正式附件。其他组合的依赖缺少目标平台 wheel 时，单独解析该解释器的依赖集合（例如 Python 3.15 不复用 3.10 的集合），不以现场编译补齐。

### 候选结果与正式来源证明

12. **候选结果**：全部验收通过后，候选结果 job 生成 `candidate-<版本>-<运行 ID>-<attempt>.json`（下称候选结果），作为候选验收记录的依据，取代过去仓库外的统一门槛脚本。它带格式版本，键集合固定，读取方缺键、多键或格式版本不认识都拒绝。阶段按仓库内固定的阶段矩阵（带矩阵格式版本）核对：四个平台与 sdist 的每个阶段、每个阶段的计数键与预期数量（分片执行的套件以收集数、执行数与分组数核对，Rust 以失败与 ignored 为 0 核对）、各平台的环境键都固定，缺平台、缺阶段、多阶段、计数或环境键不符都拒绝；工作流的预期计数也从这份矩阵读取。内容：
    - `mode`（`release` 或 `dry-run`）、`candidate_id`（由版本、冻结提交与本运行的 ID / attempt 组成）、本运行的 ID 与 attempt；
    - 冻结身份、所继承 `CI` / `Compare` 运行的 ID 与 attempt；
    - 四个正式 wheel 与 sdist 的文件名和 SHA256，FI wheel 另列；
    - 四个平台构建机的工具版本（`build_environment`：托管机器镜像、内核与 glibc 或 macOS 与 Xcode、rustc、cargo、maturin、uv），按平台固定键集合核对；
    - 每个阶段的退出码、计数与执行环境，包括第 9 条正式附件上的测试结果；环境记录托管机器镜像版本、内核与 glibc 或 macOS 与 Xcode、Docker、rustc 与 uv 版本（标准来源证明只记录构建器类型）。容器 job 内看不到宿主镜像版本，记录托管机器标签与固定的容器镜像摘要。
    随后生成最终的 `SHA256SUMS`，覆盖五个正式附件与候选结果；候选结果不记录 `SHA256SUMS` 的哈希，避免互相引用。
13. **正式来源证明**：最后一个 job，job 名 `attest` 与签发步骤名 `sign` 是版本消费判定的固定键。正式运行使用环境 `release-signing`，演练使用 `dry-run-signing`（第 19 条）。顺序固定为：**环境审批 → 签发前复核 → 保全回执 → `sign`**。获得审批后先复核：所继承 `CI` / `Compare` 的最新运行仍是同一 ID 与 attempt（第 2 条），版本仍未被消费（第 3 条）；再执行保全回执核对（第 20 条）；都通过后，以**一次** `actions/attest-build-provenance` 调用生成一个覆盖七个主体的证明：五个正式附件、候选结果与 `SHA256SUMS`，把它们的摘要绑定到仓库、工作流与冻结提交。一次调用避免多次调用部分成功、留下不完整的一组证明。证明写入公开的透明日志，不可撤回；任何人可用 `gh attestation verify` 核实。演练运行不执行这一步，只为演练候选结果签发证明，见「实施与试点」第 2 条。
### 平台调整（负责人已确认）

14. **Linux x86_64**：`ubuntu-24.04` 托管机器上的 manylinux_2_28 容器承担标准层，远端原生主机退出必选候选矩阵，保留为**只供诊断**的老内核兼容抽查：候选改动涉及 CLI 启停、端口、网络、LOCK 或持久化时，可在正式运行前用同一冻结提交的演练产物运行一组轻量冒烟。远端主机不是工作流的 job，其结果无法由前置检查或候选结果机器核实，因此不作为候选门槛，也不写入候选结果；抽查发现问题时按缺陷处理，由负责人决定是否继续该候选。它不是正式附件的字节证据，不能替代标准层，也不据此宣称正式 wheel 已在老内核验收；发行记录关于老内核只引用 0013 决策 1 记录的内核 3.10 历史证据。
15. **Linux arm64**：`ubuntu-24.04-arm` 托管机器承担标准层，本机 Docker 退出必选候选矩阵，保留作故障复现与本地诊断，不产生独立的候选通过结论。
16. **Intel Mac**：升级为标准层，在 `macos-15-intel` 上原生运行，执行与 macOS arm64 相同的适用门槛，包括第四个 FI wheel 的内容检查与恢复专项、默认与完整 FI Rust、Python 端点全套与 3.11–3.14 联合冒烟；README 与发行说明的支持矩阵相应修改。试点须证明 CPython 3.15、两条 SDK、参照依赖与资源限制均可行；不可行时回到评审，不保留标准层名称而减少门槛。
17. **仍无法覆盖**：macOS 11 真机（托管机器没有该系统，与现状相同）、真实断电。
18. **资源暂不清理**：远端主机上的镜像与工具链、本机的 Docker 卷与固定身份镜像，等首个 CI 候选完整通过、0013 与 README 完成相应修订后再单独授权清理；远端老内核探测材料至少保留到首个 CI 候选证明没有不可替代的兼容证据。

### 发布与权限

19. 发行工作流默认只有 `contents: read`；前置 job 另有 `actions: read`；正式来源证明 job 另有 `actions: read`、`id-token: write` 与 `attestations: write`，且只接收待签发的文件。工作流不获得 `contents: write`，不能创建 tag 或 Release。
    候选结果与正式来源证明之间有一个只读 job `preserve-digests`（只有 `contents: read`），重新计算 `fi` 产物中四个 FI wheel 的摘要并与候选结果的 `fi_wheels` 交叉核对，作为 job 输出交给正式来源证明 job；正式来源证明 job 仍只接收待签发的七个文件。
    **必需的仓库设置**（由负责人设置与变更，不属于任何阶段结束后的清理）：

    | 设置 | 要求 | 缺失或偏离的后果 |
    | --- | --- | --- |
    | 环境 `release-signing` | 只有一条 `required_reviewers` 规则：审批人恰为仓库所有者一人，规则内 `prevent_self_review=false`；环境 `can_admins_bypass=false`、`deployment_branch_policy` 为空；不设等待计时器、环境 secret 或变量 | 缺失或任何偏离：正式运行在前置检查失败，不进入构建；等待审批期间被删或被改：保全回执的复核失败或筛不出审批，`sign` 跳过；均不消费版本 |
    | 环境 `dry-run-signing` | 无保护规则 | 被删除时 GitHub 会在下一次演练自动重建无保护的同名环境，演练照常运行，但会掩盖配置缺失，因此作为必需设置记录，不依赖隐式重建 |
    | 发布不可变 | 开启（0013 决策 6） | 沿用 0013 |

    改动 `release-signing` 后，下一次正式运行之前先以只读接口读回其配置。
    **签发环境预检**：正式运行在前置检查中读取 `release-signing`，按上表核对，审批人按用户 ID 比较（所有者 ID 取工作流上下文）；等待计时器、部署分支规则或第三方规则都拒绝，否则在第一个构建之前失败。保全回执步骤在读取审批记录之前再复核一次，防止等待期间配置被改。两处都只用现有 `GITHUB_TOKEN` 的 `actions: read`，环境名为字面量，不来自输入。预检只让失败更早、更清楚，不替代保全回执的核对（第 20 条）。
20. 产物以工作流产物交出（保留 30 天）。Release 附件为四个正式 wheel、sdist、候选结果与 `SHA256SUMS` 共七个文件，FI wheel 不在其中。负责人在签发前按下文保存完整候选证据集，签发后用发布准备工具核对，再按 0013 决策 6 先建草稿、上传、核对，后发布不可变 Release。发布准备工具在创建草稿前：
    - 以 `gh attestation verify --format json` 验证七个文件的来源证明，限定仓库、签发工作流与冻结提交；每个文件的全部证明都须来自候选结果声称的那次运行（`invocationId` 中的运行 ID 与 attempt），主体恰为这七个文件，即同一次多主体签发；
    - 解析候选结果：格式版本与键集合正确，`mode=release`，版本与准备发布的版本一致且没有 tag / Release 冲突；版本台账中该版本无条目，或条目正是这次运行且结局为 `candidate`；
    - 五个正式附件的文件名与 SHA256 与候选结果及 `SHA256SUMS` 完全一致，`SHA256SUMS` 恰好覆盖六个文件；
    任一项不符即拒绝。
    发布准备工具与公开下载检查都使用候选冻结提交（即 tag）中的工具：阶段矩阵随测试数量变化，用后来的工具校验较早的候选会按矩阵不符拒绝。
    发布后的公开下载工作流（手动触发，只读取公开地址，不需要写权限）重复同样的核对：先验证候选结果的证明，再从候选结果核对五个正式附件的哈希与证明，然后安装冒烟。附件缺失或多出、候选结果被删除或篡改、`mode` 不是 `release`，均使检查失败。判定按行为描述：正向要求 verify、四个平台 install 与 public-pass 全部成功；负向要求 verify 在预定步骤失败、install 没有执行任何安装、public-pass 失败；不以 GitHub 对未展开矩阵显示的占位 job 数量为条件。工作流内的 `main` 守卫只约束未修改过的工作流文件，引用公开检查结果时核对运行元数据：`head_branch=main`、`head_sha` 为当时的 `main`、工作流为已合入的 `public-check.yml`。版本、tag 与发布继续分别授权。
    **签发前保全与签发后补存**：对一次签发已开始的正式运行整体重跑会删除此前 attempt 的全部工作流产物（见[试点记录](../testing/0021-release-pilot.md#失败注入-b-阶段签发开始即消费)），而透明日志中的证明不可撤回、版本已经消费，附件字节一旦丢失只能换版本重来；人工在候选结果 job 完成后下载也无法保证先于签发（[试点记录](../testing/0021-release-pilot.md) C 阶段「观察」）。因此以签发门闩使保存成为签发的前置条件（机制与实测见 [0022](0022-pre-signing-preservation-gate.md) 与其[试点记录](../testing/0022-gate-pilot.md)）：
    - **完整候选证据集**是候选结果产物中的七个来源证明主体，加上 `fi` 产物中的四个 FI wheel（候选结果记录其哈希，按[证据的存放与复核范围](../testing/README.md)属于本地留存）。七个来源证明主体是公开发布的门槛，不是完整的候选证据集；
    - **签发门闩**：正式来源证明 job 在 `release-signing` 获得审批之前不分配执行机、不执行任何步骤；演练使用无保护规则的 `dry-run-signing`，不暂停；
    - **保存**：attest 等待审批期间，负责人在冻结提交的干净 worktree 中执行 `tests/release/preserve.py save --mode release`；前置条件、来源、核对、原子完成、目录布局、恢复与回执的定义以 [0022 第 2 节](0022-pre-signing-preservation-gate.md#2-保存时点与候选产物来源)为准。两个原始 zip 存于保全目录的 `zips/`，不进入回执，`preserve.json` 记录各自的产物 ID、API digest 与 SHA256，复核时与 `zips/` 的文件交叉核对；同一存放根以 `flock` 互斥，接受的残余见 0022 第 2 节。保存与复核都通过后，工具末行输出审批行 `preserved <候选 ID> <回执>`；
    - **放行**：负责人以该审批行原文批准。保全回执步骤用七个主体与 `preserve-digests` 的输出独立计算回执，再读取本 attempt 的审批记录：出现任何 `rejected`（不论备注）即失败；其余记录按备注逐字等于 `preserved <本次候选 ID> <本次回执>` 筛选，必须恰好一条，且 `state=approved`、环境恰为 `release-signing`、审批人为仓库所有者；审批记录接口不可用或返回异常按失败处理，不重试掩盖。任何一项不符，`sign` 跳过，版本不消费；
    - **签发后补存**：签发成功后，负责人的第一项操作是在同一保全目录的 `post-sign/` 下补存证明包、Rekor 记录、签发证书、检索结果、attest 日志与 closeout，然后重新执行 `verify`，回执必须不变；此后才进行发布准备、台账更新、分支清理或后续发布操作；
    - **禁止重跑**：真实候选的正式运行，sign 步骤一旦开始，该运行的任何 attempt 都不得重跑，包括重跑全部 job 与只重跑失败的 job（后者是否同样删除产物未实测，一律禁止），没有例外。发行流程的故障注入经负责人逐次授权、先保存所需的全部证据后可以重跑，且只能使用专用的、永不发布的测试版本；
    - 自动写入外部不可变存储未采纳，理由见 0022。

### 证据

21. 按[证据的存放与复核范围](../testing/README.md)分开归类：
    - 构建来源证明及透明日志：公开，第三方可核实附件摘要与冻结提交的对应；
    - 候选结果：作为 Release 附件公开且不可变，由来源证明覆盖，是测试结果与正式附件之间的持久连接；
    - CI 运行日志：公开但有保留期限，候选验收记录引用运行链接与提交号，负责人另行下载作为本地留存；
    - 工作流产物：job 间与交给负责人的临时交接物，需要仓库访问权限且 30 天后过期（工作流对每个交接上传显式设置，不依赖仓库默认保留期；只在失败时上传的诊断记录保留 14 天），不是公开产物；候选 wheel 与 sdist 由负责人本地留存，以相同字节进入不可变 Release 后才成为公开产物。

## 实施与试点

1. 本方案经评审通过后实施，0020 合入 main 前在 `ci/release` 分支上本地推进，不推送。
2. 试点在当前 main 上构建一组不发布的演练候选（版本保持现值）。前置检查的版本唯一性对已发布版本必然失败；改用未发布的版本号又须同时修改 README 安装命令与检查器，偏离真实候选。因此工作流设一个默认关闭的演练输入，开启时与正式运行只有以下差别：
   - 跳过版本唯一性检查，也不消费版本；
   - 不执行正式来源证明，五个正式附件与 `SHA256SUMS` 都不签发。这些文件保持规范文件名，供检查器、安装与验收使用；若照常签发，透明日志会永久留下另一组已发布版本附件的有效证明。改用 `dry-run/<run-id>/` 前缀的主体名称也不够：`gh attestation verify` 按文件摘要查找证明，不核对主体名称，演练 wheel 的字节仍能通过验证。演练改为签发两个只属于本次运行的文件：文件名前加 `dry-run-` 的演练候选结果，以及覆盖它与五个附件的 `dry-run-SHA256SUMS-<运行 ID>-<attempt>`。两者的摘要都因含运行 ID 而唯一，与正式附件无关。仍用一次多主体调用签发，以 `gh attestation verify` 验证，实测签发与验证机制及“一次调用生成单个证明”；并核对证明中的 `resolvedDependencies[0].digest.gitCommit` 等于演练提交；
   - 候选结果的 `mode` 为 `dry-run`，运行标题与工作流产物名称标明演练。
   其余构建、测试、装配与候选结果与正式运行相同。演练产物不得上传为 Release 附件，发布准备工具与公开下载工作流都拒绝 `mode=dry-run`。七个主体的正式签发已以测试版本 `0.0.1rc903`（[0021 试点](../testing/0021-release-pilot.md) C 阶段）与 `0.0.1rc904`（[0022 试点](../testing/0022-gate-pilot.md)）实测，真实候选沿用同一流程。完整执行发行工作流，与 0.3.0rc2 候选的阶段与计数逐项对照。
   演练保存：`preserve.py save --mode dry-run` 只用于已成功完成、`sign` 成功的演练，保存演练候选结果、`dry-run-SHA256SUMS-<运行>-<attempt>` 与 `fi` 产物，存放根为 `<根目录>/dry-run/<版本>/`，末行为 `dry-run-receipt <候选 ID> <回执>`；该行不能用于审批，正式与演练的运行、产物与候选结果不能混用。
3. 失败注入，在临时分支执行、不合入，每项都须使工作流失败，且不产生可被误认为候选通过的候选结果：
   - 从非冻结提交的分支触发；
   - 同一提交的 `CI` 失败而版本与构建正常；旧运行 success 而新运行 in_progress；旧运行 success 而新运行 failure；签发前对同一提交启动新运行；
   - 版本已存在；同一版本已有签发步骤开始过的运行；版本台账已登记；版本台账格式错误或同一版本重复；
   - 正式运行未引用演练；引用的演练不是同一 SHA、不是 `mode=dry-run`、结论不是 success 或缺少成功的 PID 1 job；较早 attempt 已开始签发而最新 attempt 未签发；
   - 某个构建 job 失败；产物缺失、多出或混入 FI wheel；哈希不符；未跟踪的构建输入；
   - 把正式 wheel 替换为同名的其他构建，差分与互通阶段必须失败，不能只依赖原 `Compare` 运行；
   - 在正式签发前注入测试失败：任何正式主体都不得有证明（`gh attestation verify` 报告找不到）；
   - 正式签发失败：该版本视为已消费，随后同版本的运行被前置检查拒绝。
   另有一组反证，结论为拒绝而不是工作流失败：
   - 把演练候选结果交给发布准备工具；
   - 对演练产出的五个文件执行 `gh attestation verify` 必须报告找不到证明，演练证明的主体列表中不得出现五个正式文件名；
   - 公开下载检查遇到候选结果被删除或篡改、`mode` 被改为 `dry-run`、演练候选结果混入 Release、附件多出或缺失。
   失败注入中涉及正式签发的项会真实消费版本，使用专门的未发布测试版本号并登记台账，不占用真实候选的版本。
4. 实施时在 0020 快速层加入冻结身份生成工具的自检（第 5 条），工具自检的收集数随之更新；版本台账随工作流一起建立，初始为空，已发布的 RC 由 tag 判据覆盖。最终采纳（2026-10-27）已同步修订 0013 的候选矩阵、Release 附件集合（增加候选结果）、资源说明与决策 7 的镜像保留要求，[证据的存放与复核范围](../testing/README.md)中来源证明与临时工作流产物的边界，以及 AGENTS 索引与常用命令；README 与发行说明的支持矩阵在首个 CI 候选的版本切换时修改。
5. Windows 是否立项另行决定。
6. **未采纳与后续**（据 [0022 试点记录](../testing/0022-gate-pilot.md#未采纳的提速提案)）：
   - SDK 线与 Python 端点矩阵保持完整（第 9 条不变）；缩减属于支持声明变更，至少在一个真实 CI 候选完整通过后另立决策，并修订 0013、本决策与验收记录；
   - 正式运行继续从冻结提交独立构建全部附件（第 6、7 条不变）；复用演练产物需要独立的候选身份与来源证明设计，并重新完成全平台试点；
   - 只读接口的有限重试与发行工作流的编排调整都未实施，首个真实候选之后若仍需要，分别单独评审；前者须同时修订第 11 条；
   - 门闩失败信息是否省略期望审批行，属可观测性改进，不影响合同。
