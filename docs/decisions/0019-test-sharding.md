## 问题与实测

下表按各平台步骤记录（`steps.json` 一类文件的起止时间）逐项求和，不含步骤之间的间隔；差分、互通与 Python 全套按 pytest 自报时长计，避开主机睡眠与远端断连对墙钟的影响。

| 阶段（分钟） | Linux x86_64 | Linux arm64 | macOS arm64 |
| --- | --- | --- | --- |
| 两 SDK 完整差分（各 420 项） | 42.7 + 42.8 | 26.1 + 26.6 | 17.6 + 15.0 |
| Arrow 15 / 25 互通（211 项） | 34.0 | 18.7 | 8.7 |
| 安装阶段（含 4 轮 Python 全套，自报合计） | 16.8（15.0） | 11.9（10.9） | 13.9（13.1） |
| Rust / 构建 / 静态 / 回退等其余步骤 | 4.5 | 3.4 | 10.9 |
| PID 1 | 13.8 | 0.2 | 不适用 |
| 合计 | 154.6 | 86.9 | 66.1 |

arm64 差分 3.0.2 的步骤墙钟为 45.2 分钟，其中约 19 分钟为本机合盖睡眠、Docker VM 挂起；按 pytest 自报为 26.6 分钟，两条 SDK 线并无明显差别。arm64 PID 1 的镜像层命中缓存，完整探针（正常、强杀、排空三场景）用时 11.4 秒；x86 未命中，构建期间直连下载约 18 个依赖。

rc2 的平台顺序为 Mac → 本机 arm64 → 远端 x86，x86 中途才改为独立运行，端到端约 296 分钟。远端 x86 是独立物理机，若从一开始就与本机序列同时进行，端到端约等于两者中较长的一个（约 155 分钟），无需改动任何测试。

x86 差分单轮平均 6.1 秒、中位数 5.4 秒，超过 10 秒的约 30 项，最长为 32768 维距离用例约 54 秒。差分有三类用例：

- 276 项使用函数级 `pair`（[test_reopen.py](../../tests/differential/test_reopen.py)），每次打开都启动新的 3.x 参照子进程与 Rust 服务，含重开的用例启动多次；占单轮约 83% 的时间，中位数约 8.4 秒。
- 117 项使用会话级 `diff`，共享同一个进程内 Rust 服务和同一个 3.x 参照进程（[conftest.py](../../tests/differential/conftest.py)），合计约 6.9 分钟，中位数约 1.1 秒。
- 27 项不使用这两个 fixture：23 项为比较器自身的用例，不启动服务；3 项 CLI 用例与 1 项 fork / LOCK 探针用例自行启动子进程服务。

两条 SDK 线的同步 `create_index` 都在第一次查询索引状态前无条件等待 0.5 秒，每次调用在每个服务上各等一次；这是客户端空等，可由并行吸收。3.x 参照冷启动主要是导入的 CPU 开销，并发时会争用 CPU。互通每个用例多次冷启动 3.x 参照解释器与 Rust 工具二进制，数据在各自的 `tmp_path` 中，个别模块级 fixture 使用共享临时目录，Cargo 调用写仓库的共享 target。

按 x86 JUnit 实测耗时做最长处理时间优先分配，单轮差分在 2 / 4 / 8 片下的理想下限为 21.4 / 10.7 / 5.4 分钟。该估计不含进程启动与资源争用，只说明上限；JUnit 耗时含 setup / teardown，模块级 fixture 的成本只记在首个用例上，分片后各片会重复承担。会话组约 6.9 分钟不可拆分，构成分片均衡的下限。实际收益以试点为准。若试点选定的 N ≥ 3，P1 之后 x86 最大的串行块将是安装阶段（4 轮 Python 全套约 15 分钟）；N = 2 时仍是单条差分线。

## 不损失测试效果的定义

本方案只改变执行方式。以下任何一条不成立即视为回退：

1. 用例集合与同一源码的串行收集逐项相同，并以插件记录的 nodeid 机械核对；不删除、合并或跳过用例，不放宽断言，不增加重试；基线三平台两套件的 skip / xfail / xpass 均为 0，执行中也必须为 0。
2. 保持现有 fixture 作用域：函数级用例仍各自启动服务；使用会话级服务的用例仍在同一个会话中、按原相对顺序执行。两条 SDK 线、三个标准平台及互通矩阵保持 0013 的范围。
3. tests/differential、tests/storage_interop 与 tests/conftest.py 和冻结源码逐字节一致；分片插件放在这些目录之外，只做筛选、不改变用例。SDK 固定等待、同步建索引、关闭重开与持久化步骤因此保持不变。
4. 每个进程的退出码、nodeid 并集与计数都进入统一门槛；失败不以“并行偶发”为由放行。

## P0：编排层并行（不改测试）

1. **跨主机**：远端 x86 与本机序列同时启动，各自独立完成并分别取证。macOS 原生与 arm64 Docker VM 共用本机，二者是否重叠，与 arm64 的并发度一起按试点的资源记录确定。
2. **同平台套件**：两条 SDK 的完整差分与互通作为三个 pytest 进程同时运行。每个进程使用独立的 `--basetemp`、`TMPDIR`、日志与 JUnit，并加 `-p no:cacheprovider`，避免并发写冻结源码树中的 pytest 缓存。Rust 服务在各自进程内，参照服务为各自子进程，端口由系统分配；SDK 端点缓存已有[函数级隔离](../../tests/conftest.py)。启动时显式将 SIGINT / SIGQUIT 设为默认处理，并在开始前记录实际处理函数。
3. **互通预构建**：并行开始前，用与用例完全相同的环境（`CARGO_TARGET_DIR`、profile、增量与 `PYO3_PYTHON` 等）逐字执行互通用例中的三条 Cargo 命令，再加 `--message-format=json` 复跑，确认全部产物为 `fresh` 并留证。三条命令是：
   - `cargo build -p milvus-lite-core --example storage_interop --quiet`（[test_cross_implementation.py](../../tests/storage_interop/test_cross_implementation.py)）；
   - `cargo test -p milvus-lite-core --features fault-injection --test crash_recovery --no-run --message-format=json`（同上）；
   - `cargo build -p milvus-lite-core --features fault-injection --example index_change_fault --message-format=json`（[test_index_storage_interop.py](../../tests/storage_interop/test_index_storage_interop.py)）。

   FI 特性的 core 构建会覆盖用例直接使用的 example 路径，因此 Rust / FI 阶段不与互通同时运行。
4. **保持串行**：Python 全套与四组安装阶段保持串行，不与差分 / 互通同时运行，因为其中有按 CPU 速度标定的时序用例（[停服在途请求](../../tests/python/test_server_manager.py)）。Rust / FI、构建、PID 1、回退与 LOCK / strace 阶段维持原顺序。
5. **记录**：候选验收在调度一节写明并行的阶段、并发度与资源条件。本机运行期间持有防睡眠断言，并保留电源日志。各阶段的通过判据不变。

**残余风险**：差分的 CLI 用例（[test_cli_server.py](../../tests/differential/test_cli_server.py)）先绑定 0 号端口、关闭后交给子进程，并发时其他进程可能在这一窗口取得同一端口。本实现的 CLI 不设 SO_REUSEPORT，冲突时报绑定错误；3.x CLI 设有 SO_REUSEPORT，极小概率与其他进程共用端口，表现为结果不一致。两种情况都以用例失败暴露，不会被判为通过。彻底消除需要改动用例，不在本方案范围内；试点在最大并发下重复验证。

## P1：确定性分片

差分与互通各自切成 N 个独立 pytest 进程，仍按 P0 同时运行，平台总并发为两条差分线各 N 片加互通 N 片。工具放在 `tests/sharding/`，只依赖 pytest，不引入 pytest-xdist。

1. **收集**：插件在 `pytest_collection_finish` 中把收集到的 nodeid 逐行写成文件，不解析 `-q` 文本输出（nodeid 可能含空格、引号与方括号）。收集出错、出现模块级 skip 或数量与串行基线不一致时停止；条件型 skip 只能在执行阶段判定，由第 5 步的零 skip 要求拦截。收集与执行使用同一解释器、参数、rootdir 与插件集。
2. **分配**：
   - 使用会话级服务 fixture（`diff`、`rust_uri`、`ref_uri`）的用例整组放入同一片，保持收集顺序；
   - 其余用例按上一轮插件执行记录中的逐 nodeid 耗时降序分配到当前总耗时最小的分片，并列时按 nodeid 排序；缺少耗时的用例取已知中位数，没有耗时记录时每个用例按相同权重计。不从 JUnit 反推 nodeid。也可显式选择按收集顺序或倒序对单元轮转分配。

   计划文件记录 N、分配方式、输入耗时记录与收集列表的哈希，随证据保存；同一输入总得到同一计划。耗时数据不入库，过期只影响均衡，不影响正确性。
3. **执行**：每片由插件按计划筛选。插件先断言本次收集的全集等于计划全集，否则以非零码退出；取消选择的数量必须等于全集减去本片的分配数；保持收集顺序，不重排。同时，在 `pytest_runtest_logreport` 中逐项记录实际执行的 nodeid 与结果。各片拥有独立的 basetemp、TMPDIR、JUnit 与日志，信号处理同 P0。
4. **串行组**：只接受测试 fixture 层的资源冲突，例如固定路径、固定端口或 CPU 标定计时；产品缺陷必须修复，不得入组。入组需同时具备三项证据：并发下失败、串行通过、指明共享资源，并经评审。串行组在全部分片结束后由一个进程运行，结果仍计入并集并单独列出。初始为空；空的串行组或分片不启动进程。
5. **核对与失败传播**：
   - 一个进程失败不提前终止其他进程，收齐全部结果；中断时终止所有子进程组，并计为失败。
   - 汇总要求所有进程退出码为 0，插件记录的实际执行 nodeid 并集等于收集全集，且无重复、遗漏或额外项，失败、错误与 skip / xfail / xpass 均为 0。
   - JUnit 只用于交叉核对：各片的用例数须等于分配数，失败、错误与跳过均为 0。汇总输出机器可读结果，供候选门槛直接核对，不再只解析日志中的 “N passed”。

工具自检用构造的坏输入覆盖以下情形：分配的确定性；会话组不被拆分；遗漏、重复、额外用例，含空格或引号的 nodeid，以及收集全集与计划不符时被拒绝；子进程失败能传播。

并发度按试点实测确定。每个 Rust 服务的 IO 线程与计算池按可用 CPU 数创建，不通过环境变量改变被测配置。试点记录以下资源，据此设定各平台默认的 N 与平台总并发：

- 进程数与线程数峰值、`ulimit -u`；
- 内存峰值（arm64 按平台总并发计量）；
- 负载。

x86 为多人共享物理机，按当时的可用核数、负载与 uid 进程上限设定；arm64 的 Docker VM 资源有限，以内存峰值留有余量为准。

## 试点与验收

试点在方案通过后进行，不改变已发布版本的证据。“结果一致”指 nodeid 集合与每项结果逐一相同。

| 试点 | 平台 | 内容 | 通过条件 |
| --- | --- | --- | --- |
| 串行基线 | 三平台 | 同一源码与环境下，差分与互通各以单片计划运行一轮（即串行执行），产出逐 nodeid 耗时与 JUnit（rc2 互通未产出） | 计数与 0.3.0rc2 候选一致 |
| P0 | 三平台 | 两 SDK 差分与互通同时运行；x86 与本机序列同时运行 | 与基线一致；记录墙钟与资源 |
| P1 | 三平台 | 选定 N，分别按耗时均衡、单元顺序轮转、单元倒序轮转三种计划各运行一次；x86 另试一个更高的 N | 三次均与基线一致；无 OOM 或进程上限错误 |
| 敏感用例 | 三平台 | 带防挂死超时、信号、LOCK 或 compaction 等待的用例，以及上述 CLI 用例，在最大平台总并发下各重复 10 次 | 无新增失败；如失败，按串行组规则处理或修复 |

试点完成后另写验收记录，给出实测墙钟、资源与核对结果，并据此确定各平台的默认并发度。采用后在 0013 的候选矩阵中补一句执行方式与证据形式的说明，链接本文，不复制合同。

## 构建缓存（PID 1）

x86 PID 1 改用预热镜像：与冻结 Dockerfile 前缀逐字相同、基础镜像身份相同，被测产品容器的定义不变。Dockerfile 中 SDK 的传递依赖未固定，命中缓存时实际使用的是预热时解析出的依赖，因此须记录预热层的镜像 ID 与层内 `pip freeze`。arm64 已命中同类层缓存。

## 不做的事

- 不修改或绕过 SDK 的固定等待，不改用异步建索引：这会改变被测的 SDK 调用路径，而且该等待可由并行吸收。
- 不让用例共用 collection，不省略关闭重开，不缩小平台 × SDK 矩阵。
- 本阶段不引入 pytest-xdist：动态调度的执行顺序不固定，不利于复现顺序依赖；会话组约束和信号处理也需另行核实。确定性分片稳定后，若维护成本过高再另行评估。
- Python 全套与 Rust 测试本阶段不分片：前者含时序标定用例，后者合计只有数分钟。
