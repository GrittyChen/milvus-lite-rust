## 背景

0006 第 1 步要求先写这份设计说明，再实现存储。0006 已经定下对外语义与约束：

- 回放与提交的规则（第 8 项）；
- flush 与 WAL 追加失败之后的写入（第 9、10 项）；
- 懒打开与打开的顺序（第 16 项）；
- drop 与 create 的原子性（第 17 项）；
- 持久化保证与 fsync 集合（第 19 项）；
- 物理行序（第 23 项）。

本文定下实现它们的内部结构、取锁顺序与各条协议，并处理 0005 留给 M2 的遗留项：长检索全程持读锁、按请求轮转、快照与取消。

M1 的结构（[collection.rs](../../crates/core/src/collection.rs)）：

- 每次 insert 追加一个列式 `Chunk`；
- 每行一个 `live` 标记，被覆盖时清除；
- `pk_index` 指向每个主键的最新版本；
- 每个 collection 一把 `RwLock`，检索在整个计算期间持读锁（0005）。

M2 保留「按行增量维护有效性、查询路径不逐行判定」这一做法（0001 约束 2），把数据源从 chunk 扩展为 segment 与多代 memtable。

## 结论

### 数据结构

- **数据源**：segment、冻结的 memtable、活跃的 memtable。每个数据源有一个稳定的 ID，冻结的 memtable 发布成 segment 时换一个新 ID。「全局顺序」中的序号在取快照时由列表派生，不存进任何索引。
- **segment**：一个 data 文件读入内存后的列式数据，打开后不再改变，以 `Arc` 共享。
  - 包括各字段的列、`_seq` 列，以及向量的范数（COSINE 用，在加载时算好，与 M1 相同）。
  - 行号就是 Parquet 中的物理行号，已失效的行照样占号，与 3.x 的并列顺序一致（0006「3.x 的相关事实」）。
  - 新 segment 直接由写文件时的那个 RecordBatch 建成，保证与重开时读到的逐位相同，包括 JSON 文本、`_seq` 与范数。
- **memtable 的数据**：
  - 按写入调用追加成不可变的块，以 `Arc` 共享。被覆盖的旧版本留在块里，直到 flush，与 3.x 相同。
  - 行按 memtable 内的全局行号寻址。块中除各字段外还有两列不可变的元数据：`_seq`，以及写入时定下的**位次**。
  - **块的合并**：相邻的块在大小相近时合并成一个，合并后的块不超过检索的一个行块（2^20 个浮点数，0005）。
    - 块数因此为 O(n / 上限 + log 上限)，每次合并复制不超过约 4 MB，在写锁内完成。
    - 合并只是拼接，不丢掉任何行，全局行号与位次都不变；已被快照持有的旧块照样可用。
  - 用户逐行写入时，没有合并的话，1 万次调用就是 1 万个块，检索的逐块开销与内存都会放大（M1 的遗留项「每次 insert 一个 Chunk」）。
- **memtable 的主键表**：存活主键 → 最新行的全局行号、`_seq` 与位次，实现第 23 项的 dict 语义：
  - 新主键取下一个位次；
  - 覆盖写：旧版本在这个 memtable 中时沿用原位次；否则（旧版本在 segment 或已冻结的 memtable 中）取下一个位次；
  - 删除使主键离开这张表，之后再插入取新的位次；
  - 同一批中重复的主键，位置取第一次出现的，内容取最后一次的。
- **memtable 的 tombstone 表**：主键 → (最大删除 `_seq`，目标分区)，按 dict 的顺序排列，与 3.x 相同。M2 只支持 `_default`，`_all` 与 `_default` 的生效范围相同；当前实现可只保留 `_seq` 与位次，分区功能进入范围时再保留目标分区：
  - 同一主键再次删除只更新值，位置不动；
  - 重新插入这个主键时移除它的 tombstone（[memtable.py:106](https://github.com/milvus-io/milvus-lite/blob/v3.2.1/milvus_lite/storage/memtable.py#L106)），之后再删除则排到末尾；
  - 分区功能进入范围后，flush 须先写显式指定 `_default` 的，再写 `_all` 复制出的，与 3.x 的行序相同。当前单分区 M2 的验收核对 delta 的内容与可见性；混合目标标签的物理行序留到分区功能验收。
- **按 `_seq` 判定**：正常的唯一 `_seq` 操作与回放顺序无关；重复 `_seq` 是 3.x 并发缺陷可能留下的例外。同一 memtable 中 data 与 delete 同号时，[memtable.py](../../references/milvus-lite/milvus_lite/storage/memtable.py) 先应用者赢；已提交 delta 与 data 同号时，[DeltaIndex.is_deleted](../../references/milvus-lite/milvus_lite/storage/delta_index.py) 只在删除号严格大于数据号时屏蔽，故 data 可见。重复 data 同号时保留物理位置最先的一行。回放仍按 WAL 编号及编号内 batch 顺序，不能沿用 M1「新行一定是最新」的假设。
- `size()` 与 `max_seq` 的定义与 3.x 相同：前者是存活主键数加 tombstone 数，后者是两张表中 `_seq` 的最大值。
- **有效位图**：每个数据源一张，放在可变状态中，以 `Arc` 共享、写时复制。
  - 写入时若有读者正持有它，就先复制再改（`Arc::make_mut`）。一次写入对它触及的每个数据源至多复制一次；一个 segment 的位图是 1 万行、约 1.25 KB。
  - 一行有效，当且仅当它是该主键 `_seq` 最大的一行，且没有 `_seq` 更大的删除（0002 约束 13）。已提交的删除与 memtable 中的 tombstone 都算，memtable 中的行同样适用（第 8 项 a）。
  - 同一 (pk, `_seq`) 有多份时，只有全局顺序中最先的一份有效（第 8 项）。
- **主键索引**：主键 → 最新版本所在的数据源 ID、行号与 `_seq`，用于覆盖写与删除时清除旧行的位、get、upsert 读旧行。
- **已提交删除的索引**：主键 → 已提交删除中的最大 `_seq`（deltaMax），用于打开时的回放规则（第 8 项 a），以及判定 memtable 中比它更旧的行。
- **存活行计数**：随写入维护，供空 expr 的 `count(*)`、`row_count` 与 DescribeIndex 使用。
- **全局顺序**：
  - segment 严格按 manifest 中 `data_files` 的列表顺序，新文件追加在末尾；然后是冻结的 memtable（按代的先后）；最后是活跃的 memtable。
  - 检索的 TopK 全序沿用 M1 的 (名次, 数据源, 位置)：数据源取快照中的序号；位置对 segment 是物理行号，对 memtable 是位次。
  - 查询按这个顺序遍历有效的行，memtable 内按位次排序（O(m log m)，m 为 memtable 的行数），从头取 offset + limit 行，再丢掉前 offset 行，与 3.x 相同。

### 取锁顺序

- 有序的五层：数据库写入闸门 → 目录变更锁 → 名字锁 → flush 锁 → 状态读写锁，只能按这个方向取，例如持状态写锁时不得取 flush 锁。
  - 数据库写入闸门是一把读写锁，由 core 的数据库入口统一获取，不能仅在 gRPC adapter 中检查：除 create/drop 外，每个可能改数据、WAL、manifest 或目录的操作从开始到返回都持共享许可；create/drop **直接**持独占许可，不先取共享许可再升级。内部的自动 flush 沿用调用方的许可，不重入这把锁。collection 的写方法只能经持有许可的数据库入口调用。独占许可等先前在途的写入结束后才取得；目录 fsync 报错时，在放开它之前标记整个数据库写入封锁。之后的写入取得共享许可时先检查封锁并拒绝，因而没有「先检查、封锁后才写 WAL」的窗口。已打开 collection 上的纯读计算不取这把锁；共享许可不会把不同 collection 的写入串行化。
  - 目录变更锁是 db 级的一把互斥锁，只由 create、drop 及其悬空别名清理持有，从名字存在性判定前一直持有到改名后的别名维护结束。不区分大小写或会规范化名字的文件系统上，两个不同的精确名字可能指向同一物理路径；只锁精确名字不能隔离 `Foo` 的 drop 与 `FOO` 的 create。create/drop 低频，串行化它们比推断文件系统的名字等价关系更可靠。
  - 名字锁是 db 级的、每个名字一把：打开、drop、create 都持有它。
  - flush 锁是每个 collection 一把互斥锁：串行化所有写 manifest 的操作（flush、CreateIndex 等）与 drop。
  - 状态读写锁保护 collection 的全部可变状态。
- 叶子锁：collection 表锁、名字锁注册表、失败判定缓存、aliases 锁、关闭闸门与 WAL 文件锁。持有任何锁时都可以取叶子锁，持有叶子锁时不取任何其他锁。
  - collection 表锁只保护查表、登记与移除。打开时持名字锁登记句柄、drop 在移出句柄时已持有外层的数据库写入闸门、目录变更锁、名字锁与 collection 锁，都是这种用法。
  - aliases 叶子锁独立保护 `aliases.json` 的完整读改写与原子改名；create 在该叶子临界区内清理悬空别名并判断名字，随后释放它；drop 在目录提交后重新取得它、重新读取别名并清理目标。前置元数据校验只短暂持锁，不能跨 flush 锁或状态锁持有叶子锁。create/drop 的数据库独占许可与目录变更锁仍保留，两个别名事务的串行与不丢更新分别有用例。tmp 用 `create_new` 的唯一名字，避免共享 tmp 覆盖。
- 0005 的计算池任务不取任何锁，不变。
- [lock_order](../../crates/core/src/lock_order.rs) 在 debug 构建中检查五层锁及 collection 表、名字锁注册表、判定缓存与 aliases 的叶子锁；反向、同层嵌套与同锁重入在阻塞之前报错，禁止共享许可升级。失败的非阻塞探测不登记临界区；测试观察锁占用使用不构造业务守卫的独立接口。release 不注册线程局部状态或执行顺序断言。关闭闸门和 `wal_files` 的内部锁仍由结构保证叶子性质，不在该包装器内；其临界区不得获取五层锁。

### 写入

- insert、upsert、非空主键列表的 delete 都持状态写锁，在锁内依次完成：分配 `_seq`、追加 WAL、应用到 memtable、主键索引与位图（缺陷 e，第 8 项）。空主键列表在引擎入口直接返回 0，不分配 `_seq`、不创建 WAL；3.x 的 [Collection.delete](../../references/milvus-lite/milvus_lite/engine/collection.py) 也在检查分区与分配 `_seq` 之前返回。过滤删除零命中时同样如此。
  - WAL 追加成功之后的步骤都不会失败：不对用户数据做 `unwrap`，内存分配失败则进程中止。
  - 若仍有 panic（实现缺陷），按「失败」一节的「锁内的 panic」处理。
- **upsert**：读旧行、合并、写入都在同一次写锁内，并发的部分 upsert 因此不会丢更新（0006「验收」第 4 项的原子性）。
  - 按主键索引取有效的最新版本，不检查 load 状态，与 3.x 相同。
  - 与 3.x 不同，这里不会读到已被已提交删除覆盖的旧行（3.x 的 `_get_raw` 命中 memtable 就返回，不查 deltaMax；只在缺陷 a 这类目录上出现）。
  - 同一批中的每一行都与本批之前的状态合并，最后一行生效。
- **`_seq` 与 auto_id**：
  - insert 与 upsert 每行一个 `_seq`，非空 delete 每次调用一个，auto_id 取所在行的 `_seq`（0004）。
  - 快路径删除中主键类型转换失败时也消耗一个 `_seq`（0006「范围」）。
  - WAL 追加失败时，这次用过的 `_seq` 不回退、不再分配。
- **覆盖写与删除**：清除旧行的位，更新主键索引与计数。只修改可变状态，不改任何不可变的块。
- **JSON 与 `$meta`**：按第 26 项写出与 3.x `json.dumps` 相同的文本，WAL 与 Parquet 都如此。

### WAL

- **一代对应一个编号**：每一代一对 `wal_data_N.arrow` 与 `wal_delta_N.arrow`，都在首次写入时以 `create_new`（O_EXCL）创建。「绝不续写已有的编号」由此成为能检出的错误。
- **追加**：每个文件保留一个 `StreamWriter<Vec<u8>>`，使 schema 只写一次、后续 batch 共用同一个 Arrow IPC stream 的编码状态。每次 `write(batch)` 后取出缓冲中的新字节，再用 `write_all` 交给 File；首次追加的字节同时包含 schema 与首个 batch。不能为每个 batch 新建 writer：那会把多个带 schema 的 stream 拼接进一个文件，3.x 的 `open_stream` 不能据此读回全部 batch。
  - 数据在确认写入之前就已交给操作系统，不逐次 fsync（第 19 项）。
  - 不用 `BufWriter`：std 的 `BufWriter` 在写出失败后保留未写出的字节，之后 drop 或 flush 时会把它们补写进文件，使报错的写入变成完整的 batch，重开时被回放（已实测复现）。
  - 编码或写盘失败后丢弃这个 writer，不调用 `finish` / `into_inner`，也不再向这个文件追加；失败前的完整 batch 由冻结与回放处理。
- **批的语义**：一次 insert / upsert 调用一个 data batch；一次 delete 调用一个 delta batch，只含一个 `_seq` 与一个 `_partition`，不指定分区时为 `_all`（0002 约束 3）。
- **追加失败**（第 10 项）：
  - 这次写入报错，memtable 不变（先写 WAL，成功后才改内存）；
  - 这个文件的写者作废：之后不再写、不 flush、不写 EOS，保留时只对 File 做 fsync；
  - 这一代若非空，立即冻结，按 flush 处理；若为空，只换一个新的编号。
  - 非空的一代中另一个文件创建失败（例如 data 文件已有数据，delta 文件创建失败），同样按追加失败处理，冻结这一代，不把它的写入分到两个编号里。
- **冻结时**：丢弃内存中的 stream writer，保留 File 用于之后的 fsync；不写 EOS。3.x 运行中的 WAL 也不带 EOS。
  - 原 File 由冻结代持有。flush 的锁外阶段先同步该代全部原 File 与 `wal/` 目录，全部成功后才关闭；若失败，句柄全部保留，错误仍按提交点之前处理。关闭或 drop 的全局 WAL 同步也只有在全部文件及目录同步成功后才关闭活跃与冻结代的句柄。该步骤补齐关闭前同步合同；现有删除前的同步仍保留，其性能由最终基准核对。


### flush

- **触发与冻结**：写入调用在锁内完成之后，若活跃 memtable 的 `size()` 不小于 10000（第 22 项），在同一次持锁中把它冻结：
  - 移入冻结列表，同时固定这一刻的有效位图快照。它的块、主键表与 tombstone 表随之成为不可变的 `Arc`；锁外写盘只按冻结时的行集合与位图快照选行，之后的写入只改全局的主键索引与当前位图。发布时再用当前位图换算新 segment 的可见性；
  - 换上新的活跃 memtable；
  - 取新的 WAL 编号，文件在首次写入时才创建。
- 冻结之后放开写锁，由这次写入调用**同步地**执行 flush，完成后才返回，与 3.x 的不变量 6 相同，也给写入以背压。
  - 冻结的代数至多为并发写入者数加一。每代约 1 万行，dim 128 时约 5 MB。
- **flush 锁的持有者**按先后提交冻结列表中的代，然后才放开 flush 锁：
  - 每个持有者先完成待完成的重新提交（若有），再提交冻结的代：触发 flush 的写者提交不晚于自己那一代的全部代；重试者、显式 Flush 与关闭提交冻结列表中的全部代，所以不会有代留在列表中无人认领；
  - 所以后冻结的写者即使先拿到 flush 锁，也会先提交更早的代（第 8 项「按代的顺序提交」）；
  - 某一代失败（无论在提交点之前还是之后）就停下，不再尝试之后的代。因提交点之后的失败而保留的已提交 WAL 因此至多一代（第 8 项）；删除 WAL 失败不阻止写入，那种情况下残留的已提交 WAL 可以跨多代累积（见「提交之后」）。
  - 每一代的提交、发布与 WAL 删除都在放开 flush 锁之前完成。
  - 持有者在取得 flush 锁时、以及之后每次取状态锁时，检查 collection 是否已被删除或已损坏；是就停下，不再做任何文件操作（第 21 项）。
- **锁外阶段**，只持 flush 锁：
  1. 从冻结 memtable 的不可变块中，按位次拷出冻结时存活的行，生成 data 文件；按 tombstone 表生成 delta 文件。
     - 冻结之后被覆盖或删除的行照样写出：新版本与 tombstone 都在下一代里，与 3.x 相同。
     - 文件名取写出行的 `_seq` 范围。遇到同名文件时：
       - 未被引用的孤儿，先删除再写；如果同 stem 的 3.x `.idx` / `.sidx` 侧车仍在，即使 Parquet 已不存在也向外放宽 seq_max，避免新 data 文件加载旧索引。未复用的孤儿留给打开后的清理阶段；
       - 被 manifest 或 snapshot 引用的，绝不覆盖，而是向外放宽 seq_max 取新名。这对 GC 是安全的，3.x compaction 的 `_pick_unique_seq_range` 也这样做；seq_min 不改（0002 约束 2）。3.x 缺陷 e 的目录中两条操作可能共用一个 `_seq`，回放出的一代可能恰好与已引用的文件同名，不能因此卡死。
  2. fsync 新文件、它们所在的目录，以及本次新建目录的各级上级（第 19 项）。
     - 本进程对该 collection 的第一次 manifest 提交之前（包括空提交或 CreateIndex），还要 fsync manifest 已引用、但不是本进程写出的文件，以及从数据目录根的上级到 collection 与这些文件所在目录的各级。3.x 不 fsync Parquet；本进程的 create 若在改名后目录 fsync 失败，会报「已创建、持久化未确认」，并进入下文的写入封锁状态，本服务实例不再做 manifest 提交。正常路径必须在 replace 之前补齐这些 sync；若失败，本次仍处于提交点之前，manifest 不得引用新的文件。
  3. 提交 manifest：写 tmp 并 fsync、复制 `.prev`、replace、fsync 目录。
     - 新的 manifest 只含已提交的状态：`current_seq` 取 `max(已提交的值, 冻结代的 max_seq)`，不得改用写出 Parquet 的最大 `_seq`（[0002 约束 4](0002-data-dir-compat.md#共享状态的语义约束)）；空的一代不会让它变小（3.x 的 setter 遇到更小的值会报错）；`active_wal_number` 取这一代的编号加 1，空的一代同样推进。
     - 复制 `.prev` 失败与 3.x 一样只写日志、不算失败：本实现从不读 `.prev`（第 11 项）。
- **锁内发布**，在 flush 锁内取状态写锁，亚毫秒：
  - 把冻结的 memtable 换成新 segment，追加在 segment 列表末尾；
  - 主键索引中仍指向这一代的项，改指新 segment 的行；行的对应关系取自写文件时用的那份列表；
  - 位图按冻结以后的清除情况换算到新 segment 上；
  - 这一代的 tombstone 并入 deltaMax；存活行计数不变。
  - 读者在整个 flush 期间都能看到冻结 memtable 中的数据，不会看到行消失（缺陷 c）。
- **提交之后**，仍在 flush 锁内：
  - **统一的删除规则**：每次完整的提交（包括目录 fsync，flush 与 CreateIndex 等都算）之后，删除编号不大于「最后一个已发布的代」的全部 WAL，一趟升序，从最小的编号开始。
    - 「最后一个已发布的代」在打开时为「无」，这条规则在第一次发布之前什么都不删。打开时就已存在的 WAL 编号都小于打开后的第一个活跃代，它们的内容在这一代发布之后才全部提交，之后与其他已提交的 WAL 一样删除。冻结而未发布的代编号更大，不会被删。
    - 每个 WAL 删除之前先 fsync（第 19 项）。
    - 第一次提交之前对已有文件与目录的 sync 已在提交点之前完成；删除打开时就存在的 WAL 仍须等第一次活跃代发布。3.x 从不 fsync Parquet，建 collection 目录时也不 fsync `collections/`（[db.py:205](https://github.com/milvus-io/milvus-lite/blob/v3.2.1/milvus_lite/db.py#L205)），不能仅凭打开成功就删除其 WAL。
    - 同一编号内先删 data、后删 delta，与 3.x 的 `_cleanup_old_wals` 相同。Linux 与 macOS 上每次 unlink 成功后 fsync `wal/`，然后才能删下一文件或下一编号；否则断电可能让后一次 unlink 先落盘，顺序调用仍会留下只含 data 的 WAL，或让较大编号先消失。Windows 上没有目录 fsync，只保证进程崩溃时的顺序（第 19 项）。两种中断的结果都对 3.x 有害，但只剩 data 更糟：
      - 只剩 data 时，3.x 打开后会回放出已在同一代内删除的行，之后的 compaction 与 GC 可能让它永久复活；
      - 只剩 delta 时，若同一代内删除后又重新插入过某个主键，3.x 回放出的 tombstone 会让 get 返回空、部分 upsert 不与旧行合并而丢掉字段，因为 3.x 的 get 看到 memtable 中的 tombstone 就当作已删除、不比较 `_seq`（[collection.py:494](https://github.com/milvus-io/milvus-lite/blob/v3.2.1/milvus_lite/engine/collection.py#L494)，3.2.1 实测）；检索、查询与计数不受影响。3.x 自己的 `_cleanup_old_wals` 在两次 unlink 之间崩溃也会留下这样的目录，登记为继承风险。
  - **删除失败**：遇到第一处失败（文件或目录 fsync、unlink）就停，不删更大的编号。逐次目录 sync 成功后，断电恢复所见的已提交 WAL 才能保持编号的后缀形状；sync 失败后的落盘顺序无法证明，保留为故障风险并在下一次提交、显式 Flush 与关闭时重试检查。它不影响写入，因为数据已经提交。
  - Linux 与 macOS 上，目录 fsync 返回 `EINVAL` / `ENOTSUP` 也算失败，不能按 0006 第 19 项原稿跳过；否则会在尚不能证明目录项持久化时确认 Flush 并删 WAL。改名或删除前先对相关目录做一次能力检查，使稳定的不支持尽量在提交点之前暴露；检查成功后仍可能遇到 I/O 错误，按提交点前后分别处理。Windows 沿用第 19 项已登记的较弱保证。
- **不持状态写锁的各段中的 panic**：以局部 `catch_unwind` 兜住，不能让一次 panic 跳过改名之后必做的内存收尾；目录 sync 未成功时，本服务实例不再维护别名，重开后按实际目录状态收尾。按位置归类：
  - 锁外阶段：replace 之前按提交点之前的失败处理，之后按提交点之后的失败处理；
  - 提交之后的 WAL 删除：按删除失败处理，停下，下次提交时重试；
  - CreateIndex 的 replace 之后：按它在提交点之后的失败处理；
  - drop 与 create 的改名之后：先完成改名之后的表项与缓存收尾；目录 sync 失败就保留别名与 staging、封锁本服务实例的写入，重开后按实际目录状态收尾，并按「目录已变更、持久化未确认」向调用方报错；仅 staging 目录删除的失败按第 17 项写日志。

### 失败与「有待提交」状态

- **提交点之前失败**（写 Parquet、fsync、写 tmp 或 replace 失败）：
  - 冻结的 memtable 留在冻结列表中，读者照常看得到；它的 WAL 保留；
  - collection 进入「有待提交」状态。
- **提交点之后失败**（replace 之后的目录 fsync 失败）：
  - 按已提交处理：先 fsync 编号不大于这一代的全部 WAL（包括打开时就已存在、内容已回放进这一代的）与 `wal/` 目录，再在发布的同一次状态写锁内置上「待完成的重新提交」，这样任何人都不会在发布之后、标志置上之前看到「没有待做的事」；
  - 这些 WAL 都保留，等下一次完整的提交之后按统一的规则删除；
  - 同样进入「有待提交」状态，待完成的是一次完整的重新提交：新的 tmp、fsync、replace、目录 fsync（第 8 项）。
- **写入遇到「有待提交」状态时的协议**：
  1. 在状态锁内看到标志，放开状态锁；
  2. 取 flush 锁，重新检查标志与节流：距上次失败不足 1 秒就不重试，直接拒绝，错误中带上上次失败的原因（第 9 项）；
  3. 重试：先完成待完成的重新提交，再按代提交冻结的各代，发布与 WAL 删除都在 flush 锁内完成；
  4. 重试失败则拒绝这次写入，不分配 `_seq`、不写 WAL、不改 memtable；
  5. 重试成功则放开 flush 锁，重新取状态写锁；若这段间隙又出现待提交状态，回到第 1 步，只有再次确认没有待提交状态后才写入。
  - 节流在拿到 flush 锁之后才判断，所以排在 flush 锁上的写者不会各自重做一遍 flush。
  - 「有待提交」由两个条件构成：冻结列表中有提交失败过的代，或者有待完成的重新提交。前者只有这些代提交成功才清除；后者被任何一次完整的提交清除，包括 CreateIndex 等非 flush 的提交；之后按统一的规则删除 WAL。
  - 显式 Flush 不受节流，走同样的协议。
  - 读照常。
  - 触发 flush 的写者：它自己的写入在冻结之前已经完成，所以不论之后的 flush 成功、失败，还是 collection 在它等待 flush 锁时被删除或标记为损坏，它都返回成功（第 9 项 (i)）。只有还没写入的重试者会被拒绝。drop 成功时，这次写入排在 drop 之前，结果同样一致。
- **CreateIndex 等写 manifest 的操作**：
  - 在提交点之前失败：报错，内存状态不变；
  - 在提交点之后失败：按已提交处理，返回成功，进入「待完成的重新提交」，与第 9 项 (i) 的原则相同：生效的写入都返回成功。
- **锁内的 panic**（持状态写锁的各段：写入的应用、冻结、块的合并、锁内发布、CreateIndex 的内存更新，以及 drop 的标记与 WAL 同步、manifest 重新提交，都是实现缺陷）：内存状态可能只改了一半，不能再用。
  - **在放开写锁之前**把 collection 标记为损坏：持状态写锁调用 `state_change`，在该边界用 `catch_unwind` 捕获 panic，并在返回错误前显式调用 `persistent.poison()`。parking_lot 的锁没有中毒语义，unwind 时锁会先被放开；若等到 RPC 边界再置位，排在写锁上的写者会基于改了一半的状态写入并返回成功。
  - 之后的请求在取锁后看到这个标记就报错；flush 锁的持有者看到它就停下（见「flush」）。
  - **损坏的 collection 在这个服务实例内不再可用，直到服务重启**（进程重启，或 `release_server` 之后重新打开，0003），不在服务内从盘上重开：重开要与仍在锁外写盘的旧 flush 协调，否则同一目录上会同时有两个句柄。重启时照常从盘上恢复，已写进 WAL 与已提交的都在。
  - 残余风险（规则 6）：
    - panic 的那次 RPC 报 code 1；它若已越过提交点（WAL 追加成功，或 manifest 已 replace），重启后效果存在。0006「验收」第 4 项的参考模型对实现缺陷导致的 panic 例外。
    - 关闭时不处理损坏的 collection，盘上若有已提交而未删除的 WAL，服务重启之前由 3.x 打开会重复计数。
  - 关闭时不 flush 它的内存状态，它的 WAL 留给重启后恢复。
- 所有失败都写日志；显式 Flush 与之后被拒绝的写入都会把错误返回调用方（规则 5）。

### 显式 Flush

- 在写锁内冻结非空的活跃 memtable，并记下此刻最新的冻结代；
- 然后取 flush 锁，按顺序提交冻结列表中直到这一代的全部代，包括触发它们的写者已经返回、无人认领的代，以及待完成的重新提交与有待删除的 WAL；
- 全部完成才返回成功，否则返回错误。不这样做的话，另一个写者正在 flush 时 Flush 会看到空的活跃 memtable 而立即返回，断电后刚确认的写入就可能丢失，违背第 19 项；
- 没有任何待做的事时返回成功，与 3.x 相同；但「没有待做的事」在取得 flush 锁之后才判断，不能像 3.x 那样只看活跃 memtable 的 `size()`，否则会插进另一次 flush 在提交点之后失败的中间。

### 读

- **检索与过滤查询**：
  - 在读锁内取一份**快照**：各数据源的 ID 与不可变数据、位图的 `Arc`，冻结 memtable 的块与位图，活跃 memtable 此刻的块列表与位图；位次在块中，快照里就有；
  - 随即放开读锁，在快照上计算（0005 的计算池不变）。
  - 快照的代价是复制一批 `Arc`，个数与 segment 数加块数成正比。M2 没有 compaction，100 万行约 100 个 segment，复制 100 个 `Arc` 约 0.25 µs。
- 这替代了 0005「检索在整个计算期间持有 collection 的读锁」。长检索不再推迟写入、发布与 drop，0005 中「长检索全程持读锁」的遗留项因此解决。
- **过滤与有效位图的组合**：过滤表达式只对有效的行求值，结果再与向量的检索组合。第 13 项「整数列对浮点字面量的 code 1 只看存活行」依赖这一点。
- **get、`count(*)`**：
  - get 查主键索引，持读锁的时间很短；
  - 空 expr 的 `count(*)` 取存活行计数。
- **`delete(filter)` 的隔离方式**：采用 3.x 的快照求值、再按主键删除。求值不持状态锁，可能删掉求值之后才写入的同主键新版本。整个操作沿用一次共享写入许可和同一个句柄，不能在删除阶段按名字重新解析到同名重建后的 collection；不把共享许可升级为独占。Delete 不要求 load，仅在自己的视图上绕过 load 校验，不临时修改共享 load 状态。空命中不消耗 `_seq`，非空命中经既有 WAL-first 批删除协议。写锁内求值会扩大持锁时间并改变并发语义，因此不采用。
- **计算池的先进先出排队、停服时取消长检索**：仍作为残余风险，不在 M2 实现。
  - 快照之后，锁不再把后到的请求挡在长检索之后，剩下的只是计算池内的排队，0005 已测量并接受。
  - 取消与轮转等到出现需要它们的测量结果时再设计。

### 打开

- collection 在第一次被访问时打开（第 16 项）。打开成功后会删除孤儿文件，因此即使由 Query/Search/Get 触发，也先取数据库写入闸门的共享许可并检查封锁，再取名字锁；打开、清理、登记句柄结束后即可放开许可，后续纯读计算不持它。若调用方已因写入持有共享许可，沿用该许可而不重入。封锁期间拒绝新的懒打开，不做任何文件清理；已打开 collection 的纯读仍可使用。打开过程一直持有这个名字的锁，直到句柄登记进 collection 表，所以不会与同名的 drop、create 交错（缺陷 d）。步骤：
  1. **读取与判定**：
     - 读 `schema.json`、manifest、snapshot 元数据，做第 14 项的判定；
     - 读入 manifest 引用的全部 data 与 delta 文件，读取时有边界检查与 `catch_unwind`（第 12 项）。
       - 多个文件用临时线程（`std::thread::scope`）并行读，不用计算池：计算池的任务不得阻塞（0005）。
     - 读取全部 WAL：先把整个文件读进内存再解码，按编号升序、编号内按 batch 首个 `_seq` 排序，与 3.x 相同。
  2. **建索引**：由全部 segment 建主键索引与位图，由 delta 文件建 deltaMax。这是 O(总行数) 的一次性开销，在打开时发生，不在查询路径上。
  3. **回放**：按第 8 项 a 的规则，把 WAL 中未被已提交状态覆盖的操作应用到同一个活跃 memtable。可见性只比较 `_seq`；主键位次仍按第 1 步确定的 batch 回放顺序维护，覆盖写保留原位次，删除后再插入取新位次。
     - 跳过的行不占位次。
     - 多代未提交的 WAL 会回放进同一个 memtable，行序随之合并。例如第 N 代写入 1、2、3，第 N+1 代 upsert 1：崩溃前的顺序是 2、3、1，重开后是 1、2、3。这与 3.x 回放同一目录的结果相同；0006 第 23 项「重开不改变行序」只在至多一代未提交时成立，模型测试的参考结果按这条合并规则定义。
     - `_seq` 从 `max(current_seq, 回放后 memtable 的 max_seq) + 1` 继续；新的 WAL 编号为 `max(已有编号 + 1, active_wal_number)`。
  4. **清理**：读取、判定和内存状态构建全部成功之后，才按 3.x 的规则删除孤儿文件；此前任何失败都 fail-closed，不删除任何文件。清理先完成目录类型与候选文件判定，判定失败仍拒绝打开；与 3.x 跟随目录符号链接或跳过非目录扫描路径的差异见 [0006「与 3.x 的差异」](0006-m2-scope.md#与-3x-的差异)。已确认孤儿的 unlink 或删除后的目录 sync 失败只记录警告，不阻断健康 collection 的打开与读取。这与 3.x 忽略孤儿删除错误的读行为一致，日志用于保留失败证据。此处删除的是恢复不再需要的孤儿，不能套用 flush 提交与 WAL 删除的持久化要求。
     - 清理发生在每个服务实例的首次成功懒打开。仅关闭客户端连接再连接同一服务不会重复清理；停止服务并重建实例（可在同一进程内进行），或由新进程打开，才会再次尝试清理仍留在目录中的孤儿。
- fail-closed 的判定按名字缓存，保留原错误类型与信息。读取缓存前先确认精确名字、目录及 schema 文件仍存在；外部删除或移走时按 collection 不存在处理，保留原判定，路径重新出现后仍须显式清除缓存。格式、支持范围、恢复映射及引用文件缺失属于确定的判定；真实 I/O 故障（包括孤儿候选扫描失败）不缓存，下次访问可重试。WAL 解码的前缀告警不构成打开失败。同名 drop 在目录已移走或确认不存在时清除缓存；create 在改名并核对精确名字成功之后、目录 fsync 之前清除缓存。提交点之前的 create/drop 失败不清除旧判定。外部修复文件后仍须重建服务实例或由同名 drop/create 清除判定，不在每个 RPC 中重新解析损坏内容，差异见 [0006](0006-m2-scope.md#与-3x-的差异)。
- load 状态：有索引定义为 NotLoad，否则为 Loaded，与 3.x 相同。

### drop、create 与关闭

- **drop**：
  - 先取目录变更锁与名字锁。只要表中已有 collection 句柄（包括因锁内 panic 被标记损坏的），就取它的 flush 锁（等在途的锁外写盘结束）与状态写锁；健康句柄标记为已删除，损坏句柄已经拒绝后续请求。只有从未成功打开，或打开失败后按名字缓存为 fail-closed，且表中确无句柄时，才直接走下面的目录级改名。这样不必为 drop 去解析损坏的 manifest 或 Parquet，也不会与损坏句柄尚未结束的 flush 交错。
  - 原目录被外部删除或移走时，drop 也须退役已登记句柄。仍遵守闸门、名字锁、flush 锁与状态锁的顺序；只同步仍持有的原 WAL File，不创建目录或追踪移走后的路径，全部成功才关闭句柄、标记已删除并移除表项。失败保留全部文件句柄与表项，向上传递，允许显式 drop 重试。原目录仍在、仅 schema 缺失等残留继续按通常 WAL 同步协议处理。旧读快照继续有效，但旧 collection 句柄不能再写入或提交；同名 create 使用新句柄。外部改变目录不属于正常持久化保证，drop 与 3.x 的差异见 [0006](0006-m2-scope.md#与-3x-的差异)。
  - 之后持有旧句柄的请求在取锁后检查这个标记，一律报「collection 不存在」；排在 flush 锁上的写者与重试者也检查它（见「flush」），不再创建任何文件。
  - 已有句柄先 fsync **全部**打开的 WAL 文件与 `wal/` 目录，全部成功之后才关闭其中任何一个文件句柄（Windows 上目录中有打开的文件时，改名会失败），然后按第 17 项改名移入 `.database-staging/`；无句柄的分支只做改名。drop 不 flush，WAL 的同步仍遵守不变量 10。
  - 改名之前任一 WAL fsync 若失败，不关闭任何 WAL 句柄；健康句柄撤销「已删除」标记、继续持有全部写者，损坏句柄保持损坏。drop 报错且不改名，不把一次同步错误变成半完成的 drop。
  - **提交点是改名成功**：
    - 成功：仍持目录变更锁与名字锁，先从 collection 表移除旧句柄、清除 fail-closed 缓存，再放开状态写锁；这些内存收尾发生在任何后续 fsync 之前，不能被其错误或 panic 跳过。之后依次 fsync `collections/` 与 staging。两处都成功，才持 aliases 锁维护 `aliases.json`，最后删除 staging 中的目录。fsync 处的 panic 由局部 `catch_unwind` 转成错误，按同步失败处理；不能用一次包住整段、捕获后直接返回的写法。
    - 改名之后的目录 fsync 若失败，drop 报错，写明「目录已移走，但断电持久化未确认」；保留 aliases 与 staging 不动，在释放数据库写入闸门的独占许可前进入本服务实例的**写入封锁状态**。否则若别名已持久删除而目录改名在断电后回退，会出现旧 collection 存在、别名却永久丢失。封锁后所有写入、显式 Flush、CreateIndex、create 与 drop 都拒绝，不再尝试对同一脏目录原样 fsync：一次 fsync 错误可能只上报一次，之后的成功不证明原改名落盘（0006 第 8 项）。正常关闭不 flush，只同步并保留全部 WAL，写日志并释放 LOCK；重开后按实际目录状态判断：原名仍在时保留别名，原名不在时清理 staging；悬空别名由同名 drop 重试、同名 create，或之后触发的 `aliases.json` 写入清理。删除 staging 中目录的失败属于第 17 项已采纳的提交后清理例外，只写日志，下次打开时再尝试清理。启动期 staging 同样先完整扫描与判定，已确认残留的删除或目录同步失败只记警告并保留重试机会；路径类型与扫描错误仍拒绝打开。单条目类型判定错误的严格处理与 3.x 的差异见 [0006「与 3.x 的差异」](0006-m2-scope.md#与-3x-的差异)。
    - 写 `aliases.json` 失败则向上传递错误，文案说明 collection 已移走、别名尚待清理；3.x 也在删除目录之后写别名，写别名失败会报错（[db.py:251](https://github.com/milvus-io/milvus-lite/blob/v3.2.1/milvus_lite/db.py#L251)）。同名的 drop 重试即使已找不到 collection，也要先清理指向这个已不存在目标的别名；下一次写 `aliases.json` 或同名 create 也会清理；仅重新打开数据库不写别名文件。这样 I/O 错误不被吞掉，重试也能完成未做完的工作。由于目录改名已经生效，这类报错是「操作已生效、后续元数据维护失败」，在 0006 的故障模型中单列，不能套用写入 RPC「报错即未生效」的断言。
      - 判断别名是否悬空，按目标路径是否存在，与 3.x 解析别名的方式相同，不按精确的目录列表：3.x 在不区分大小写的文件系统上允许别名指向只差大小写的名字，照常使用（3.2.1 实测），按精确列表判断会误删它们。
    - 失败：按提交点之前的失败处理，与 CreateIndex 相同：
      - 改名期间一直持状态写锁；失败时撤销「已删除」标记，内存状态不变，collection 照常可用，drop 返回错误；
      - 若为改名关闭了活跃代的 WAL 句柄，按「WAL 追加失败」处理：活跃代非空就冻结，为空就换一个新的编号；冻结代的 WAL 在删除前按路径重新打开来 fsync。
      - 这样不引入新的状态：之后重试 drop 照常执行，关闭时照常提交并删除 WAL。
- **create**：持目录变更锁与名字锁，按第 17 项在 staging 中建好再改名移入，改名之后核对精确的名字（第 18 项）；名字与已有别名相同时持 aliases 锁判断。
  - 改名之前，持 aliases 锁清理所有目标路径已不存在的悬空别名，而不只清理与新名字逐字相同的目标：不区分大小写的文件系统上，旧物理目录 `Foo` 被 drop 后，3.x 留下的别名可能指向 `foo`，新的 `FOO` 会使它重新指向新 collection。清理失败按提交点之前的失败处理。目录变更锁使「判定悬空 → 改名」之间没有另一次 create/drop 插入。
  - 提交点是改名成功；随即核对精确名字，若不符则按第 17、18 项撤销并报错。核对通过后立即清除同名的 fail-closed 缓存，再做 `collections/` 的 fsync，避免后者报错或 panic 后新 collection 仍被旧缓存挡住。fsync 失败则报「目录已创建，但断电持久化未确认」，进入同一写入封锁状态；不能对相同的目录项只重试一次 fsync 就确认后续 Flush。正常路径的首次 manifest 提交仍按「提交之前」同步已有文件与各级目录。
- **关闭**（0003「进程退出」，在途任务结束之后），按顺序完成下列各项，都不受节流：
  - 若数据库因 create/drop 改名后的目录 fsync 失败进入写入封锁状态，跳过下面的 manifest 提交与目录清理，只 fsync 所有保留的 WAL 文件与 `wal/` 目录，记录错误并释放 LOCK；下次打开按实际目录状态恢复。不能在关闭时对同一个脏目录原样重试 fsync 后再 flush。
  1. 待完成的重新提交；
  2. 按代的顺序提交冻结的各代；
  3. 提交活跃的 memtable；
  4. 若盘上仍有任何 WAL 文件（打开时就存在的、有待删除的，或活跃代为空却已创建的，例如首次追加失败留下的文件），把空的活跃代冻结，按空的一代提交并发布：`active_wal_number` 推进为这一代的编号加 1，`current_seq` 不变，「最后一个已发布的代」成为这一代，再按统一的规则删除（第 8 项）。
  - 任何一项失败就停，不再做之后的提交：否则第 4 项会删掉尚未提交的 WAL。但没有待完成的重新提交时，仍按统一的规则删除编号不大于最后一个已发布代的 WAL，它们已经完整提交，与失败的那一代无关。然后 fsync 盘上全部保留的 WAL 与 `wal/` 目录，写日志，照常释放 LOCK（0003「停止失败」）。关闭时仍删除不掉的已提交 WAL，3.x 打开时会重复计数，这一点登记差异并补进 0002「继承的 3.x 已知风险」。
  - 已删除的 collection 跳过；损坏的 collection 按「锁内的 panic」不 flush，但其 WAL 文件与 `wal/` 目录仍要 fsync 后再关闭，不得用「跳过 flush」跳过这一步。
  - LOCK 在这些都完成之后才释放。M1 的关闭闸门在「引擎已关闭、最后一个在途任务结束」时就释放 LOCK；M2 的正常关闭要等 flush 与 WAL 同步完成，非阻塞析构要等后台收尾完成，否则另一个进程（包括 3.x）会在存储收尾期间打开同一目录。
- **`close_nowait`**（`Server::drop` 的路径）：正常情况下析构线程不等待，把 Db、打开的 WAL 句柄与 LOCK 的所有权交给后台收尾线程；该线程等在途任务结束后不 flush，只 fsync 保留的 WAL 文件与 `wal/` 目录，关闭 WAL，最后释放 LOCK。不能沿用 M1「最后一个在途任务结束就释放 LOCK」的路径，因为那时 WAL 还没同步。同步失败时写日志、保留 WAL，不做删除，按正常关闭失败的规则释放 LOCK；没有调用方可接收析构错误。若后台线程创建失败，为保住不变量 10，析构线程例外地同步等待在途任务、fsync 保留 WAL 后才释放 LOCK；这一罕见故障允许析构阻塞。进程在收尾完成前被杀，与 SIGKILL 一样只保留进程崩溃保证；正常的 atexit 与显式 `stop` 仍走同步关闭。

## 与正确性不变量的关系

- `_seq` 全序、互清按 seq 判定、tombstone GC 规则（不变量 1–3）：
  - `_seq` 在写锁内分配，失败时用过的也不再分配；
  - 正常的唯一 `_seq` 操作只比较 `_seq`，应用顺序不影响结果；同号例外按上文的 3.x 来源与操作顺序处理；
  - M2 不做 GC。
- 文件不可变（不变量 4）：绝不覆盖被引用的文件；同名的只有未被引用的孤儿。
- manifest 是唯一真值、原子更新（不变量 5）：只由持 flush 锁的一方写，只写已提交的状态，提交点是 replace，`current_seq` 单调。
- 单进程独占（不变量 8）：沿用 M1 的 LOCK。
- WAL 关闭前 fsync（不变量 10）：删除 WAL 之前与保留 WAL 时都 fsync。
- 索引与 segment 1:1、未 load 禁止检索（不变量 11–13）：M2 只有 FLAT，行为与 M1 相同。

## 实现范围

下列结构是完整 M2 的实施合同，而非单个切片的完成声明。实际进度以 [README](../../README.md) 与对应测试为准；查询快照、按名字并行打开、删除、upsert、过滤及跨平台矩阵等项目只有实现并验收后才能记为完成。

  - `Collection` 改为内部持有 flush 锁与状态读写锁、以 `Arc` 共享；
  - 写入拆成锁内的写入与冻结、锁外的 flush 与发布；
  - 新增 upsert、delete、Flush 与快照；
  - 检索的行块切分、TopK 与 gather 改为跨数据源。
- **[data.rs](../../crates/core/src/data.rs)**：
  - 定下列式数据与 arrow 数组之间的转换；
  - `$meta` 与 JSON 字段改存规范化的文本（第 26 项）；
  - 主键索引的内存占用对照 0001 约束 5。
- **[db.rs](../../crates/core/src/db.rs)** 与 **[data_dir.rs](../../crates/core/src/data_dir.rs)**：
  - collection 表改为按名字加锁的懒打开，带 fail-closed 缓存；
  - create 与 drop 走 staging，维护 `aliases.json`；
  - `list_collections` 只读 schema 与 manifest；
  - `close` 按本文的顺序 flush，flush 与 WAL 同步完成后才释放 LOCK；`close_nowait` 将 Db 与 LOCK 交给后台收尾线程，完成 WAL 同步后才释放，不沿用 M1 在最后一个在途任务结束时直接解锁的路径；
  - 删除 M1「拒绝打开已有数据的目录」的检查，改为清空 `.database-staging/`。
- **新增**：WAL、Parquet、manifest 与 schema 的读写，回放，故障注入钩子（第 20 项）。
- **grpc**：
  - `IMPLEMENTED_METHODS` 加入 Delete、Upsert、Flush、GetFlushState；
  - service.rs 改用新的 API；
  - schema.rs 的编码覆盖 3.x 的全部字段类型（第 14 项）；
  - server.rs 的停止在 flush 完成之后才释放 LOCK，耗时变长。

## 验证

在 0006「验收」之外，针对本文的结构另加：

| 用例 | 断言 |
| --- | --- |
| 位图与主键索引的模型测试 | 随机的写入、upsert、删除、重新插入、flush、flush 失败、WAL 追加失败、重开、崩溃序列，每一步的可见行、行序（位次与全局顺序）、get 与计数都与逐行重算的参考结果相同；多代未提交时的回放按合并规则 |
| 锁外阶段的交错 | 用钩子暂停 flush 的锁外阶段，期间穿插覆盖写、删除与重新插入冻结代中的主键，再让提交成功或失败；发布前后的可见行、行序、get 与计数不变 |
| 快照 | 检索进行中有写入、flush 发布与 drop，检索的结果等于开始时的快照；写时复制之后旧快照不受影响 |
| 按代的顺序提交 | 两代同时等待提交，后冻结的写者先拿到 flush 锁；manifest 中文件的先后与 `active_wal_number` 的推进仍按代的顺序 |
| drop 与在途操作 | drop 发生在 flush 的锁外阶段、有写者排在 flush 锁上、有 collection 正在懒打开时：drop 等待或让对方放弃；之后不会在已删除的位置或同名的新 collection 中写入任何文件；drop 之后同名的 create 拿到的是新句柄 |
| drop 与 create 失败 | 注入 drop 改名失败：报错且 collection 照常可用，之后再次 drop 可成功。分别在 drop/create 改名之后的目录 fsync 注入错误与 panic：RPC 报「目录已变更、持久化未确认」，表项和失败缓存已清理；drop 保留别名与 staging，该服务实例内的后续写入、Flush、CreateIndex、create/drop 均被拒绝。让无关 collection 的写者在 create/drop 之前进入闸门并暂停，create/drop 必须等它完成；再令 fsync 报错，后到的无关写者也被拒绝。再让同一目录的 fsync 返回成功，也不得解除封锁或删除 WAL；正常关闭只同步 WAL。模拟断电使未确认的改名回退或生效，前者保留旧 collection 与别名，后者重开时清理 staging，并在后续同名 drop 重试、同名 create 或 `aliases.json` 写入时清理悬空别名。注入写 `aliases.json` 失败：drop 报错且明确目录已移走，同名 drop 重试、下一次写 `aliases.json` 或同名 create 都能清理悬空别名；仅重开不清理；立即同名 create 后别名不指向新 collection。不得出现半个 collection 目录 |
| fail-closed 后 drop | 从未打开过、schema 不支持、manifest 有未知键、被引用 Parquet 损坏或缺失时直接 drop；无 collection 句柄也能改名并清理别名，之后同名 create 成功，不读取或删除原目录内的单个数据文件 |
| 损坏句柄的 drop | 锁内 panic 标记损坏时，旧 flush 正在锁外写盘；drop 等待 flush 锁、同步并关闭 WAL 后才改名，旧 flush 不会在删除位置或同名新 collection 中继续写文件；WAL 同步失败则不改名 |
| drop 前 WAL 同步失败 | 活跃代同时有 data 与 delta WAL，对 data 的 fsync 成功、delta 的 fsync 失败：两个 writer 都不关闭，drop 不改名；解除故障后同一 collection 的 insert 与 delete 仍能写 WAL，重开与 3.x 读取都不丢行 |
| 大小写别名交错 | 在不区分大小写的文件系统上，3.x 建物理 `Foo` 与指向 `foo` 的别名 `old`；暂停本实现 drop `Foo` 的改名之后，并发 create `FOO`，旧别名在新 collection 出现之前被清理，不能指向新 collection；区分大小写的文件系统上三个名字按精确名字处理 |
| 首次读触发懒打开 | 尚未打开的健康 collection 有孤儿 data/delta 文件；另一 collection 的 create/drop 在目录 fsync 失败后封锁数据库，再对前者发 Query/Search/Get：不得删除孤儿文件，首次打开返回封锁错误；已打开 collection 的纯读仍可继续。另以钩子暂停首次打开的清理，create/drop 的独占许可须等清理结束，不能反向持名字锁等写入闸门 |
| 空 delete | 过滤删除零命中、主键快路径的空列表都返回 0，且不创建 WAL、不消耗 `_seq`；随后重开并插入 auto_id，主键与 3.x 相同。非空但全为不存在主键的列表仍消耗一个 `_seq` |
| 有待提交状态 | 注入提交点前后的失败：触发 flush 的写入成功；1 秒内的写入被拒绝且不生效；多个写者并发时不死锁；恢复之后的写入先完成重新提交；显式 Flush 返回错误；之后正常关闭，3.x 打开时行数不变 |
| WAL 追加失败 | 在 File 这一层注入部分写入加报错，包括 batch 小于写缓冲大小的情形；之后空间恢复，文件长度不再增长；经冻结、fsync、关闭与崩溃，重开时失败的写入不存在；进程内不再分配用过的 `_seq`，重开之后按本实现已校验的前缀继续分配 `_seq`；与 3.x 的同号断言限于失败恢复 flush 与 WAL 清理已经完成，或双方确实恢复出同一前缀的目录（失败的写入在该前缀中不存在，复用是安全的；保留半截批并继续拼接字节的故障目录不承诺同号，见 0002 的继承风险） |
| 空的一代与 `current_seq` | 关闭时的空提交，以及追加失败时这一代为空、只换编号之后，`current_seq` 不下降；3.x 打开后能继续写入并 flush；打开时全部跳过、只读后关闭，3.x 打开时行数不变 |
| 打开后第一次提交前的 fsync | 文件系统操作顺序的断言中，第一次 replace 之前，非本进程写出的被引用文件与各级目录都已 sync；在这一步注入失败，manifest 仍为旧版且 WAL 未删；第一次删除打开时就存在的 WAL 只能发生在首个活跃代发布之后。3.x 打开只剩 delta WAL 的目录时，本实现读出的结果正确 |
| 乱序回放 | WAL 编号的先后与 `_seq` 的先后不一致（3.x 缺陷 e 写出的目录）时，回放结果与按 `_seq` 判定的参考结果相同；回放出的一代与已被引用的文件同名时，向外放宽 seq_max 后提交成功 |
| panic | 在 flush 的锁外阶段注入 panic：replace 之前的按提交点之前的失败处理，之后的按提交点之后的失败处理。在持状态写锁的各段注入 panic：该 RPC 报 code 1，collection 在本进程内不再可用，重启后的状态等于从盘上恢复的结果。注入时有写者与读者排在状态锁上、有写者排在 flush 锁上：没有一次写入基于改了一半的状态返回成功；已完成自己写入的触发写者返回成功，还没写入的报错；锁外阶段正在写盘的 flush 停在下一次取锁处，不再有第二个句柄打开同一目录。在只持 flush 锁或名字锁的各段注入 panic（提交之后的 WAL 删除、CreateIndex 的 replace 之后、drop 与 create 的改名之后）：分别按删除失败、提交点之后的失败、改名之后的失败处理 |
| 显式 Flush | Flush 与另一写者的 flush 并发，以及冻结列表中有无人认领的代时：Flush 只在这些代全部提交之后返回成功；并发的另一次 flush 在提交点之后失败时，Flush 不返回成功；之后模拟断电（丢弃未 fsync 的 WAL 与未持久化的 replace），已确认的写入都在 |
| 删除 WAL 失败 | 注入文件与 `wal/` 目录的 fsync 或 unlink 失败，包括同一编号的 data 与 delta 两次 unlink 之间的失败与崩溃：Linux 与 macOS 上已确认的目录 sync 保证不删更大的编号，断电后不会只留下 data；sync 失败时报告无法保证的残余风险。之后的提交或关闭完成删除；关闭时仍失败则停下、保留并 fsync，写日志；打开时就存在的 WAL 在第一个活跃代发布之前不被任何提交删除 |
| WAL 的多 batch 互通 | 同一 data / delta WAL 连续写入多个 batch，分别由 pyarrow 15.0.0、25.0.1 与 arrow-rs 读回全部 batch；中途注入一次部分 `write_all`，该 writer 不再产生字节，新编号的 WAL 仍能回放，报错的 batch 不出现 |
| 打开后第一代在提交点之后失败 | 分别由写入的重试、CreateIndex、显式 Flush、关闭完成重新提交，并在每一步注入崩溃：已成功 sync 的 WAL 删除仍按编号成前缀。已提交 WAL 仍在时，本实现重开不重复；3.x 会重复，按已登记差异验收。只有重新提交与 WAL 清理完整成功之后，才断言 3.x 打开行数不变 |
| CreateIndex 的失败 | 提交点之前失败则报错、索引定义不存在；之后失败则返回成功，之后的提交完成重新提交；冻结代提交失败的标志不被 CreateIndex 清除 |
| aliases | 并发 drop 两个都有别名的 collection：`aliases.json` 中两个别名都被删除，文件始终是合法的 JSON，3.x 能打开 |
| 并发的 upsert | 多个写者对同一主键做部分 upsert，结果等于某个串行顺序 |
| 并列的先后 | 覆盖写与删除后再插入之后，检索中不在截断位置的并列，先后与 3.x 相同 |
| 关闭与 LOCK | 关闭时的 flush 进行中，另一个进程拿不到 LOCK；关闭中途某一项失败时停下，不删除未提交的 WAL。`Server::drop` 的后台收尾在 fsync 保留 WAL 之前不释放 LOCK；损坏 collection 不 flush，但同步其 WAL；后台收尾完成后另一进程能打开 |
| 多 collection Flush | gRPC `Flush` 请求含多个 collection 名，其中有不存在的名字时跳过它，逐个刷新存在的 collection；任一存在的 collection 刷新失败时返回该错误，与参照实现逐名处理的路径做差分 |
| 持续写入时的检索 | 基准中持续写入的同时测检索的 p99，与不写入时对比；另测 100 万行主键索引下锁内发布的耗时 |
| 逐行写入 | 1 万次单行写入之后，块数不超过 O(n / 上限 + log 上限)；检索与 flush 的结果与一次性写入相同 |

## 放弃的方案

- **flush 全程持写锁**：实现最简单，但检索每次要排队约 30 ms，dim 越大越长（原型测量）。
- **后台线程 flush**：写入不必等 flush，但冻结的代数不再受并发写入者数约束，内存没有背压。不变量 6 是 Python 时代的选择，目前没有改变它的证据。
- **检索继续全程持读锁**：锁外写 Parquet 之后，发布仍要写锁，一次 100 万行、上百条查询的检索（约数百毫秒）会推迟发布，进而推迟同步等待 flush 的写入与 drop。
- **WAL 用 `BufWriter`**：写出失败后缓冲中的残留会被补写，使报错的写入复活（见「WAL」）。
- **memtable 原地改写**：覆盖写直接改写块中的行，可以省掉旧版本占用的内存，但块不再不可变，快照就要复制数据。按位次排序已经能得到 3.x 的顺序。
- **发布时不改指主键索引，改为给 segment 附一张行号换算表**：发布可以做到常数时间，但每次按主键访问都要多查一次表。亚毫秒的发布已经可以接受，等测量显示需要时再考虑。
- **每行一个原子的「失效 `_seq`」列替代位图**：快照只需要一个 `_seq`，完全不必复制，但每行多 8 字节，扫描带宽更高。
- **按 3.x 的方式逐源取前 k 个再合并**：可以复刻截断位置上并列的取舍，但要放弃流式 TopK 与按行块并行，而 3.x 的取舍本身由 numpy 决定、近似任意（0006 第 23 项）。

### WAL 故障恢复的当前验收证据

- [wal_recovery.rs](../../crates/core/tests/wal_recovery.rs)：data/delta、多批 WAL 的每个字节截断位置与中间消息损坏/零填充；首次与后续批的每个部分写入位置注入 ENOSPC，断言原 writer 作废、关闭不补写、只恢复完整批前缀；schema/批解码 panic 保留格式错误诊断，真实 I/O 错误向上传递。
- [db_persistence.rs](../../crates/core/tests/db_persistence.rs)：insert/upsert/delete 的首次与已有 writer、零字节/头部/批末 ENOSPC，失败后内存不变，停止或继续写入后正常关闭重开；auto_id 在进程内不复用失败序号，重开仅从可恢复序号继续；读取 I/O 失败保留文件且懒打开可重试；flush 预同步分别在 data/delta/目录处失败时保持 BeforeReplace、manifest 与行集不变，同步失败的 collection 在重试窗口内拒绝写入，无关 collection 不受影响，显式 Flush 可立即完成重试并恢复写入。窗口断言使用仅测试构建可用的线程局部护栏，不依赖机器执行速度。
- [runtime.rs](../../crates/core/src/storage/runtime.rs)：冻结代保留原 WAL File；文件与目录同步任一点失败均不关闭其中任何句柄，全成功后才关闭；Unix 上删除 wal/ 后仍持有活跃或冻结句柄时同步报错，确实没有句柄时允许目录不存在。
- [crash_recovery.rs](../../crates/core/tests/crash_recovery.rs) 与 [互通用例](../../tests/storage_interop/test_cross_implementation.py)：ENOSPC 报错后停止或继续写入，再由独立进程立即退出；Rust 恢复结果与成功操作一致。3.x 与 Rust 的真实客户端分别读取两类目录：追加失败后恢复 flush 已完成、失败 WAL 已清理；以及注入恢复 flush 的 WAL 预同步失败，令半截 WAL 保留在盘上再退出。用例先断言实际 WAL 文件集合，再核对 count、get、主键 query、search 与向量；参考实现及 pyarrow 15/25 逐字节读取 Rust WAL，与 Rust 的完整批前缀及值一致。
- 边界：ENOSPC 是 File 层错误注入，并未填满宿主磁盘；本节自身不覆盖并发写入后崩溃、Parquet 读取 panic 或文件系统顺序；后续证据见[验收记录](../testing/m2-correctness.md)，不推断跨平台行为。仍有效的载荷位翻转不由格式校验检出，继承风险见 [0002](0002-data-dir-compat.md#继承的-3x-已知风险)。

### 读快照的当前实现与验收范围

[collection.rs](../../crates/core/src/collection.rs) 的 `ReadSnapshot` 共享不可变的列式块（含范数、动态字段与位次）及按位压缩的有效位图；写入仅对触及的有效位图写时复制。取得检索快照不复制列数据或全量主键表。`GetSnapshot` 在状态读锁内按请求顺序定位主键，只钉住命中的块；投影结果的复制在放锁后完成。空 expr 的 `count(*)` 仍在短读锁内取计数。Search 的度量定义、load/deleted 状态和主键 Query 的校验均来自同一次状态视图，后续 release、覆盖或 drop 不改变已取得的视图。

- [read_snapshot.rs](../../crates/core/tests/read_snapshot.rs) 用通道暂停取得视图后的读者，在恢复计算之前要求覆盖、删除、Upsert、重新插入、flush 发布、release、drop 与同名重建全部完成。活跃代及已提交数据各自覆盖；旧视图的主键、列、JSON、动态字段、距离与并列顺序保持不变；提交点前后失败的待提交代快照也在重试发布与后续覆盖删除之后保持原结果。
- collection 单测核对共享数据块与只钉住 Get 命中块；VARCHAR 主键用例另核对跨块重映射、重复与缺失主键，以及覆盖、删除、flush 与 drop 后旧投影不变。[service.rs](../../crates/grpc/src/service.rs) 与 [query.rs](../../crates/grpc/src/query.rs) 的测试分别暂停真实 Search RPC 与主键 Query 的锁外阶段，要求 drop 或删除与 flush 先完成，再核对旧响应。
- [test_read_snapshot.py](../../tests/differential/test_read_snapshot.py) 以真实 3.x 核对覆盖、删除后重插、flush 与部分 Upsert 前后的主键读取、投影、计数和非截断的并列检索顺序。

读快照切片保留既有列式视图，不改变落盘格式与发布协议；后续接通的数据源映射与块合并以[下节](#数据源映射与块合并的当前实现与验收范围)为准。S1 的接入以 [S1 过滤](#s1-过滤的当前实现与验收范围)为准，按名字并行打开的范围见下文。快照测试不替代完整的并发崩溃矩阵或性能基准，不能据此声明吞吐或延迟提升。

### 数据源映射与块合并的当前实现与验收范围

读取块记录稳定块 ID、存储源 ID、源内物理行号起点、不可变 `_seq` 与位次。主键索引引用稳定块 ID；尾块拼接只重映射参与拼接的引用，不搬动其他数据源。检索的源序在取得快照时派生，只进入本次检索的候选；segment 以 Parquet 物理行号打破并列，memtable 以位次打破并列。

- 活跃代的读取块与存储 memtable 的批缓存均合并大小相近的相邻尾块；向量拼接不超过 2^20 个浮点数，不跨源或代，不合并已提交 segment，不过滤任何失效行。原块与位图由旧快照继续持有。大批量写入原有的大块可直接由行块切分并行扫描，不因合并规则而拆写 WAL。
- flush 在锁外从实际写出批次解码列数据并计算范数；状态写锁内按冻结代的物理行映射转换读取引用和存储位图，保留最新可见性，移除该冻结源的旧读取块，并以一个新源 ID 发布 segment。提交点之前失败保持旧映射，之后的持久化或 WAL 清理错误仍先发布，再按原协议处理。发布只访问冻结源的物理主键，不扫描无关源的全量主键表；生产发布与格式恢复测试统一使用已知行集合的换源接口。
- 打开时保留 WAL 回放后的物理行范围，以 memtable 主键位次建立读取顺序；不再先压缩为存活行再与未压缩的发布映射配对。segment 的批次保留文件内行号，读取顺序保持 manifest 列表顺序。
- 持久化写入的 JSON 列在推进序号并追加 WAL 之前复用 Arrow 编码的规范化规则，使写入、发布、重开使用同一文本。归一化时拒绝会溢出为非有限 float64 的浮点形式数字（包括对象或数组中的值），在序号与 WAL 变更之前返回明确错误；保留有限数、宽整数与字面量字符串。3.x 接受这种 raw 输入但返回非标准 JSON 字节的差异见 [0006](0006-m2-scope.md#与-3x-的差异)，历史 `$meta` 非有限值的互通限制见 [0002](0002-data-dir-compat.md#继承的-3x-已知风险)。独立内存 Collection 仍保留原接口的输入文本；此规则不改变共享文件格式。发布发现内部映射不完整或与写出行不符时，不改读取源，标记当前 collection 不可用，缓存访问及写入拒绝，重启后从磁盘恢复；此前已经取得的不可变快照仍可使用。

验证证据：

- collection 模型测试在每次写入、Upsert、删除和发布后核对存活主键、值、读取块与存储位图、源内行号和 `_seq`；持续保留旧快照并核对它们的结果，关闭重开后再次核对映射；另以已提交 manifest、保留 WAL 和发布毒化的真实目录验证重开不重复回放。另固定跨 segment 的并列顺序、原物理行号，以及内部发布映射错误的拒绝路径。
- collection 与 memtable 单测固定合并后的块数边界、复制上限、失效行保留、主键引用重映射与旧块不变；这些是结构验收，不代表性能基准。
- [read_snapshot.rs](../../crates/core/tests/read_snapshot.rs) 在锁外构建写出批次后、提交与锁内发布前暂停 flush，下一代穿插覆盖、删除、Upsert 和重插；发布前后新视图相同，旧快照不变，再次 flush 与重开结果一致。暂停钩子的通道断开也须归类为提交点前失败，manifest 不变且可重试。
- [test_read_snapshot.py](../../tests/differential/test_read_snapshot.py) 的小批量差分核对多代发布前后的主键读取、计数、JSON 原始 RPC 字节与非截断并列顺序；参照实现保持最多三个 data 文件，并断言文件数量，避免将四文件触发的 compaction 重排混入本切片。[test_reopen.py](../../tests/differential/test_reopen.py) 另固定两侧关闭重开后的非截断并列顺序、原物理行号与 JSON RPC 字节。

数据源映射切片自身不实施 compaction 或 S1；后续 S1 的接入以 [S1 过滤](#s1-过滤的当前实现与验收范围)为准；并发与故障的后续证据见[验收记录](../testing/m2-correctness.md)；平台行为与最终性能基准仍待验证。块合并对写锁、复制与快照保留内存的实际代价尚未量化，不声明性能提升。

### 按名字懒打开与失败缓存的当前实现与验收范围

- [db.rs](../../crates/core/src/db.rs) 的首次打开沿用写入闸门的共享许可，按精确名字取锁；create/drop 仍直接取独占许可及目录变更锁，再取名字锁。不同名字的恢复与孤儿清理可以并行，同名的恢复、清理、登记只执行一次。已打开句柄继续走短表锁的快路径。
- 名字锁表仅在获取或释放锁引用时持有，不包住恢复或等待名字锁；等待者持强引用，每个使用者放开名字锁后，在表锁内析构自身的强引用，再以 Weak 的强引用计数为零判定回收；不能等析构体返回后才自动析构 Arc 字段。不为不存在的名字永久保留锁，create/drop 不强行替换仍被等待者持有的锁。错误缓存表与 collection 表同样是叶子锁，不在持表锁时等待状态锁或执行 I/O。
- 缓存的分类、错误保留与提交点失效规则以[打开](#打开)为准。`list_collections` 对已有失败判定返回 Released，不能因外部已修复 schema/manifest 就显示 Loaded。缓存不是磁盘状态，服务重建后重新判定；目录提交点之后的封锁仍优先阻止首次打开，缓存不会绕过写入闸门。
- core 的受控并发用例暂停一次打开：同名请求等待且最后取得相同 Arc，不同名在暂停期间完成恢复；create/drop 等待共享许可、同名重建不复用旧句柄；持有在途任务时关闭等待句柄登记与恢复结束，之后才释放 LOCK。两线程两万轮循环取放及析构窗口交错后的锁表回收（两处同步均为带超时的 channel，析构中的同步故障在析构之外断言；栈展开时不等待同伴，另以用例固定超时、断连与原始 panic 保留）、schema/manifest/snapshot/Parquet/引用文件缺失的判定缓存、外部修复后仍拒绝、服务重建重试、提交点前失败保留与提交点后同步失败清除缓存均有断言。
- [db_persistence.rs](../../crates/core/tests/db_persistence.rs) 的真实 WAL I/O 失败用例仍证明文件不变、首次访问报错、下一次访问重试成功；core 分类用例覆盖各读取层的 I/O 错误及 Parquet 包装的 I/O 来源，清理扫描故障不缓存。清理钩子断连也不会成为永久判定。
- [重开差分](../../tests/differential/test_reopen.py) 固定并发 Rust 首次读取与参照实现串行真值的一致性、同名重建及无关 collection 的可见行，并对外部修复后的两侧缓存差异分别断言；首次打开失败且未登记句柄时，目录删除/移走后的 has/describe/load state/stats 均按不存在处理，移回后恢复原缓存判定。3.x 没有首次打开互斥，不能用其并发打开缺陷生成真值。

本切片不调整读取文件的格式、发布、别名维护或恢复策略，不代替完整并发崩溃矩阵、跨平台实测或性能基准。aliases 文件的完整读改写事务由独立叶子锁保护；debug 锁序检查与故障组合的后续证据见[验收记录](../testing/m2-correctness.md)。

### S1 过滤的当前实现与验收范围

求值范围以 [0006 第 1 项](0006-m2-scope.md#决策项)为准：[filter](../../crates/core/src/filter.rs) 完整解析参照实现 v3.2.1（43d1257）的语法，再拒绝范围外构造；只绑定标量字段与字面量的六种比较、and、括号，以及顶层主键 in。字面量在左侧和 `&&` 归约为相同构造。`or`、`not`、LIKE、算术、字段间比较、独立布尔谓词、JSON / 动态字段、数组、时间、全文与几何谓词只解析，不求值。范围外构造的语义错误不复现；语法错误仍逐字对齐。原 M1 主键识别器已由完整解析取代，快路径仍保留请求的主键顺序、重复与类型转换语义。

- 查询和检索的 load/deleted 检查、字段绑定、过滤与投影使用同一次状态视图。Query 的 schema 无关解析先在状态锁外产生 `ParsedFilter`，load 校验后才传播解析错误；通用路径与主键分派复用该结果，不再二次解析。每个块按列及既有有效位生成掩码，计算期间不做逐行版本查找；无过滤时复用原位图，不额外复制块表。and 的各操作数都求值，不能因先前谓词为假屏蔽转换错误；仅失效旧行不参与转换（0006 第 13 项）。FLOAT 与整数字面量使用 float32 的 ±2^24 安全转换范围，DOUBLE 或浮点字面量使用 float64 的 ±2^53 范围，错误原文与 Arrow 一致。
- 通用 Query 按数据源序、segment 物理行序或 memtable 位次排序，再执行 3.x 的 limit / offset；主键 in 的 get 快路径继续忽略分页。零 / 负 limit、负 offset 与无效字符串参数保留参照实现的实际行为，不新增校验。带 expr 的 count 使用同一过滤掩码、不使用分页；空 expr 的 count 保留不检查 load 与分区的短锁路径。query iterator 仍显式拒绝。
- 主键 `in` 的数值集合按 Arrow 的实际转换路径求值：先构建 value_set，再尝试完整转成 int64；成功时不把列转为 double，失败时才按 double 位模式查集合，因此非整数浮点集合中的 `-0.0` 不匹配整数零。普通比较仍将正负零判为相等。整浮混合的集合构造错误、宽整数列的安全转换错误和边界饱和行为均由真实 3.x 的 Query/count/Search/Delete、发布与重开用例固定，不另登记数学语义差异。列式存储上的逐行标量分派开销留待最终基准核对，本切片不据此声明性能改善。
- [filter_s1.rs](../../crates/core/tests/filter_s1.rs) 固定旧快照在发布、过滤删除、drop 与同名重建后仍不变，失效旧行的数值边界，以及过滤失败不改变行集、序号与 WAL。Delete 取得视图之前仍先检查毒化与待重试提交，存储失败的错误优先级由注入用例固定。[db.rs](../../crates/core/src/db.rs) 的受控用例暂停求值结束后的 Delete，覆盖同时写入新版本与 release 的行为。S1 不改变 WAL、manifest 或失败重试协议。
- [test_filter_s1.py](../../tests/differential/test_filter_s1.py) 通过真实客户端对照八类标量、六种比较的两个方向、and、Query/count/Search/Delete、分页参数、错误码与原文、主键两种类型和关闭重开后的顺序；顺序用例显式限制参照实现的 data 文件数小于四，排除 compaction 重排。原 [CRUD 副本](../../tests/python/adapter/test_grpc_crud.py) 恢复原过滤表达式，并复用除 LIKE 外的十九条上游用例；此前标为待复用的其余 40 条 S1 用例已在[后续验收](../testing/m2-correctness.md)迁移并双线对照，[INVENTORY](../../tests/python/adapter/INVENTORY.md) 已同步实际状态。
- 语法真值通过 [生成脚本](../../tests/differential/generate_filter_parse_fixtures.py) 从真实 3.x 导出，[语料](../../tests/differential/fixtures/filter_parse_v321.json)覆盖语法分支、截断与固定种子的词法变异；`--verify` 可核验。Unicode 字符分类按 CPython 3.12 / Unicode 15.0 固定，[生成脚本](../../tests/differential/generate_filter_unicode.py) 可核验分类表。嵌套深度另有明确服务上限，差异见 0006。
- ISO 时间与偏移共用按 [CPython 3.12.14 的 C 解析器](https://github.com/python/cpython/blob/v3.12.14/Modules/_datetimemodule.c) `parse_hh_mm_ss_ff` / `parse_isoformat_time` 推进的扫描器：覆盖紧凑与冒号形态、无分隔符的小数、六位微秒截断、逻辑时区边界与实际尾字节、零秒偏移忽略小数的规则；日期与 INTERVAL 不在本次重写范围。固定语料保留此前的全部 2857 条，并增加时间与偏移的长度/尾字节矩阵。另以[直接模糊对照器](../../tests/differential/fuzz_temporal.py)把结构生成与字符变异的表达式交给真实 3.x `parse_expr` 与 [Rust 解析入口](../../crates/core/examples/filter_parse_probe.rs)，逐字比较接受结果及诊断，不依赖 gRPC 或固定语料；每次输出覆盖计数与反例报告，任何分歧返回失败。真实入口仍由 Query/Search/Delete 的差分用例固定；时间求值仍属范围外。

本切片不实施过滤索引或表达式缓存，不声明吞吐、延迟或内存改善；S1 用例复用、并发故障与 Parquet 读取的后续证据见[验收记录](../testing/m2-correctness.md)；跨平台实测与最终性能基准另行验收。
