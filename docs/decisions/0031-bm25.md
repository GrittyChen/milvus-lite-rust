# 0031：BM25 函数与全文检索

状态：设计已通过（v3），四步均已实施并逐步评审通过。参照版本 `1320d26`。

## 范围

- 建表时的 BM25 function（`FunctionType.BM25`，proto 类型 1）：校验、持久化、DescribeCollection 回显，与 3.x 数据目录双向互通。
- 写入时由输入文本生成输出稀疏字段（Insert、Upsert、partial upsert）。
- `SPARSE_INVERTED_INDEX` + BM25 的定义与调参项 `bm25_k1` / `bm25_b`，以文本作为查询的 BM25 检索。
- BM25 在 Search、HybridSearch、range、offset、分组、boost、L2 rerank、`round_decimal`、search iterator 和带分区检索中的行为。
- 输入字段的 `analyzer_params`：standard 分词器和 `stop` 过滤器。

不做：
- jieba 分词器：返回 UNIMPLEMENTED，见差异表。路线上 jieba 单独成片且排在后面。
- TEXT_EMBEDDING function（类型 2）：需要外部付费服务，保持现有的 UNIMPLEMENTED。
- 跨 segment 的全局 IDF：3.x 只有 TODO，没有实现。

对齐口径按已定的决定：完整复现 3.x 按 segment 计算的统计，只把 segment 布局本身的差异登记出来。

## 3.x 的行为

以下都是在 `1320d26` 上实测的，探针放在仓库外。

**建表**

- 函数类型由 `_decode_function` 在翻译阶段检查，只认 1 和 2，否则报 code 6 `function 'bm' uses unsupported type 3`。
- 函数参数逐个按 `json.loads` 解析，解析失败就保留原字符串（实测 `{"b": "x"}` 能建表，`schema.json` 存字符串，重开后原样回显）。DescribeCollection 回显时，非字符串的值用 `json.dumps` 写回。
- 输出字段在 schema 中标记 `is_function_output`。
- `validate_schema` 最后校验函数，全部报 code 6：
  - `duplicate function name 'bm'`
  - `function output field 'sp' is used by multiple functions`
  - BM25 自身的检查，依次是：输入恰好一个、输入存在、输入是 VARCHAR、输入 `enable_analyzer=True`、输出恰好一个、输出存在、输出是 SPARSE_FLOAT_VECTOR，文案形如 `BM25 function 'bm' input field 'text' must have enable_analyzer=True`。
  - 标了 `is_function_output` 却没有函数产出的稀疏字段：`sparse function output field 'sp' has no producing Function`。
- 以下组合都能建表：两个 BM25 function 用同一个输入、输入是 VARCHAR 主键、输入或输出字段 nullable。
- 校验通过之后，构造 Collection 时为每个 BM25 输入字段建分词器（[factory.py](https://github.com/milvus-io/milvus-lite/blob/1320d26/milvus_lite/analyzer/factory.py)）。在这一步失败时不会留下集合目录。

**`analyzer_params`**（仅对 BM25 输入字段生效；text_match 仍按 [0029](0029-text-match.md) 不读它）

- `null` 或没有设置：standard。
- 其他非对象值（`0`、`false`、`[]`、`""`、列表、数字、字符串）：报 code 1 `'int' object has no attribute 'get'`，类型名随值变化（int / float / bool / list / str）。这与 0029 中「为假值时视为没有设置」的保存规则不同：保存规则管的是持久化，构造分词器拿到的是解析后的原值。
- 分词器名取 `params.get("tokenizer") or params.get("type", "standard")`：
  - 名字为字符串时直接使用。
  - 名字为对象时取它的 `type`，缺省为 `"standard"`。
  - 其余类型报 code 6 `analyzer_params 'tokenizer' must be a string or dict, got int`。
- 名字按大小写敏感比较：`"standard"` 可用；`"jieba"` 在没装 jieba 的参照环境报 code 1 `JiebaAnalyzer requires the 'jieba' package. ...`；其他名字报 code 6 `unknown tokenizer type: 'english' (supported: 'standard', 'jieba')`，名字按 Python repr 写出（`'Standard'`、`None`、`5`）。
- 停用词：`filter` 是列表时，取其中 `type == "stop"` 的对象，它的 `stop_words` 是列表时，逐项 `str()` 后加入集合。其余形状一律忽略，例如 `"lowercase"` 这样的字符串、`stop_words` 是字符串或对象。分词后（已转小写）按原样比较，所以 `"The"`、`True`（`str` 后是 `"True"`）永远不会命中。

**写入**（[collection.py](https://github.com/milvus-io/milvus-lite/blob/1320d26/milvus_lite/engine/collection.py#L365)）

- 翻译层解码完成后，引擎先检查记录里有没有输出字段，有就报 code 6 `BM25 output field 'sp' is generated; provide its source text instead`。检查的是解包动态字段之后的记录：原始 RPC 只在 `$meta` 里放 `sp` 也报这个错（已实测）。Insert、Upsert 和 partial upsert 都一样，pymilvus 会在客户端先拦下。
- 之后依次是：分配 auto_id、生成输出字段、补默认值并校验。
- 生成规则：
  - 文本是字符串时：转小写，按 `\w+` 切词，去掉停用词，每个词取 UTF-8 字节的 FNV-1a 32 位哈希，按词频计数（`float(count)`），按维度排序后写成打包字节。
  - 文本是 null 或缺失时，生成空向量。由于生成发生在补默认值之前，带默认值的文本字段缺失时，存下的文本是默认值，稀疏向量却是空的。
- 输出字段跳过稀疏值校验。
- Upsert 遇到已有主键时，先合并旧记录，丢掉旧的输出值，再按合并后的文本重新生成。

**检索**（[sparse_inverted.py](https://github.com/milvus-io/milvus-lite/blob/1320d26/milvus_lite/index/sparse_inverted.py)、[`_search_sparse`](https://github.com/milvus-io/milvus-lite/blob/1320d26/milvus_lite/engine/collection.py#L975)）

- **度量与查询格式**：
  - BM25 输出字段要求的度量是 BM25。请求指定其他度量时报 code 6 `sparse field 'sp' requires metric BM25, got 'IP'`；请求的度量名不区分大小写。
  - 普通稀疏字段指定 BM25 时，报 `... requires metric IP, got 'BM25'`。
  - 查询必须是文本，给稀疏向量时报 `BM25 field 'sp' requires a text query, not a sparse vector`。
  - 给普通稀疏字段文本时，沿用 0030 的 `sparse vector must be a dict, got str`。
  - 原始 RPC 的 VarChar placeholder 按 UTF-8 解码，失败时报 code 1，文案是 Python `UnicodeDecodeError` 的原文，例如 `'utf-8' codec can't decode byte 0xff in position 0: invalid start byte`。
- **查询的预处理**：查询文本用同一个分词器切词，词频作为查询权重，所以重复的词权重加倍。词的顺序是首次出现的顺序；本实现的 BM25 查询保持 `Vec<(词项哈希, 权重)>` 的这个顺序，不经过 `sparse::normalize`（它按维度排序、去重、丢零，会把顺序变成哈希序），同分时先比首个命中的查询词序号、再比行号。空文本或只剩停用词时，这条查询没有命中。
- **每个 segment 的统计**：倒排构建时不带有效位。N 是全部物理行（含空向量、已删除、旧版本的行），doc_len 是行内权重之和，avgdl = Σdoc_len / N（为 0 时取 1），df 是含该词的行数。删除、旧版本和过滤只在打分时排除，不影响统计。构建不校验权重，没有 0030 对 IP 的那套坏行检查；字节长度不是 8 的倍数时照样报 code 1。
- **MemTable 的统计**：每次检索重建，只统计存活且通过过滤的行，所以同一条查询加上过滤后分数会变。这一点已实测。
- **公式**：
  - IDF = `math.log((N - df + 0.5) / (df + 0.5) + 1.0)`。
  - tf_norm = `tf·(k1+1) / (tf + k1·(1 - b + b·dl/avgdl))`。
  - 每条查询按查询词顺序、每个词按行号顺序累加 `idf · tf_norm · 查询权重`。
- **数值**：doc_len 存在 float32 数组里，而 Python float 与 `np.float32` 的混合运算在 NumPy 1 和 2 下的类型提升不同（NEP 50）。
  - NumPy 2：凡是有 `np.float32` 参与的运算都是 float32，另一侧的 Python float 先转成 float32；只有 Python float 之间的运算仍是 float64。所以 `idf`（`math.log`）与 `tf·(k1+1)` 先在 float64 中算出，到与 float32 相乘、相除时才转 float32；`b·dl`、`/avgdl`、`(1-b)+…`、`k1·…`、`tf+…`、`tf·(k1+1)/…`、`idf·…`、`·查询权重` 与累加都是 float32。
  - NumPy 1：全部是 float64，取负后才转成 float32。
  - 我在仓库外写了两种逐步舍入的模拟，各在 2 万轮随机数据（随机 k1、b、过滤与查询）上与对应环境的 3.x 打分结果逐位一致；而两种语义之间约 90% 的轮次结果不同（距离位或次序）。CI 与 Compare 的参照环境（ref25）是 NumPy 2.5.3，Arrow 15 的互通环境（ref15）是 NumPy 1.26.4。
- **次序**：每个数据源按分数降序取 top-k，同分时保持字典的插入先后，也就是先比首个命中的查询词序号，再比行号；之后按数据源次序拼接，再按 float32 距离稳定排序。这与 0030 的排序键相同；NumPy 2 下源内分数就是 float32，排序键里的 double 一项与它相等。
- **负的 top_k**：报错时机与 0030 相同，打分开始就报。
- **对外的距离**：距离是 `-score`，以 float32 返回，所以 pymilvus 看到的是负数，越小越相关。各处的换算如下：
  - range 按 L2 一侧比较，即 `d < radius` 且 `d >= range_filter`，d 是这个负数。例如 `radius=-0.3, range_filter=-3` 能命中，反过来写则一条都不命中。
  - boost：sum 模式用 `distance - value`，与 IP 相同；multiply 模式用 `distance·value`。
  - rerank 链的输入分数是 `-distance`，归一化用 `2·atan(score)/π`，属于正相关度量。
  - `round_decimal` 作用在这个负数上。
  - 分组按距离升序。
  - search iterator 在 3.x 上的分页表现出自上述 range 规则与 pymilvus 的客户端逻辑：实测 limit 6、batch 2 时跳过了第二名。本实现复现服务端的规则，iterator 结果随之一致。
- **调参项**：
  - 只有原始 RPC 的 `params` JSON 生效。pymilvus 把调参项拆成独立的 kv，3.x 不读这些 kv，所以经 pymilvus 设置的 k1 / b 无效（实测分数与默认值相同，非法值也能建成）。
  - 合法范围：`bm25_k1` 用 `float()` 转换后有限、> 0、不是 bool；`bm25_b` 在 [0, 1] 内、不是 bool。字符串 `"2"` 合法，`true`、`null`、`[1]`、`"x"`、`Infinity`、`NaN` 都不合法，报 `field 'sp': invalid bm25_k1`。
  - 按 `bm25_k1`、`bm25_b`、drop ratio、算法名的顺序校验。
  - 索引定义的 `params` 与 `search_params` 都校验，但打分只用定义的 `params`（默认 k1 = 1.5、b = 0.75）。检索请求里的同名参数只校验，不参与打分。
  - k1 大到 float32 溢出（如 1e308）时，分数为 NaN，照样返回。
  - `Infinity`、`-Infinity`、`NaN`、`1e999` 在 3.x 中先被读成浮点再报 `invalid bm25_k1`。`NaN` / `Infinity` / `-Infinity` 字面量不是严格 JSON，本实现按 [0030](0030-sparse-vectors.md#与-3x-的差异) 已登记的规则在解码时返回 UNIMPLEMENTED，索引定义与检索请求的 `params` 都如此。`1e999` 与超出 float64 的整数是严格 JSON，与 3.x 一样在调参项校验中报 `invalid`（drop ratio、算法名同理），不会进入持久化。`1e308` 是有限值，照常接受。
- **索引类型**：BM25 输出字段只接受 `SPARSE_INVERTED_INDEX` + BM25，否则报 `sparse field 'sp' requires SPARSE_INVERTED_INDEX with metric BM25; got 'AUTOINDEX'/'BM25'. ...`，校验时机与 0030 相同。不建索引也能 load 和检索，此时按默认 k1 / b。

## 设计

**schema 与持久化**：
- 解除 `functions` 的 UNIMPLEMENTED，仅对 BM25。TEXT_EMBEDDING 维持原样，在原来的位置报出。
- `CollectionSchema` 增加函数列表，字段增加 `is_function_output`，校验接在 `validate_schema` 末尾，按上文顺序。
- `schema.json` 按 3.x 的 `_function_to_dict` / `_function_from_dict` 读写；[schema_file.rs](../../crates/core/src/storage/schema_file.rs) 已能解析，只需去掉拒绝并补上写出。
- 函数参数与 3.x 一样逐个解析：是严格 JSON 就存解析后的值，否则存原字符串；回显时字符串原样、其余用 `pyjson` 按 `json.dumps` 写回；`schema.json` 读写同形。建表、打开、回显三条路径都接受字符串参数。解析结果含 `NaN`、`Infinity`、溢出数或超深嵌套（只能来自 3.x 的 Python JSON）时，按 [0029](0029-text-match.md) 已登记的 schema 非严格 JSON 规则处理：建表 UNIMPLEMENTED，3.x 写出的这类 `schema.json` 打不开、可以 drop。
- 打开时，与建表走同一套校验和分词器构造；失败时沿用「含不支持内容的集合」的处理：集合打不开，可以 drop，同库其他集合不受影响。
- 此前的版本已经把带函数的 `schema.json` 当作不支持的内容，降级时不会读错。
- 函数的输出字段在规范化时统一标记 `is_function_output`，经引擎接口建的 schema 与 gRPC 建的保存相同。3.x 接受标了 `is_function_output` 却没有函数产出的非稀疏字段（写入时把它当作可以缺失），本实现对这种 schema 返回 UNIMPLEMENTED（建表与打开都是）；稀疏字段的这种情况按 3.x 报 `has no producing Function`。

**分词器**：
- 在 [analyzer.rs](../../crates/core/src/analyzer.rs) 已有的 standard 切词上，加停用词集合与 FNV-1a 词项哈希。
- `analyzer_params` 的解释单独做成一个函数，返回分词器或 3.x 原文的错误。它拿的是 JSON 解析后的原值，不经过 0029 的假值过滤：现有的 `classify_analyzer_params`（gRPC）与 `schema_file` 打开路径都会把 `0`、`[]`、`""`、`false` 当作没有设置。字段因此分两个值：`analyzer_params` 仍是过滤后的持久化与回显值，另存一份只供构造分词器的原值；BM25 输入要在函数解码后才知道，所以 gRPC 解码与 `schema_file::to_core` 都先读函数，再对 BM25 输入字段用原值构造。非法 JSON 仍当作没有设置（standard）。`{"tokenizer": []}`、`{"tokenizer": 0}` 经 `or` 回退到 standard，`{"tokenizer": 5}` 报 code 6。
- 停用词的 `str()`：字符串取原值，整数取十进制，`true` / `false` / `null` 分别取 `True` / `False` / `None`。浮点、列表和对象转成字符串后都含有 `\w` 以外的字符，不可能命中，可以不加入集合。`NaN` / `Infinity` 已被 0029 拒绝。
- 分词器在建表或打开集合时构造一次，随集合保存。

**写入**：
- 在引擎的写入入口（gRPC 解码、动态字段解包之后）做两步：先检查输出字段是否出现在记录里（顶层或动态字段），再在 auto_id 之后、补默认值之前生成输出列。输出列按普通稀疏列存储，字节与 3.x 逐位相同（按维度排序、f32 计数）。生成直接写字节，不经过 `sparse::normalize`：FNV 哈希可以等于 `2^32-1`，3.x 对输出字段跳过校验，这个维度合法；输出层的 `dim` 已按 64 位计算。
- partial upsert 不继承输出字段，按合并后的文本重新生成。
- 输出字段不走稀疏值校验。

**查询解码**：`QueryVectors::Text` 带上字符串。gRPC 层按 Python 的规则报 UTF-8 错误：
- 原因：数据不完整时为 `unexpected end of data`；首字节非法时为 `invalid start byte`；其余为 `invalid continuation byte`。
- 位置：区间按 Rust `Utf8Error` 的 `valid_up_to` / `error_len` 换算，两者都按「最大非法子序列」划分。
- 区间长度：`error_len` 为 `Some(n)` 时取 n；为 `None`（末尾不完整）时取 `len - valid_up_to`。
- 首字节非法指 0x80–0xC1 与 0xF5–0xFF；合法首字节后接非法字节（含 `ED A0`、`E0 80` 这类）是 invalid continuation。
- 单字节写 `byte 0xff in position N`，多字节写 `bytes in position N-M`。例：`E2 82` → `bytes in position 0-1: unexpected end of data`；`E2 82 28` → `bytes in position 0-1: invalid continuation byte`。
- HybridSearch 的各路同样处理。

**度量**：`Metric` 新增 `Bm25`。BM25 在 3.x 中的内部距离就是 `-score`，对外距离也是它（`_internal_distance_to_milvus_distance` 对 BM25 原样返回），所以各换算都是恒等，**不是** IP 那一支的取负。逐层如下：

| 层 | BM25 | 本仓位置 |
| --- | --- | --- |
| 对外距离 / `Hits.scores` | `-score`（负数，f32） | — |
| `public_f64` / `internal` / `public_from_internal` | 恒等 | [index.rs](../../crates/core/src/index.rs) |
| `higher_is_better` | 假：只服务排序与 range，越小越好 | `flat::rank`、`TopK`、`SearchRange::contains` |
| range | L2 一侧：`d < radius` 且 `d >= range_filter`，不平方 | `SearchRange::contains` 经 `higher_is_better` 自动正确 |
| boost sum / multiply | `distance - value` / `distance·value` | [boost.rs](../../crates/core/src/rerank/boost.rs) `transform` 的 sum 分支并入 `Cosine \| Ip` |
| boost 后还原对外分数 | 恒等。`$distance` 被同名字段覆盖时：不接链，只有响应编码的 `float()`（`"1.5"` 得 1.5）；接链（Search + L2、HybridSearch），链入口的一元负号对非数值报 `bad operand type for unary -: 'str'`（已实测） | `boost::public_score` 新增一支，`BoostPlan.chained` 区分 |
| rerank 链输入 | `-public`（正分） | `run_chain` 是所有度量共用的：仅当 `metric == Metric::Bm25` 时取负，无 boost 用 `-public_f64(score)`，有 boost 用 `-query.public[i]`；IP / COSINE / L2 保持现有的 `public_f64` / `query.public` 不变。Search + L2 与 HybridSearch 都经过这里 |
| rerank 正相关 / 归一化 | 正相关；`2·atan(x)/π` | [chain.rs](../../crates/core/src/rerank/chain.rs) `positively_related` 与 `Norm` |
| `round_decimal` | 作用在负距离上，与 IP 的 f64 还原相同 | gRPC `round_score` |
| 稀疏打分的 TopK | `TopK::new(Metric::Bm25)`，`push` 传负距离；`RankedRow` 的 double 一项存正分供源内同分降序 | `rank_sparse` |

`higher_is_better` 与 rerank 的「正相关」是两个概念，不能互相推导。`Metric::parse` 不接纳 BM25：稠密字段的度量解析用它，3.x 对稠密字段 + BM25 报 `field 'v': unsupported dense metric 'BM25'`；BM25 只在稀疏分支按「是否 BM25 输出」直接取得。`build_spec`、load 时的定义校验与 `check_sparse_tuning` 都按期望度量参数化，后者增加 k1 / b 的取值校验。

**倒排与缓存**：
- BM25 字段按块构建「tf 倒排 + 每行 doc_len（f32）+ 块的行数与 doc_len 之和（f64）」，存在 0030 已有的槽位里，同样不看有效位。
- 构建只解码，按 dict 语义处理重复维度，不规范化、不丢零值、不校验权重。字节长度错误照样报出。
- 检索时，按数据源汇总各块的 N、总长度（f64 相加）和查询词的 df（倒排列表长度之和），在 f64 中算出 IDF 与 avgdl，进入 f32 运算时才转换，再打分。总长度不能用 f32 累加，否则大 segment 的误差会超过 1 ULP。所以多块组成的 segment 与 3.x 的单个 segment 统计相同。
- k1 / b 只在打分时读当前定义，不进缓存键（注释写明倒排只含 tf、doc_len、N 与 df）；定义变化仍经过 0030 的三个入口清空槽位。
- 额外内存是每行 4 字节。

**打分**：
- 按 NumPy 2 的语义逐步舍入：`idf` 与 `tf·(k1+1)` 先在 f64 中算出；b、avgdl、`1-b`、k1、tf 只在进入 f32 运算时转 f32（`tf·(k1+1)` 不能拆成 f32 相乘，否则差 1 ULP）；其余每一步与累加都是 f32。
- 0030 的打分暂存（f64 分数 + 首个命中序号）原样复用，f64 中存 f32 的值。
- 分段并行、排序键、错误先后、负 top_k 与分区选择都沿用 0030。

**MemTable**：沿用 0030 的路线（解码 → Python 路线的过滤 → 构建），只用存活且通过过滤的行计算统计。

**DescribeCollection**：回显 `functions`（名称、类型、输入、输出、参数）与字段的 `is_function_output`。

## 与 3.x 的差异

| 差异 | 3.x | 本实现 | 理由 |
| --- | --- | --- | --- |
| NumPy 1.x 环境中的 3.x | float64 计算，结果与 NumPy 2 下差若干 ULP，同分次序也可能不同 | 按 NumPy 2 逐位对齐 | 3.x 的结果本身随 NumPy 主版本变化。CI 与 Compare 的参照环境是 NumPy 2，NumPy 1 已停止维护。互通测试在 Arrow 15（NumPy 1.26）环境上不逐位比较 BM25 分数 |
| segment 布局不同 | — | — | 总规则：布局相同（且一个 segment 的多个块按 segment 汇总）时逐位一致；布局不同时统计不同，分数、次序与结果集合都可能不同。来源包括自动 flush 的触发点（[0027](0027-reference-3.2.2-upgrade.md)）、compaction 的文件大小桶（[0010](0010-compaction-and-tombstone-gc.md)）、flush 进行中的检索（同一行算在 MemTable 还是 segment，两者统计口径不同）等。差分测试串行化 flush 与 compaction，用显式 flush 固定布局 |
| jieba 分词器 | 装了 jieba 时可用，没装时建表报 code 1 | 建表返回 UNIMPLEMENTED；3.x 建的使用 jieba 的集合打不开，可以 drop | jieba 需要词典与分词算法，路线上单独成片 |
| NaN 分数的次序 | k1 使 float32 溢出（如合法的 1e308）、或 BM25 输出列被改写成 NaN 权重或会使分母为 0 的值时，分数可能为 NaN，次序取决于 Python 排序遇到 NaN 时的比较结果 | 同样计算出 NaN，但结果集合与次序都可能不同（top-k 截断时 NaN 参与排序会改变入选的行） | 逐位复现需要模拟 timsort 在 NaN 上的比较顺序；正常写入的数据与不使 float32 溢出的常规 k1 不会出现；1e308 这类合法但极端的 k1 会出现，只登记结果集合与次序 |

此外，被改写成非整数计数的 BM25 输出列，avgdl 的求和次序可能使结果差 1 ULP。这类数据只能来自手工改写，不单列。

标了 `is_function_output` 却没有函数产出的非稀疏字段：3.x 能建表、也能打开这样的数据目录；本实现建表返回 UNIMPLEMENTED，打开 3.x 写出的这种目录时该集合打不开（UNIMPLEMENTED，可以 drop）。只有原始 RPC 能建出这种 schema。

调参项的 `params` 不是严格 JSON 时（含 `Infinity`、`-Infinity`、`NaN` 字面量），沿用 0014 / 0030 的 UNIMPLEMENTED，3.x 报 `invalid bm25_k1`；索引定义与检索请求的这三种字面量都在 `bm25_cases.REGISTERED` 中两边分别断言。调参项里的 `1e999` 这类溢出数是严格 JSON，与 3.x 一致，不是差异；索引定义其余键里的溢出数仍按 0030 的 UNIMPLEMENTED 处理（3.x 会把它以 `Infinity` 写进 manifest）。函数参数与 `analyzer_params` 中的非严格 JSON 沿用 0029 的登记（0029 已补「函数参数同样适用」）。

## 已定事项

第一轮评审（2026-11-11）确认：数值按 NumPy 2 对齐；NaN 按差异登记，不复现 timsort；segment 布局差异按总规则登记，含 compaction 与 flush 进行中两个来源。

## 实施步骤

每一步做完由子 agent 复核，直到没有问题。

1. **schema、分词器与写入**：
   - 函数的解码、校验、持久化与回显（含字符串参数）；`analyzer_params` 的原值与分词器构造；FNV 哈希与停用词。
   - 写入：输出字段检查（含 `$meta` 同名键）、生成（不经 `normalize`）、默认值前生成，以及 Upsert / partial upsert 的重新生成。
   - 测试：`analyzer_params` 为 `0`、`[]`、`""`、`false`、`true`、`null`、`{}`、`{"tokenizer": []}`、`{"tokenizer": 0}`、`{"tokenizer": 5}`、非法 JSON（这几条测试先于代码写好）；原始 RPC 的 `$meta` 同名键；字符串参数的建表、重开与回显；默认文本加空向量；partial upsert 重新生成；含 `0xFFFFFFFF` 维度的字节。
   - 与 3.x 的数据目录双向打开。
2. **索引与度量**：先按度量表落 `Metric::Bm25`（含 boost 的 `public_score` 与 `run_chain` 的 BM25 取负分支，以单测覆盖）；`build_spec` 与 load 校验参数化；k1 / b 校验（非法值与溢出数按 3.x 报 `invalid`，`NaN` / `Infinity` / `-Infinity` 字面量为 UNIMPLEMENTED，含原始 Search 请求 `params` 里的用例）；度量解析（`parse` 不接纳 BM25，稠密 + BM25 报 `unsupported dense metric`）；文本 placeholder 解码与 UTF-8 错误语料；HybridSearch 子请求解码。
3. **检索**：BM25 倒排与缓存、按数据源汇总统计、f32 打分、MemTable、排序与错误先后，以及 range、boost、rerank 链、`round_decimal`、分组、iterator、HybridSearch 的端到端接入（度量表的各支已在第 2 步落地）。测试含一个 segment 多个块的汇总（单测对照逐行参考计算）、k1 = 1e308 的 NaN（只断言为 NaN、不崩溃）、两个查询词分别命中不同行且分数相同的并列次序，以及 IP 或 COSINE 的 boost + rerank 回归（防止 BM25 的取负污染原路径）。
4. **差分、互通、参照用例、文档与性能**：
   - 差分覆盖 MemTable、过滤对 MemTable 统计的影响、flush 与重开、多 segment 与多块 segment、删除后统计不变、k1 / b、分区、HybridSearch 与 iterator，在 pymilvus 两条线上运行；串行化 flush 与 compaction；加 NumPy 主版本守卫（参照环境须为 NumPy 2）。
   - Arrow 15 / 25 双向互通。Arrow 15（NumPy 1.26）只比较数据与存储字节，用例照常运行，只是不断言 BM25 分数。
   - 迁入参照的 `test_grpc_fts.py`、`test_milvus_fts_compat.py` 中不依赖内部模块的用例，并重新盘点 `test_sparse_field_contract.py`。
   - 文档同步 0002、0006、0014、0029、0030、AGENTS、README。
   - 对照 3.x 的写入与检索性能；2.5.1 是否支持同样的 BM25 写法，实施时先确认，支持就一并对照。
