# 0022：签发前的候选保全门闩

- 日期：2026-10-26。
- 依据：[0021 第 19、20 条](0021-release-build-in-ci.md#发布与权限)；[0021 试点记录](../testing/0021-release-pilot.md)的 B 阶段「重跑删除了已签发 attempt 的产物」与 C 阶段「观察」；[证据的存放与复核范围](../testing/README.md)。

## 问题

正式运行的候选文件在签发前后都只以工作流产物存在：保留 30 天，整体重跑该运行即被删除（B 阶段实测）。来源证明写入透明日志后不可撤回、版本随即消费，签发后一旦丢失候选字节，只能换版本重来。

0021 第 20 条目前靠人工：候选结果 job 一完成就下载候选结果与 `fi` 两个产物，签发后再核对并存入本地留存。C 阶段实测 attest 在候选结果 job 结束 2 秒后开始、11 秒后开始签发，按 30 秒间隔轮询发现时签发已经完成：**当前人工流程无法保证保存先于签发**，只是缩小了时间窗。要消除的缺口是这个顺序，而不是保存本身。

约束（0021 第 19、20 条）：发行工作流不获得 `contents: write`，不提前公开未验收的候选。

## 推荐方案：环境审批门闩与机器核对的保全回执

### 1. 阻断点

attest job 加上 GitHub 环境（environment）。正式运行使用设有必需审批人的环境 `release-signing`，审批人只有负责人；attest 在获得审批前不会分配执行机、不会执行任何步骤。演练使用不设保护规则的环境 `dry-run-signing`，不暂停，演练行为不变。job 名 `attest` 与步骤名 `sign` 是版本消费判定的固定键，保持不变。

**环境保护规则预检**：工作流引用不存在的环境时，GitHub 会自动创建同名环境且不带任何保护规则（官方文档，探针实测），`release-signing` 被删除、改名或写错时 attest 会不经审批直接开始。因此正式运行在前置检查中读取 `release-signing`，要求环境存在、有必需审批人规则且审批人恰为仓库所有者，否则在第一个构建之前失败；attest 的「保全回执」步骤在读取审批记录之前再复核一次，防止等待期间配置被改。两处都用现有的 `GITHUB_TOKEN`（前置 job 与 attest 都已有 `actions: read`，探针实测可读取 `required_reviewers` 与 `branch_policy`），不新增 PAT。预检只让失败更早、更清楚，不替代回执核对：即使预检被绕过，没有匹配的审批记录也不会签发。

### 2. 保存时点与候选产物来源

候选结果 job 成功后、审批之前，负责人在本机用新工具（暂名 `tests/release/preserve.py`）保存：

- 来源：本运行、本 attempt 的 `release-candidate-v<版本>` 与 `fi` 两个工作流产物，以负责人本人的认证经 GitHub API 下载；
- 核对：七个主体与 `SHA256SUMS` 一致，四个 FI wheel 与候选结果的 `fi_wheels` 一致，候选结果的版本、`mode=release` 与运行身份正确；
- 原子完成：先写入同级的临时目录，全部下载、核对、`fsync`（文件与目录）并回读重算摘要通过后，才 `rename` 为最终目录「版本 / 运行 ID.attempt」；`rename` 之后对父目录再 `fsync` 一次，使最终目录项本身持久化，随后回读最终目录、由其内容计算并输出回执；最终目录已存在即拒绝；任何一步失败都不产生最终目录，临时目录以明显的未完成名称留下或删除，不会被误认为已完成的证据；
- 回执：对规范文本计算的 SHA256。规范文本第一行是候选 ID，其后每个文件一行「SHA256␣␣规范路径」，按规范路径排序。规范路径区分来源：七个主体为 `release/<文件名>`，四个 FI wheel 为 `fi/<文件名>`。四个正式 wheel 与四个 FI wheel 同名、只有哈希不同，只按文件名排序得不到唯一的文本；加上前缀后十一条路径互不相同（四个 FI wheel 的文件名因平台标签而不同）。规范文本的字节形式固定为：UTF-8、无 BOM，LF 换行，末尾恰有一个换行，SHA256 用小写十六进制。本地工具与工作流调用同一个规范化函数，并以同一组测试向量自检。回执与规范文本一并写入最终目录。

### 3. 签发前的放行条件

- **FI 摘要的来源**：在候选结果与 attest 之间新增一个只读 job（暂名 `preserve-digests`，只有 `contents: read`），下载本运行的 `fi` 产物，重新计算四个 FI wheel 的摘要，与候选结果的 `fi_wheels` 交叉核对，不一致即失败；通过后把四条 `fi/<文件名>` 摘要作为 job 输出。attest 依赖它，仍然只接收待签发的七个文件（0021 第 19 条不变）。演练中同样运行，演练的签发不读取它。
- **回执格式**：负责人审批时把回执写进审批备注，格式固定为 `preserved <候选 ID> <回执>`。
- **核对步骤**：attest 在「签发前复核」之后、`sign` 之前新增步骤「保全回执」。它用下载的七个主体与 `preserve-digests` 的输出独立构造规范文本、计算回执，再经 `GET /repos/{owner}/{repo}/actions/runs/{run_id}/approvals`（`actions: read` 可读，记录含 `environments`、`state`、`user` 与 `comment`）读取本运行的审批记录：
  - 先按备注筛选：只看备注与 `preserved <本次候选 ID> <本次回执>` 逐字相同的记录；
  - 筛出的记录必须恰好一条，且为 `approved`、环境为 `release-signing`、审批人为仓库所有者；
  - 本次候选 ID 下出现任何 `rejected` 记录、筛不出记录或筛出多条，都失败，`sign` 随之跳过。
- **同一运行的新 attempt**（探针实测）：只重跑失败 job 与重跑全部 job 产生的新 attempt 都重新等待审批；审批记录接口只返回当前 attempt 的记录，旧 attempt 的批准或拒绝不会出现。按完整备注（含候选 ID 与回执）筛选仍然保留，作为第二道保险：候选 ID 含运行 ID 与 attempt，即使平台行为将来变化，旧审批也匹配不上本次回执。
- **签发前的重跑**：`sign` 开始之前失败（包括在门闩处拒绝、回执不符、签发前复核失败），允许对同一运行「重跑全部 job」，新 attempt 产生新的候选 ID，须重新保存、重新以新回执审批；也可以改开新的运行。不得只重跑 attest 或只重跑失败的 job：前置检查与候选结果的 attempt 一致性守卫会拒绝。`sign` 一旦开始，该运行的任何 attempt 仍然禁止重跑（0021 第 20 条）。

这样签发的前提是：负责人在签发前已经持有与本次候选逐字节一致的完整候选证据集（十一个文件），并以审批确认；人工步骤仍在，但不再与签发赛跑。

### 4. 权限边界

- 工作流的 `permissions` 不变：没有 `contents: write`，不新增 secret 或外部凭据；attest 仍是 `contents: read`、`actions: read`、`id-token: write`、`attestations: write`。探针实测在同样的受限权限（不含 `deployments`）下引用环境能正常创建部署并运行，环境预检与审批记录都用现有 `GITHUB_TOKEN` 读取。
- 新增的只是仓库设置：两个环境及 `release-signing` 的必需审批人。由负责人设置，不开启「禁止自审」（触发与审批是同一人），部署分支不限（冻结分支是临时的，保护来自审批人）。
- 审批与下载都用负责人本人的认证，在本机执行。

### 5. 不可用时的失败语义

| 情形 | 结果 | 版本 |
| --- | --- | --- |
| 等待审批中 | attest 处于 `waiting`，不分配执行机、不执行步骤 | 不消费：探针实测 `runner_name` 为空、步骤为空，`runs.signing_started` 判为未开始 |
| 负责人拒绝 | attest 以 `failure` 结束，没有执行机、没有步骤，运行失败 | 不消费：同上，探针实测 |
| `release-signing` 缺失、无必需审批人或审批人不是恰为仓库所有者 | 前置检查失败，不进入构建 | 不消费 |
| 等待期间环境被删除或保护规则被改（含被自动重建成无保护环境） | attest 可能直接开始；「保全回执」的复核失败或筛不出审批，`sign` 跳过 | 不消费 |
| 审批了但回执缺失、格式不符或摘要不一致 | 「保全回执」失败，`sign` 跳过 | 不消费：跳过的 `sign` 不算开始（A 阶段已实测） |
| 审批记录接口不可用或返回异常 | 同上，按失败处理，不重试掩盖 | 不消费 |
| `preserve-digests` 失败（`fi` 产物缺失或与 `fi_wheels` 不符） | attest 因依赖失败而跳过 | 不消费：跳过的 attest 不算开始 |
| 等待期间所继承的 `CI` / `Compare` 有新运行或重跑 | 「签发前复核」失败（现有判据），`sign` 跳过 | 不消费 |
| 回执正确 | 签发 | 消费；签发后的规则不变，禁止重跑该运行的任何 attempt |

签发前的任何失败都可以用同一版本重新运行（0021 第 3 条）：按第 3 节重跑全部 job 或改开新运行，重新保存、重新取得回执。官方没有定义审批等待的上限；等待态不消费版本，负责人应主动拒绝或取消，不依赖超时。

### 6. 保留与恢复

- 保全目录即完整候选证据集的本地留存，签发后在同一目录补存证明包、Rekor 记录与 closeout，与现行第 20 条一致。
- 恢复：以发布准备工具（`release_set.py --prepare`）核对七个主体，以候选结果核对四个 FI wheel；回执可随时由目录内容重新计算核对。
- 本地留存是单一位置，介质损坏的风险由负责人另行备份承担；本方案只保证“签发前已保存”，不提供异地不可变存储。

### 7. 幂等性

- 回执绑定候选 ID（版本、冻结提交、运行 ID 与 attempt），不能挪用到其他运行或 attempt；同一目录内容重复计算得到同一回执。
- 保全工具拒绝写入已存在的最终目录，未完成的临时目录不会被当作证据，重复执行不会覆盖已保存的证据。
- 放行只认备注与本次候选 ID 和回执逐字相同的唯一一条审批；签发前失败后重跑全部 job 或新开的运行都产生新的候选 ID，必须重新保存。

### 8. 验证方式

- **工具自检**（快速层）：规范文本的字节形式（以固定测试向量核对编码、换行、末尾换行与小写十六进制，本地工具与工作流共用）与排序，含正式 wheel 与 FI wheel 同名而哈希不同时仍唯一；`preserve-digests` 对 `fi` 产物与 `fi_wheels` 的交叉核对；审批记录按备注筛选的正反例（其他 attempt 的旧备注、审批人不符、本次候选 ID 下的 `rejected`、缺少或不符的备注、筛出多条、环境名不符）；保全工具的原子完成（中途失败不产生最终目录、最终目录已存在时拒绝）；环境预检的正反例（环境缺失、没有必需审批人规则、审批人多一个或不是仓库所有者）；没有执行机的 attest 不算开始签发（以探针取得的等待态与拒绝态 jobs 响应为测试数据）；工作流静态检查（attest 的环境按模式选择并依赖 `preserve-digests`、「保全回执」位于 `sign` 之前、attest 的签发主体仍只来自候选产物）。
- **已确认的平台行为**（官方文档与门闩探针，探针为临时诊断分支上的运行 40281637463，分三个 attempt：拒绝、只重跑失败 job 后以回执格式备注批准、重跑全部 job 后拒绝）：
  - 保护规则通过之前 job 不会分配执行机；等待态 `status=waiting`、`runner_name` 为空、没有步骤（`started_at` 已有值）；拒绝后 `conclusion=failure`、`runner_name` 为空字符串、没有步骤；`runs.signing_started` 对两种状态都判为未开始；
  - 新 attempt 都重新等待审批，审批记录接口只返回当前 attempt 的记录；
  - 审批备注经接口原样返回，与提交的字节一致；
  - 受限权限（不含 `deployments`）下引用环境正常；`GITHUB_TOKEN` 以 `actions: read` 可读取审批记录与环境保护规则；
  - 环境名可用表达式；引用不存在的环境会自动创建无保护的同名环境，`permissions: {}` 的 job 照常运行；
  - 官方没有定义审批等待上限（文档中的 30 天是等待计时器的取值范围），不实测超时。
- **试点**（专用测试版本 `0.0.1rc904`，新的冻结提交，逐次授权）：

  | 步骤 | 预期 | 版本 |
  | --- | --- | --- |
  | 演练（作为 PID 1 引用） | 使用 `dry-run-signing`，不暂停，与现行演练一致 | 不消费 |
  | 正式运行，在门闩处拒绝 | attest 未开始；随后同版本运行的前置检查不认为版本已消费 | 不消费 |
  | 正式运行，审批时故意写错回执（可选） | 「保全回执」失败，`sign` 跳过 | 不消费 |
  | 正式运行，保存后以正确回执审批 | 签发成功；审批时间早于 `sign` 开始；本地留存与签发的字节一致 | 消费 |

  预算：一次演练与两到三次正式运行，每次约 80 分钟托管时间；可选步骤的审批解析已由工具自检覆盖，负责人可以决定省去。

## 最小替代方案：只加环境审批

attest 加同样的环境与必需审批人，但不加 `preserve-digests` 与回执核对：负责人按操作清单保存、核对后再审批。

- 优点：工作流只改一行环境配置与演练环境，不新增工具和步骤；同样从结构上消除“签发先于保存”的赛跑。
- 缺点：审批与已保存的证据没有机器绑定，漏存、存错版本或存成另一个 attempt 的产物都不会被发现；试点只能验证暂停与拒绝，不能验证“保存了正确的字节”。
- **不可用于真实候选**：`release-signing` 不存在时 GitHub 会自动创建无保护的同名环境，这个方案会直接放行签发。它只能作为说明门闩机制的诊断示例，不能作为推荐方案的降级路径。

## 未采纳：自动写入外部不可变存储

在候选结果之后增加一个 job，把完整候选证据集上传到独立的私有归档仓库（发布不可变 Release）或带对象锁的对象存储，attest 依赖其成功。它能提供异地、自动、写一次的副本，但要给运行候选代码的工作流加一个写凭据（即使只对归档位置有效），并引入外部依赖与凭据轮换；在目前单一维护者、发布频率低的情况下，代价大于收益。发布频率提高或有多名维护者时再评估，届时可与本方案叠加。
