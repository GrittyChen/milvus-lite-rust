## 问题与选择

正式 wheel 的两种普通 JSON raw Insert 本轮分别为 124.66 / 228.47 ms，参照为 92.47 / 165.65 ms；Upsert、nullable 和 key 的差距不同，不能合并成一个写入退化结论。组件测量和调用链共同确认：持久化列已由 `normalize_data_json` 完整解析、检查有限浮点并转成规范文本，随后 `wal_data_batch` 又为同一列执行 `json_strings`，重复解析、检查和序列化。

首片推荐只移除这条已规范化 typed JSON → WAL Arrow 路径中的重复工作。保留逐行业务校验和第一轮规范化，收益实测后再判断；不以分项相减预测端到端提速。相比引入新 JSON 解析器、保留整批 AST 或改变列共享结构，此方案约束范围更小，也避免把更大的状态 / 内存设计混入当前切片。

进程峰值继续独立登记。重复编码会产生临时字符串，但本轮没有 allocator 调用栈或全部活数据的字节归因，不能承诺该切片解决全部 RSS 差距。

## 冻结的行为边界

1. **规范化仍是必经步骤。** 原始请求、旧目录、默认值、Upsert 合并值都先按既有规则校验并规范化；私有快速入口只能接收该步骤成功后的 typed JSON 列。不能根据“字段类型是 JSON”或调用者传入的任意布尔标志，就假定外部文本已可信。
2. **公开存储入口保持原合同。** [arrow_data](../../crates/core/src/storage/arrow_data.rs) 的通用 `data_batch` / `wal_data_batch` 仍可被互通工具和其它调用方传入未规范化数据，继续解析、检查和编码。建议在持久化写路径内建立一个明确命名、最小可见范围的已准备 WAL 入口；具体签名由实施选择，不新增持久化类型或公开的跳过校验选项。
3. **调用链必须完整。** 普通 Insert、普通 / partial Upsert，以及 key Insert / Upsert 的每个桶均覆盖。保留原先字段转换、规范化、全桶预构造、WAL 追加、MemTable 应用与读视图发布的先后顺序。恢复、Flush、compaction 和直接存储工具的路径不因新入口自动改变。
4. **错误优先级保持。** 列解码 / 长度 / valid_data → 主键与向量 → 逐行业务与原位置 JSON 检查 → 列转换 / 规范化 → WAL。保留被同名后列覆盖或掩码遮住的坏 JSON 拒绝、默认值、缺字段、显式 null 和 0004 已登记的顶层 JSON 差异，不提前或延后错误以换取速度。
5. **规范字节保持。** 对象键序、空白、Unicode 转义、宽整数、浮点、JSON null 与父有效位均遵循现有编码。新 WAL Arrow 列的逻辑内容、字段名、父 / 子空值、序号和分区标签与原路径相同。不能只比较 Python 解码后的对象就宣称字节编码未变。
6. **失败语义保持。** 后字段或后桶的确定性错误仍在追加任何 WAL 前整批拒绝；I/O 失败仍按已校验前缀恢复，不引入整批原子写入承诺。自动 ID、碰撞保护、关闭 / LOCK、快照和并发许可沿用 0017 / 0007。
7. **不引入新格式。** schema、manifest、WAL、Parquet 与索引文件格式均不变；新旧实现继续在既有范围内双向读取。无需版本化用户数据目录，也不改发布过的附件或 tag。

J08 的普通基准同时保留约 2 KB 简单语料和约 2.7 KB 混合语料；原数据集的 null 密度、重复 PK、每批新 collection 或跨批复用 collection 均保持。key 不与不支持它的 2.5.1 比速度。资源分别记录原整进程峰值与分进程服务器 / 客户端口径；单独峰值不相加当作同时峰值，组件 RSS 不替代 allocator 归因。

验收要求目标场景在三轮配对结果中有可重复改善，普通非 JSON / nullable / key 旁路无可重复退化；若轮间区间重叠或结果矛盾，保留原数据并调查，不预先设置一个可被噪声满足的提速百分比。性能改善只对实测工作负载声明，不自动判为 0001 全部写入或资源目标达成。

## 范围与推进顺序

调查、诊断工具和本合同已独立复审通过，产品实施与验收见[0018 验收记录](../testing/0018-json-write-acceptance.md)。原调查工具仅在仓库外的冻结源码副本追加诊断函数，不作为已经优化的产品构建。

平台与证据层级沿用 0013；本片实施验收不自动等于下一发行候选通过，也不新增原生 Intel 全套、最低系统真机或真实断电门槛。
