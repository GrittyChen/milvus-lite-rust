# 0005 检索的线程模型

- 状态：已采纳
- 日期：2026-09-25
- 对照版本：不涉及 3.x 的对外行为；rayon 的语义按 rayon-core 1.13.0 的源码核对
- 前置决策：[0001 重构基线选择](0001-refactor-baseline.md)（约束 4「检索可并行」）、[0003 进程内服务的生命周期](0003-in-process-server-lifecycle.md)（「所有权」「进程退出」「fork」）、[0004 M1 的范围与验收](0004-m1-scope.md)

## 背景

M1 的暴力检索是计算密集型的。距离改为 16 路累加、top-k 改为只保留候选之后，一条查询在引擎内单线程约 1.3 ms（10 万行）与 13 ms（100 万行）；同一请求中的多条查询、以及一条查询中的各行，都还是串行计算的。0001 约束 4 要求检索可以并行，0003 已经定下线程池的归属：每个服务实例创建自己的 CPU 检索线程池并注入引擎，不得使用进程级的全局线程池。

本文定下线程池怎样与现有的 RPC 执行方式、collection 的读写锁、停服与 fork 配合。按 [AGENTS.md](../../AGENTS.md) 规则 3，这是并发方面的改动，先写设计说明，经负责人确认后再实现。

M1 的实现：每个 RPC 的处理体在 tokio 的阻塞线程池（`spawn_blocking`）中执行，先经 `Db::enter` 通过关闭闸门；检索在持有 collection 读锁（parking_lot `RwLock`）期间完成全部计算。M2 已接通取快照后放锁计算，具体锁边界与数据源全序见 [0007「读」](0007-m2-storage-engine.md#读) 和 [0007「数据结构」](0007-m2-storage-engine.md#数据结构)；以下未特别注明的锁描述记录的是 M1 的实现。

文中的耗时都是初步测量：本机 Apple silicon（10 核）、计算池 10 个线程、128 维，行数随文注明，原型脚本不入库，重跑时量级一致而具体数值波动较大。正式数字以 M1 基准写入 [0001「M1 部分验证」](0001-refactor-baseline.md) 的为准。

## 结论

### 线程与任务

- **RPC 处理体仍在 `spawn_blocking` 中执行**，关闭闸门、panic 映射与现在相同。处理体会在读写锁上阻塞，这正是阻塞线程池的用途。
- **每个服务有一个 rayon 计算池**，依赖 rayon-core（rayon 的线程池部分，不含并行迭代器，并行迭代器这一类接口因此无从调用）：
  - 线程数取 `available_parallelism`，取不到时为 1（与 rayon 的默认相同）。线程数暂不可配置，CLI 的 `--max-workers` 在本实现中的含义随 CLI 一起定。
  - 它在服务启动时创建，是 `Db` 的一个字段，检索时从 `Db` 借用。
  - 一个进程打开多个路径时会有多个计算池，线程数超过核数；用户同时打开的路径通常只有一个，接受这一点（与 0003「放弃的方案」中一个服务一套资源的理由相同）。
- **M1 检索在持有读锁期间，经计算池的 `in_place_scope` 并行计算**；M2 只在取快照期间持读锁，计算池仍按下列任务模型工作（[0007「读」](0007-m2-storage-engine.md#读)）：
  - 请求拆成「查询组 × 行块」的叶子任务。查询组是 4 条查询，与距离计算的批量打分一致。
  - 行块是扫描顺序上连续的一段行，按行区间切分，可以跨 chunk，也可以落在 chunk 内部：每次写入是一个 chunk，一次大批量写入可达数十万行，只按 chunk 切分时这类 collection 完全无法并行。每块的计算量约 2^20 个浮点数：在 2^16 到 2^21 之间比较，10 万与 100 万行、1 / 4 / 100 条查询下 2^20 都在最优附近，块太小（2^16）时 10 万行的单条检索因调度开销变慢。
  - 每个叶子任务写入自己独占的结果槽：它的每条查询各一个 top-k，保留该块中的前 `limit + offset` 名。
  - **查询组分波提交**：每一波只提交填满计算池所需的查询组，即 ⌈线程数 ÷ 块数⌉ 组（至少 1 组），这一波的叶子任务全部完成、由调用线程合并进各查询的结果之后，再提交下一波。
    - 原因：结果槽中同时存活的候选数是「在途的查询数 × 各块保留数之和」。一次提交全部查询组时，它随 nq 增长：100 万行、123 块、nq 100、limit 16384 时约 2.4 GB，串行约 79 MB；本实现与 3.x 都不限制 limit 与 nq。分波后它与 nq 无关，与串行同量级。
    - 代价：只有块数少于线程数时，每波的组数才大于 1；10 万行 128 维已有 13 块，并行度的损失可以忽略。
  - 只有一个叶子任务时直接在调用线程上计算，不进入计算池。
- **结果与串行计算逐位相同**：
  - 每个距离的计算与所在任务无关。
  - M1 各块按与串行相同的全序（分数的名次、chunk、行）保留前 `limit + offset` 名；M2 改为（名次、数据源、位置），见 [0007「数据结构」](0007-m2-storage-engine.md#数据结构)。全局前 `limit + offset` 名中的每一个，在它所在的块里也必然在前 `limit + offset` 名之内。
  - 合并时按同一全序再选一次，结果与串行相同。

### 计算任务的约束

计算任务只读 collection 的数据，必须满足：

- **不拿任何锁、不阻塞**：不取 collection 或 `Db` 的锁，不等待通道或条件变量，写结果只写自己独占的结果槽；
- **只用计算池的 `in_place_scope` 与其中的 `spawn`**，而且只能从计算池之外的线程（RPC 所在的 tokio 阻塞线程）调用 `in_place_scope`；
- **由 clippy 强制**：除 `ThreadPool::in_place_scope` 与 `Scope::spawn` 之外，rayon 所有提交任务的接口一律由 `clippy.toml` 的 `disallowed-methods` 禁止，它对 trait 方法同样有效（已实测）。例如：
  - 会落到 rayon 全局池的自由函数，如 `rayon::join`、`rayon::scope`、`rayon::spawn`、`rayon::spawn_fifo`、`rayon::broadcast`、`rayon::in_place_scope`（0003「所有权」）；
  - `ThreadPool` 的其他提交接口，如 `install`、`spawn`、`spawn_fifo`、`scope`、`scope_fifo`、`in_place_scope_fifo`、`join`、`broadcast`、`spawn_broadcast`；
  - 并行迭代器，如 `par_iter`、`into_par_iter`、`par_bridge`。

  rayon 的调用集中在引擎的一个 module 里。

原因，均已实测复现：

- **RPC 与计算共用一个池会死锁**：工作线程在等待自己派出的子任务时，会接走队列中的其他任务。如果接走的是一个要取写锁的 RPC，而同一线程的调用栈上还持有读锁，就会永久阻塞。parking_lot 在有写者排队时也会阻塞新的读者，所以接走的是只读的 RPC 同样可能死锁。
- **`install` 加嵌套并行会优先级反转**：
  - `install` 把闭包交给计算池的工作线程执行，工作线程在等待子任务时会接走队列中的其他任务，包括后到请求的整个任务，要在自己的调用栈上执行完才返回。
  - 实测一个单独耗时 2 ms 的检索，在一个 200 ms 的检索之前 0.2 ms 提交，也要等约 202 ms 才返回。100 万行、8 个客户端并发时，p99 为数百毫秒（两次测量分别为 405–559 ms 与 776 ms）。
  - 从计算池之外的线程调用 `in_place_scope` 时，调用线程在锁存器上阻塞等待、不偷任务。同样条件下 p99 为 71–84 ms。
- **`ThreadPool::spawn` 中的 panic 会让进程中止**（rayon 在没有 panic handler 时的默认行为）；`in_place_scope` 会等其余叶子任务结束，再把 panic 传回调用线程。

### 锁的边界与排队

- M1 检索在整个计算期间持有 collection 的读锁；M2 在状态读锁内取快照后放锁计算，写入、flush 发布与 drop 不再等长检索计算结束，见 [0007「读」](0007-m2-storage-engine.md#读)。
- **计算池按先进先出排队，是 M1 接受的残余风险**：
  - 从计算池之外提交的叶子任务进入同一个全局队列，工作线程按先进先出取用，不分是否同一个 collection。
  - 查询组分波提交，每个请求一次只有一波叶子任务在队列里，所以后到的请求最多要等先到请求的一波任务（一个查询组在全部行块上）。实测有一个 700 条查询的检索正在进行时，单条检索在 10 万行下从单独执行的 0.9 ms 变为 1.9–3.4 ms，100 万行下从 7 ms 变为 12–30 ms。
  - 若一次提交全部查询组，后到的请求要等先到请求的全部任务：在没有分波的原型上，一个 2 ms 的检索在一个 200 ms 的检索之后 0.2 ms 提交，耗时约 202 ms。
  - M2 采用快照；按请求轮转与停服时取消长检索仍是接受的残余风险，见 [0007「读」](0007-m2-storage-engine.md#读)。
- 请求的解析（包括解码查询向量）在取读锁之前完成，collection 不存在的错误仍然最先报出。

### panic、停服与 fork

- **panic**：叶子任务的 panic 经 `in_place_scope` 传回 RPC 处理体，再经 `spawn_blocking` 映射成现有的错误（code 1，error_code 0）。计算池在 panic 之后照常可用。
- **停服**，以下几条是不变量：
  - 计算池是 `Db` 的字段。服务的运行状态与每个在途的 RPC 处理体都持有 `Arc<Db>`，所以计算池在最后一个 `Arc<Db>` 释放之后才析构。
  - RPC 处理体持有关闭闸门的 `InFlight` 期间，它派出的叶子任务在 `in_place_scope` 返回之前全部结束，panic 时也是如此。
  - 0003「进程退出」的停止顺序不变：`Db::close` 等到在途请求结束时，不会有计算任务还在读引擎的数据，之后才释放 LOCK。
  - 不经 `stop`、直接析构服务时（[Server::drop](../../crates/grpc/src/server.rs)），运行状态先释放，而在途的引擎任务仍在阻塞线程上运行；它们手中的 `Arc<Db>` 让计算池存活到它们结束。
  - rayon 析构线程池时只通知线程退出、不等待。空闲的线程随后自行结束，此时 LOCK 可能已经释放，但它们不再访问引擎。
- **fork**：子进程中继承来的服务按 0003 直接泄漏，`Db` 与其中的计算池随之泄漏，绝不在子进程中释放：子进程里没有它的线程，释放时会碰到 fork 时刻可能被持有的内部锁。子进程只经 URI 使用父进程的服务，不会在进程内调用继承来的引擎；子进程为新路径启动的服务创建自己的计算池。

## 验证

后续批量距离核展开、TopK 内联与候选位次懒读取保持本节任务、分波、内存和锁约束不变，数值及测量证据见[批量检索专项](../testing/batch-search-performance.md)。

| 用例 | 断言 |
| --- | --- |
| 并行与串行等价 | 各种 chunk 布局、查询条数、limit / offset（含 0 与超过行数）、并列、±0、±inf、NaN 下，并行结果与串行逐位相同（含 NaN 位模式，二者走同一扫描代码）；包括行块边界落在 chunk 内部，以及某个行块中的行全部已被覆盖、没有存活行。与逐条打分的独立参照比较时，NaN 只要求同为 NaN（见 [flat.rs](../../crates/core/src/flat.rs) 模块说明） |
| 检索中有写入排队 | 检索、写入与后到的检索都能完成，不死锁 |
| 叶子任务 panic | 分两段验证，不在发布代码中加注入点：计算池把叶子任务的 panic 传回调用方、之后照常可用（core 的 compute 用例）；RPC 处理体中的 panic 映射成 code 1、error_code 0，之后服务照常可用（grpc 的 service 用例） |
| 停服时有检索在进行 | 宽限期内完成的请求照常返回，已入场的引擎任务结束后才释放 LOCK：两项都由 grpc 的受控 RPC 用例以钩子确定性判定（见 0003「验证」）；正式 wheel 的检索用例只验证短请求照常返回、宽限期满后客户端收到取消、停服后 LOCK 释放与重开数据完整，不做跨请求耗时推断 |
| 检索进行中 fork | 子进程为新路径启动服务并检索，父进程的检索照常完成 |
| 大 limit、大 nq | 每波的查询组数只由线程数与块数决定（单元测试 `groups_per_wave`），同时存活的候选数因此不超过「每波组数 × 4 × 块数 × max(2 × (limit + offset), 64)」（TopK 攒够这么多候选才筛一次），与 nq 无关。分波不改变结果，结果对照类的用例发现不了它被去掉，由这条单元测试与评审把关 |
| 并发检索的尾延迟 | 基准：8 个客户端下的 p50 / p99，与串行对比 |

## 放弃的方案

- **用计算池替换 `spawn_blocking`**（AGENTS.md 原来的计划）：RPC 处理体会在锁上阻塞，与计算任务共用一个池就会出现上面的死锁。
- **每次请求临时开线程（`std::thread::scope`）**：不引入依赖，但开 10 个线程每次就要约 90–135 µs，是 10 万行单条检索并行后耗时（约 0.45 ms）的 20%–30%；并发时线程数超过核数，尾延迟更差。
- **不做请求内的并行**：同一时段交替对比（引擎内、单条检索、10 线程计算池）：
  - 单个客户端时，单条检索在 10 万行下约 1.3 ms、100 万行下约 13.9 ms；并行后分别约 0.51 ms 与 4.6 ms（100 万行时受内存带宽限制，约 120 GB/s）。
  - 8 个客户端占满机器时，串行的吞吐反而更高：10 万行约 2770 对 2300 QPS（并行低约 17%），100 万行约 230 对 220 QPS；多出的开销来自叶子任务的调度与合并。
  - 选择并行，是因为单个客户端（本地嵌入式的典型用法）的延迟降到约三分之一，而满载时的吞吐损失有限。满载时减少拆分等办法，与「锁的边界与排队」中按请求轮转的缓解一起留到 M2。
