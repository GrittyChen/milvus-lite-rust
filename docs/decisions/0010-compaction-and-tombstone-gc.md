## 背景与范围

回收已提交的覆盖/删除旧行与安全过期 tombstone，限制长期写入积累的文件、读取块和恢复工作量。首个切片只覆盖默认分区、已有 schema/FLAT 能力，不实现 snapshot RPC、ANN、标量索引构建、多分区或新的查询调度。

共享 schema、manifest、WAL、Parquet 格式不变，不引入 C++、系统依赖或通用任务框架。本设计改变后台存储并发和读取映射，负责人已按 AGENTS 规则 3 确认设计与测试矩阵。以下为实施合同，当前实现、产物身份与验证边界见[实施验收](../testing/compaction-correctness.md)。

## 参照行为

### 触发与选择

参照创建和懒打开 collection 都会构造 Collection，构造末尾提交一次后台任务；实际 flush 后再提交一次。创建时通常为空，但这次触发仍计入轮数。任务不合并、不自行循环，每个任务在每个分区至多合并一次。

memtable.size 是活跃主键数加 tombstone 数，只有删除也属于非空、会触发实际 flush；完全空的 Flush 不增加任务。正常关闭的最后一次非空 flush 同样提交任务，随后 shutdown(wait=True) 排空所有已接受任务。

选择器的规则如下：

- 按实际文件字节数分桶，边界为 1 MB、10 MB、100 MB，等于边界时进入较大的桶。
- 按桶从小到大尝试；桶内至少 4 个文件，并且行数预算截取后仍有至少 4 个，才能选中该桶。桶内保持 manifest 顺序，不另按文件大小排序。
- 若没有桶满足条件，且总 data 文件数超过 32，则按小桶优先、桶内 manifest 顺序拼接候选；预算截取后至少有 2 个才能合并。
- 单轮最多输入 200000 个物理行。单个文件行数达到这个预算就跳过；累计行数加上下一文件会超过预算时结束该候选前缀。
- 输出按 `_seq` 排序，每 100000 行切一个文件。

参照选择器会跳过缺失文件和读取元数据失败的文件。本实现不继承这种降级，真实 I/O、类型或引用损坏使本轮失败；差异见下表。

### 数据与 RPC

只在选中输入中按主键保留最大 `_seq`，再用已提交 delta_index 删除 `_seq` 严格更小的行。未选中文件、活跃 memtable 和未提交代不参与输出去重，不能用全局 live 位图替代物理输入。

新文件追加到移除输入后的 manifest 列表末尾。每个输出文件名取该块内容的 `[min(_seq), max(_seq)]`，重名时保持 min、仅增大 max；不是保留输入文件的最小值。[0002 约束 2](0002-data-dir-compat.md#共享状态的语义约束)要求文件名范围覆盖自身内容。

ManualCompaction 只成功应答，没有即时触发、目标存在性检查或强制等待；GetCompactionState 恒为 Completed。实际自动维护完成后才解除这两条 RPC 的 UNIMPLEMENTED，返回值按两条 SDK 核对。Completed 不代表任务已排空。

## 拟采用的方案

1. 每个 Db 一个专用维护线程；不同 collection 的维护串行，不使用检索计算池。
2. 按真实 CollectionHandle 身份保存待执行计数。一次触发消耗一次计数、执行一轮，不把多次触发压成一次，不因有进展自行排队。
3. 准备阶段使用内存中的不可变已提交块，不持 flush_lock；临时输出写完即在准备阶段 fsync。提交阶段取 flush_lock，从当前 manifest 重算替换结果，同目录改名、同步目录并提交。
4. data 替换与整份 delta GC 合成一次 manifest 提交。提交点、目录同步、发布与失败分类沿用 0007。
5. 保留写入闸门共享许可保护目录生命周期，对 create/drop 增加协作取消；正常关闭不取消已接受任务，完成最后一次有效 flush 的触发后排空维护。
6. 已提交删除按随后确认的 [0011](0011-committed-delete-state.md) 独立保存，visibility.latest_delete 继续负责全局可见性；snapshot 钉住集合沿用打开时已校验的 PinnedFiles。

## 与正确性不变量的关系

| 不变量 | 本设计的约束 |
| --- | --- |
| 1：`_seq` 全序 | 合并不分配新写入序号，不降低 current_seq 或 auto_id 下界；异常重复序号仍按 0007 已登记的来源/行号平局规则处理 |
| 2：MemTable 互清、seq-aware | 活跃/冻结代不参与输出去重；发布按最新主键引用和删除状态重映射，不能用准备时的位图覆盖并发更新 |
| 3：tombstone GC | 阈值从完整候选 manifest 的 data 文件下界计算；旧 WAL 风险未解除时不做本轮替换，删除证据不能先于持久化确认被丢弃 |
| 4：文件不可变 | 输入不修改；输出先用 data 目录内临时名写出并 fsync，再以不覆盖已有文件的方式取得最终名称；旧快照仍持有原列与原位图 |
| 5：manifest 唯一真值、原子更新 | 一次 replace 同时提交 data 和 delta 引用变化；其前保留旧状态，其后按实际提交点发布或 poison |
| 11：索引与 segment 生命周期一致 | 未淘汰 segment 的索引不变；淘汰 segment 的同 stem 3.x idx/sidx 一并清理，被 snapshot 钉住的除外；不改写现有索引定义 |

LOCK、schema 不可变、load 校验、距离口径、adapter 只翻译和 WAL 关闭前 fsync 均保持。新增并发不能降低 0007 的持久化保证。

## 所有权、调度与关闭

### Db 与线程

拟将内部构造统一为 `Result<Arc<Db>>`，线程通过 Weak<Db> 取得单次任务的强引用。Db 持有停止/唤醒状态和线程句柄，线程不常驻持有 Arc<Db>，不形成所有权环。

构造返回前线程须已就绪。启动失败释放资源并向上传递；gRPC/Python 对外入口不变，core 调用方同步调整所有权。这项 API 取舍已获确认，替代方案见后文。

队列只保存句柄身份、待执行计数和等待所需状态。一个实例至多一个排队表项，执行一次后若仍有计数则排到队尾，让其他 collection 有机会运行。计数耗尽、drop 或关闭排空后回收表项，不为不存在的名字保留任务。

调度点覆盖成功 create、成功懒打开，以及自动/显式/正常关闭 flush 的每个实际成功发布的非空操作代；单次 RPC 若发布多个代，逐代计数。create 在目录持久化确认、句柄登记且释放目录变更的独占许可/等待者计数后提出一次请求，不能被自己尚未撤销的取消标志消耗。后续取得已登记句柄不再当成懒打开触发。非空按 memtable 的活跃主键与 tombstone 判定，不按输出 data 行数判定；仅删除代和输出数据已全失效的有效代仍计一次。

为了清理空 WAL 而强制冻结的空代不计数。同代重试首次成功发布仍计一次；已经计数的代及纯 recommit 不重复计数。此对应关系须按参照的实际 flush 分支逐条测试。CreateIndex 的定义提交和后台本身的提交不增加计数。

失败记录任务结果和诊断，由下一次正常打开/flush 触发重试；已存在的后续计数照常逐次处理，不在失败后新增任务或忙轮询。取消也不新增补偿任务。

### 关闭与析构

等待中的任务不取得 InFlight。工作线程取任务后登记单次维护在途，再取得写入共享许可。正常运行时遵循关闭闸门；正常关闭期间仅允许已经接受的维护继续登记，外部 Db::enter 仍拒绝新请求。这个内部登记只用于持有 LOCK 的排空阶段，不能成为任意关闭后调用的旁路，也不能在释放 LOCK 后接受任务。

拟选择正常关闭排空，流程如下：

1. 关闭外部入口，等前台已接受操作完成；这些操作产生的维护触发仍正常接收。维护可继续运行，不在持 gate/队列锁时等待它。
2. 正常 close 执行既有最后一次 flush；每个有效发布代增加一次触发，仅清理空 WAL 的代不增加。此前排队/执行中的任务不撤销。
3. 最后一次 flush 完成后停止接收新维护，等待全部已接受计数及正在执行任务结束，再停止/join worker、同步保留 WAL 并释放 LOCK。后台提交不增加任务，因此任务总数有限，不自循环；这不保证 OS I/O 在固定时间内返回。
4. 关闭期间 flush、重新提交或发布失败仍按 0007 保留 WAL/文件并记录诊断。poison 或持久化未确认而无法继续的任务以失败结束，不能为凑轮数继续破坏性提交。

这覆盖显式停服与 Python atexit 的正常退出，接受额外维护等待，不承诺固定退出时限。此选择已获确认，并附退出等待实测条件；不把缩短退出等待作为取消正常任务的理由。

close_nowait/Server 析构、关闭级 panic 与数据库目录持久化未确认的收尾，沿用已采纳的 0003/0007 异常边界：不新启动排队的 manifest 提交，不执行最后一次 flush；取消尚未提交的维护，当前已越过提交点的任务先完成分类，随后只同步保留 WAL。它们可能少做维护及改变重开布局/分页或并列顺序，不能与正常关闭的轮数对齐混称。若以后要改变这条异常边界，另行确认生命周期设计。

join 时不得持 gate、队列、flush 或 collection 状态锁。未显式关闭就析构时先唤醒停止线程，按上述异常边界收尾；不能留下永久等待的 idle 线程。若 worker 释放最后一个 Arc 导致 Db 在 worker 上析构，只请求停止，不 join 自己；任务的有序锁与维护在途登记必须先释放。测试覆盖该析构路径。

## 取锁与取消

锁序仍为写入闸门 → 目录变更锁 → 名字锁 → flush_lock → collection 状态锁 → 叶子锁。维护不取得目录变更锁或名字锁；不按名字重新打开目标。队列锁只用于登记、取走与完成任务，不持锁做 I/O、取其他锁或 join。

单轮先取得写入闸门共享许可。短暂取得 flush_lock 检查既有待完成状态并清理已提交 WAL，再取得状态视图；准备输入、写 data 目录内临时文件及其 fsync 时释放 flush_lock 与状态锁。提交时重新取得 flush_lock 和必要的状态锁。普通写入、同步 flush 和 CreateIndex 可以在准备期间继续。

create/drop 在等待写入闸门独占许可之前，用 RAII 登记数据库级的“目录变更等待者”计数，操作结束后撤销。多个调用不能用一个可被提前清零的 bool 代替。维护在入场前、取得共享许可后、准备批次之间、每个输出文件前后及提交前检查该计数；计数非零就放弃提交前的本轮。正常 close 的排空状态不触发取消；仅异常收尾的停止状态触发同样的取消。

共享许可仍保护旧目录不被改名。释放许可前停止本轮全部文件操作；drop/同名重建不会接收旧句柄任务，不追踪被移走的路径、不重建旧目录。若已经开始 manifest 提交，必须先完成该提交的分类和状态发布，再释放许可，不能把提交后的取消伪装成提交前失败。

这是协作取消：减少准备阶段造成的跨 collection 等待，但不能承诺硬性的墙钟上界。正在进行的 Parquet 编码、文件同步或 OS I/O 不能靠原子标志打断；提交阶段和原有前台 flush 的等待仍存在。验收需用受控暂停证明 create/drop 取消能推进、正常关闭会等待既有任务，不把输出行数预算写成毫秒保证。

## 输入、删除快照与文件钉住

输入列、meta、seqs 和物理行数来自内存中的已提交块，借用其不可变 Arc。选择器仍 stat 读取实际文件大小并检查引用文件类型，不重复读取整个 Parquet。打开时已经完成的列校验继续有效；运行期间外部篡改数据文件不在 LOCK 保证内。

选定输入并整理主键后，在状态锁内按这些主键从独立 committed_deletes 表摘取已提交删除快照。准备视图的 manifest.current_seq 记作 C_prepare，提交时的值记作 C_commit。新表只在恢复已提交 delta 和冻结代发布后更新，不能从已被活跃删除覆盖的全局最大值倒推；细节与新增内存代价见 0011。

首次受控负载显示原保守方案留下 20% 失效物理行，3.x 为 0%，连续五轮不回收。负责人因此确认本轮实施独立表，取代最初“复用最大删除表”的选择。此变化不改磁盘格式、全局读取判定或未提交代的保护；改进结论必须以最终负载复跑确认。摘取快照与发布映射仍有输入规模的工作量，不宣称为常数时间。

历史故障目录可能有 seq 不大于当前 manifest.current_seq 的未提交操作。若活跃/冻结代仍有这种操作，或仍有已提交 WAL 未清理，本轮整体延后，既不按删除过滤，也不做替换/GC。准备和提交分别按当时的 current_seq 检查，不能只保留准备时的判定。检测依据来自恢复/代的未提交操作信息及既有 WAL 清理状态，不能仅看 latest_delete。维护不抢先执行前台 recommit、不绕过既有失败重试节流；有待提交状态时延后。正常 flush 和 WAL 清理解除风险后由后续触发继续，不后台强制 flush。

打开时 recovery 得到的 PinnedFiles 移交 persistent runtime；新集合为空集。本实现没有 snapshot RPC，LOCK 排除另一引擎同时新增 snapshot，所以维护无需每轮重读元数据。损坏元数据仍在打开阶段拒绝；运行期间直接改 snapshot 文件不在本保证内。将来引入 snapshot RPC 时必须另行修改这一边界。

## 一轮事务

### 1. 取得基线与准备

在上述边界取得 manifest、选中块、删除快照与 pins。只在选中物理输入中去重；普通唯一序号与参照一致，历史重复序号按 0007 的既定规则。按 seq 排序并切分输出，生成完整的 old-source/row → output-source/row 映射；去重或已提交删除淘汰的行没有目标。

全部能够提前判定的失败须在写临时文件前检查：

- 形态：输入引用/来源完整，文件与祖先目录类型正确，schema/列长度/主键/序号有效，映射没有越界，snapshot 钉住集合已经校验。
- 能力：既有 data 目录的写入、目录枚举，以及文件/目录同步操作可执行。权限预检不能替代实际操作时的错误处理。
- 编码：JSON/动态值符合当前共享编码要求；继承的 Infinity/NaN 再编码限制仍按 0002 处理。

最终文件名是否仍可用、当前引用是否变化、当前 WAL 清理状态，只能在提交锁内重检，不能用准备时的检查代替。

### 2. data 目录内临时输出

准备期间不能把文件直接写成最终 `data_<min>_<max>.parquet`：现有 flush 会删除并复用未引用的同名孤儿，这会破坏并行准备的输出。

本轮输出直接写在已校验的 `data/` 目录，以 create_new 创建任务独有的 `.compaction-<id>.tmp` 名称；名称不符合最终 data 文件格式，不得与 manifest/pins 引用相交。现有 flush 只删除自己要用的最终名称对应的孤儿，不会碰这些临时文件。提交时同目录改名，无需新暂存目录或另一套恢复清理。

每个临时输出完成 Parquet 收尾后，立即在准备阶段 fsync 文件，复用现有 parquet_file::write_new 的同步保证。成功同步后不再修改文件内容；同目录改名不改变其 inode，提交阶段无需重新 fsync 输出文件。编码、写入或同步失败均在 replace 前结束本轮，旧 manifest/读取映射不变。

这个阶段不持 flush_lock、状态锁或队列锁，仍持保护目录生命周期的写入闸门共享许可。取消检查覆盖每个输出写入/同步前后；进行中的 fsync 不能被标志强制中断。

首次提交若尚未同步继承文件，也在准备阶段按基线 manifest 完成引用文件/schema 及祖先目录同步，不把大文件同步留在提交锁内。准备期间其他 flush 只追加已由其提交链同步的文件，既有输入不可变且不被移除；提交时核对当前引用由这两部分覆盖。不能把尚未覆盖或未确认持久化的引用当成已同步，也不能为缩短持锁跳过原同步链。

运行期仅清理自身临时文件与本轮明确淘汰的文件，不能用全目录孤儿扫描删掉正在准备的输出。Rust 与 3.x 的打开清理都删除 data 目录下未引用的陌生文件，沿用既有验证后清理的时机和类型规则；复用这些用例覆盖临时文件残留，不增加新的共享格式或清理入口。

### 3. 提交前重检与候选 manifest

重新取得 flush_lock，确认前台已完成必要的 recommit，并完成已提交 WAL 清理，然后重新检查：

1. 句柄仍是该实例，未 deleted/poisoned，目录未被移走，未请求取消。
2. 所选输入仍被当前 manifest 引用，来源/物理内容未变。
3. 没有已提交 WAL 残留，也没有上述历史旧序号未提交操作。
4. 当前主键引用和有效位允许完整发布映射；不可遗漏当前活行。

失败即不提交，不用旧计划修改当前 manifest。并发 flush 新追加的文件和索引定义原样保留；候选从**当前 manifest − 所选输入 + 本轮输出**产生，输出仍追加在已提交来源末尾。

在 flush_lock 内按每个输出块的内容范围选择最终名称；已存在文件、manifest/snapshot 引用、同 stem 索引均不能被覆盖或复用。冲突只递增 max，有界重试且检查 u64 溢出。最终名称的选择和临时文件改名都在同一 flush_lock 内完成；flush/CreateIndex 无法在其间占用该名称，其他引擎由 LOCK 排除，因此不增加 create_new 空文件占位。改名前显式检查目标不存在，真实 metadata 错误不能当作不存在；不得有意覆盖已有文件。运行期间绕过 LOCK 直接改目录的外部进程不在这一保证内。零行输出不创建 Parquet 或 manifest 引用。

从候选的完整 data 列表计算 T，并同时去掉符合下节条件的整份 delta 引用。current_seq、active_wal_number、索引定义等非本轮内容沿用当前值，不因合并降低序号下界。候选的 current_seq 记作 C_commit，可能已因并发 flush 大于 C_prepare；GC 使用前者，输出删除过滤仍使用准备时的快照。

### 4. 一次提交与发布

提交沿用准备阶段已成功同步的输出文件；在 flush_lock 内完成最终改名并同步 data 目录，再按 0007 原子 replace manifest，随后同步父目录。manifest 的临时文件自身 fsync 仍由既有提交原语完成，不能省掉。data 替换与 delta GC 只有这一个提交点；本轮不在该锁内重复同步输出 Parquet 或继承的大文件。

提交期间持 flush_lock，状态锁分成两段：

1. replace 前短暂取得状态读锁，校验完整的结构映射、选中来源与当前状态，取得候选 manifest 和提交边界信息；随后释放读锁。输出编码/文件 fsync 位于准备阶段，manifest replace 与目录 fsync 位于提交阶段，这些 I/O 均不持状态锁。
2. replace 后取得状态写锁，按当前有效位、latest_data/latest_delete 和 ID 分配状态形成实际发布结果。先完整校验再一次更新 manifest、读取块、visibility 和 pk_index；不能逐个调用单源换源接口形成半应用。

这能释放状态锁的依据是：flush_lock 排除其他 manifest 提交/已提交来源替换，写入共享许可排除 drop；普通写入只会清除选中旧行的有效位或把主键引用移向更晚来源，不会修改已提交列、源内行号或“旧物理行 → 输出物理行”的结构映射。故预检时未遗漏活行，之后也不会凭普通写入新增一个无法映射的旧活行。

预检仅固定不可变结构，不缓存最终 live 位图、主键更新列表或会与并发冻结争用的 next_source/next_chunk 值。发布重新读取当前状态，保留并发覆盖/删除、冻结、新来源与 load 状态；不能恢复旧 live 位。若并发状态操作发生 panic 并 poison，提交后必须沿用 poison 分类、停止清理，不能强行把实例恢复成健康。没有失败不代表状态锁时间必定小于一毫秒，发布工作量仍须如实测量，当前 Int64/VARCHAR 的发布锁与并发 Query 数据见[实施验收](../testing/compaction-correctness.md)。

latest_data 的处置按其**当前位置**决定：

- 当前引用属于选中旧行且该行有输出目标：重映射 source/row，保留 seq。
- 当前引用属于选中旧行且被物理删除：移除该项。被 tombstone 删除的行由更大的 latest_delete 保护；被去重的行须由保留的最大序号行承接，不得遗漏当前主键赢家。
- 当前引用已指向更晚的活跃/冻结或未选中来源：保持原样，不因旧输入被淘汰而删除它。

显式不变量：若某个 pk 仍有剩余物理行而 latest_data 缺失，则它必须没有存活行，且 latest_delete 严格大于该 pk 的全部剩余物理行序号。没有剩余物理行时可以缺失而不保留 tombstone；有存活行时必须有正确的 latest_data 和 pk_index。

删除选中赢家时，更大的删除已超过原全局最大数据 seq，因此也超过未选中的旧行；若已有更晚来源成为赢家，则保持其引用而不删除。GC 只有在 T 已排除所有更旧物理行、旧 WAL 风险解除后才能移除保护删除。运行期可以没有该项，恢复可能重建一个仍被 tombstone 隐藏的旧位置；两种内部状态必须对 upsert/delete/get 给出相同结果。

不是为 latest_data 新增“无行”位置或另一份序号表。允许删除证据 GC 的前提见下节；未清理的旧 WAL 不能在这里失去恢复判定证据。提交后的内部异常沿用 state_change 的放锁前 poison 协议。

### 5. 清理

只有 manifest 持久化已确认且发布成功后，才删除不再引用、未被 pins 钉住的旧 data/delta 及对应 3.x idx/sidx。内存旧快照不读取文件，不额外钉住旧磁盘文件。

先确认完整清理集合与类型，未知/错误类型不做部分破坏性清理。unlink/目录同步失败留作孤儿并记录可重试诊断，不撤销已提交状态，不改报 BeforeReplace。取消发生在清理期则停止后续清理，留下的孤儿由之后维护/恢复处理。若 replace 后目录同步尚未确认，保留全部旧文件和删除证据，先沿用 recommit 协议解除风险。

## Tombstone GC

T 为候选 manifest **全部仍引用的 data 文件**的最小文件名 seq_min，不只看本轮输入或输出。整份 delta 只有在文件名 seq_max 严格小于 T、且未被磁盘 snapshot 钉住时才能从候选移除；部分过期文件不重写。

没有 data 时使用显式“无有限下界”状态，不能用平台 sys.maxsize 代表 u64 全域。此时可移除未钉住的已提交 delta 文件；活跃/冻结删除不能跟着清空。

内存 GC 是发布后的内存优化，不再形成磁盘事务；committed_deletes 按同一 T 回收（无 data 时可清空），全局 visibility 的规则为：有限 T 时删除 latest_delete < T 的项；没有 data 时，仅移除不大于 C_commit 的项。大于 C_commit 的活跃/冻结删除仍保留。并发更晚的删除自然不满足这些条件，不需要“被活跃删除替换”的另一套特殊分支。

遗留旧序号 WAL 或已提交 WAL 残留时整轮已被延后；目录同步未确认时内存 GC 也延后。保留额外内存 tombstone 只增加占用，不能被当作维护失败后的数据丢失。snapshot 钉住的 delta 文件仍保留在 active manifest，与参照一致。

## 来源顺序与旧快照

移除选中旧来源，在 committed 尾部按输出顺序追加新来源，随后才是冻结/活跃来源。当前从 ChunkId 递增推出 manifest 顺序的前提将不再成立。

读取视图拟按持久化来源顺序排列块并生成 source_rank，稳定块 ID 和主键定位仍不移动。Visibility 的 source_order、ReadSnapshot 的块序、恢复后的 manifest 来源顺序必须一致，不能各自推导一份顺序。Get 的命中块下标重映射保持原协议。

新 Query 分页、Search 并列和动态过滤的来源分组按新顺序；旧快照仍使用旧列、旧有效位与旧来源顺序。合并改变物理来源边界可能改变动态类型推断，必须对照 0009 验证，不能仅核对总行数或主键集合。

## 失败与重试

每个任务由 catch_unwind 包住，单任务 panic 不使维护线程退出。任务完成状态与等待通知在成功、失败、取消和 panic 时都要推进。

| 边界 | 行为 |
| --- | --- |
| 选择/准备/临时输出及其 fsync/提交重检失败或 panic，replace 尚未发生 | 旧 manifest 与读取状态不变；诊断为提交点前失败；只清理自身孤儿，不自动增加重试任务 |
| replace 已发生、目录同步失败或 panic | 按实际提交点处理，发布新候选或 poison；保留旧文件/证据，未确认前禁止进一步替换和 GC；重启按盘上恢复 |
| 发布校验/状态应用 panic | 放状态写锁前 poison，该实例拒绝继续使用；不能跳过异常后让任务线程继续操作坏句柄 |
| unlink/目录同步失败或 panic | 已持久化发布的结果保持；停止本轮清理、记录孤儿，下一次维护/恢复处理 |
| 工作线程启动失败 | 构造失败并释放资源，不返回缺失维护能力的 Db |

最外层 catch 不能把 replace 后的 panic 统一降为 BeforeReplace。后台失败不篡改已经返回的前台写入结果；真实错误必须有日志/任务结果，不能静默成功。没有 data→GC 两事务之间的失败状态。

## 与 3.x 的差异

以下差异已随本轮实现同步到 0003/0006/0007；正常关闭排空也已同步 0003「进程退出」、退出验证口径与 Server::stop 注释。停止可能等待若干轮维护，grace 只用于 RPC 宽限，不是整个停服时限。实跑证据与未验证边界见[实施验收](../testing/compaction-correctness.md)。

| 场景 | 3.x / 本方案 | 理由与影响、验收用例 |
| --- | --- | --- |
| 多 collection 维护 | 参照每 collection 一个 executor；本方案每 Db 一线程 | 限制并行 I/O/缓冲区；跨 collection 吞吐和完成时序不同，需任务公平性与关闭测试，不宣称性能更好 |
| 文件大小桶 | 同一批物理文件使用相同阈值和选择顺序；分别写出的同内容文件字节数可能不同 | arrow-rs/pyarrow 输出不同可使桶、布局、分页/并列顺序与动态来源分组不同；同文件选择器精确比较，双方独立写入的差分避开桶边界，另测边界差异，不声称全布局一致 |
| 选择器损坏输入 | 参照跳过缺失/坏元数据；本方案整轮 fail-closed | 不在坏引用上继续提交；缺失、异物占据及真实 I/O 注入固定错误和零提交 |
| 历史旧序号 WAL 或已提交 WAL 残留 | 本方案延后整个替换/GC，直到正常 flush 与清理解除风险 | 避免旧 seq 被误当成 committed，并防旧 WAL 在删除证据消失后复活；历史故障目录矩阵必须证明 |
| 故障目录的跨输入/未选中来源同主键同 seq | 实施采用整轮拒绝并记录诊断，不移动这类歧义来源；参照仍可能合并并改变平局赢家 | 来源移到末尾后，运行期保留的赢家可能与恢复重建不同。首个切片先保留一致的旧状态；准备阶段只扫描主键/seq 找到反例，不复制未选中的向量；用反例证明零提交与重开结果一致。此实施边界需在本轮评审中单独核对 |
| 准备期并发 flush | 参照整轮持 maintenance_lock；本方案准备不持 flush_lock，提交按最新 manifest 重算 | 新追加来源仍保留，追加输出的相对顺序可能因交错而异；受控并发固定合法顺序及旧视图，不宣称此交错逐序对齐参照 |
| data/delta 提交 | 参照 data 与 GC 分次保存；本方案一次原子保存 | 只可见旧组合或新组合；缩小事务状态数，提交点前后崩溃和两引擎重开验证一致性 |
| create/drop 与维护 | 本方案协作取消提交前任务；参照不使用该取消协议 | 避免准备长时间挡住目录变更；成功/失败的目录变更请求都可能少做维护、改变后续布局与结果顺序，测试多请求计数、取消及再次打开 |
| 异常析构/关闭失败 | close_nowait/析构及已确认的异常收尾保留不再提交 manifest 的边界；正常 close 则排空 | 异常路径可能改变重开后的布局、分页/并列顺序；沿用 0003/0007 的 WAL 保留保证，分别覆盖正常脚本退出和异常收尾，不能混称轮数对齐 |
| snapshot 钉住元数据 | 参照维护重读；本方案使用打开时 PinnedFiles | 无 snapshot RPC、LOCK 排他；运行期外部直接改元数据不受支持，验证打开拒绝与已钉文件保留 |

一次触发一轮、输出内容的 seq 范围和最终 manifest 追加规则已按参照修正，不另保留触发自循环的差异。

## 放弃的方案

- **合并触发并自动跑到稳定**：改变参照的轮数、文件布局和结果顺序；改为计数，不自行追加任务。
- **整轮持 flush_lock/在提交锁内同步输出 Parquet**：让同步 flush 等待最多 200000 行的准备 I/O；采用 data 目录内临时名，在准备阶段写出并 fsync，提交只保留改名、目录同步及原子 manifest 提交所需的串行。
- **准备直接写最终名/增加全局文件预约表**：前者会被 flush 当孤儿删掉，后者增加常驻协调状态；用 data 目录中的非最终格式临时名，最终命名集中在现有 flush_lock 边界。
- **状态写锁跨越 replace/fsync**：不可变结构映射受 flush_lock 和共享许可保护，发布时重读当前可变状态即可，不让文件同步阻塞快照获取。
- **新暂存目录/最终空文件占位**：前者重复现有 data 孤儿清理，后者在 flush_lock 与 LOCK 的正常边界内没有独立收益；复用同目录临时名和提交锁。
- **正常关闭撤销触发**：会少掉常见脚本退出的最后一次维护，改变重开布局与结果顺序；拟排空正常任务，接受等待。异常无提交收尾仍遵循既有生命周期合同。
- **两次 manifest 提交**：data 和 delta 一次切换已经自洽，不为参照的代码顺序保留第二个事务。
- **每轮重读全部 delta**：不采用；最初拒绝第二份常驻表的选择已被实际 20% 残留推翻，负责人按 0011 确认本轮采用独立 committed-delete 表。
- **每轮重读 pins 或 Parquet 输入**：当前没有运行期修改 pins 的受支持入口，列已在内存且不可变；复用已校验数据。
- **首次调度时惰性启动线程**：技术上可行，也能把 spawn 失败降为单次维护失败。现有 Db 是值对象，弱引用仍需要统一共享所有权或抽出独立的 worker 所有者，不能只延迟 spawn 就绕过生命周期设计。选择构造时统一 Arc 与启动错误边界；代价是内部签名/core 调用方调整，不把惰性方案说成不可实现。

## 验证与验收

### 确定的等待

本实现提供仅 fault-injection/test 构建可用的按句柄维护等待钩子：在报告锁内捕获该实例已接受的触发边界，等待这些任务成功、失败或取消后返回结果，后来接受的任务不属于此等待。计数和完成通知必须区分正在执行与等待中的任务，不能用“队列暂时空”表示排空。所有测试等待有超时。

验收明确区分两类 wheel 与 Rust 测试二进制：

- **正式 release wheel**：不启用 fault-injection，不含等待/暂停/故障入口。两条 SDK 的常规端到端、差分和互通仍在该 wheel 上运行；需要关闭后稳定目录的用例通过既有正常停服入口等待 drain，再离线检查 manifest/文件与重开结果。MilvusClient.close 本身不停 Lite 服务，不能用它代替真正停服。
- **隔离的测试 wheel**：另以 release 编译模式启用 fault-injection，并由 py → grpc → core 显式转发 feature，供需要运行期精确等待/暂停的附加并发、差分与互通用例使用。该 feature 转发已实现，构建与测试命令见[实施验收](../testing/compaction-correctness.md#产物身份)。两个 SDK 分别装入仓库外独立 venv，记录 wheel/native 哈希和 feature；结果单列，不能冒充正式 wheel 的验证或性能证据。
- **Rust 测试二进制**：单测直接使用测试钩子；跨进程 runner 只能调用其所拥有实例的钩子，不假定正式 Python wheel 有这个方法。

参照在服务所属进程调用 `_wait_for_bg(timeout)`，随后检查日志/manifest/结果，不能把 noop 完成当成前序任务成功。测试 wheel 的 runner 同样在实例所属进程完成等待并传回结果。不新增公开 drain RPC、不把私有等待入口编入发布 wheel，也不只靠轮询文件数猜完成。正式产物的扫描必须确认这些接缝缺席。

### 矩阵

| 边界/组合 | 必须固定的结果 |
| --- | --- |
| create/首次懒打开/重复取句柄、一次/多次触发、执行中再触发、无候选、失败、取消 | create 和实际首次懒打开各一次，重复取句柄不计数；精确消费触发计数，无合并丢轮、无自循环；create 请求不被自身取消计数误耗，不同实例公平运行，等待边界不误包含后续任务 |
| 同一物理文件的桶边界、4/32 文件门槛、199999/200000 行、100000 行切分 | 选择顺序与参照一致；分别编码的字节差异另测，不混作选择器回归 |
| Int64/VARCHAR、重复 pk/seq、空输出、未选中较新行 | 去重、seq 文件名、latest_data 移除/重映射和 pk_index/位图一致；普通唯一 seq 做真实差分 |
| 旧已提交删除 + 更新活跃删除、T-1/T/T+1、空 data、u64 边界、遗留 WAL | 不误用活跃删除、不误 GC、不复活旧行；无 data 仍保留活跃删除，current_seq/auto_id 不回退 |
| prepare 与 flush/CreateIndex 并行、最终同名冲突、临时文件/改名中断 | flush 不删除非最终格式输出；当前 manifest 追加/索引定义不丢失，最终路径不覆盖；复用两侧恢复清理临时文件 |
| 临时输出文件 fsync 暂停/失败、继承文件首次同步、提交改名 | 准备同步不占 flush_lock 或状态锁，前台 flush/快照可推进；trace 固定文件 SyncFile 先于改名、data 目录同步与 manifest replace，提交不重复同步输出内容；失败不替换 manifest |
| 选择、编码、write/sync、replace 前失败/panic；replace 后 sync/发布 panic | 按实际提交点分类，提交前旧状态不变，提交后发布或 poison；未确认前不删旧输入/证据 |
| data 与 delta 同一次 replace 前后退出；旧文件 unlink/目录同步失败 | 不出现半套引用，重开不复活被删行，孤儿能安全重试清理 |
| insert/upsert/delete、freeze/flush、release、drop/同名重建 | 旧视图原样，新映射保留并发更新；不向旧目录写文件、不追踪移走路径、无半应用 |
| 多个 create/drop 等待、正常 close、异常 close_nowait、I/O 检查点 | 等待计数不提前清零；create/drop 可取消，正常关闭最终有效代触发一次并排空，异常无提交收尾单独固定；全部文件操作结束前不释放 LOCK |
| 原读快照、snapshot data/delta/index 钉住、坏 snapshot/data 路径 | 旧视图可继续；被钉文件不删；打开验证失败前不清理，未知路径不部分删除 |
| 启动失败、idle 析构、worker 最后释放 Arc、任务 panic、fork | 无环、无永久等待、自 join 或锁内 join；任务 panic 后线程仍能处理健康 collection，poison 句柄仍被拒绝 |
| replace/fsync 暂停期间读取与写入 | 快照仍可获取，当前旧映射保持；插入/覆盖/删除/冻结不使结构映射失效，发布不恢复已清位、不覆盖新主键引用；并发 poison 时不继续健康发布 |
| latest_data 缺失与恢复重建隐藏旧位置 | 固定未选中 seq 3、选中 seq 5、delete 7 的模型；运行期合并后和从同一盘态恢复后，对相同 upsert/delete/get 序列返回一致，逐步核对主键、有效位与删除证据 |
| 正常脚本写入→退出→重开、仅删除/全失效输出/空 WAL/重试 | 两侧触发次数逐项对应，最后有效 flush 的任务不能丢；已排队任务不取消，重复 close 不重复计数；异常路径按差异登记核对 |
| 来源变化、分页/并列、异构动态类型、关闭重开、3.x↔Rust 交替合并 | manifest 来源序与读取序一致，顺序/类型边界按登记范围对照；共享格式、索引共存及 snapshot 保留不变 |
| ManualCompaction/GetCompactionState，两 SDK | 值与参照一致；测试等待走私有钩子，不能假定 Completed 已 drain |

实施必须有分支单测、受控并发、提交点前后子进程退出、fsync/replace/unlink 顺序证据，并对误删证据、覆盖并发输出、半应用与错误来源序做反证。套件不得 skip 或靠放宽断言/无限重试通过。

两条 SDK 的正式 wheel 端到端/差分/互通、另列的测试 wheel 受控组合、默认与故障注入 Rust 全套、Clippy 为门槛。Windows、真实断电与性能按首发/专项合同分别验收；本设计不宣称停顿或吞吐改善已经得到测量证明。

## 确认点与实施顺序

负责人已确认本设计的并发选择与差异，重点为：

1. 每 Db 一个 worker，内部构造统一为 Result<Arc<Db>>，构造时处理线程启动失败。
2. 准备阶段不持 flush_lock/状态锁，输出在 data 目录内用临时名写完并 fsync；目录生命周期仍由共享许可保护。
3. 仅 create/drop 协作取消；正常 close 接收最后一次有效 flush 的触发并排空，异常收尾沿用不再提交 manifest 的边界。
4. data 替换与 delta GC 一次 manifest 提交，replace/fsync 不持状态锁；发布按最新状态完成完整映射。
5. 最初确认复用最大删除表，随后因实测残留明显按 0011 改为本轮独立保留已提交删除；历史旧 WAL 仍延后，其他已登记布局/顺序/并发差异保持。
6. 正式 wheel 与隔离的 fault-injection 测试 wheel 分开验收，发布产物不包含等待/故障接缝。

### 确认附加条件

- **第 3 项，退出等待实测**：以百万行、dim 128 的大数据场景测量单轮最多 200000 物理行合并的耗时，记录重复测量中的最大值和正常关闭排空的等待。该最大值是观测值，不是任意机器/故障 I/O 的绝对上界。若单轮超过 10 秒，必须重新评估方案，不能按原门槛直接放行。README 已知限制写明退出可能等待后台合并；进程强杀的恢复仍遵守 WAL/提交协议，不把 SIGKILL 的进程恢复证据推广为真实断电保证。Ctrl-C 能否中断退出等待需实际验证，不能靠释放 GIL 推断。
- **第 5 项，保守回收对照**：重复删除、重新插入、再删除，在相同逻辑负载和确定触发边界下对照 3.x，测量失效物理行比例、文件数及字节量，记录回收差距。若差距明显，另起决策评估独立 committed-delete 表，不默认永久接受；原始比例/差值须完整披露，不能只报告逻辑行数相等。
- 实现落地时同步 0003 与 Server::stop 的退出等待口径，不提前将未实现能力写成现状。正式产物与测试产物的证据仍分开记录。

按“事务与来源映射 → GC/文件共存 → 后台生命周期与 RPC”的内部顺序实现，每一步守住完整不变量。首发能力只在全部矩阵及上述附加条件收口后宣布完成；设计确认与落库授权分开；负责人在本轮复审收口后另行授权提交与推送，发布仍需独立授权。
