## 范围

`milvus-lite dump` 子命令，也可写成 `python -m milvus_lite dump`。它把一个集合的全部可见行导出为 Milvus BulkWriter 的 JSON 文件，供 Milvus Bulk Insert 或 Zilliz Cloud 导入。

[0008](0008-first-release-scope.md) 把 dump 列为“后续补齐”。[0012](0012-cli-server.md) 只做了 `server`，`dump` 目前返回 argparse 的 `invalid choice`（退出码 2）。

不包含：

- **导出 schema、索引、分区或别名**：3.x 只导出行，目标集合由用户在 Milvus 侧另建。
- **导入、格式迁移，以及读取旧版 milvus-lite v1 的 `.db` 文件**：3.x 的 README 写明 dump 是导出工具，不是存储格式迁移。
- **BulkWriter 的 Parquet、CSV 等其他格式**：3.x 固定为 JSON。

## 3.x 的行为

dump 是一个纯客户端工具，代码见 [cmdline.py](../../references/milvus-lite/milvus_lite/cmdline.py)，测试见 [test_dump_tool.py](../../references/milvus-lite/tests/test_dump_tool.py)。它只经 pymilvus 的公共接口读数据，不碰引擎与存储。代码沿用 `fb63dca`（Add dump tool），`04fb87a` 做纯 Python 重写时改为当前形态。

**参数**：

| 参数 | 含义 |
| --- | --- |
| `-d/--db-file` 与 `--uri` | 二选一，且必须给一个（argparse 互斥组，违反时退出码 2）。`-d` 先检查路径存在，再原样作为 pymilvus 的 URI；`--uri` 可以指向任意 Milvus 服务 |
| `-c/--collection` | 必填 |
| `-p/--path` | 必填，输出目录。父目录须存在；输出目录本身已存在时须是目录 |
| `--batch-size` | query iterator 的批大小，默认 1000 |
| `--chunk-size` | BulkWriter 单个文件的字节上限，默认 512 MiB |

**`-d` 的前提**：pymilvus 只把以 `.db` 结尾的本地路径当作本地库。其他路径会报 `uri: <path> is illegal, needs start with [unix, http, https, tcp] or a local file endswith [.db]`。而 `milvus-lite server --data-dir ./data` 不要求后缀，所以这样的目录只能先改名，或者起 server 后用 `--uri` 导出。

`-d` 在 dump 进程内打开数据目录，恢复与关闭时的 flush 照常发生。同一目录正被别的进程（包括运行中的 `milvus-lite server`）持有 LOCK 时，pymilvus 报 `Open local milvus failed`，这时只能用 `--uri`。

**流程**：

1. 依次校验：集合名与路径非空 → `-d` 的路径存在 → 输出路径的父目录存在，且输出路径不是文件。这几步失败都抛 `RuntimeError`，此时还没有连接服务。
2. 导入 pymilvus。缺少时报 `milvus-lite dump requires pymilvus to already be installed.`。随后用 ORM 接口以别名 `milvus_lite_dump` 连接；`-d` 走 pymilvus 的 `.db` 接入点，在本进程内起服务。
3. 集合不存在时报 `Collection: <name> not exists`。随后调用 `collection.load()`，所以 dump 会把已 release 的集合重新 load。本地库的 load 状态不落盘（评审实测前后都是 `NotLoad`）；`--uri` 指向的服务上，这一 load 会保留下来。
4. 用 `count(*)` 取总行数，只用于进度条。装了 tqdm 时进度条显示在 stderr，没装就不显示。
5. 导入 `pymilvus.bulk_writer`，缺少时报 `... requires pymilvus bulk writer dependencies to already be installed.`。这一步在连接与 load 之后，所以缺依赖时进程内服务已经起来了。然后用集合的 schema 构造 `LocalBulkWriter(file_type=JSON)`。
6. 用 `query_iterator(batch_size, output_fields=["*"])` 逐批读取，每行做以下处理：
   - 主键为 auto_id 时删去主键，导入时由 Milvus 重新分配；
   - BFLOAT16 / BINARY 向量从字节转成浮点数组或 0/1 数组。只有 `--uri` 指向 Milvus 时会遇到，3.x 和本实现都不支持这两种类型；
   - numpy 值转成 Python 值；
   - 交给 `append_row`。BulkWriter 按 schema 校验，动态字段收进 `$meta`。
7. 调用 `writer.commit()`，打印 `Dump collection <c> success: <n> rows -> <path>`，退出码 0。
8. 结束时断开连接，忽略断开失败。

**输出**：文件为 `<path>/<uuid>/1.json`、`2.json`……，内容为 `{"rows": [...]}`。

- 输出目录已存在时不清空，在其下新建 uuid 子目录。
- 集合为空时只建目录，不写文件。
- BulkWriter 在析构时只删除空的 uuid 子目录。中途失败时，已写出的文件会留下来（评审实测：5 个文件写出后追加一行坏数据，5 个文件都保留）。

**错误呈现**：3.x 不捕获异常，失败时打印 traceback，退出码 1。

**依赖**：3.x 包本身依赖 numpy。pymilvus 与 `pymilvus[bulk_writer]`（pyarrow、minio、azure-storage-blob、ml-dtypes 等）由用户自行安装，3.x 不声明这些依赖。

## 实测

调查脚本在仓库外运行，结果本地留存，覆盖 24 个场景：

- 自增主键与动态字段，含未 flush 的行；
- 各类标量：nullable、默认值、JSON 大整数、INT64 最小值、中文与转义、ARRAY；
- upsert 与删除；
- 稀疏向量与 BM25；
- partition key 与显式分区；
- TIMESTAMPTZ 与 GEOMETRY；
- 多向量与 nullable 向量；
- 空集合与已 release 的集合；
- 2500 行用小 chunk 分成 278 个文件；
- 10 条参数与错误路径。

每个场景在独立子进程中建数据，再在另一个子进程里运行 dump。

把 3.x 的 dump 函数原样复制成独立脚本，在本实现的服务上运行，再与 3.x 自身对照：

| 环境 | 结果 |
| --- | --- |
| pymilvus 3.0.2：3.x 对本实现 | 23/24 逐字节一致（比较文件内容、退出码、末行错误与 stdout，不含 uuid 目录名） |
| pymilvus 2.6.18：3.x 对本实现 | 23/24 逐字节一致 |
| 3.x：pymilvus 3.0.2 对 2.6.18 | 24/24 一致 |

上表合并了两轮运行。第一轮里，标量场景 `scalars3` 因为调查脚本自身的写入值不合法，两侧都在建表时失败，修正后单独重跑，四个环境逐字节一致。唯一不一致的是 nullable 向量：本实现还不支持它，建表就失败，与 dump 无关。

结论：本实现的服务已经能支撑 3.x 的 dump 逻辑，本切片不需要改 Rust 代码。

评审另外验证了以下场景，都正常：

- 6000 行 × 1024 维、批大小 6000；
- 含非 ASCII 和组合字符的 VARCHAR 主键，在批大小 1、3、50 下行数一致；
- 用 `--uri` 连接本实现的 `milvus-lite server`。

### 3.x 的缺陷

本实现的服务上表现与 3.x 相同：

| 编号 | 场景 | 3.x 的表现 | 原因 |
| --- | --- | --- | --- |
| A | 带 BM25 function 的集合 | 退出码 1：`Field 'sp' is function output, no need to provide` | `output_fields=["*"]` 读回了 function 的输出字段，BulkWriter 拒绝 |
| B | 带 `ARRAY<VARCHAR>` 字段的集合 | 退出码 1：`KeyError: 'max_length'` | DescribeCollection 不回显 ARRAY 元素的 `max_length`，BulkWriter 校验 VARCHAR 元素时要读它。本实现在 [0015](0015-nullable-defaults-and-array.md) 中有意与 3.x 对齐，同样不回显 |
| C | 非空集合，`--batch-size 0` | 退出码 0，报告 `success: 0 rows` | pymilvus 的 iterator 在批大小为 0 时直接结束，数据静默丢失 |
| D | 写文件失败（磁盘满、无写权限） | 退出码 0，报告 `success`，但没有文件 | BulkWriter 在子线程里写文件，异常只打印，`commit()` 照常返回 |
| E | FLOAT / DOUBLE / `ARRAY<FLOAT/DOUBLE>` / 向量含 NaN 或 ±Inf | 退出码 0，文件里是裸的 `NaN` / `Infinity`，不是合法 JSON | `json.dump` 默认 `allow_nan`。JSON 字段与动态字段里的非有限值已被服务端写成 `null`，不受影响；本实现写入稀疏向量时拒绝非有限值，只有 `--uri` 会遇到 |

参数边界：

- `--batch-size` 为负数时，pymilvus 报 `batch size cannot be less than zero`；大于 16384 时报 `batch size cannot be larger than 16384`。两者都在 BulkWriter 建好之后才报。
- `--chunk-size` 为 0 或负数时结果正确，但每行一个文件。由于 `commit()` 会以 1 秒为间隔轮询前一个写文件线程，2500 行超过 120 秒仍未结束。

### 已知限制

以下情况本切片不处理，写进 README：

- **VARCHAR 主键含 `"` 或 `\`**：pymilvus 的 query iterator 拼接 `pk > "..."` 时不转义，翻页必然失败，报错是显式的。3.x 和真实 Milvus 上相同，属于 pymilvus 的行为。
- **`--uri` 指向有并发写入的服务**：iterator 没有服务端快照，导出的不是一致快照。
- **nullable 向量**：3.x 把 null 存为全零向量，见 [0002](0002-data-dir-compat.md)，导出后与真正的零向量无法区分。本实现自 [0038](0038-nullable-dense-vectors.md) 起把空值存为 null，dump 导出 `null`，不需要改 dump 的代码；3.x 写下的目录里空值已是零向量，仍导出零向量。
- **text embedding function 的输出字段**：按缺陷 A 的处理不导出，导入时由 Milvus 调用 provider 重新生成，目标端需要凭据。

## 决策

### 1. 实现方式

在 [cmdline.py](../../crates/py/python/milvus_lite/cmdline.py) 中按 3.x 的 dump 改写，Apache-2.0，注明来源。它是 Python 胶水：

- 只经 pymilvus 的公共接口，不调用 `_native`，不经引擎，因此符合“绑定层只做胶水”的边界。`--uri` 指向任意 Milvus 时行为相同。
- **改用 `MilvusClient`**：用 `describe_collection` 加 `CollectionSchema.construct_from_dict` 取得 schema，再依次调用 `load_collection`、`query(count(*))` 与 `query_iterator`。原因是 ORM 接口每次运行都打印 `PyMilvusDeprecationWarning`，并将在 pymilvus 3.1 移除。评审验证过，这条路径在 3.0.2 与 2.6.18 上都没有警告，`is_function_output` 与 `params` 也正确。
- **不新增包依赖**：numpy、pymilvus、bulk_writer 只在 dump 分支内延迟导入，`milvus-lite server` 与 `--help` 的导入面不变。0012 §1 原写“仅使用 Python 标准库”，补一句 dump 分支的例外。pymilvus 与 bulk_writer 的导入检查提前到连接之前，缺依赖时不先起服务。
- **与 3.x 相同的部分**：参数、默认值、帮助文案（`--batch-size` 另注明取值范围）、成功输出、输出目录结构。保留 BFLOAT16 / BINARY 的转换，供 `--uri` 使用。
- **`--uri` 的检查**：值以 `.db` 结尾时（与 pymilvus 的判定相同：它先看 `.db` 后缀再看协议），按 `-d` 做同样的存在性检查。否则会在该路径新建数据目录（评审实测会留下 `LOCK`）。
- **进程内服务的收尾**：`-d`（或指向本地 `.db` 的 `--uri`）在本进程内起服务。关闭客户端之后、报告结果之前，经 `server_manager_instance.release_server` 主动停掉它：LOCK 在报告前释放，停服日志也排在结论行之前，结论行因此是 stderr 的最后一行。停服失败按 0003 只记录日志。
- **`main` 的校验**：现有 `main` 对所有子命令统一校验 `port` / `max-workers`，dump 没有这两个参数，会抛 AttributeError。改为只在 server 分支校验；失败文案按子命令区分。

### 2. 错误呈现

沿用 0012 已登记的 server 口径：

- 失败时向 stderr 打印一行 `MilvusLite dump failed: <原因>`，退出码 1。
- `RuntimeError` 只打印信息；pymilvus 的 `MilvusException` 取 `.message`，因为它的 `str()` 已自带类名与 code，再加会重复；其他异常带上类型名，例如 `KeyError: 'x'`。
- argparse 错误仍为退出码 2。
- SIGINT 与 SIGTERM：先按「失败残留」清理，再打印一行中断说明，以退出码 130 / 143 正常退出。这是新口径：0012 的 server 收到这两个信号是正常停止、退出 0，而 dump 被中断时导出并未完成。3.x 没有 handler，被信号杀死（子进程返回码 -2 / -15，shell 中显示 130 / 143）；差分用例按各自的形态断言。
  - 两个信号都在主线程用 `signal.signal` 显式接管，不依赖默认的 `KeyboardInterrupt`：继承 `SIG_IGN` 时 Python 不装后者，SIGINT 不生效（0012 差异表已记录，rc1 实际出过问题）。非主线程调用 `main` 的 dump 分支与 0012 的 server 一样拒绝，在连接之前返回 1。
  - handler 抛出一个专用的 `BaseException` 子类，而不是像 0012 §5 那样只置标志：只置标志打不断阻塞中的 RPC。评审实测，抛出的异常能在约 1.8 秒内打断阻塞的 gRPC 调用（3.0.2 与 2.6.18）；`-d` 模式下迭代中收到 SIGTERM，清理后退出，atexit 中进程内服务的收尾无冲突，重开数据目录行数完整、LOCK 已释放。这一 handler 差异登记到 0012 的差异表。
  - 第一次信号进入清理时，立即把 SIGINT / SIGTERM 恢复为 `SIG_DFL`，与 0012 进入收尾前的做法相同：第二次信号直接终止进程，不在清理中途再抛异常（评审实测否则会打印 traceback、退出 1 并残留目录）。恢复后的默认处置也覆盖随后 atexit 中的服务收尾。容器 PID 1 上 SIG_DFL 不终止进程（0012 §5），第二次信号在那里不起作用，dump 照常完成清理后退出。
  - 清理不覆盖的情形写进 README：SIGKILL、断电、SIGHUP（关闭终端）与第二次信号，这些情况下可能残留 uuid 子目录。
- 失败行与中断说明都在写文件线程结束之后输出，保证它们是 stderr 的最后一行：pymilvus 的 bulk_writer 日志会在 INFO 级别写 stderr，包括写文件失败的日志。

pymilvus 自身的 RPC 错误日志也写到 stderr，所以测试只断言最后一行。与 3.x 的差异（3.x 打印 traceback、信号不清理）登记在本文与 0012 的差异表。

### 3. 缺陷与边界的处理

dump 的用途是迁出数据，“失败”“静默少导”或“导出无法导入的文件”都直接违背这个用途，所以缺陷都修正并登记差异。修正只在客户端工具内，不改服务端行为：

- **A**：判据用 `field.is_function_output`，与 BulkWriter 拒绝时用的判据相同，两条 SDK 线都有这个属性，`--uri` 时取自 DescribeCollection。构造行时用 `pop(name, None)` 去掉这些字段，与 auto_id 主键的处理相同。导入时由 Milvus 按输入重新生成。
- **B**：复制一份 schema 专供 BulkWriter 校验，给缺少 `max_length` 的 `ARRAY<VARCHAR>` 补上 Milvus 的上限 65535。已有 `max_length` 时不动，所以对真实 Milvus 不起作用。DescribeCollection 不变，仍按 0015 与 3.x 对齐。BulkWriter 只有 `_verify_varchar` 读这个值；本实现与 3.x 都不校验元素长度，超过 65535 的元素由 BulkWriter 报错。
- **C**：`--batch-size` 限定为 1–16384，`--chunk-size` 下限为 1，越界由 argparse 拒绝，退出码 2。`commit()` 在前一个写文件线程未结束时以 1 秒为间隔轮询，评审实测每多一个文件最多多等约 1 秒，从 64 KiB 到 4 MiB 都如此。因此不设固定阈值，README 注明“chunk 越小文件越多，每多一个文件最多多等约 1 秒”。
- **D**：子类化 `LocalBulkWriter`，覆写 `_flush`，在 try/except 中记下写文件线程的异常（不重抛，避免线程打印）。每批 append 之后只读一次记录、不等待写线程（已失败时尽早停止）；`commit()` 之后先等全部写线程结束再检查一次，有记录就按失败处理。
  - 不用全局 `threading.excepthook`：它会收到进程内任何线程的异常，评审实测会把无关线程的异常误判为导出失败。
  - 不靠核对 `batch_files`：写入中途失败时，可能留下截断的文件而 `batch_files` 为空；某一块失败时，其余文件都在但那一块已丢。
  - 线程竞态：pymilvus 的 `_flush` 在 `finally` 里先从 `_working_thread` 删除自己，之后异常才传到子类的 `except`。只 join `_working_thread` 中的线程，会在两者之间漏判（评审在该处注入延迟复现：commit 之后无记录，稍后才出现）。因此子类 `_flush` 第一行为当前线程登记一个 Event，结束时（finally，在记下异常之后）置位；commit 之后与清理时，先等 `_working_thread` 中的每个线程都已登记（线程 `start()` 之后、执行到 `_flush` 第一行之前只出现在那里），再等全部 Event，然后才读错误记录。不用 `Thread.join`：CPython 中被信号异常打断的 join 会把仍在运行的线程标记为已停止，之后再 join 立即返回（实施时实测，3.12）；Event 与 Condition 的等待被打断后可以安全地重来。不调用 `LocalBulkWriter._exit`：它直接迭代 `_working_thread`，线程同时删除条目时可能报 `dictionary changed size`。
  - 子类依赖 `pymilvus.bulk_writer`，在 dump 分支内导入之后才定义，不破坏延迟导入。
  - 评审实测（3.0.2 与 2.6.18）：正常写出不受影响；`Buffer.persist` 抛错时第一次 append 之后即检出；`RLIMIT_FSIZE` 截断时检出 Errno 27，此时磁盘上有截断的文件而 `batch_files` 为空。
  - `_flush`、`_working_thread` 是 pymilvus 的私有名，写进 pymilvus 升级核对。
- **E**：在已有的 `_to_plain` 递归里统一检查每个 `float`，一次覆盖标量、数组、向量、稀疏向量、JSON 与动态字段，不逐字段枚举。3.x 的 `_to_plain` 对 `np.ndarray` / `np.generic` 直接返回 `.tolist()` / `.item()`，不再递归；本实现改为对转换结果继续递归，否则 numpy 来源的值会漏查。评审实测 `-d` 时各类值都已是 Python float，numpy 分支只在 `--uri` 时用到。
  - BFLOAT16 在字节转成列表之后检查。FLOAT16 若以字节或 ndarray 到达，先解码再检查。
  - 3.x 在 `--uri` 下能否导出 FLOAT16 本身存疑：BulkWriter 的 float16 校验不接受字节，且 3.0.2 与 2.6.x 处理列表的方式不同，没有真实 Milvus 可验，留作已知限制。
  - 遇到 NaN 或 ±Inf 时报错，信息带上字段名与主键（auto_id 时带行序号），不写出非法 JSON。
  - 评审实测代价：20000 × 768 维检查约 0.11 秒，相对 JSON 序列化（约 7.3 秒）可忽略。
- **失败残留**：dump 失败时，删除本次由 BulkWriter 创建的 uuid 子目录，输出目录本身及其中原有的内容不动。
  - 触发路径：append 校验失败、E、迭代器或 RPC 报错、D，以及 SIGINT / SIGTERM（见「错误呈现」）。
  - 顺序：先等 BulkWriter 的写文件线程全部结束，否则线程在删除后仍会写文件并打印错误；等待方式同 D。等待途中收到信号（handler 已恢复 SIG_DFL，不会再有第二个）时记下它并继续等待，清理完成后按中断报告（退出 130 / 143），原错误作为原因保留；再确认 `writer.data_path` 的父目录与输出目录是同一目录（用 `os.path.samefile`，输出路径可能是相对路径、带尾斜杠或经过软链）、目录名等于 `writer.uuid`；然后删除。
  - 输出目录若是本次新建的，失败后保留这个空目录，与 BulkWriter 的行为一致。
  - 删除也失败时，在错误信息中写出残留路径。

未采用的做法：照搬 3.x，只在 README 中说明。

## 放弃的方案

- **用 Rust 直接读数据目录导出**：要重复实现读路径，绕开服务与 LOCK 语义，也不能支持 `--uri`。
- **自己写 JSON 而不用 BulkWriter**：BulkWriter 是导入格式的权威，自写容易与 Milvus 的导入端产生偏差。
- **让 DescribeCollection 回显 ARRAY 元素的 `max_length` 来解决 B**：会改变已与 3.x 对齐的对外行为（0015），影响面超出 dump。
- **整体推后 `--exclude-newer` 重新生成所有锁文件**：pyarrow 26.x 有 cp311–cp315 的 wheel，但没有 cp310，3.10 仍要停在 25.0.1，而且全部传递依赖都会跟着变，需要重新核对整个矩阵。改动面远大于拆出独立套件。
- **继续用 ORM 接口**：可以原样复制 3.x 的单测，但 pymilvus 3.1 会断，且每次运行都打印弃用警告。

- 高度可能的原因（失败详情缺失，未能确认）：两侧共用 pymilvus `LocalBulkWriter`。缓冲区超过 `chunk_size` 后它起写线程并立即返回、继续追加，写线程开始运行时才换掉旧缓冲区；线程起得晚时，后续的行落进上一个文件。原用例逐个文件比较两侧产物，文件切分因此随时机变化。本机给写线程注入 0.3 秒延迟，同一数据由 3 个文件（834 / 834 / 832 行）变为 2 个（1668 / 832 行）；只延迟本实现一侧时，原用例失败。旁证：同一 job 的另外 19 条单文件用例与其余 7 个 `dump-diff` job（含同机的 diff-2.6.17）都通过；pymilvus 2.6.17 与 3.0.2 的 `local_bulk_writer.py` 逐字节相同，竞态两条线都有，失败是间歇的，不是 Intel 或某一 SDK 特有；CI 上这 20 条用例要 3–7 分钟（本机约 35 秒），机器慢时线程更容易起晚。
- 修正：除 `many` 外仍逐字节比较（这些场景用默认 chunk，只在最后同步提交一次，切出多个文件本身就是差异）；`many` 断言两侧都切出了多个文件，按顺序拼接全部行，逐行比较保留键序的序列化文本，并核对每个文件正好是这些行的 `json.dumps(..., indent=2)`、行非空、文件名为互不相同的正整数序号。切分不是本实现的行为，3.x 一侧同样如此。
