## 问题

0.7.0rc1 从冻结到签发，发行工作流本身耗时三段：

- 冻结提交上的 `CI` 与 `Compare`，约 33 分钟；
- 演练 [44728358779](https://github.com/GrittyChen/milvus-lite-rust/actions/runs/44728358779)，约 82 分钟；
- 正式运行 [44741797152](https://github.com/GrittyChen/milvus-lite-rust/actions/runs/44741797152)，从触发到候选结果约 85 分钟，另有审批等待。

0.6.0rc1、0.5.0rc1 的形态相同。数据取自各运行的 jobs 接口，按 job 的开始与结束时间计算。

### 演练是一整次重复运行，覆盖的签发分支却很少

0021 第 10 条要求每个正式运行引用同一冻结提交上一次包含 PID 1 的成功演练。演练与正式运行的构建、测试与候选结果完全相同（「实施与试点」第 2 条）。

**演练对构建与测试不提供额外保护。** 正式运行在 `sign` 开始之前失败不消费版本，修复后可用同一版本重跑（第 3 条）。过去的记录也是如此：

- 0.7.0rc1 第一次演练因 dump 差分的判定层问题失败（[验收记录「第一次演练与修复」](../testing/0.7.0rc1-acceptance.md#第一次演练与修复)）。同样的失败若出现在正式运行中，也在签发前停下、不消费版本。
- 0.6.0rc1 演练一次通过，随后四次正式运行仍在签发前失败（托管执行机未分配与冒烟问题），都没有消费版本。

**在 `attest` job 内，演练与正式运行走的分支也大多不同。**

| 环节 | 正式运行 | 演练 |
| --- | --- | --- |
| 签发环境 | `release-signing`，须负责人审批；前置检查核对其保护规则 | `dry-run-signing`，无保护、不暂停；不做环境预检 |
| 签发前复核（[runs.py](../../tests/release/runs.py) `recheck`） | 核对继承运行未变、版本未被消费 | 只核对继承运行；跳过版本消费判定 |
| 保全回执（[preserve.py](../../tests/release/preserve.py) `gate`） | 核对审批备注与回执 | 直接通过，不访问审批接口 |
| `sign` | 七个主体 | 两个演练文件 |
| 签发结果核对 | [release_set.py](../../tests/release/release_set.py) 核对七主体与证明 | `gh attestation verify` 与证明 404 检查，不运行 `release_set.py` |

演练真正与正式运行共用的签发部分，只有以下几项：`attest` job 的依赖与权限、`actions/attest-build-provenance` 在本工作流上的 OIDC 签发、签发前复核中的继承运行快照。只在正式模式运行的分支（审批门闩、环境预检、版本消费判定、`release_set.py` 的签发后核对），演练从来没有覆盖过。它们由工具自检，以及 0021、0022 用测试版本 `0.0.1rc903`、`0.0.1rc904` 做的真实签发试点覆盖。

第 10 条的原始理由是 PID 1 基础镜像刚固定、尚未在托管机器上验证。此后 0.3.0rc3 至 0.7.0rc1 五个版本的正式运行都执行了两个架构的 PID 1，正式运行的阶段矩阵本身也包含 PID 1。

### 单次运行受 macOS 并发上限约束

托管 macOS 的并发上限是账户级的，同时最多 5 个 job。正式运行中 12 个 macOS 测试 job 合计约 280 个执行机分钟，另有两个 macOS 构建约 17 分钟：

| job | Intel Mac（分钟） | macOS arm64（分钟） |
| --- | --- | --- |
| 构建（正式与 FI 两次 `maturin build`） | 14（演练 10） | 3–6 |
| diff-2.6.17 | 46–51 | 29–32 |
| diff-3.0.2 | 40–45 | 27–30 |
| python | 36–38 | 27–29 |
| interop | 34 | 21–22 |
| static | 9–10 | 5–7 |
| fi | 1–2 | 1 |

**排队过程**：

- 全部测试 job 都要等 `assemble`，`assemble` 要等最慢的 Intel Mac 构建，在第 15 分钟左右放行。arm64 的构建在第 4–6 分钟就已完成。
- macOS 测试从第 15 分钟一起放行。矩阵按 part 在外、平台在内的顺序放行，前 5 个是两个平台的两条差分与 Intel 互通。
- Intel 的 python 排到第 48 分钟才开始，第 84 分钟最后完成。

**模拟**：按实测时长做离散模拟（5 个并发位、按就绪时间与矩阵顺序放行）。现状的模拟结果为 83 分钟，与实测 84 分钟吻合。构建结束后的理论下限约 71 分钟。

### 差分 job 的长杆（推测，已由 D 测量更正）

差分 874 个用例中，405 个使用会话级服务 fixture（`diff`、`rust_uri`、`ref_uri`），按 0019 整组放入同一片，3 片的计划为 `[405, 235, 234]`。0019 试点时会话组只有 118 个。`Compare` 的 macOS 差分同样受此约束。

**测量更正**：D 的测量（[试点记录](../testing/0039-release-speedup-pilot.md#d差分会话组的测量)）依据本机的串行耗时表明，3 片时会话组（串行 399 秒，占整轮 25%）不是最慢的一片。最慢的是非会话组的两片：CI 没有提供耗时数据，全部用例按相同权重计，即按用例数切分。按耗时分配可使最慢一片缩短约 20%；会话组只在 4 片及以上时成为下限。上文的推测保留原样，结论以测量为准；CI 机型上的相对耗时待另立决策时复核。

## 决策

### A. 签发路径未变时，正式运行可以不引用演练

#### 1. 签发路径

签发路径是签发开始之后才执行、或决定签发怎样执行的部分，由工具（[runs.py](../../tests/release/runs.py)）计算一个摘要，下称签发路径摘要。摘要覆盖三部分。

**工作流头部**：[release.yml](../../.github/workflows/release.yml) 中 `jobs:` 之前的全部行，`env` 块只保留 `MODE` 与 `VERSION` 两行。被保留的包括以下各项，其中 `defaults.run.shell: bash` 给 `run` 脚本 pipefail，签发后核对的管道依赖它：

- `on.workflow_dispatch.inputs`；
- `run-name`；
- 顶层 `permissions`；
- `defaults`；
- `concurrency`。

`env` 中的其他键每个版本都可能改，例如兼容探针的上一版本 `PREVIOUS_*` 与 `REFERENCE_COMMIT`。`attest` 与 `preserve-digests` 不读这些键，由工具自检固定。

**最后两个 job**：从 `preserve-digests:` 这一 job 键所在行到文件末尾，即 `preserve-digests` 与 `attest` 两个 job。

**工具**：两个 job 调用的 `tests/release/` 工具，及其在 `tests/release/` 内的 import 闭包。工具以常量列出入口：`runs.py`、`preserve.py`、`release_set.py`、`sums.py`。按当前代码，闭包为以下六个：

- `runs.py`；
- `preserve.py`；
- `release_set.py`；
- `sums.py`；
- `candidate.py`；
- `ledger.py`。

[scorecard.py](../../tests/release/scorecard.py) 是闭包中唯一显式豁免的文件。理由：测试数量变化时随功能提交修改；它在签发前已由候选结果 job 用同一份矩阵核对过，签发后的核对用的是同一份。

**不纳入的部分**：构建、验收与候选结果 job。它们在签发之前运行，失败不消费版本。

**计算与自检**：摘要按「路径 + 内容」逐项计算，文件缺失视为不同。工具自检核对：

- 由入口重算的 import 闭包等于工具内登记的清单；
- 两个 job 的 `run` 中引用的 `tests/release/` 与 `.github/ci/` 文件都是入口之一。目前没有 `.github/ci/` 文件；
- `preserve-digests` 与 `attest` 是文件中最后两个 job；
- `env` 块中各键都是单行。

**保守性**：`sums.py` 与 `candidate.py` 在构建与候选结果侧也被使用，与签发无关的改动也会使摘要变化，从而要求演练。这是有意的保守：工具宁可多要求演练，也不做语义级的区分。

#### 2. 基线

基线来自冻结提交中的版本台账：在 `outcome` 为 `released` 的条目中，取 tag `v<版本>` 存在的、版本号最高的条目，并核对以下两项：

- 该 tag 为附注 tag；
- tag 指向的提交，等于台账所记运行（`actions/runs/<运行>/attempts/<attempt>`）的 `head_sha`。

**处理规则**：

- 只有「tag 不存在」的条目被跳过，例如没有公开 tag 的测试版本。
- 以下任一情形，整体判为无基线，不回退到更低的版本，以免掩盖 tag 被移动或台账有误：
  - tag 存在但为轻量 tag；
  - tag 指向的提交与运行的 `head_sha` 不符；
  - 运行记录读取失败（只读请求照常走传输层有限重试，重试用尽或 HTTP 4xx 即失败）。
- 全部条目都被跳过时，也是无基线。

**版本比较**：只用标准库，按台账版本的正则 `X.Y.Z[(a|b|rc)N]` 比较。比较键为（X，Y，Z，阶段，N），阶段的顺序为 a < b < rc < 无后缀。

基线读的是冻结提交中的台账。版本消费判定读的是 `main` 上最新的台账（0021 第 3 条），两处用途不同，互不替代。基线可由任何人从公开仓库的 tag、台账与运行记录重算。

#### 3. 判定

正式运行的 `pid1_dry_run` 输入改为可选。

- **提供该输入时**：按现行第 10 条核对被引用的演练：同一 SHA、`mode=dry-run`、结论 success、两个 PID 1 job 成功。签发路径相对基线有无变化都允许提供。
- **未提供时**：前置检查计算冻结提交与基线提交的签发路径摘要。两者相等，允许继续；不相等或没有基线，前置检查失败，失败信息列出变化的路径。

前置检查内的顺序改为：参数格式 → 签发环境预检 → 版本消费 → 演练引用或签发路径判定 → 继承的 `CI` 与 `Compare`。判定放在继承运行之前，不满足时在前置 job 的第一分钟内失败，不必先等同一提交的 `CI` 与 `Compare`。前置检查在构建之前，这种失败不消费版本。

#### 4. 候选结果

候选结果的格式版本由 1 升为 2，新增键 `dry_run_basis`。取值有三种情形：

| 情形 | `pid1_dry_run` | `dry_run_basis` |
| --- | --- | --- |
| 演练 | `null` | `null` |
| 正式运行，引用了演练 | 演练的运行与 attempt | `null` |
| 正式运行，未引用演练 | `null` | 对象，见下 |

未引用演练时，`dry_run_basis` 记录四项：

- 基线版本；
- 基线提交（40 位十六进制）；
- 签发路径摘要（64 位十六进制；两侧相等，只记一个）；
- 计算所用的路径清单。

读取方核对以上取值形式，且路径清单须等于常量清单，防止清单被悄悄缩小。该常量放在 [candidate.py](../../tests/release/candidate.py)：`runs.py` 导入 `candidate`，放在 `runs.py` 会造成循环导入。

格式 2 的问题会在签发前暴露，不需要新增校验步骤：

- 候选结果 job 的 `candidate.write` 经 `build` 最后一步的 `validate` 生成候选结果；
- `preserve-digests` job 与保全回执的 `check_candidate_set` 在签发前再以 `load` 读取一次。

读取方只接受格式 2，已有的格式 1 文件仍由各自版本的工具核对：

- 公开下载核验用的是各版本冻结 tag 中的 `release_set.py`（[public-check.yml](../../.github/workflows/public-check.yml) 的说明）；
- 本地复核 0.5.0rc1 至 0.7.0rc1 已保存的目录（`preserve.py verify`），改用对应 tag 中的工具。docs/README 的命令说明同步写明这一点。

#### 5. 演练保留为工具

**须演练的情形**：签发路径有变化或没有基线时，仍须先演练。负责人也可以在任何时候选择演练，例如工作流的构建或验收部分有大改动，想在占用审批之前先看一遍。候选方案文档写明本版是否演练及理由。

**演练覆盖不到的改动**：签发路径的改动若落在只有正式模式才运行的分支（见「问题」中的表），演练覆盖不到。本决策不改变这类改动的验证方式：由工具自检覆盖；需要真实签发证据时，以专用测试版本做一次真实签发试点（0021、0022 的做法）。是否需要试点，由引入改动的决策规定。

#### 6. 首次生效

本决策的实施本身修改 `runs.py`、`candidate.py` 与 `release.yml` 的 `attest` 部分。所以实施后的第一个版本相对基线必然有变化，仍须演练；从第二个版本起，签发路径没有再改时才能省去演练。

按 tag 回看过去四次发版：

| 区间 | 签发路径 |
| --- | --- |
| 0.3.0rc3→0.4.0rc1 | `runs.py`、`preserve.py`、`release_set.py` 与 `attest` 都改过，须演练 |
| 0.4.0rc1→0.5.0rc1 | 未变，可省去演练 |
| 0.5.0rc1→0.6.0rc1 | 未变，可省去演练 |
| 0.6.0rc1→0.7.0rc1 | 未变，可省去演练 |

后三个区间里，`release.yml` 的其他部分与 `scorecard.py` 都有修改（计数、兼容探针、jieba 与 dump 阶段），只是签发路径没有变。实施时用新工具对这四个区间做一次回放核对（「实施与验证」第 3 条）。

### B. 验收不等装配，macOS 按平台分别排队

#### 7. 构建拆为两个 job

| job | 内容 |
| --- | --- |
| `build` | 保留 Linux x86_64、Linux aarch64、macOS arm64 三个矩阵项 |
| `build-mac-x86_64` | Intel Mac 单独成 job，步骤与 `build` 共用（YAML 锚点，与 `tests` / `tests-mac` 现有做法相同） |

产物名仍为 `build-<平台>`，`assemble` 的 `build-*` 模式照常收集。构建内容与命令不变，0021 第 6 条不变。

#### 8. 验收 job 直接取构建产物

依赖关系如下：

| job | `needs` |
| --- | --- |
| `assemble` | `build`、`build-mac-x86_64` |
| `tests`（Linux） | `build`、`orjson`、`jieba` |
| `tests-mac-arm64` | `build`、`orjson`、`jieba` |
| `tests-mac-x86_64` | `build`、`build-mac-x86_64`、`orjson`、`jieba` |
| `linux-system`、`pid1`、`sdist`、`previous-reader` | 不变，仍为 `assemble` 等；它们都不在关键路径上 |
| `candidate` | 除 `candidate`、`preserve-digests`、`attest` 外的全部 job |

`candidate` 的依赖是「签发的是全部成功之后的产物」的闸门，由工具自检按上表最后一行逐字核对。

测试 job 的产物处理：

- 下载 `build-<平台>` 与 `build-linux-x86_64`（sdist 在此构建）两份产物，按各自的 `build.sha256` 核对后取用：本平台的正式 wheel、FI wheel，以及 sdist。
- 测试 job 不再下载装配交出的 `formal` / `fi` 产物。
- 每个测试 job 把实际使用的三个文件写成 `tested-<平台>-<part>.sha256`，随阶段产物上传。
  - 格式与 `sums.py` 相同，每行为「摘要、两个空格、名字」。
  - 正式 wheel 与 FI wheel 文件名相同、只是目录不同，因此名字带清单前缀：
    - 正式 wheel 与 sdist 写作 `formal/<formal.sha256 中的名字>`；
    - FI wheel 写作 `fi/<fi.sha256 中的名字>`，即 `fi/build-<平台>/<文件名>`。

候选结果 job 的交叉核对：

- 4 个平台 × 6 个 part，共 24 份 `tested-*.sha256` 都须存在，不多不少。
- 每份恰好三行，内容逐一核对：
  - 本平台的正式 wheel：文件名带该平台的 wheel 标签，在 `formal.sha256` 中；
  - 本平台的 FI wheel：位于 `fi/build-<平台>/`，在 `fi.sha256` 中；
  - sdist：在 `formal.sha256` 中。
- 去掉前缀后，名字与摘要须在对应清单中成对出现。
- 每个平台应使用的文件名，由 `candidate.py` 新增的「平台到 wheel 标签」映射推出。该映射现在只在工作流矩阵的 `platform.tag` 中；工具自检核对矩阵与映射一致。`scorecard.py` 不改。

**字节绑定由哪一步完成**：`build.sha256` 与产物同包上传，只能发现传输损坏，不能发现替换。把「测试用的字节」与「签发的字节」绑在一起的是候选结果 job 的两步：

- 用 `sums.py check` 核对 `formal` / `fi` 产物与装配清单一致（现有）；
- 用这次交叉核对，确认每个测试 job 用的正是清单中的文件。

两步都在签发之前。`assemble` 若在测试之后才失败，只是浪费算力，候选结果 job 不会放行。这样仍满足第 7 条「验收的就是将要发布的字节」。

#### 9. macOS 测试按平台分 job

`tests-mac` 拆为 `tests-mac-x86_64` 与 `tests-mac-arm64`，步骤不变。

- **矩阵顺序**：两者都为 diff-2.6.17、diff-3.0.2、python、interop、static、fi。Intel 的 python 因此在第一批。
- **并发上限**：Intel 为 4，arm64 为 3。

以实测时长模拟，各方案的结果如下：

| 方案 | 模拟耗时（分钟） |
| --- | --- |
| 现状 | 83 |
| 只调整放行顺序（最长优先） | 76 |
| 拆分后 arm64 上限 3、Intel 上限 4 | 69 |
| 拆分后 arm64 上限 2 | 77（arm64 拖尾） |
| 拆分后 arm64 不设上限 | 69–74（视放行先后） |

GitHub 文档没有写明放行顺序，0.7.0rc1 两次运行的实际放行与矩阵顺序一致。实际效果以实施后的运行实测为准。上限是编排参数，可以按实测调整，不属于本决策的合同。

#### 10. 证据范围不变

- 阶段矩阵、计数、平台与 SDK 组合都不变，`scorecard.py` 不改。
- 正式 wheel 上的差分与互通继续在四个平台执行，0021 第 9 条的判据不变，只改「取自装配 job」这一来源说明。

### D. 会话组能否拆分：只测量

#### 11. 测量项

在本机参照环境上测量以下几项，结论写入试点记录：

- 差分会话组的串行耗时，以及占整轮的比例：用 `shard.py --shards 1` 取逐 nodeid 耗时；
- 会话组按模块拆成 2–3 个进程、每个模块内保持收集顺序时，重复 10 轮有无新增失败；
- 拆分后各片的估计耗时。

本文不改 0019 与分片工具。若测量支持拆分，另立决策，届时 `Compare` 与发行工作流的差分 job 都会受益。

### 不采纳

- **发行工作流不再跑差分，改由冻结提交的 `Compare` 继承**：`Compare` 用 `maturin develop` 或临时 wheel，与正式附件不是同一份字节（0021 第 2 条），且 `Compare` 没有 Intel Mac。这是证据范围的缩减，不在本轮。
- **部分平台不在正式 wheel 上跑差分**、**缩减 SDK 与 Python 端点矩阵**：同属证据或支持声明的缩减。做完 B 之后，python job 已不在关键路径上，收益不足以抵消缩减证据的代价。
- **缓存 Intel Mac 的构建**：第 11 条不缓存 `target`，构建只发生一次且须可复核；B 已让 arm64 不再等它。

## 风险与残余

### 签发路径划分有误

若某项改动在签发前不会暴露、却会让 `sign` 或签发后的核对失败，并且它落在签发路径之外，那么省去演练后，它会在正式运行中消费版本。签发前复核与保全回执失败不消费版本，代价只是重跑一次正式运行（约 85 分钟）并重新保存与审批。

缓解措施：

- 签发路径由工具按入口与 import 闭包计算，自检固定 `attest` 只调用入口内的工具；
- 签发环境的保护规则仍由前置检查核对（0022）；
- 负责人在可疑时可以主动演练。

### 托管环境漂移

ubuntu-24.04 镜像、`gh`、`python3` 与 GitHub 的签发服务都是浮动的。基线与正式运行可能相隔数周，比演练与正式运行之间的数小时长得多。

本文接受这一暴露面，理由有三：

- 漂移若影响签发，演练在数小时前通过也不能排除它；
- 0.6.0rc1 的四次托管侧失败都发生在签发前，没有消费版本；
- 负责人可以在距上次发版较久或 GitHub 有相关变更公告时主动演练。

不设基线时效上限。若以后出现签发步骤本身因托管侧漂移失败的情形，再评估时效上限。

### macOS 放行顺序

GitHub 未承诺按矩阵顺序放行。不按顺序时，耗时介于现状与模拟值之间，证据不受影响。

### 执行机容量

macOS arm64 每次运行都有容量 notice，0.6.0rc1 曾因执行机未分配而失败。本文不改变这一点；省去演练后，每个版本暴露于该风险的运行次数减少一次。
