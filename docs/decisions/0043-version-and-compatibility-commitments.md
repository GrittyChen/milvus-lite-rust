## 问题

用户升级前需要知道哪些东西不会变、哪些可能变、变之前会不会预告。这些规则现在散在 0002、0013、[AGENTS.md](../../AGENTS.md) 与各版本的发行说明中，没有一处是写给用户的。版本号也没有约定：0.x 的每个版本都可能加功能，用户无法从版本号判断升级风险。1.0 需要把这些写成对外承诺。

## 承诺

本文的“对外行为”包括两部分：

- [AGENTS.md](../../AGENTS.md) 规则 2 所列：RPC 语义、结果与排序、距离数值、错误码与错误信息、过滤语义；
- 本项目的 CLI 与 Python 入口。

### 1. 版本号

- 版本号形如 `X.Y.Z`，预发布为 `X.Y.ZrcN`（PEP 440；Cargo 中为 `X.Y.Z-rc.N`）。
- 每个正式版本之前至少有一个 rc。正式版本与最后一个 rc 的差异，只限版本号与随之改变的文字。正式版本的字节与 rc 不同，因此仍按 0021 走完整候选，单独验收。
- **补丁版本（Z）**只修缺陷。不新增功能，不新增或改变数据目录中的任何文件格式，不收窄支持范围。
- **次版本（Y）**是向后兼容的变化，包括以下几类：
  - 新增功能，包括把某项从 `UNIMPLEMENTED` 改为支持；
  - 新增私有文件或新的集合内容，降级时的表现登记在降级表中；
  - 跟进新的 3.x 对照基线或新的 pymilvus 版本，但不含共享文件格式的变化，由此带来的行为变化在发行说明中逐项写明；共享文件格式变化的分级见第 3 条「与 3.x 互通」；
  - 支持范围的增加，以及第 4 条允许的 CPython 版本退出：它以官方停止维护为前提，用户本来就该迁移，因此不按破坏性变化处理；平台与系统下限没有这样的外部期限，按主版本处理。
- **主版本（X）**是破坏性变化，包括：
  - 去掉某条已支持的 pymilvus 版本线；
  - 写出的数据文件，上一个 3.x 对照版本不再能读（见第 3 条「与 3.x 互通」）；
  - 新主版本不再能打开上一主版本写出的数据目录；
  - 去掉某个已支持的平台或提高系统下限；
  - 不属于修缺陷、也不属于跟进 3.x 的对外行为改变，例如去掉或改变 CLI 参数的含义。

### 2. 与官方 3.x 的行为

- 对外行为以第 3 条的 3.x 对照版本为准。所有差异，包括错误码的差异，都登记在[兼容性说明](../compatibility.md)及其链接的决策中，没有未登记的差异。
- 修正与 3.x 不一致的缺陷属于修缺陷，可以出现在任何版本，并在发行说明中写明。
- 改变一项已登记的差异按第 1 条分级，并在发行说明中写明。
- 除上述已登记的差异外，错误码与 3.x 一致。
- 错误码是稳定接口。错误信息的文字以当时的 3.x 对照版本为对齐目标，但不承诺跨版本稳定；文字改变时在发行说明中写明。程序应以错误码判断，不依赖文字。这一口径只决定对外承诺的强度，不改变 [AGENTS.md](../../AGENTS.md) 规则 2 的开发目标。

### 3. 数据目录

- **升级**：1.0 起，同一主版本中，已发布版本写出的数据目录都能被之后的版本打开，不需要手工迁移。
- **1.0 与 0.x**：尚未承诺。1.0 是否打开 0.x 预发布版本写出的目录、对哪些 0.x 版本承诺，由采纳前事项 1 的矩阵结果决定，并回填到这里；回填前不对外写成承诺。
- **与 3.x 互通**：数据文件与 3.x 双向互通，索引文件不互通。
  - 对照版本为本仓当前对照的 3.x，现为 v3.2.2 之后的 `1320d26`，每个版本的发行说明写明当时的对照版本。
  - 范围与约束见 0002，并受[兼容性说明](../compatibility.md)中各功能的差异约束，例如含空值的 nullable 向量要求 3.x 一侧使用 pyarrow 26 及以上。
  - 3.x 之后若改变共享文件的格式，本实现是否跟进、以及跟进前的影响，在下一个版本的发行说明中登记。
  - 跟进时的分级：“上一个 3.x 对照版本”指上一版本发行说明记录的对照版本（现为 `1320d26`），不是最新的 3.x。
    - 它能读本实现跟进后写出的数据文件，按次版本；不能读，按主版本。
    - 存储互通矩阵同时核对另一方向，即新的 3.x 对照版本读取本实现旧版本写出的数据。若失败源于 3.x 自身的不兼容，按第 2 条登记差异，不单独据此判主版本。
- **降级**：降级前须先用新版本正常打开并关闭一次，这对任何降级都适用。
  - 同一个次版本中的补丁版本之间（`X.Y.*`），可以互相升降，打开时的表现与原版本相同；补丁版本不新增文件格式，因此不会产生降级表中的情形。
  - 跨次版本降级只承诺降级表中登记的表现，不作更一般的承诺。
- **私有文件**：
  - 改名、清空与索引删除的意图文件带格式版本，改变其格式按次版本处理，并在 0002 中登记旧目录的处理方式。
  - HNSW 图文件（`.mlrs`）是缓存，任何版本都可以作废并重建它，不报错，不算格式变更。

### 4. 支持范围

- **pymilvus**：支持 2.6.x 与 3.0.x 两条线。
  - 每个版本对每条线的最新补丁版各跑该线适用的全套测试，发行说明写明测到的版本，现为 2.6.18 与 3.0.3。端到端、dump 与差分两条线都跑；存储互通只以 3.0.x 线为参照环境。
  - 未测的 pymilvus 新版本（如 3.1）不承诺可用，跟进后在发行说明中写明。
  - 去掉一条线须升主版本，并按第 5 条预告。
- **Python**：GIL CPython 3.10–3.15。
  - 新的 CPython 版本经验证后加入。
  - 某个 CPython 版本在官方停止维护之后，可以在之后的某个次版本中去掉，并按第 5 条预告。
  - 3.10 已于 2026-10-01 停止官方维护（PEP 619），1.0 仍保留：3.x 的下限是 `>=3.10`，abi3-py310 wheel 与 CI 已覆盖 3.10。等 3.x 或 pymilvus 的依赖不再支持 3.10 时，再按本条去掉。
- **平台**：
  - Linux x86_64 / arm64，glibc 2.28 及以上，验收在 glibc 2.28 容器中进行；
  - macOS arm64 / x86_64，构建的最低系统版本为 macOS 11。验收在 macOS 15 上进行，macOS 11 只由二进制检查核对，没有真机运行。
  - 其他 Linux / macOS 平台可以从 sdist 尝试构建，没有支持承诺；Windows、free-threaded CPython 与非 CPython 解释器在构建时明确拒绝（[build.rs](../../crates/py/build.rs)、0013）。
- **CLI**：`milvus-lite server` 与 `milvus-lite dump` 的参数都与 3.x 一致（[0012](0012-cli-server.md)、[0037](0037-dump.md)）。

### 5. 预告与支持周期

- 需要预告的变化，写进发行说明与[兼容性说明](../compatibility.md)，至少提前一个次版本。
- 只有最新的次版本线接受修复，不向旧的次版本回移补丁。本项目维护者少，不提供长期支持，这一点写明。
- 数据损坏或安全问题以补丁版本尽快修复，发行说明标出受影响的版本范围。

### 6. 不在承诺内

- Rust crate 的接口。crate 不单独发布。
- 故障注入测试包及其接口。
- 性能数字。各版本只给当时的测量，不承诺不回退；回退在发行说明中写明。
- 线程模型与资源占用。
- 日志与 stderr 的文字。
- 未登记的私有文件名。

## 采纳前须完成的事项

1. **升级矩阵**：第 3 条「1.0 与 0.x」目前没有直接证据。
   - 现有证据只覆盖其他方向：降级表证明新目录在旧版本中的表现，互通矩阵证明与 3.x 的互通。发行工作流的兼容探针（[previous_reader.py](../../tests/release/previous_reader.py)）主要覆盖“上一版本读取新目录”，另有 partition key 集合由上一版本追加、再由新版本重开核对的反向用例，只在 Linux x86_64 上运行。
   - 补一个升级矩阵：用十三个已发布 wheel 分别写出目录，由 1.0 的候选 wheel 打开并核对。在 1.0 候选上执行；若在更早的版本上先跑，1.0 候选要重跑。做不到的旧版本排除在承诺之外，结论回填第 3 条。
2. **补丁版本互开**：现在还没有发过补丁版本。第一次发补丁版本时，候选验收要补一项“新旧补丁版本互相打开”的检查。现有探针的用例是按次版本的特性写的，上一版本的 wheel 也是在工作流中写死的哈希，因此需要调整探针的期望与用例，不能直接复用。
3. **停服段错误**：它不属于兼容承诺，但仍是 1.0 的单独门槛（[停服段错误调查](../testing/shutdown-segfault-investigation.md)与各版本发行说明），不在本文处理。
