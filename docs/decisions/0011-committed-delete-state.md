# 0011 已提交删除状态的独立保留

- 状态：已确认，已实现并通过修复复审
- 日期：2026-10-09
- 确认日期：2026-10-09；负责人选择本轮实现独立已提交删除表
- 前置：[0010](0010-compaction-and-tombstone-gc.md) 第 5 项的附加验收条件
- 参照：milvus-lite v3.2.1 / `43d1257` 的 committed DeltaIndex

## 触发原因与证据

0010 已确认首个切片可以复用全局最大删除表，但当回收差距明显时应另起决策，不能默认永久接受。受控负载在同一机器顺序运行 Rust 测试 wheel 与真实 3.x：4000 行、dim 128，首轮合并准备时，以未提交的新删除遮住较早已提交删除；再重复插入这 800 个主键并删除、flush、确定等待，共 5 轮。

| 每轮结果 | Rust | 3.x |
| --- | --- | --- |
| 存活行 | 3200 | 3200 |
| manifest 引用的物理 data 行 | 4000 | 3200 |
| 已失效物理行 | 800（20%） | 0（0%） |
| data 文件 | 1 | 1 |
| data 字节 | 2716441 | 2297622 |

5 轮中的上述比例保持不变。字节差额还包含两种 Parquet 编码器的差异，不能全部归因于死行。证据来自隔离 fault-injection wheel 的受控组件负载，不是正式产物的性能结论，也不能推广到任意删除比例、文件规模或并发负载。

复现入口为 [delete_load.py](../../benchmarks/compaction/delete_load.py)，确定等待与暂停由 [engine_runner.py](../../tests/compaction/engine_runner.py) 在实例所属进程执行；不修改参照 checkout。原始 JSON/日志保存在仓库外，实施验收记录应附产物身份与最终复跑结果。

## 已确认方案

在 persistent runtime 中独立保存每个主键的**已提交最大删除序号**，而 visibility.latest_delete 继续保存包含活跃/冻结代的全局最大值。两张表的职责明确：读取/写入判定沿用 visibility，物理合并使用 committed 表。

- 打开时从已提交 delta 的恢复结果取得 committed 表，不能从已混入 WAL 的最大值倒推；不克隆全量主键读取表或整个 Visibility。
- 普通 flush 发布时，仅将该冻结代实际提交的删除更新到 committed 表；提交点前失败不更新，replace 后按既有发布/重新提交协议处理。
- compaction 只摘取选中主键的 committed 删除快照，不每轮重读全部 delta，不用活跃删除代替已提交删除。
- GC 按同一个安全阈值回收 committed 表与允许回收的 visibility 删除；活跃/冻结删除和旧 WAL 风险保护照旧。
- WAL、manifest、Parquet 字节格式、写入 `_seq`、快照与锁边界不改；新表只是一份可从磁盘重建的内存状态。

## 代价与验证

新增内存与已提交 tombstone 数成正比；VARCHAR 的主键拥有成本尤其需要记录。应实测删除重负载下的额外占用，不能拿普通无删除百万行的结果证明它没有成本。

必须重跑上述 5 轮负载，并验证未提交删除不泄漏进输出、提交点前后失败、更新/重插、空 data、旧 WAL、GC 边界及重开等价。原有回收差异的登记只能在这些证据通过后收窄。

## 已确认的实施选择

负责人已选择在当前 compaction 切片中实现，并重新冻结上述已提交删除状态合同与对应矩阵。暂不采用“保留 20% 残留、下一切片再做”的方案；重跑负载与额外内存证据通过后才能将原差距记为已解决。

## 本轮实现与条件复核

独立表已接入恢复、冻结代发布、合并输入与安全 GC；全局读取表和磁盘格式保持。相同五轮负载复跑后，Rust 与 3.x 均为 3200 物理行、3200 存活行、0% 失效行，原受控残留差距在本负载中已解决。

额外内存通过 Int64 与 16 字符 VARCHAR 的 25 万/100 万删除键组件诊断披露；不是全引擎 RSS。数值、正式/测试产物身份、变异检验与未验证边界集中在[实施验收](../testing/compaction-correctness.md#第-5-项附加条件删除重负载与内存)，不由此宣称任意删除比例或长期并发负载均已验收。

评审修复构建再次执行同一五轮负载，结果不变；本轮重新测量与沿用的组件 RSS 证据在验收记录中分别标明。

## 0023 清空对独立表的影响

[0023](0023-aliases-rename-truncate-databases.md) 的 TruncateCollection 在候选 manifest 提交之后，按重开的路径重新加载集合并原地替换读视图：候选 manifest 的 delta 列表为空，独立已提交删除表随新读视图重建为空，没有旧表残留；WAL 代与数据源编号继续递增，保证清空前的来源不会与清空后的新来源重号。清空期间不会有合并在运行（清空持独占许可，合并持共享许可）。
