## 停服段错误：再次做发布级风险接受

`0.8.0rc1` 的接受以 `crates/` 树 `576c178b…` 为适用范围。本版 `crates/` 有变化，按调查记录「失效与继承」第二条，差异涉及原生交界或服务生命周期时不能继承。核对相对 `476a822` 的 `git diff -- crates`（14 个文件）：

1. **停服顺序没有改动**：`Db::close`、`close_nowait`、`Drop for Db`、`graphs.stop()`、`Server::stop` 与 `NativeServer.stop` 的函数体都没有改动；`crates/grpc` 与 `crates/py` 没有改动。
2. **服务生命周期中的线程**：建图线程的任务（[graph_build.rs](../../crates/core/src/graph_build.rs) 的 `run_task`）在构建前新增一步 `attach_file`：读图文件、校验后在状态读锁内挂到第一块；`load_collection` 中原有的同一段读入逻辑改为调用它，这是 `db.rs` 唯一的非测试改动。这一步运行在建图线程上，停服时由同一 `graphs.stop()` 取消与 join，不新增线程，不改变取锁顺序。
3. **原生交界**：x86_64 的 AVX2 分派（[flat.rs](../../crates/core/src/flat.rs) 的 `dispatch!`）新增两个 `#[target_feature(enable = "avx2")]` 函数 `diff_sq_tile` / `product_tile`，经既有 `dispatch!` 宏在检测到 AVX2 后调用，即新增两处宏展开的 `unsafe` 调用点（`SAFETY` 说明在宏内，宏文本未改）；手写的新增 `unsafe` 块只在测试中。没有新增 `extern "C"`、`transmute`、PyO3 或 libc 调用。检索在计算池上执行，不在停服函数上。
4. **依赖**：`Cargo.lock` 与 `0.8.0rc1` 逐字相同；Rust 1.98.1；CI 的 SDK 约束不变。
5. **运行核对**：自 `0.8.0rc1` 正式运行 `45556724615`（创建于 2026-11-25 05:53:53 UTC）之后至 D，`CI` 31 次、`Compare` 19 次。没有失败的测试；不在第 1 次 attempt 全部成功的有四次：
   - `CI` `45642946121`（`d346c8f` 的 `main`）attempt 1 中两个 macOS job 未分配到托管执行机（0 个步骤）而被取消，attempt 2 成功；
   - `Compare` `45578147578`（`0.8.0rc1` 台账分支）attempt 1 中 `diff-2.6.18 (macos-15)` 在差分步骤中达到 30 分钟时限被取消，`--failed` 重跑后 attempt 2 成功；`0.8.0rc1` 验收记录登记了两种无法区分的解释（时限余量过薄、执行机偏慢），没有分片级证据，「挂起」不能排除。该 job 的日志中没有段错误、SIGSEGV 或 core 的记录，被测代码与 0.8.0rc1 相同；
   - `f7f872f` 的 `CI` `45576872782` 与 `Compare` `45576872641` 各被取消一次，已记入 `0.8.0rc1` 验收记录。
   常设崩溃现场采集持续开启。

理由：停服路径的函数体与顺序都没有改动；第 2 项是建图线程上已有的读文件逻辑换了调用位置，第 3 项是检索热路径上的安全分派。它们不直接作用于停服窗口，但触及「服务生命周期中的线程」与「原生交界」，按规则须再次接受，不写「继承」或「停服路径未变」。

**残余风险**（接受的对象）：`0.8.0rc1` 接受的全部残余风险；加上建图线程在停服窗口内执行 `attach_file`（读文件、取状态读锁）时的取消与 join 没有定向停服压力证据；新增的 AVX2 按段打分函数与本版的过滤代码不在任何一次 ASan 运行的覆盖内。

**适用范围**：谱系以 D 的 `crates/` 树 `f2c94889…` 与 `Cargo.lock`（相对 D 只差三个本项目 crate 的版本）为准，工具链为 Rust 1.98.1，同进程 grpcio 为 CI 固定的 1.84.0。下一个候选以此为基准比较。

冻结提交须同时满足以下条件，任何一项不满足即停止候选准备：

1. `crates/` 树与 D 相同；
2. 相对 D，`Cargo.lock` 只有三个本项目 crate 的版本变化；
3. Rust 工具链为 1.98.1，CI 的 SDK 约束不变；
4. 上面第 1–4 项的结论在冻结提交上仍然成立。

候选的任何运行再次出现停服路径 SIGSEGV，立即停止快进与发布并撤回接受，按调查记录的停止条件处理，不重跑掩盖。

3. 冻结确认：冻结条件、`Cargo.lock` 结构比对、远端没有该版本的 tag、Release、台账条目或进行中的运行，冻结分支 head 即冻结提交，`main` 仍为 D；`release-signing` 环境在冻结提交上没有部署（按 `sha` 过滤）；`PREVIOUS_WHEEL_SHA256` 与 `0.8.0rc1` Release 的 API 摘要一致；以冻结提交运行 `runs.py basis`，判定为「未变」。
4. 正式运行（不提供 `pid1_dry_run`）：`attest` 等待审批期间保存候选证据集，负责人以审批行批准；签发后在 `post-sign/` 补存并复核回执不变。
5. 把 `main` 普通快进到冻结提交，单独登记台账 `candidate`，以冻结提交中的工具运行发布准备核对（`release_set.py --prepare`，必须在创建 tag 之前）。
6. 候选验收记录（引用计划中的 tag 名 `v0.9.0rc1`）复审并合入。除 `0.8.0rc1` 记录的各项外，写明：冻结条件的逐项核对与负责人的再次接受；「负责人的决定」各项的决定与理由；「重新计数」的运行映射；签发路径判定与不引用演练的执行结果；按 0021 第 11 条检索正式运行的 `transport-retry` 注解逐条登记（没有也写明）。
7. 创建指向冻结提交的 tag（消息中的验收记录链接固定到上一步的合入提交），在验收记录中追加 tag 对象，该次合入是 Release 正文链接的最终验收记录提交。
8. 从冻结的发行说明组装 Release 正文：以签后证明包验证七个附件，七个摘要以证明的主体列表为唯一来源，与候选结果的五个正式附件、`SHA256SUMS` 的六条及本地文件逐项核对；相对链接改为固定提交链接，追加候选验收记录与七个附件的身份，校验链接与正文哈希。
9. 创建草稿、上传七个附件并核对（API 摘要、逐字节、正文哈希、不带 `--prepare` 的发布准备工具），发布不可变 Release（prerelease，不设为 latest）。
10. 发布后立即单独把台账改为 `released`，不等待其他文档。
11. 在 `main` 上触发公开下载核验，完成发布后记录（风险处置改为发布后口径）；临时与冻结分支打包验证后删除。

**外部写入的三态**、**`main` 冻结窗口**、**台账结局**与**运行预算**沿用 [0.4.0rc1 候选方案「执行检查点」](0.4.0rc1-candidate-plan.md#执行检查点)的规定，只把版本、冻结提交与开发基线换成本版，并去掉演练：执行后先只读回读再判定成功、确定失败或结果不明，结果不明时不重复写入；从推送冻结分支起 `main` 保持 D 不动，推送前、正式运行触发前、批准前与快进前各核对一次；`sign` 开始前经授权放弃不登记台账，`sign` 开始但没有成功签发登记 `signing-failed`，签发成功后放弃登记 `abandoned` 并换用新版本号。正式运行在 `sign` 之前因未分配托管执行机失败时，经单独授权另开一次正式运行；因测试或安装失败时先查明根因，不直接另开。任何失败、意外跳过、部分成功、SHA 不一致或必需检查缺失都立即停止，不重跑变绿；正式运行的 `sign` 一旦开始，该运行的任何 attempt 都不重跑（0021 第 3、20 条）。
