## 停服段错误：再次做发布级风险接受

`0.6.0rc1` 继承的接受以 `crates/` 树 `c695221b…` 与当时的 `Cargo.lock` 为适用范围，本版两者都有变化，不自动适用。本版相对 `0.6.0rc1` 的差异涉及原生交界（本仓新增 `unsafe`，新依赖带运行时 SIMD 的 `unsafe`）与服务生命周期的新用法（dump 在进程内启停服务并在 atexit 前改信号处置），按调查记录「失效与继承」第二条不能继承，须由负责人**再次做发布级风险接受**：根因仍未查明，没有新的定向证据，依据是下面的只读核对。

相对 `0.6.0rc1` 冻结提交 `5f7c191` 的核对结果：

1. **停服顺序本身逐字未变**：
   - `crates/core/src/db.rs` 的差异只有新增的 `Db::has_collection`，以及模块与既有 `alias_target_exists` 的注释；`Drop for Db`、`enter`、`begin_shutdown`、`close` 与 `finish_storage*` 没有改动；
   - `maintenance.rs`、`storage/runtime.rs`、`storage/fs_commit.rs`、`lock_order.rs` 只改了 `//!` 注释；`compute.rs`、`storage/flush.rs`、`crates/grpc/src/server.rs` 没有改动；
   - `crates/py` 只改了 `python/milvus_lite/cmdline.py`；`server_manager.py`、`__init__.py`、`__main__.py` 与 Rust 绑定没有改动。
2. **服务生命周期与停服下游有改动**：
   - **dump（Python）**：`milvus-lite dump -d` 经 `MilvusClient` 走既有的 `server_manager.start_and_get_uri` 启动进程内服务，导出结束（含失败）后在报告前调用既有的 `server_manager_instance.release_server` 停服以释放 LOCK；导出期间对 SIGINT / SIGTERM 安装自己的处理函数，收到信号后恢复为 `SIG_DFL` 并保持到进程退出，覆盖随后 atexit 中的进程内服务收尾。没有新增停服入口，但这是新的调用时机与信号处置。
   - **最终 flush 写出与打开时读入的数据**：`storage/arrow_data.rs` 支持 nullable 向量的 Arrow null（父级 null、子元素为零），flush 写出与打开、恢复时的解码都经过它；`storage/memtable.rs`、`storage/schema_file.rs` 只放开 nullable 向量的校验。flush 的提交协议与恢复流程没有改动。
   - **停服窗口内的并发**：`close` 等待的在途 RPC 处理体里有新增代码：jieba 分词与词典加载（`jieba.rs`、`analyzer.rs`，经 `jieba-rs` 调用 `bytecount`）、nullable 向量的编解码（`crates/grpc/src/insert.rs`、`output.rs`）、HasCollection，以及批量检索新的「查询片 × 行块」任务模型（`collection.rs`）。检索计算仍只经 `Compute::for_each`。CheckHealth 不经 `Db::enter`、不碰引擎，与 Connect / GetVersion 同类。
3. **原生交界**：本仓 `crates/` 中新增的 `unsafe` 只在 `flat.rs` 的 AVX2 分派语句（运行时 `is_x86_feature_detected!("avx2")` 确认后调用 `#[target_feature(enable = "avx2")]` 的副本，附 `// SAFETY:`）与逐位比对两套副本的单测上；只在 x86_64 生效，由叶子计算任务执行，不在停服函数上。没有新增 `extern "C"`、`libc::`、`transmute`、PyO3 交界；产品代码没有新建线程（新增的 `thread::spawn` / `thread::scope` 只在单测与 `flat_batch_probe` 示例中）。依赖一侧，`bytecount` 0.6.9 的 SIMD（x86_64 按运行时检测选 SSE2 / AVX2，aarch64 在输入不短于 16 字节时无条件用 NEON）含 `unsafe` 与 `#[target_feature]`，在所有平台的 jieba 路径上执行，同样只在在途处理体中、不在停服函数上。

**外部写入的三态**、**`main` 冻结窗口**、**台账结局**与**运行预算**沿用 [0.4.0rc1 候选方案「执行检查点」](0.4.0rc1-candidate-plan.md#执行检查点)的规定，只把版本、冻结提交与开发基线换成本版：执行后先只读回读再判定成功、确定失败或结果不明，结果不明时不重复写入；从推送冻结分支起 `main` 保持 D 不动，推送前、演练与正式运行触发前、批准前与快进前各核对一次；`sign` 开始前经授权放弃不登记台账，`sign` 开始但没有成功签发登记 `signing-failed`，签发成功后放弃登记 `abandoned` 并换用新版本号；演练原则上一次，失败属于已登记类型的托管基础设施故障时经单独授权可再开一次新演练或整次重跑，不得只重跑失败的 job（0021 第 3 条），判定层失败先查明根因；演练因计数、阶段或产物不一致失败时停下修复，修复须新的冻结提交，版本未消费可以沿用，从第 1 步重新执行。本候选第一次演练的判定层失败与第二次演练的条件见「第一次演练与修复」与待决定第 7 项。正式运行在 `sign` 之前因未分配托管执行机失败时，按 `0.6.0rc1` 的先例经单独授权另开一次正式运行；因测试或安装失败时先查明根因，不直接另开（`0.6.0rc1` 第一次正式运行未查明根因即继续，已登记为执行偏差）。任何失败、意外跳过、部分成功、SHA 不一致或必需检查缺失都立即停止，不重跑变绿；正式运行的 `sign` 一旦开始，该运行的任何 attempt 都不重跑（0021 第 3、20 条）。
