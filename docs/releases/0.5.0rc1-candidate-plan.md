## 停服段错误：再次做发布级风险接受

`0.4.0rc1` 的接受以它的 `crates/` 树为适用范围，本版 `crates/` 有变化，不自动适用。本版与 `0.4.0rc1` 的差异涉及服务生命周期（最终 flush、打开路径）与原生交界（新增一个 PyO3 函数），按调查记录「失效与继承」第二条不能继承，须由负责人**再次做发布级风险接受**：根因仍未查明，没有新的定向证据，依据是下面的只读核对。

相对 `0.4.0rc1` 冻结提交 `4fdffbb` 的核对结果：

1. **停服顺序本身逐字未变**：
   - `crates/core/src/db.rs` 的 `Drop for Db`、`enter`、`begin_shutdown`、`release_data_dir`、`close`、`close_nowait`、`finish_storage`、`finish_storage_inner` 没有改动（`db.rs` 的差异只在 `Db` 结构体字段、`new` / `with_flush_budgets`、写入后的自动 flush、`flush_handle`、打开集合、`cacheable_recovery_error` 与单测）；
   - `maintenance.rs`、`compute.rs` 没有改动；`crates/grpc/src/server.rs` 只改了单测；
   - `rust-toolchain.toml`、`pyproject.toml` 没有改动；`clippy.toml` 只新增禁止直接调用 `serde_json::from_*` 的 lint，不影响生成代码。
2. **服务生命周期与停服下游有改动**（都是安全 Rust）：
   - **绑定层**：`crates/py` 新增一个 `#[pyfunction]` `configure_flush_budgets`，由 `milvus_lite/__init__.py` 在导入时调用一次，把两个环境变量的预算写入进程级 `OnceLock`（只有第一次调用生效）；环境变量不是正整数时导入报 `ValueError`。该值由服务启动时的 `Db::new` 读取。它不在 `NativeServer.stop` 的路径上。
   - **最终 flush**：`finish_storage_inner` 调用的 `flush_handle` 成为 `flush_handle_with(…, schedule = true)` 的包装；冻结时按字节预算决定是否在活跃表为空时也提交一代（只有 delta、WAL 超预算时）。停服时 `schedule` 为真，与原先一样在提交后调度维护，而维护在关闭闸门后不再接受新任务。flush 前计算范数的代码改为按字段（`flat::row_norms`），不再要求有稠密向量列。
   - **打开路径**：打开集合时若旧版本留下的 WAL 或活跃表已超预算，在注册句柄之前先 flush 一次（`schedule` 为假，不进入维护队列）；WAL 中的 null 行由截断改为打开失败。
   - **停服窗口内的并发**：`close` 等待的在途 RPC 处理体里有新增代码（稀疏与 BM25 检索、分词、写入时生成输出字段、按字节预算的自动 flush）。它们不由停服函数调用，但可能在在途请求中与停服并发执行；检索计算仍只经 `Compute::for_each`。
3. **原生交界**：`crates/` 的差异里没有新增 `unsafe`、`extern "C"`、`libc::` 或 `transmute`，没有新建线程；唯一新增的 PyO3 交界是上面的 `#[pyfunction]`：参数为两个 `u64`，只写入进程级 `OnceLock`，不创建线程、不释放 GIL。
4. **依赖**：`Cargo.lock` 与 `0.4.0rc1` 逐字相同（冻结后只差三个本项目 crate 的版本）；Rust 1.98.1；CI 固定的 grpcio 1.84.0、protobuf 7.36.2、pymilvus 2.6.17 / 3.0.2 不变。
5. **新代码上没有再现**：自 `0.4.0rc1` 冻结分支（`4fdffbb`）的运行起至 D 的最后一次运行（含两端；`CI` 为 D 在 `main` 上的运行，`Compare` 为 D 在工作分支上的运行），`CI` 27 次、`Compare` 18 次，全部成功；期间没有运行发行工作流。常设崩溃现场采集持续开启。

理由：崩溃现场位于停服顺序的前段（停止信号、宽限等待、runtime 关闭、`db.close()` 开始到 flush 写文件之前），这段代码与它依赖的原生库没有变化；新增的 PyO3 函数只在导入时执行一次。上面第 5 项的运行统计只是辅助证据，不说明根因已排除。

**残余风险**（接受的对象，不因停服函数未变而消失）：最终 flush 与打开路径的新代码、停服窗口内的新在途处理体（稀疏与 BM25 检索、写入时生成输出字段、按字节预算的自动 flush）都没有托管机器上的定向压力证据。

负责人已于 2026-11-11 在本措辞下确认再次接受。

**适用范围**：谱系以 D 的 `crates/` 树 `73fb12ff…` 与 `Cargo.lock`（相对 D 只差三个本项目 crate 的版本）为准，工具链为 Rust 1.98.1，同进程 grpcio 为 CI 固定的 1.84.0。下一个候选以此为基准比较；`crates/`、`Cargo.lock`、工具链或上述停服相关依赖发生变化时，本接受不再自动适用，须由负责人再次决定。

冻结提交须同时满足以下条件，任何一项不满足即停止候选准备：

1. `crates/` 树与 D 相同（三个 crate 都用 `version.workspace`，版本切换不改 `crates/`）；
2. 相对 D，`Cargo.lock` 只有三个本项目 crate 的版本变化，其余包逐字不变；
3. Rust 工具链为 1.98.1，CI 的 SDK 约束不变；
4. 「相对 `4fdffbb` 的核对结果」中的停服顺序（第 1 项）、原生交界（第 3 项）与依赖（第 4 项）三项结论在冻结提交上仍然成立。

这是「根因未查明、再次显式风险接受」，不是修复，也不是继承。候选的任何运行再次出现停服路径 SIGSEGV，立即停止快进与发布并撤回接受，按调查记录的停止条件处理，不重跑掩盖。冻结提交号与上述条件的逐项核对结果写入候选验收记录。

| 变体 | 做法 | 轮数 | 结果 |
| --- | --- | --- | --- |
| A：超预算与最终 flush | 两个预算设为 4096 字节，建稀疏 + BM25 集合，反复 Upsert 频繁触发自动 flush，最后写入一小批后立即停服、由最终 flush 落盘，停服后重开核对行数 | 4265 | 全部正常退出，每轮重开后行数正确 |
| B：稀疏与 BM25 请求在途时停服 | 同一集合，3 个线程持续发稀疏检索、BM25 检索与写入（停服前每轮已完成约 600 组），在请求进行中停服；每轮一个新进程 | 4292 | 没有崩溃，没有其他非零退出 |

变体 B 前两次在同一进程里循环多轮，分别有 2 个与 4 个工作者以 Python 异常（退出码 1）中途退出：失败都在下一轮新建 `MilvusClient` 时，pymilvus 连接管理器对已停服务端口的连接走了恢复路径并被拒绝，属于同一进程反复起停服务时 SDK 的连接注册表状态，与本版已登记的「同一进程中释放后复用端口」同类，没有崩溃迹象；第一次运行时 shell 的代理变量还让本地 gRPC 连接经过了本机代理。因此改为每轮一个新进程、去掉代理变量后重跑，上表为重跑结果。托管机器（Linux x86_64）上的同类诊断未执行，本节不能替代它。

自动 flush 预算的两个环境变量（非法值在导入时报错、合法写法、小预算下反复 Upsert 触发 flush）由差分用例 [test_flush_budget_env.py](../../tests/differential/test_flush_budget_env.py) 与 3.x 对照，不另做预检；README 不列这两个变量，由发行说明写明名字与默认值（128 MiB / 256 MiB，见 0027）。

12. 发布后立即单独把台账改为 `released`，不等待其他文档；
13. 在 `main` 上触发公开下载核验，完成发布后记录（风险处置改为发布后口径）；临时与冻结分支打包验证后删除。

**外部写入的三态**、**`main` 冻结窗口**、**台账结局**与**运行预算**沿用 [0.4.0rc1 候选方案「执行检查点」](0.4.0rc1-candidate-plan.md#执行检查点)的规定，只把版本、冻结提交与开发基线换成本版：执行后先只读回读再判定成功、确定失败或结果不明，结果不明时不重复写入；从推送冻结分支起 `main` 保持 D 不动，推送前、演练与正式运行触发前、批准前与快进前各核对一次；`sign` 开始前经授权放弃不登记台账，`sign` 开始但没有成功签发登记 `signing-failed`，签发成功后放弃登记 `abandoned` 并换用新版本号；演练原则上一次，失败属于已登记类型的托管基础设施故障时经单独授权可再开一次新演练或整次重跑，不得只重跑失败的 job（0021 第 3 条），判定层失败先查明根因；演练因计数、阶段或产物不一致失败时停下修复，修复须新的冻结提交，版本未消费可以沿用，从第 1 步重新执行。任何失败、意外跳过、部分成功、SHA 不一致或必需检查缺失都立即停止，不重跑变绿；正式运行的 `sign` 一旦开始，该运行的任何 attempt 都不重跑（0021 第 3、20 条）。
