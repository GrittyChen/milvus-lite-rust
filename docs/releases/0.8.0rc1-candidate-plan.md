用户可见的变化与限制见发行说明（随冻结提交新增 `docs/releases/0.8.0rc1.md`）。性能变化只写 [0041 性能记录](../testing/0041-hnsw-performance.md)与[分配器保留内存](../testing/allocator-retention.md)实测的结论与口径（都只在原生 x86_64 服务器上测得，aarch64 与 macOS 没有同等测量）。发行说明须写明：

- **HNSW 的结论与口径**：100 万行、128 维、L2、top10、默认 ef 下，nq1 约 1.7 ms（本实现 FLAT 8.7 ms、2.5.1 FLAT 66–67 ms、3.x HNSW 约 740 ms），8 客户端并发 5000–6500 QPS（本实现 FLAT 139 QPS）；召回与 3.x 基本一致、略低（2.5.1 没有 HNSW，召回不可比）。只测了这一组参数，IP / COSINE、其他维度与 ef 没有同等的性能结论；段的大小只覆盖 10 万与 25 万行；构建期间前台检索的延迟只在 0041 第 1 步的原型上对 10 万行段测过，产品的 100 万行没有测。
- **HNSW 的代价**：图在后台构建，100 万行需 453–639 s，期间按 FLAT 检索，结果正确但较慢；3.x 在 load 时同步构建，约 20 s。
- **内存（[0001 约束 5](../decisions/0001-refactor-baseline.md#对-rust-实现的约束)须显式说明的突破）**：本仓对同机 2.5.1 的百万行 RSS 有两种口径，结论相反，发行说明须注明口径，不能只取其一：
  - [0041 的 `bench.py`](../testing/0041-hnsw-performance.md)（服务端进程树，load 就绪时 / 重开后）：本实现 HNSW 845–850 / 824–825 MB，本实现 FLAT 718–719 MB，2.5.1 FLAT 717–723 / 737–772 MB，3.x HNSW 约 2.8 GB。此口径下 HNSW 比 2.5.1 高约 18%（就绪时）/ 7%–12%（重开后）；nq1000 × limit 1000 的峰值 1090 对 1049 MB，高约 4%。
  - [分配器保留内存](../testing/allocator-retention.md)（flush 后 / 重开后，三轮中位数）：2.5.1 为 930.5 / 955.1 MiB，本实现 FLAT 为 742.3 / 734.4 MiB。此口径没有测 HNSW；按 0041 的 HNSW 增量（约 130 MB）推算仍低于 2.5.1，但这是推算，不是实测。
  - 两种口径的差别可能来自进程范围与取样时点，未查明。图构建期间的 RSS 峰值没有记录。
  - 写入期间的 RSS 峰值经行组上限降到 1229–1309 MiB，仍比同机 2.5.1（约 940 MiB）高约 290–370 MiB（[Parquet 行组与写入峰值](../testing/parquet-row-group-memory.md)「剩余的峰值」）。
  - 见「负责人的决定」第 8 项。
- **HNSW 与 3.x 的差异**：以[兼容性说明「索引」](../compatibility.md)为准，摘要写 AUTOINDEX 仍按 FLAT（需要 ANN 须显式建 HNSW）、`max(ef, 候选窗口)`、FLAT 回退条件、后台构建不阻塞 load、参数解析差异。
- **`.mlrs` 侧车**：本实现私有缓存，与 3.x 的 faiss 侧车互不读取，丢失或损坏时从数据重建；降级行为按本地检查的实测写。
- **`malloc_trim` 与行组**：Linux glibc 上 `malloc_trim` 的收益与代价（与之重叠的请求最多多等约 10 ms；重开后首次检索变慢；更大数据量与多集合没有测量）；macOS 无效，可设 `MallocLargeCache=0`。Parquet 行组上限降低 flush 峰值，文件布局与 3.x 不同但双向可读。
- **SDK**：两条线的测试版本改为 2.6.18 / 3.0.3；proto 仍取 3.0.2 对应的 commit，3.0.3 新增的字段本实现不读取；新增的行级权限 RPC 返回 UNIMPLEMENTED（3.x 同样不实现）。
- **已登记、未处理**：nq1000 × limit 1000 的大结果比 2.5.1 慢约 35%（与是否走图无关），只登记。
- **fork 的使用限制**：在已运行服务的进程中 fork 时，若父进程恰有线程在内部锁上等待，子进程为另一路径启停服务时仍可能挂起或崩溃；建议没有在途调用时 fork，或改用 spawn / forkserver（0003 的残余风险，见「补充计数中的失败、定因与修复」）。
- **停服段错误**：「根因未查明、显式风险接受」，并引用第二轮调查的新增证据（见下文）。

不纳入：Windows、PyPI、macOS 11 真机或真实断电、AUTOINDEX / HNSW_SQ / IVF 系列的 ANN 执行、TEXT_EMBEDDING、model rerank、boost `random_score`、`ARRAY<TIMESTAMPTZ>` / `ARRAY<GEOMETRY>`、0040（已搁置）、0039 决策 D 的两项后续、SDK 或 Python 矩阵缩减、正式运行复用演练产物。

候选矩阵按 0021 第 9 条与[阶段矩阵](../../tests/release/scorecard.py)完整执行，不缩减。兼容探针的上一版本由 `0.6.0rc1` 改为已发布的 `0.7.0rc1`，Linux x86_64 wheel 的 SHA256 `7c9f1011652c12626c71b701fb91de3ca237828ea066c47cf93a430fc05a1b53` 取自 `0.7.0rc1` Release 的 API 摘要，并与本地留存的 `SHA256SUMS` 一致；冻结前再核对一次。`PREVIOUS_*` 不在签发路径内（签发路径的定义见 0039 决策 A，「实施与验证」第 2 条有对应的自检用例），改它不影响签发路径判定。

## 补充计数中的失败、定因与修复

在原定的 D（`5ddcb73`）上补充计数时，fork 相关用例两次失败：

- `CI` [45111650713](https://github.com/GrittyChen/milvus-lite-rust/actions/runs/45111650713)（attempt 1）：`python-2.6.18 (ubuntu-24.04-arm)` 的 `test_fork_during_parallel_search` 中，父进程检索期间连续 fork 的三个子进程退出码为 0、-14、-14：后两个检索正常后在停服时挂起，被用例的 alarm 以 SIGALRM 结束；挂起子进程的数据目录只有 WAL，挂起在最后一次 flush 之前。
- `CI` [45240100646](https://github.com/GrittyChen/milvus-lite-rust/actions/runs/45240100646)（attempt 1）：`python-3.0.3 (ubuntu-24.04)` 的 `test_fork_child_owns_new_path` 中，子进程在 atexit 停服时 SIGSEGV，崩溃现场采集到的栈为 `NativeServer.stop → Server::stop → Db::close → GraphBuilder::stop → parking_lot::Condvar::notify_all_slow`。

**定因**（本地证据，2026-11-24）：在本机 aarch64 容器（ubuntu 24.04、CPython 3.10.22、pymilvus 2.6.18、grpcio 1.84.0，源码在容器内构建）中，父进程启动服务后 fork、子进程为新路径启停服务，`5ddcb73` 的构建 300 轮挂起 34 次；fork 前先等 0.5 秒仍挂起 9 次。挂起时子进程主线程卡在 `GraphBuilder::stop` 的 join，建图线程仍停在 `parking_lot::Condvar::wait`，收不到 `notify_all`。机理：parking_lot 把等待者登记在进程级的全局停车表里，节点放在等待线程的线程局部存储中；fork 后父进程停放线程的节点留在子进程的表里，子进程新建的线程可能复用其栈与 TLS（这一环是推断），队列随之损坏。0041 的建图线程大部分时间停在 parking_lot 条件变量上，使父进程在 fork 时几乎总有这样的线程；此前的常驻线程（维护线程的空闲等待用 `thread::park`，tokio 与 rayon-core 用 std 同步原语）没有这个问题。机理与残余风险见 [0003「fork」](../decisions/0003-in-process-server-lifecycle.md#fork)。早先在同一容器中用并行检索用例的形态 900 次 fork 没有复现，是因为那种形态下触发概率低。

## 停服段错误：再次做发布级风险接受

`0.7.0rc1` 的接受以 `crates/` 树 `4126edbc…` 为适用范围。本版 `crates/` 有变化，并且涉及停服顺序、服务生命周期中的新线程、fork 子进程停服的修复与原生交界（新增 `libc::malloc_trim`），按调查记录「失效与继承」第二条不能继承，须由负责人**再次做发布级风险接受**。根因仍未查明。第二轮调查（2026-11-22）没有找到根因，补充了 ASan 与停服间隙进程退出的证据，但 ASan 的基线早于 HNSW。

相对 `0.7.0rc1` 冻结提交 `eb4bbd3` 的核对结果：

1. **停服顺序有改动**：
   - [db.rs](../../crates/core/src/db.rs) 的 `close` 与 `close_nowait` 在等在途任务结束之后、`finish_storage` 与停维护之前，新增 `graphs.stop()`；`Drop for Db` 不等在途任务，`graphs.stop()` 是它的第一步，在 `maintenance.stop` 之前。`graphs.stop()` 置取消标志、清空建图队列，并 join 全部建图线程；`Db` 的最后一个强引用在建图线程上释放时，析构跳过对自身的 join。`enter`、`begin_shutdown` 与 `finish_storage` 的函数体没有改动。
   - [server.rs](../../crates/grpc/src/server.rs) 的改动只在 `#[cfg(test)]` 中（`cae3b5b` 的用例）；`crates/py` 没有改动。
   - [service.rs](../../crates/grpc/src/service.rs) 的 LoadCollection 改经 `Db::load_collection`（排队建图），仍在 `Db::enter` 之内。
2. **服务生命周期中的新线程与新任务**：
   - 每个 `Db` 在 `Db::new` 中启动 1–4 个建图线程（`cores / 8`，[graph_build.rs](../../crates/core/src/graph_build.rs)），空闲时停在 std 的条件变量上（`26564f8`；此前为 parking_lot，fork 子进程停服时挂起或段错误，见「补充计数中的失败、定因与修复」），只持 `Weak<Db>`，构建全程不持锁，发布时按「许可 → flush 锁 → 状态读锁」取锁（与 compaction 相同），图文件的编码与写出发生在持有共享写入许可之后、取 flush 锁之前，期间需要独占许可的操作（create、drop 等）会等待；图文件先写临时文件再改名。这些线程在停服时由上一项的 `graphs.stop()` 收尾，是停服窗口内新增的并发。
   - 维护线程在每轮 compaction 之后排队建图，并在队列已空、未停止、结果不是 Closed 时调用一次 `malloc_trim`（[maintenance.rs](../../crates/core/src/maintenance.rs)）；关闭排空时不调用。
   - 最后一次 flush 经新的 Parquet 行组切分写出（[parquet_file.rs](../../crates/core/src/storage/parquet_file.rs)）；flush 发布之后先释放冻结代的工作数据、再排维护（`a82bc41`），`finish_storage(true)` 的最终 flush 也走这条路径。flush 选文件名时的侧车检查（`storage/flush.rs`）、compaction 清理索引文件（`storage/compaction.rs`）与删除意图的文件清单（`storage/index_files.rs`）都把 `.mlrs` 纳入；恢复新增图临时文件 `*.hnsw.mlrs.tmp-*` 的清理（`.mlrs` 孤儿随既有侧车规则清理）。提交协议本身没有改动。维护线程的启动握手同样改用 std 的 `Mutex` / `Condvar`（`26564f8`）。冻结前按 `git diff eb4bbd3 D -- crates` 的全部 16 个文件逐个复核本节结论。
3. **原生交界**：本仓新增的 `unsafe` 只有 [allocator.rs](../../crates/core/src/allocator.rs) 的 `libc::malloc_trim(0)`（只在 Linux glibc 编译，附 `// SAFETY:`），在维护线程上执行，不在停服函数上。[hnsw.rs](../../crates/core/src/hnsw.rs) 与 [graph_build.rs](../../crates/core/src/graph_build.rs) 没有 `unsafe`。没有新增 `extern "C"`、`transmute` 或 PyO3 交界。
4. **依赖**：`Cargo.lock` 与 `0.7.0rc1` 逐字相同；Rust 1.98.1；grpcio 1.84.0、protobuf 7.36.2 不变；同进程的 pymilvus 升到 2.6.18 / 3.0.3（纯 Python，`65a6995` 核对了接入点与 dump 依赖的私有名逐字相同）。
5. **新增证据与覆盖边界**：
   - 第二轮 B 段在 `350cd31` 上以 ASan 跑 `tests/python` 765 项与差分 874 项，没有内存错误。Parquet 行组（`8cb1671`）在其覆盖内；`malloc_trim`（`a82bc41`）编入了插桩构建，ASan 期间是否实际调用没有计数；即使调用了，ASan 运行时接管了 `malloc`，trim 与真实 glibc 堆、在途分配的交互也没有被检验；HNSW（`bf025da` 起）不在覆盖内。
   - 第二轮 C 段的用例证明进程在停服的两个间隙死亡时，已应答的写入在重开后仍在。
   - 原定 D 上的补充计数暴露了 fork 子进程停服挂起与段错误，已定因并修复（见「补充计数中的失败、定因与修复」）；修复后的计数在新 D 上重做，运行号写入验收记录。
   - 自 `0.7.0rc1` 正式运行之后至 2026-11-23 补充计数开始前（04:24 UTC）：`CI` 40 次（36 次成功；2 次失败与 2 次取消见「重新计数」）、`Compare` 26 次（24 次成功、2 次取消；成功的运行中 2 次最终 attempt 为 2，是 `0.7.0rc1` 台账分支上未分配 macOS 执行机的取消重跑，已记入 `0.7.0rc1` 验收记录）、发行工作流 1 次（0039 的失败注入，按预期在前置检查失败）。冻结前逐个核对失败、取消与多 attempt 运行的 job 中没有以信号结束的，结果写入候选验收记录。常设崩溃现场采集持续开启。

理由：**本次的依据与 `0.7.0rc1` 不同。** `0.7.0rc1` 的依据是停服顺序逐字未变；本版在崩溃现场所在的窗口（停止信号、宽限等待、runtime 关闭、`db.close()` 开始到 flush 写文件之前）中新增了 `graphs.stop()`，窗口的内容变了。本次的依据是：新增的建图代码是安全 Rust，建图线程只持 `Weak<Db>`，构建过程不持锁、每插入 256 行检查一次取消；发布在 `Db` 的闸门与既有锁序之内（闸门已关闭时拒绝发布，否则先占在途计数，再取写入许可、flush 锁与状态读锁）；`graphs.stop()` 以取消标志与 join 收尾；`malloc_trim` 只在维护线程上执行，排空轮次不调用，但维护线程已越过空闲检查时，正在执行的 trim 仍可能与停止重叠（列入残余风险）。上面第 5 项是辅助证据，不说明根因已排除。候选验收记录照此写明，不沿用「停服路径未变」的措辞。

**残余风险**（接受的对象）：`0.7.0rc1` 接受的全部残余风险；加上建图线程在停服窗口内的取消与 join、`malloc_trim` 与在途请求、与停止的重叠（作用于整个宿主进程的堆）、多行组 Parquet 的最后一次 flush、HNSW 图文件的写出与改名，都没有托管机器上的定向停服压力证据；HNSW 的代码不在任何一次 ASan 运行的覆盖内（第 6 项可选补充）；fork 时父进程里仍停放在 parking_lot 上的等待者（如争用集合锁的请求线程、`close_nowait` 的收尾线程）会在子进程的停车表里留下残留节点，子进程启停服务时仍可能挂起或崩溃（此前就存在，常驻线程这一高频来源已由 `26564f8` 消除，见 0003）。

**外部写入的三态**、**`main` 冻结窗口**、**台账结局**与**运行预算**沿用 [0.4.0rc1 候选方案「执行检查点」](0.4.0rc1-candidate-plan.md#执行检查点)的规定，只把版本、冻结提交与开发基线换成本版：执行后先只读回读再判定成功、确定失败或结果不明，结果不明时不重复写入；从推送冻结分支起 `main` 保持 D 不动，推送前、演练与正式运行触发前、批准前与快进前各核对一次；`sign` 开始前经授权放弃不登记台账，`sign` 开始但没有成功签发登记 `signing-failed`，签发成功后放弃登记 `abandoned` 并换用新版本号；演练原则上一次，失败属于已登记类型的托管基础设施故障时经单独授权可再开一次新演练或整次重跑，不得只重跑失败的 job（0021 第 3 条），判定层失败先查明根因；演练因计数、阶段或产物不一致失败时停下修复，修复须新的冻结提交，版本未消费可以沿用，从第 1 步重新执行。正式运行在 `sign` 之前因未分配托管执行机失败时，经单独授权另开一次正式运行；因测试或安装失败时先查明根因，不直接另开。任何失败、意外跳过、部分成功、SHA 不一致或必需检查缺失都立即停止，不重跑变绿；正式运行的 `sign` 一旦开始，该运行的任何 attempt 都不重跑（0021 第 3、20 条）。

## 证据边界

候选结果、来源证明与透明日志、Release 附件为公开产物；工作流产物有保留期限；签发前的完整候选证据集与本地预检的原始输出由负责人本地留存（[证据的存放与复核范围](../testing/README.md)）。HNSW 的性能与召回结论只来自 x86_64 服务器上的本地留存；第二轮 ASan 只有本地证据。
