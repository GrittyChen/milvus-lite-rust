# 0.8.0rc1 发行范围与说明

本文固定本版本的范围、限制与安装说明，作为 GitHub Release 正文的唯一内容来源，不记录随发布推进变化的状态。冻结提交与执行结果由 Release 附件中的候选结果给出，七个附件的哈希由 Release 正文的候选证据一节与链接的候选验收记录给出；是否已发布及公开下载结果以该正文为准。

这是以 Rust 实现的非官方 milvus-lite，与 Milvus／Zilliz 无隶属关系。该版本为预发布试用，不建议用于生产；RC 阶段通过本项目 GitHub Release 分发，不上传 PyPI。以下安装入口须等对应 Release 正式发布后使用。

## 相对 0.7.0rc1 的变化

参照仍为官方 milvus-lite `1320d26ec3d88b23b525e774df6e3c8e7c208f81`，与参照的逐项差异登记在[兼容性说明](../compatibility.md)、[0006 差异表](../decisions/0006-m2-scope.md#与-3x-的差异)与各项决策（HNSW 见 [0041](../decisions/0041-hnsw.md)）。

- **HNSW 建图检索**（[0041](../decisions/0041-hnsw.md)）：显式建了 HNSW 索引的稠密向量字段，按段在后台建本实现自己的图（纯 Rust，不依赖 faiss），检索在图上进行；参数 `M`、`efConstruction`、`ef` 的含义与默认值（16、200、64）与官方 3.x 相同。结果是近似的：返回的每一行都满足过滤与删除可见性，距离与 FLAT 对同一行算出的值逐位相同，但可能漏掉真正更近的行。AUTOINDEX（pymilvus 快速建表使用）、HNSW_SQ、IVF_FLAT、IVF_SQ8 仍按 FLAT 精确执行；需要 ANN 时请显式建 HNSW。图写在 `indexes/<段>.<字段>.hnsw.mlrs`，见下文「兼容性与已知限制」。
- **内存**：Linux（glibc）上后台维护每轮结束后调用 `malloc_trim`，把 flush、合并与打开集合释放的空闲内存交还系统（[分配器保留内存](../testing/allocator-retention.md)）；Parquet 写入改为每个行组最多 65536 行、约 32 MiB，降低 flush 写文件时的内存峰值（[Parquet 行组与写入峰值](../testing/parquet-row-group-memory.md)）。建了 HNSW 时内存反而更高，见下文「兼容性与已知限制」。
- **SDK**：两条线的测试版本改为 pymilvus 2.6.18 与 3.0.3。proto 仍取 3.0.2 对应的 commit，3.0.3 新增的字段本实现不读取；新增的行级权限 RPC 返回 UNIMPLEMENTED，官方 3.x 同样不实现。

没有新增或升级依赖，`Cargo.lock` 除本项目三个 crate 的版本外与 `0.7.0rc1` 相同；Rust 1.98.1 工具链不变。`0.7.0rc1` 及更早版本的能力（jieba 分词器、nullable 稠密向量、dump、过滤中的算术、GEOMETRY、公共 function chain、`text_match` 与分析器属性、稀疏向量、BM25、多向量字段、集合管理与多数据库、分组检索、TIMESTAMPTZ 与 `timezone`、HybridSearch 与 rerank、显式分区与 partition key、标量 nullable / 默认值、ARRAY、Query iterator、range search / Search iterator V1、JSON 写入优化）继续保留，各项说明见 [0.7.0rc1 发行说明](0.7.0rc1.md)及其链接的各版本说明。

## 与 3.x 的主要已登记差异

完整清单与理由见[兼容性说明「索引」](../compatibility.md#索引)与 [0041](../decisions/0041-hnsw.md)，下面只摘要本版新增的部分：

- **实际束宽取 `max(ef, 候选窗口)`**；某段的图返回不足窗口条数时（如过滤后剩下的行在图上走不到），该段改走 FLAT，因此与 FLAT 一样返回足 k 条。官方 3.x 直接使用 ef，在 k 或候选窗口大于 ef 时召回明显下降，甚至返回不足 k 条。
- **FLAT 回退**：行数不足 1 万的段、内存中尚未落盘的数据、尚未建好图的段，以及过滤后有效行不多于实际束宽 800 倍的段，按 FLAT 精确检索；图搜索的距离计算超过该段有效行数时也改走 FLAT。3.x 只在有效行不多于 k 时才精确检索。
- **后台构建**：load 与 CreateIndex 不等图建完，建好之前按 FLAT 检索，建好后自动切换；DescribeIndex 始终显示完成，没有建图进度可查。构建失败时记录日志并重试，期间按 FLAT 检索，load 不报错。官方 3.x 首次 load 与 loaded 状态下的 CreateIndex 会同步建完，构建失败时 load 报错。
- **参数解析**：`M`、`efConstruction`、`ef` 只接受整数、有限浮点数（截断）、ASCII 十进制整数字符串与布尔；其他写法以及 `M` 超过 512、`efConstruction` 超过 100000 时，不建图或不用图，按 FLAT 执行，不报错。3.x 对无法解析的值报错，对合法的大值照常构建。
- **AUTOINDEX**：官方 3.x 实际走 HNSW；本实现按 FLAT，召回不低于 ANN，数据量大时更慢。

## 相对 0.7.0rc1 新拒绝或改变的行为

- **HNSW 字段的检索结果**：原先按 FLAT 返回精确结果，现在图建好后返回近似结果，可能漏掉真正更近的行（见上节）。需要精确结果的调用方可改用 FLAT 定义。
- **Linux 上的 `malloc_trim`**：作用于整个进程的堆，宿主 Python 的空闲块也会交还；trim 期间与之重叠的请求最多多等约 10 ms，重开后第一次检索变慢（百万行 12.2 ms 变为 20.8 ms，同机 2.5.1 为 82.4 ms）；只测了 10 万与 100 万行的单集合，更大数据量与多集合没有测量。macOS 上无效，见[使用说明](../usage.md#后台维护与内存)。
- **数据文件的行组**：新写出的 Parquet 文件可能有多个行组；官方 3.x（pyarrow 15 与 25）与 `0.7.0rc1` 都照常读取，文件大小约增 2%，可能让个别文件落进不同的合并档。

## 兼容性与已知限制

- **数据格式**：数据文件沿用 schema.json、Arrow IPC WAL、Parquet 与 manifest format 2 编码。新增的 `.mlrs` 图文件（格式版本 1）是本实现私有的缓存，不进 manifest 与 snapshot，丢失、损坏或与段不符时从数据重建；官方 3.x 忽略它，本实现也不读写 3.x 的 `.idx`。删除意图与清空意图的文件清单自本版起可以列出 `.mlrs`（[0002](../decisions/0002-data-dir-compat.md)）。已发布的 `0.7.0rc1` 读取本版写出的目录，由候选验收在 Linux x86_64 上核验。
- **降级到 0.7.0rc1 及更早**（macOS arm64 实测，**降级前先用本实现正常打开并关闭一次**）：
  - 普通与 partition key 集合（只在 WAL、已 flush、flush 后删除并追加三种状态）、7 万行 flush 后有多个行组的集合，都可以正常读写，再升级回来数据完整。
  - HNSW 集合在旧版按 FLAT 精确检索，图文件原样保留、不读取；旧版合并段后，被合并段的图成为孤儿，升级回来时清理并在后台重建，其余图直接读入。
  - HNSW 字段的 DropIndex 或清空中断后又降级时，旧版读到列出 `.mlrs` 的意图文件会判为格式不符，按 [0014](../decisions/0014-index-definitions-and-filter-expressions.md) / [0023](../decisions/0023-aliases-rename-truncate-databases.md) 的人工恢复处理。
  - 降级到 `0.6.0rc1` 及更早的拒绝边界（jieba、nullable 向量等）继续适用，见 [0.7.0rc1 发行说明](0.7.0rc1.md#兼容性与已知限制)。
- **HNSW 的性能与代价**（[0041 性能记录](../testing/0041-hnsw-performance.md)，只在原生 x86_64 服务器（AMD EPYC 7702，16 核）上测得，aarch64 与 macOS 没有同等测量；128 维、L2、top10、默认 ef）：
  - 100 万行时单条检索约 1.7 ms（本实现 FLAT 8.7 ms、2.5.1 FLAT 66–67 ms、3.x HNSW 约 740 ms），8 个客户端并发 5000–6500 QPS（本实现 FLAT 139 QPS）；召回与 3.x 基本一致、略低（2.5.1 没有 HNSW）。IP / COSINE、其他维度与 ef 没有同等的性能结论；段的大小只覆盖 10 万与 25 万行。
  - 图在后台构建：100 万行需 453–639 s，期间按 FLAT 检索，结果正确但较慢；3.x 在 load 时同步构建，约 19–21 s。构建期间前台检索的延迟在产品的 100 万行上没有测量。
- **内存与 2.5.1 的比较（两种测量口径对 2.5.1 自身的读数不一致：717–723 MB 对 930.5 MiB，HNSW 与 2.5.1 的大小关系因此取决于口径；差异原因未查明，另立调查；项目目标见 [0001 约束 5](../decisions/0001-refactor-baseline.md#对-rust-实现的约束)）**：
  - 按 0041 基准的口径（服务端进程树，load 就绪时 / 重开后）：建了 HNSW 时百万行 RSS 为 845–850 / 824–825 MB，比同机 2.5.1 FLAT 的 717–723 / 737–772 MB 高约 18% / 7%–12%，也略高于项目目标的约 0.8 GB；这是本版显式登记的超出。nq1000、limit 1000 的峰值 1090 MB，比 2.5.1 的 1049 MB 高约 4%。
  - 按[分配器保留内存](../testing/allocator-retention.md)的口径（flush 后 / 重开后，三轮中位数）：2.5.1 为 930.5 / 955.1 MiB，本实现 FLAT 为 742.3 / 734.4 MiB；这一口径没有测 HNSW，按 HNSW 约 130 MB 的增量推算低于 2.5.1，但不是实测。
  - 百万行写入期间的 RSS 峰值经行组上限降到 1229–1309 MiB，仍比同机 2.5.1（约 940 MiB）高约 290–370 MiB。图构建期间的峰值没有记录。反复写删时被覆盖的旧版本行要等合并回收，内存随轮次增长；同样负载下三方都增长，本实现增长最慢（单轮测量），见[使用说明](../usage.md#后台维护与内存)与搁置的 [0040](../decisions/0040-reclaim-superseded-rows.md#搁置理由)。
- **停服路径的一次段错误：根因未查明，显式风险接受，不是修复。** 持续集成试点中，Linux x86_64 的一次差分运行在停服路径上出现过一次进程段错误；此后 valgrind、停服时序定向压力、AddressSanitizer（`tests/python` 与差分共 1639 项）与此后的运行都没有再现（[调查记录](../testing/shutdown-segfault-investigation.md)）。本版的停服窗口有变化：最后一次 flush 之前新增等待 HNSW 建图线程退出，Linux 上新增 `malloc_trim` 调用，HNSW 的代码不在 AddressSanitizer 的覆盖内。候选准备中另有一次 fork 子进程停服时的段错误，发生在本版新增的 HNSW 建图线程上，已定因并在发布前修复；它与本条那次未查明的段错误是否同源没有证据，不按本条处理。本版不继承 `0.7.0rc1` 的接受，由负责人**再次做显式发布级风险接受**，依据与适用范围见[候选方案](0.8.0rc1-candidate-plan.md#停服段错误再次做发布级风险接受)；候选或后续运行再次出现即撤回这一接受，转回根因调查。
- **大结果检索**：nq1000、limit 1000 时，本实现 FLAT 与 HNSW 都比 2.5.1 慢约 35%（100 万行 6.9–7.1 s 对 5.2 s），与是否走图无关，只登记。
- **fork 的使用限制**：在已运行服务的进程中 fork 时，若父进程恰有线程在内部锁上等待（如并发请求争用同一集合），子进程为另一路径启停服务时仍可能挂起或崩溃；建议在没有在途调用时 fork，或改用 spawn / forkserver，见 [0003「fork」](../decisions/0003-in-process-server-lifecycle.md#fork)。
- nullable 向量与官方 3.x 的互通限制（3.x 需要 pyarrow 26 及以上才能打开含空值的集合，即使在 pyarrow 26 上多行输出中排在空值之后的向量会错位）、批量检索的性能与公平性、jieba 的资源、过滤路线、距离误差预算、Search iterator V1、SDK 端点 schema 缓存与 dump 的已知限制沿用 [0.7.0rc1 发行说明](0.7.0rc1.md#兼容性与已知限制)。
- 除 HNSW 外，已接受的 ANN 定义不意味着实际 ANN；INVERTED 定义的执行仍为扫描。存量定义、DropIndex 及持久化未确认时的封锁与恢复沿用 [0014](../decisions/0014-index-definitions-and-filter-expressions.md) 与[兼容性说明](../compatibility.md#索引变更后的人工恢复)。
- LoadPartitions / ReleasePartitions、snapshot RPC、TEXT_EMBEDDING、model rerank、boost 的 `random_score`、`ARRAY<TIMESTAMPTZ>` 与 `ARRAY<GEOMETRY>`、AddCollectionField／AlterCollectionSchema、行级权限 RPC 不在本版范围。
- 稀疏向量检索在 nq 较大时仍慢于 2.5.1（[0030 验收](../decisions/0030-sparse-vectors.md#验收)中 nq=32 约慢 27%），单条查询与过滤检索追平或更快。JSON 写入优化的收益限于 [0018 已审同机工况](../testing/0018-json-write-acceptance.md)。

## 平台、解释器与证据边界

四个平台均为标准层，在发行工作流中执行相同的适用门槛（[0021](../decisions/0021-release-build-in-ci.md) 第 9、14–16 条，编排按 [0039](../decisions/0039-release-speedup.md)）：Linux x86_64 与 arm64 在 GitHub 托管机器上固定的 manylinux_2_28 容器（glibc 2.28）中执行，macOS arm64 在 `macos-15`、macOS x86_64 在 `macos-15-intel` 上原生执行。各平台覆盖正式 wheel 的归档与二进制检查、Rust 默认与故障注入构建的单测、CPython 3.10 与 3.15 上两条 SDK（pymilvus 2.6.18／3.0.3）的端到端全套、CPython 3.10 上两条 SDK 的 dump 端到端、3.11–3.14 联合冒烟、正式 wheel 上与官方 3.x（`1320d26`，NumPy 2，参照侧装 jieba 0.42.1）的差分（含 dump）及 Arrow 15/25/26 数据互通，以及故障注入测试包的恢复专项；Linux 另验 LOCK、strace 与容器 PID 1，Linux x86_64 另验已发布 `0.7.0rc1` 读取本版写出的目录。sdist 另验构建根、PEP 517 安装、Rust 1.89 MSRV 与各项构建期拒绝。

HNSW 自身没有平台相关代码，打分复用 FLAT 的距离核；0041 第 1 步的原型（L2）在 arm64 与 x86_64 上对同一输入建出的图哈希相同，产品代码没有同等的跨平台比对。性能与召回的结论只来自 x86_64 服务器。

x86_64 的 AVX2 距离核（FLAT 与 HNSW 的打分都经过它）与基线版本由逐位比对的单测在支持 AVX2 的执行机上同时执行；托管执行机都支持 AVX2，不支持 AVX2 的 x86_64 CPU 上选用基线版本的分派分支没有端到端证据。

Windows、free-threaded 和非 CPython 在构建时明确拒绝。musl、其它架构及较低 glibc 的自行构建仅为实验性尝试。Linux 容器的宿主内核是托管机器的较新版本，托管机器没有 macOS 11；二进制的最低系统字段由检查核对，不等于真机最低系统、真实断电或任意文件系统持久化已经验证。

FI wheel 仅供隔离验收，不随发行分发。旧线是否继续发修复版按实际需求另定；本候选不承诺持续维护多个版本线，也不自动将任何 RC 转为正式版。

## 安装（对应 Release 发布后）

本包与官方 milvus-lite 共用 `milvus_lite` 模块，不可同时安装；不用 `pymilvus[milvus-lite]`。

```bash
python -m pip uninstall milvus-lite
python -m pip install pymilvus
python -m pip install --no-index --only-binary :all: --find-links https://github.com/GrittyChen/milvus-lite-rust/releases/expanded_assets/v0.8.0rc1 milvus-lite-rust==0.8.0rc1
```

也可从 [v0.8.0rc1 Release](https://github.com/GrittyChen/milvus-lite-rust/releases/tag/v0.8.0rc1) 下载本平台 wheel 与 SHA256SUMS，核对后安装：

```bash
shasum -a 256 -c --ignore-missing SHA256SUMS && python -m pip install --no-index ./milvus_lite_rust-0.8.0rc1-*.whl
```

Linux 可用 sha256sum 执行同样的校验。需要核对来源时，在下载目录用已登录的 GitHub CLI 执行本平台对应的一行，成功即说明该文件由本仓库的发行工作流签发：

```bash
gh attestation verify milvus_lite_rust-0.8.0rc1-cp310-abi3-manylinux_2_28_x86_64.whl --repo GrittyChen/milvus-lite-rust --signer-workflow GrittyChen/milvus-lite-rust/.github/workflows/release.yml
gh attestation verify milvus_lite_rust-0.8.0rc1-cp310-abi3-manylinux_2_28_aarch64.whl --repo GrittyChen/milvus-lite-rust --signer-workflow GrittyChen/milvus-lite-rust/.github/workflows/release.yml
gh attestation verify milvus_lite_rust-0.8.0rc1-cp310-abi3-macosx_11_0_arm64.whl --repo GrittyChen/milvus-lite-rust --signer-workflow GrittyChen/milvus-lite-rust/.github/workflows/release.yml
gh attestation verify milvus_lite_rust-0.8.0rc1-cp310-abi3-macosx_11_0_x86_64.whl --repo GrittyChen/milvus-lite-rust --signer-workflow GrittyChen/milvus-lite-rust/.github/workflows/release.yml
```

sdist 的 Python 下限及 Rust 1.89 MSRV 沿用 [源码回退门槛](../../tests/packaging/README.md#源码与拒绝门槛)，不引导从 PyPI 按项目名解析本包。dump 需要的 `pymilvus[bulk_writer]` 另行安装，见[使用说明](../usage.md#导出-dump)。
