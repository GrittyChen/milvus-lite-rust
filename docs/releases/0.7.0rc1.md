# 0.7.0rc1 发行范围与说明

本文固定本版本的范围、限制与安装说明，作为 GitHub Release 正文的唯一内容来源，不记录随发布推进变化的状态。冻结提交与执行结果由 Release 附件中的候选结果给出，七个附件的哈希由 Release 正文的候选证据一节与链接的候选验收记录给出；是否已发布及公开下载结果以该正文为准。

这是以 Rust 实现的非官方 milvus-lite，与 Milvus／Zilliz 无隶属关系。该版本为预发布试用，不建议用于生产；RC 阶段通过本项目 GitHub Release 分发，不上传 PyPI。以下安装入口须等对应 Release 正式发布后使用。

## 相对 0.6.0rc1 的变化

参照仍为官方 milvus-lite `1320d26ec3d88b23b525e774df6e3c8e7c208f81`，与参照的逐项差异登记在 [0006 差异表](../decisions/0006-m2-scope.md#与-3x-的差异)。新增四组对外能力：

- **jieba 分词器**（[0036](../decisions/0036-jieba.md)）：BM25 输入字段的 `analyzer_params` 可以把 `tokenizer` 或 `type` 写成 `"jieba"`，或写成 `type` 为 `"jieba"`、可带 `mode` 与 `dict`（用户词）的对象：`mode` 先按 `mode or "search"` 取值，等于字符串 `"search"` 时用搜索模式，其余取值（如 `"exact"`、`"SEARCH"`）按精确模式，取值规则与官方 3.x 相同。内置 jieba 0.42.1 的词典与 HMM 模型，不需要另装 jieba；切分在对照过的输入上与 jieba 0.42.1 逐词相同。`text_match` 仍固定用 standard 分词。
- **nullable 稠密向量**（[0038](../decisions/0038-nullable-dense-vectors.md)）：FLOAT_VECTOR 字段可以 `nullable=True`，写入时给 None 或省略该字段即为空值，整批都为空也能写入；空值读出为 None，Search、range、分组、search iterator、HybridSearch 的各路与 function chain 都不返回该字段为空的行（多向量集合只在被检索的字段上排除）；partial upsert 省略该字段时保留原值。按真实 Milvus 的语义处理，与官方 3.x 不同（见下节）。
- **`milvus-lite dump` 导出命令**（[0037](../decisions/0037-dump.md)）：把一个集合的全部可见行导出为 Milvus BulkWriter 的 JSON 文件，`-d` 在进程内打开数据目录，`--uri` 连接正在运行的服务。需要另装 `pymilvus[bulk_writer]`，本包不声明这一依赖。失败时一行说明、退出 1，参数错误退出 2，SIGINT / SIGTERM 清理后退出 130 / 143；参数与清理规则见 [README](../../README.md#导出-dump)。
- **raw gRPC 的 HasCollection 与 CheckHealth**：HasCollection 与 3.x 一样先确认数据库、再解析别名，只看集合目录与 `schema.json` 是否存在、不打开集合；CheckHealth 总是报告健康。pymilvus 的 `has_collection` 走 DescribeCollection，不受影响。

另外，x86_64 上 FLAT 的距离计算在 CPU 支持 AVX2 时改用以 AVX2 编译的版本（运行时检测，不启用 FMA，与基线版本逐位相同），大批量检索改为按查询片复用候选（[0005](../decisions/0005-search-thread-model.md) 修订）；检索结果逐位不变。实测结论与口径见下文「兼容性与已知限制」。

新增依赖：jieba-rs 0.11.0 及其依赖 jieba-macros 0.11.0、bytecount 0.6.9、rustc-hash 2.1.3，均为纯 Rust，没有构建脚本与 C 代码；jieba 的词典与 HMM 模型随包分发，许可文件加入发行包。Rust 1.98.1 工具链不变。`0.6.0rc1` 及更早版本的能力（过滤中的算术、GEOMETRY、公共 function chain、`text_match` 与分析器属性、稀疏向量、BM25、多向量字段、集合管理与多数据库、分组检索、TIMESTAMPTZ 与 `timezone`、HybridSearch 与 rerank、显式分区与 partition key、标量 nullable / 默认值、ARRAY、Query iterator、range search / Search iterator V1、JSON 写入优化）继续保留，见 [0015](../decisions/0015-nullable-defaults-and-array.md)–[0018](../decisions/0018-json-write-normalization.md)、[0023](../decisions/0023-aliases-rename-truncate-databases.md)–[0035](../decisions/0035-function-chains.md)。

## 与 3.x 的主要已登记差异

完整清单与理由见 [0006 差异表](../decisions/0006-m2-scope.md#与-3x-的差异)，下面只摘要本版新增的部分：

- **jieba 用户词**：官方 3.x 把用户词加进进程全局的词典，每次打开再加一遍，一个集合的用户词会影响同一进程里的其他 jieba 集合；本实现每个集合一份词典、每项加一次。用户词中能匹配的词按每一项累加（重复项也计入）合计超过 100 万个字符，或词频总和超出 64 位整数时建表报错，3.x 没有这两个上限。官方 3.x 建的带用户词的 jieba 集合（或写入它的 3.x 进程里还有其他带用户词的集合），本实现照常打开，但查询与新写入按本实现的切法，与已存的部分词项匹配不上，召回可能下降。官方 3.x 没装 jieba 时打不开 jieba 集合，本实现内置。见 [0036「与 3.x 的差异」](../decisions/0036-jieba.md#与-3x-的差异)。
- **nullable 向量的语义**：官方 3.x 写入时把空值换成零向量，读出 `[0.0, ...]`，并让这些行按零向量参与检索；本实现存为空值、读出 None、检索排除。3.x 对整批为空的写入报错，本实现接受。原始 gRPC 以 `valid_data` 为空值的唯一依据。dump 导出空值为 `null`（3.x 导出零向量）。空行在内存中按 dim 补零，一次写入的行数 × dim 不能超过 6400 万（与一个全部有效的请求所能携带的向量数据相同），超过时报错并提示拆分批量，3.x 没有这个限制。见 [0038「与 3.x 的差异」](../decisions/0038-nullable-dense-vectors.md#与-3x-的差异)。
- **dump**：带 BM25 function 或 ARRAY VARCHAR 字段的集合在 3.x 上导出失败，这里正常导出；3.x 在批大小为 0 时报告成功却导出 0 行、在写文件失败时报告成功却没有文件、遇到 NaN 或 Infinity 时写出不合法的 JSON，这里分别拒绝参数、报告失败、报错并指出字段与主键；3.x 失败时打印 traceback，这里一行说明。见 [0037](../decisions/0037-dump.md)。
- **HasCollection**：名字含路径分隔符（如越出集合目录的 `../collections/c`、子路径、尾斜杠）或只差大小写、指向目录的符号链接、`schema.json` 是目录时，与 DescribeCollection 一样按不存在处理；3.x 按拼出的路径判断，返回 true。

## 相对 0.6.0rc1 新拒绝或改变的行为

- **原先失败的请求现在执行**：HasCollection 与 CheckHealth 原先返回 UNIMPLEMENTED；使用 jieba 分词器、带 nullable 向量字段的建表原先返回 UNIMPLEMENTED，官方 3.x 建的这两类集合原先打不开，现在照常打开（3.x 写下的空向量已是零向量，本实现读出零向量）；`milvus-lite dump` 原先报 argparse 的 `invalid choice`（退出码 2）。依赖这些请求必然失败的调用方需要调整。
- **向量默认值的报错文案**：仍返回 UNIMPLEMENTED，信息由 `nullable vectors and vector defaults: nullable vectors and vector defaults are not supported in this build of milvus-lite-rust yet` 改为 `vector defaults: not supported in this build of milvus-lite-rust`。
- **首次写入空向量时的提示**：服务首次在一个集合中写入空向量时，向 stderr 打印一行提示，说明官方 3.x 在 pyarrow 低于 26 时无法打开该集合（每次打开集合后只打印一次）。
- **大批量检索期间的单条检索**：有大批量检索在进行时，后到的单条检索要等更长时间（见下文的实测数字），这是换取批量吞吐的取舍；结果不变。

## 兼容性与已知限制

- **数据格式**：数据文件沿用 schema.json、Arrow IPC WAL、Parquet 与 manifest format 2 编码。jieba 的 `analyzer_params` 与 3.x 相同地保存在 `schema.json` 中。nullable 向量的空值存为 Arrow null（父级 null、子元素为零），官方 3.x 需要 pyarrow 26 及以上（因此需要 Python 3.11 及以上）才能打开含空值的集合；更低版本时整个集合无法 load，只有 WAL 含空值时能打开但 flush 失败，数据仍在，可用本实现或升级 pyarrow 后读取。即使在 pyarrow 26 上，3.x 的多行输出中排在空值之后的向量会错位，尚未 flush 的空行按零向量参与检索，对这些行做 upsert 会把空值改成零向量。没写过空值的 nullable 集合不受影响。已发布的 `0.6.0rc1` 读取本版写出的目录，由候选验收在 Linux x86_64 上核验。
- **降级到 0.6.0rc1 及更早**（macOS arm64 实测）：
  - 普通与 partition key 集合（只在 WAL、已 flush、flush 后删除并追加三种状态）可以正常读写，再升级回来数据完整。
  - 使用 jieba 分词器的集合在旧版 load 时明确返回 UNIMPLEMENTED（`jieba tokenizer: the jieba tokenizer is not supported in this build of milvus-lite-rust`）；带 nullable 向量字段的集合（无论是否写过空值）明确返回 UNIMPLEMENTED（`field "v" has unsupported attributes`）。两类集合都可以 drop，数据保留，升级回来后照常可用。HasCollection、CheckHealth 与 dump 在旧版不可用，不涉及数据。
  - 降级到 `0.5.0rc1` 及更早的拒绝边界（GEOMETRY 等）继续适用，见 [0.6.0rc1 发行说明](0.6.0rc1.md#兼容性与已知限制)；更早版本的边界见该文链接的各版本说明。
- **停服路径的一次段错误：根因未查明，显式风险接受，不是修复。** 持续集成试点中，Linux x86_64 的一次差分运行在停服路径上出现过一次进程段错误；此后 valgrind 检查与停服时序定向压力（合计 41568 轮）都没有再现，此后的运行中也没有再现（检索范围见候选方案）。本版相对 `0.6.0rc1` 停服顺序逐字未变，但差异涉及原生交界与服务生命周期的新用法：x86_64 上 AVX2 距离核的 `unsafe` 分派、jieba 依赖的 bytecount 中带 `unsafe` 的 SIMD、dump 在进程内启停服务并改变信号处置，以及 jieba 分词、nullable 向量编解码与新的批量检索任务模型等在途处理体，都没有托管机器上的定向停服压力证据。本版不继承 `0.6.0rc1` 的接受，由负责人**再次做显式发布级风险接受**，依据与适用范围见[候选方案](0.7.0rc1-candidate-plan.md#停服段错误再次做发布级风险接受)；候选或后续运行再次出现即撤回这一接受，转回根因调查（[调查记录](../testing/shutdown-segfault-investigation.md)）。
- **批量检索的性能**（[批量检索专项记录](../testing/batch-search-performance.md)第三轮，只在原生 x86_64 服务器（AMD EPYC 7702，16 个物理核，conservative 调频）上测得，aarch64 与 macOS 没有同等测量；128 维 FLAT L2、全存活已提交库、top10；对照只有 2.5.1 与上一构建，不是对官方 3.x 的结论）：100 万行 nq100 端到端快于 2.5.1；10 万行只在 CPU 频率升满后快于 2.5.1，在基准的 `m2` 口径与短样本下仍慢约 20%–26%。AVX2 版本只在 x86_64 且 CPU 支持时生效。代价是公平性：100 万行下有大批量检索在进行时，后到的单条检索 p50 / p99 从 12.5 / 19.8 ms 变为 21.1 / 27.1 ms。
- **jieba 的资源**：内置数据使 wheel 增大约 2.5 MB；首次使用时加载约 0.1 秒，常驻内存约多 45 MB，每个带用户词的集合另持有一份词典，约 20–40 MB（macOS arm64 实测）；用户词接近 100 万码位上限时，每个集合最坏多占约 280 MB。
- 过滤继续按参照的整条表达式路线执行，缺失值、null、短路及类型错误依路线而异；`%` 与 `**` 与 3.x 一样是解析错误。向量默认值与在向量字段上过滤（如 `vec is null`）仍不支持，与 3.x 相同。
- 距离沿用 [0004](../decisions/0004-m1-scope.md) 的浮点误差预算；范围阈值落在误差带内时，两端可能有成员或数量差异。BM25 与稀疏 IP 的分数按 3.x 逐位对齐，不使用这一误差预算；function chain 里经过 `decay` 的分数随平台数学库可能差几个 ULP，3.x 换平台同样如此。
- Search iterator V1 依赖 SDK 的有限探测算法，部分批量和距离分布下会提前结束；服务端忽略 V2 探测参数，SDK 据此自动回退 V1，与参照一致。
- 两条 SDK 的端点 schema 缓存限制仍存在：同一进程中显式释放后复用端口，或 CLI 在固定端口更换数据目录重启，可能使 SDK 沿用旧 schema；真实 3.x 上同样存在。
- dump 的已知限制：VARCHAR 主键含双引号或反斜杠时 pymilvus 的分页查询失败，无法导出；`--uri` 指向仍在写入的服务时，导出不是一致快照；`--uri` 会把已 release 的集合重新 load。
- 向量仍仅以 FLAT 执行，已接受的 ANN 定义不意味着实际 ANN；INVERTED 定义的执行仍为扫描。存量定义、DropIndex 及持久化未确认时的封锁与恢复沿用 [0014](../decisions/0014-index-definitions-and-filter-expressions.md) 和 [README](../../README.md)。
- LoadPartitions / ReleasePartitions、snapshot RPC、TEXT_EMBEDDING、model rerank、boost 的 `random_score`、`ARRAY<TIMESTAMPTZ>` 与 `ARRAY<GEOMETRY>`、真实 ANN、AddCollectionField／AlterCollectionSchema 不在本版范围。
- 稀疏向量检索在 nq 较大时仍慢于 2.5.1（[0030 验收](../decisions/0030-sparse-vectors.md#验收)中 nq=32 约慢 27%），单条查询与过滤检索追平或更快。
- JSON 写入优化的收益限于 [0018 已审同机工况](../testing/0018-json-write-acceptance.md)，不外推为任意 JSON、并发吞吐或全部写入路径的保证；进程峰值资源差距尚未解决，继续单独跟进。

## 平台、解释器与证据边界

四个平台均为标准层，在发行工作流中执行相同的适用门槛（[0021](../decisions/0021-release-build-in-ci.md) 第 9、14–16 条）：Linux x86_64 与 arm64 在 GitHub 托管机器上固定的 manylinux_2_28 容器（glibc 2.28）中执行，macOS arm64 在 `macos-15`、macOS x86_64 在 `macos-15-intel` 上原生执行。各平台覆盖正式 wheel 的归档与二进制检查、Rust 默认与故障注入构建的单测、CPython 3.10 与 3.15 上两条 SDK（pymilvus 2.6.17／3.0.2）的端到端全套、CPython 3.10 上两条 SDK 的 dump 端到端、3.11–3.14 联合冒烟、正式 wheel 上与官方 3.x（`1320d26`，NumPy 2，参照侧装 jieba 0.42.1）的差分（含 dump）及 Arrow 15/25/26 数据互通，以及故障注入测试包的恢复专项；Linux 另验 LOCK、strace 与容器 PID 1，Linux x86_64 另验已发布 `0.6.0rc1` 读取本版写出的目录。sdist 另验构建根、PEP 517 安装、Rust 1.89 MSRV 与各项构建期拒绝。

x86_64 的 AVX2 距离核与基线版本由逐位比对的单测在支持 AVX2 的执行机上同时执行；托管执行机都支持 AVX2，不支持 AVX2 的 x86_64 CPU 上选用基线版本的分派分支没有端到端证据。

Windows、free-threaded 和非 CPython 在构建时明确拒绝。musl、其它架构及较低 glibc 的自行构建仅为实验性尝试。Linux 容器的宿主内核是托管机器的较新版本，托管机器没有 macOS 11；二进制的最低系统字段由检查核对，不等于真机最低系统、真实断电或任意文件系统持久化已经验证。

FI wheel 仅供隔离验收，不随发行分发。旧线是否继续发修复版按实际需求另定；本候选不承诺持续维护多个版本线，也不自动将任何 RC 转为正式版。

## 安装（对应 Release 发布后）

本包与官方 milvus-lite 共用 `milvus_lite` 模块，不可同时安装；不用 `pymilvus[milvus-lite]`。

```bash
python -m pip uninstall milvus-lite
python -m pip install pymilvus
python -m pip install --no-index --only-binary :all: --find-links https://github.com/GrittyChen/milvus-lite-rust/releases/expanded_assets/v0.7.0rc1 milvus-lite-rust==0.7.0rc1
```

也可从 [v0.7.0rc1 Release](https://github.com/GrittyChen/milvus-lite-rust/releases/tag/v0.7.0rc1) 下载本平台 wheel 与 SHA256SUMS，核对后安装：

```bash
shasum -a 256 -c --ignore-missing SHA256SUMS && python -m pip install --no-index ./milvus_lite_rust-0.7.0rc1-*.whl
```

Linux 可用 sha256sum 执行同样的校验。需要核对来源时，在下载目录用已登录的 GitHub CLI 执行本平台对应的一行，成功即说明该文件由本仓库的发行工作流签发：

```bash
gh attestation verify milvus_lite_rust-0.7.0rc1-cp310-abi3-manylinux_2_28_x86_64.whl --repo GrittyChen/milvus-lite-rust --signer-workflow GrittyChen/milvus-lite-rust/.github/workflows/release.yml
gh attestation verify milvus_lite_rust-0.7.0rc1-cp310-abi3-manylinux_2_28_aarch64.whl --repo GrittyChen/milvus-lite-rust --signer-workflow GrittyChen/milvus-lite-rust/.github/workflows/release.yml
gh attestation verify milvus_lite_rust-0.7.0rc1-cp310-abi3-macosx_11_0_arm64.whl --repo GrittyChen/milvus-lite-rust --signer-workflow GrittyChen/milvus-lite-rust/.github/workflows/release.yml
gh attestation verify milvus_lite_rust-0.7.0rc1-cp310-abi3-macosx_11_0_x86_64.whl --repo GrittyChen/milvus-lite-rust --signer-workflow GrittyChen/milvus-lite-rust/.github/workflows/release.yml
```

sdist 的 Python 下限及 Rust 1.89 MSRV 沿用 [源码回退门槛](../../tests/packaging/README.md#源码与拒绝门槛)，不引导从 PyPI 按项目名解析本包。dump 需要的 `pymilvus[bulk_writer]` 另行安装，见 [README](../../README.md#导出-dump)。
