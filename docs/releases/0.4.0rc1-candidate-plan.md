## 停服段错误：再次做发布级风险接受

调查记录的继承条款只针对首个真实候选，而且要求差异不涉及停服或服务生命周期。本候选相对 `0.3.0rc3` 的差异涉及停服的下游与服务的打开路径，因此不继承，而是由负责人**再次做发布级风险接受**：根因仍未查明，没有新的定向证据，依据是下面的只读核对。负责人已于 2026-11-07 在本措辞下确认。

相对 `0.3.0rc3` 冻结提交 `9312618` 的核对结果：

1. **停服顺序本身逐字未变**：
   - `crates/core/src/db.rs` 的 `Drop for Db`、`enter`、`begin_shutdown`、`release_data_dir`、`close`、`close_nowait`、`finish_storage`、`finish_storage_inner` 逐字相同；
   - `maintenance.rs`、`compute.rs`、`crates/grpc/src/server.rs` 与整个 `crates/py` 没有改动；
   - `rust-toolchain.toml`、`pyproject.toml`、`clippy.toml` 没有改动。
2. **停服下游与服务生命周期有改动**（都是安全 Rust）：
   - 最终 flush：`finish_storage_inner` 调用的 `Db::flush_handle` 经过重构，发布逻辑抽为 `publish_flushed` / `post_commit_error`。`Manifest::to_bytes` 由 `serde_json::to_vec_pretty` 改为键排序的 `pyjson::dump_file`。`storage/runtime.rs` 新增了清空相关的 `truncate_wal_ready`、`continue_from`、`mark_manifest_unconfirmed`。
   - 打开路径：`Db::new` 新增数据库枚举与每个库的改名收尾；`DataDir::open` 取得 LOCK 后新增数据库根目录的临时文件清扫。
   - 停服窗口内的并发：`close` 等待的在途 RPC 处理体与维护任务里有新增代码（新 RPC、意图收尾、jiff 时区换算）。jiff 不由停服函数调用，但可能在在途写入请求中与停服并发执行。
3. **原生交界没有变化**：`crates/` 的差异里没有新增 `unsafe`、`extern "C"`、PyO3 宏、`libc::` 或 `transmute`。
4. **依赖**：
   - tokio 1.53.1、tonic 0.14.6、hyper 1.11.1、h2 0.4.19、PyO3 0.29.2、rayon-core 1.13.0、parking_lot 0.12.5 不变；四个目标上原有各包的 feature 集合也不变。
   - `Cargo.lock` 新增 9 个包，另有 4 处依赖引用由 `"bitflags"` 改写为 `"bitflags 2.13.2"`（为区分新增的 bitflags 1.3.2，没有版本变化）。
   - 四个目标三元组实际编译的新包只有 jiff 0.2.38、jiff-core 0.1.1、jiff-tzdb 0.1.9，都没有构建脚本，jiff 不创建线程；其余 6 个只出现在锁文件中。
   - Rust 1.98.1；CI 固定的 grpcio 1.84.0、protobuf 7.36.2、pymilvus 2.6.17 / 3.0.2 不变。
5. **新代码上没有再现**：2026-10-28 至开发基线，`CI` 46 次运行（44 成功、2 失败）、`Compare` 38 次（37 成功、1 取消）；2 次 `CI` 失败与 4 次测试版本演练失败（旧产品代码）的失败日志都没有段错误字样或 -11 退出码；常设崩溃现场采集持续开启。

理由：崩溃现场位于停服顺序的前段（停止信号、宽限等待、runtime 关闭、`db.close()` 开始到 flush 写文件之前），这段代码与它依赖的原生库没有变化；窗口内并发的在途处理体除外。代价：最终 flush 的新代码与停服窗口内的新在途处理体都没有定向压力证据。

**适用范围**：谱系以 D 的 `crates/` 树 `9d227062…` 与 `Cargo.lock`（相对 D 只差三个本项目 crate 的版本）为准，工具链为 Rust 1.98.1，同进程 grpcio 为 CI 固定的 1.84.0。下一个候选以此为基准比较；`crates/`、`Cargo.lock`、工具链或上述停服相关依赖发生变化时，本接受不再自动适用，须由负责人再次决定。

冻结提交须同时满足以下条件，任何一项不满足即停止候选准备：

1. `crates/` 树与 D 相同（三个 crate 都用 `version.workspace`，版本切换不改 `crates/`）；
2. 相对 D，`Cargo.lock` 只有三个本项目 crate 的版本变化，其余包逐字不变；
3. Rust 工具链为 1.98.1，CI 的 SDK 约束不变；
4. 上面第 1、3、4 项的核对结论在冻结提交上仍然成立。

这是「根因未查明、再次显式风险接受」，不是修复，也不是继承。候选的任何运行再次出现停服路径 SIGSEGV，立即停止快进与发布并撤回接受，按调查记录的停止条件处理，不重跑掩盖。冻结提交号与上述条件的逐项核对结果写入候选验收记录。

## 冻结前的本地检查

以下检查不涉及外部写入，原始输出由负责人本地留存：

- **上一版本读取**：开发基线构建的 wheel 写出目录，`0.3.0rc3` 公开 wheel 读取，在 macOS arm64 上 6/6 通过（普通与 partition key 集合各三种状态）；Linux x86_64 由候选核验。
- **降级行为**：新版本写出、`0.3.0rc3` 打开（含旧版写入）、新版本重开的矩阵覆盖普通集合、别名、只带自定义属性与带 `timezone` 属性的集合、默认库的数据库属性、完成的改名与清空、TIMESTAMPTZ 集合与非默认数据库，结果写入发行说明的降级一节。意图未收尾时的降级需要故障注入，不实测，依 0023 的设计记录。数据根下的 `databases` 为普通文件时，`0.3.0rc3` 照常启动、本版启动失败，写入发行说明。
- **发行矩阵中 CI 未覆盖的组合**：macOS arm64 上 CPython 3.15 × pymilvus 3.0.2、3.15 × 2.6.17、3.10 × 3.0.2 的端到端全套各 564 项通过。
- **容器时区数据**：两个固定摘要的 manylinux_2_28 镜像都装有 `tzdata-2026e`，与 jiff-tzdb 0.1.9 内置的 tzdata 版本相同，容器内 3.x 参照与本实现使用同一版时区数据。

## 执行检查点

每一步单独授权，或明确批次授权并留复审停点，完成即停下报告：

1. 冻结提交的实施及完整 diff 独立复审；
2. 提交，推送冻结分支一次；`CI` 与 `Compare` 按 0021 第 2 条判定：同一 SHA 最新的运行，其最新 attempt 的每个 job 都成功，只有未分配到托管执行机而被取消的 job 可用 `--failed` 重跑；
3. 冻结确认：上节冻结条件、`Cargo.lock` 结构比对、远端没有该版本的 tag、Release、台账条目或进行中的运行，冻结分支 head 即冻结提交，`main` 仍为 D；
4. 演练（含 PID 1），成功后以 `preserve.py save --mode dry-run` 保存并 `verify`，核对 `release-signing` 没有部署、正式附件没有证明；
5. **老内核抽查（0021 第 14 条，只供诊断）**：本候选改动涉及持久化（意图文件、staging、目录改名）。正式运行前，在远端原生主机（内核 3.10）上的同一固定摘要 manylinux_2_28 x86_64 容器内，以演练产物中的 Linux x86_64 wheel（本机下载，记录 SHA256）运行 [feature_smoke.py](../../tests/platform/feature_smoke.py) 与覆盖别名、改名、清空、多数据库、TIMESTAMPTZ 的写入与重开诊断脚本（负责人本地留存）；依赖按 `sdk30.txt` 固定，经镜像源安装时记录来源并核对版本。结果不是候选门槛，不写入候选结果；发现问题按缺陷处理，由负责人决定是否继续；发行记录关于老内核只引用 0013 决策 1 的历史证据。预算约 1 小时，超出即停下报告；
6. 正式运行（`pid1_dry_run` 取演练运行号与实际 attempt）：`attest` 等待审批期间保存候选证据集，负责人以审批行批准；签发后在 `post-sign/` 补存并复核回执不变；
7. 把 `main` 普通快进到冻结提交，单独登记台账 `candidate`，以冻结提交中的工具运行发布准备核对（`release_set.py --prepare`，必须在创建 tag 之前）；
8. 候选验收记录（引用计划中的 tag 名 `v0.4.0rc1`）独立评审并合入。除 0.3.0rc3 记录的各项外，写明上节冻结条件的逐项核对，并按 0021 第 11 条检索演练与正式运行的 `transport-retry` 注解逐条登记（没有也写明）；
9. 创建指向冻结提交的 tag（消息中的验收记录链接固定到上一步的合入提交），在验收记录中追加 tag 对象，该次合入是 Release 正文链接的最终验收记录提交；
10. 从冻结的发行说明组装 Release 正文：以签后证明包验证七个附件，七个摘要以证明的主体列表为唯一来源，与候选结果的五个正式附件、`SHA256SUMS` 的六条及本地文件逐项核对；相对链接改为固定提交链接，追加候选验收记录与七个附件的身份，校验链接与正文哈希；
11. 创建草稿、上传七个附件并核对（API 摘要、逐字节、正文哈希、不带 `--prepare` 的发布准备工具），发布不可变 Release（prerelease，不设为 latest）；
12. 发布后立即单独把台账改为 `released`，不等待其他文档；
13. 在 `main` 上触发公开下载核验，完成发布后记录（风险处置改为发布后口径）；临时与冻结分支打包验证后删除。

**外部写入的三态**：推送、触发工作流、批准与拒绝、tag、草稿、上传与删除附件、发布等外部写入，执行后都先只读回读，再判定为成功、确定失败或结果不明；结果不明时不重复写入，只做经授权的只读回读；确定失败后的重试须授权，且写入内容与原来相同。只读检查自身失败不视为被检查对象失败：只对网络错误、502/503/504、`stream CANCEL`、超时与限流，在同一步授权内以相同命令最多再查 2 次（间隔 60 秒，每次设超时并记录），401/403、404、明确的否定结果与内容错误不重查，仍不确定即判为结果不明；重新触发工作流属于写入，须单独授权；公开核验只有在附件、证明、不可变性或安装结果确定错误时，才标注版本不可用。

**`main` 冻结窗口**：从推送冻结分支起，`main` 保持开发基线 D 不动，使冻结提交始终是它的直接后继，签发后可以普通快进。推送前、演练与正式运行触发前、批准前与快进前各核对一次。批准前发现 `main` 已变化，不批准、不启动 `sign`，本次运行在签发前停止，版本不消费；`sign` 开始后 `main` 意外推进，立即停止发布并报告，不 rebase、不强推。窗口在三种情况下结束：普通快进成功；`sign` 开始前经授权放弃（不登记台账、不快进）；`sign` 开始后登记最终结局（不快进，台账从当时的 `main` 提交）。

**台账结局**（0021 第 3 条）：`sign` 开始但没有成功签发，登记 `signing-failed`；签发成功、等待发布决定期间为 `candidate`；签发后补存失败可经授权重新补存，放弃则登记 `abandoned`；独立验收或发布决定放弃、草稿阶段发现问题不发布，登记 `abandoned`，按 0013 保留已创建的 tag、不移动，下一个候选换用新版本号；正式 Release 发布成功后改为 `released`，发布后检查失败仍保持 `released`，按 0013 在 Release 说明中标明该版本不可用，不替换附件。

**运行预算**：演练原则上一次。失败原因属于已登记类型的托管基础设施故障（执行机失联、执行机 DNS 故障、包索引响应截断、未分配到执行机）时，经单独授权可再开一次新演练或整次重跑，不得只重跑失败的 job（0021 第 3 条）；失败属于判定层（包括慢机上的测试超时）时，按 0020「判定与流程」第 1 条先查明并写下根因，再决定是否继续。演练因计数、阶段或产物不一致失败时停下修复，修复须新的冻结提交，版本未消费可以沿用，从第 1 步重新执行。

任何失败、意外跳过、部分成功、SHA 不一致或必需检查缺失都立即停止，不重跑变绿；正式运行的 `sign` 一旦开始，该运行的任何 attempt 都不重跑（0021 第 3、20 条）。
