- 日期：2026-10-27。

- 依据：[0021 发行构建](../decisions/0021-release-build-in-ci.md)（含 [0022 签发前保全门闩](../decisions/0022-pre-signing-preservation-gate.md)）、[停服段错误调查「结果与出口」](../testing/shutdown-segfault-investigation.md#结果与出口)。本文确定准备顺序与检查点，不替代上述合同。

## 已确认版本与范围

采用 Python 版本 `0.3.0rc3`、Cargo 版本 `0.3.0-rc.3`，tag `v0.3.0rc3`。这是按 0021 执行的首个真实 CI 候选（此前的 `0.0.1rc901`–`rc904` 为受控测试版本），继承 `0.3.0rc2` 的全部产品能力、数据格式与语义，纳入 `0.3.0rc2` 之后的测试隔离、分片、持续集成、崩溃现场采集与发行流程改动，以及 0021 的最终采纳与 0022 门闩。

用户可见的变化只有：README 与[发行说明](0.3.0rc3.md)的四平台标准矩阵、七个附件与来源证明校验命令；发行说明对停服路径一次段错误的显式风险披露（根因未查明、显式风险接受，见下节）；打包检查器按版本绑定的校验命令白名单。

不纳入：Windows、macOS 11 真机或真实断电、新功能 / RPC / 格式 / 语义、PyPI、SDK 或 Python 矩阵缩减、正式运行复用演练产物、发行流程的只读重试（B1）与 job 编排拆分（B2）。下文「外部写入的三态」中的只读重查是负责人一侧的人工状态核对，不是 B1：工作流、`runs.Gh` 与发布工具都不加自动重试。

候选矩阵按 0021 第 9 条与[阶段矩阵](../../tests/release/scorecard.py)完整执行，不缩减。本版只声明继承运行时行为，不声明与 `0.3.0rc2` 附件逐字节相同。

## 停服段错误风险接受的继承

负责人于 2026-10-27 复核并确认：本候选可以显式继承[停服段错误调查](../testing/shutdown-segfault-investigation.md#结果与出口)对当前谱系的发布级风险接受。比较的提交与差异：

- `0.3.0rc2`（`df6fd30`）→ 开发基线 `d896869`：`crates/` 只有 `68c8887`、`3308b13` 两个提交的改动，涉及三个文件，全部在 `#[cfg(test)]` 模块内或带 `#[cfg(test)]` 标注，发行二进制不编译；
- 风险接受基准 `2ddf5a7` → `d896869`：`crates/`、`Cargo.toml`、`Cargo.lock`、`rust-toolchain.toml`、`pyproject.toml` 完全相同；CI 的 SDK 约束（grpcio 1.84.0、protobuf 7.36.2、pymilvus 2.6.17／3.0.2）没有变化；
- 版本切换只改根 `Cargo.toml` 的 workspace 版本与 `Cargo.lock` 中三个本项目 crate 的版本，其余 187 个包逐字不变。

冻结提交须同时满足以下条件，任何一项不满足，继承立即失效并停止候选准备：

1. `crates/` 树与 `2ddf5a7` 相同，即生产运行代码不变；
2. grpcio、PyO3、tonic、tokio、hyper、h2、rayon-core、parking_lot 等停服相关依赖不变；
3. Rust 工具链仍为 1.98.1；
4. `Cargo.lock` 只有三个本项目 crate 的版本变化；
5. 没有新的生命周期、停服、原生交界、FFI 或 `unsafe` 变化。

这是「根因未查明、显式风险接受」，不是修复。候选的任何运行再次出现停服路径 SIGSEGV，立即停止发布并撤回接受，按调查记录的停止条件处理。冻结提交号与上述条件的逐项核对结果写入候选验收记录。

## 执行检查点

每一步单独授权，完成即停下报告：

1. 版本切换与校验命令白名单的实施及完整 diff 复审；
2. 提交，推送冻结分支一次，`CI` 与 `Compare` 的 attempt 1 全量全部成功；
3. 冻结确认：上节五项核对，以及冻结分支 head 即冻结提交；
4. 演练（含 PID 1），成功后以 `preserve.py save --mode dry-run` 保存并 `verify`；
5. 正式运行：`attest` 等待审批期间保存候选证据集，负责人以审批行批准；签发后在 `post-sign/` 补存并复核回执不变；
6. 把 `main` 普通快进到冻结提交，单独登记台账 `candidate`，运行发布准备工具核对；
7. 候选验收记录（引用计划中的 tag 名 `v0.3.0rc3`）独立评审并合入；
8. 创建指向冻结提交的 tag，在验收记录中追加 tag 对象，该次合入是 Release 正文链接的最终验收记录提交；
9. 从冻结的发行说明组装 Release 正文：先以签后证明包验证七个附件，七个摘要以证明的主体列表为唯一来源，与候选结果的五个正式附件、`SHA256SUMS` 的六条及本地文件逐项核对；相对链接改为固定提交链接，追加候选验收记录与七个附件的身份，校验链接与正文哈希；组装工具先通过固定的正反例；
10. 创建草稿、上传七个附件并核对（API 摘要、逐字节、正文哈希、发布准备工具），发布不可变 Release；
11. 发布后立即单独把台账改为 `released`，不等待其他文档；
12. 公开下载核验与发布后记录。

**外部写入的三态**：推送、触发工作流、批准与拒绝、tag、草稿、上传与删除附件、发布等外部写入，执行后都先只读回读，再判定为成功、确定失败或结果不明；结果不明时不重复写入，只做经授权的只读回读；确定失败后的重试须授权，且写入内容与原来相同。只读检查自身失败不视为被检查对象失败：只对网络错误、502/503/504、`stream CANCEL`、超时与限流，在同一步授权内以相同命令最多再查 2 次（间隔 60 秒，每次设超时并记录），401/403、404、明确的否定结果与内容错误不重查，仍不确定即判为结果不明；重新触发工作流属于写入，须单独授权；公开核验只有在附件、证明、不可变性或安装结果确定错误时，才标注版本不可用。

**`main` 冻结窗口**：从推送冻结分支起，到签发后补存完成，`main` 保持开发基线 `d896869` 不动，使冻结提交始终是它的直接后继，签发后可以普通快进。推送前、演练与正式运行触发前、批准前与快进前各核对一次。批准前发现 `main` 已变化，不批准、不启动 `sign`，本次运行在签发前停止，版本不消费；`sign` 开始后 `main` 意外推进，立即停止发布并报告，不 rebase、不强推。窗口在三种情况下结束：普通快进成功；`sign` 开始前经授权放弃（不登记台账、不快进）；`sign` 开始后登记最终结局（不快进，台账从当时的 `main` 提交）。

**台账结局**（0021 第 3 条）：`sign` 开始但没有成功签发，登记 `signing-failed`；签发成功、等待发布决定期间为 `candidate`；签发后补存失败可经授权重新补存，放弃则登记 `abandoned`；独立验收或发布决定放弃、草稿阶段发现问题不发布，登记 `abandoned`，按 0013 保留已创建的 tag、不移动，下一个候选换用新版本号；正式 Release 发布成功后改为 `released`，发布后检查失败仍保持 `released`，按 0013 在 Release 说明中标明该版本不可用，不替换附件。

任何失败、意外跳过、部分成功、SHA 不一致或必需检查缺失都立即停止，不重跑变绿；正式运行的 `sign` 一旦开始，该运行的任何 attempt 都不重跑（0021 第 3、20 条）。

## 证据边界

候选结果、来源证明与透明日志、Release 附件为公开产物；工作流产物有保留期限；签发前的完整候选证据集由负责人本地留存（[证据的存放与复核范围](../testing/README.md)）。远端原生主机的老内核抽查只在改动涉及 CLI 启停、端口、网络、LOCK 或持久化时考虑，本候选没有这类改动，不安排。
