# 0.3.0rc3 发行范围与说明

本文固定本版本的范围、限制与安装说明，作为 GitHub Release 正文的唯一内容来源，不记录随发布推进变化的状态。冻结提交与执行结果由 Release 附件中的候选结果给出，七个附件的哈希由 Release 正文的候选证据一节与链接的候选验收记录给出；是否已发布及公开下载结果以该正文为准。

这是以 Rust 实现的非官方 milvus-lite，与 Milvus／Zilliz 无隶属关系。该版本为预发布试用，不建议用于生产；RC 阶段通过本项目 GitHub Release 分发，不上传 PyPI。以下安装入口须等对应 Release 正式发布后使用。

## 相对 0.3.0rc2 的变化

**产品运行源码与依赖继承 0.3.0rc2。** 本版不新增 RPC、字段类型、索引算法、数据格式或依赖，运行时行为继承 `0.3.0rc2`。`crates/` 中相对 `0.3.0rc2` 的变化全部位于 `cfg(test)`（崩溃边界用例的信号生命周期，以及库内派生子进程的测试与重开互斥），发行二进制不编译；依赖锁定结果与 Rust 1.98.1 工具链相同，版本切换只改本项目 crate 的版本元数据。仓库另包含持续集成、测试工具、发行工作流与文档改动，这些不进入运行时二进制或产品依赖。本版从新的冻结提交重新构建，不声明附件与 `0.3.0rc2` 逐字节相同。

**候选改由发行工作流构建、验收与签发。** 这是按 [0021](../decisions/0021-release-build-in-ci.md) 执行的首个真实 CI 候选（此前的 `0.0.1rc901`–`rc904` 是永不作为产品版本的受控测试版本）：

- 四个平台的正式 wheel 与 sdist 由本仓库的发行工作流在 GitHub 托管机器上从冻结提交构建，并在同一次运行中完成全部验收；
- macOS x86_64（Intel Mac）升级为标准层，在 `macos-15-intel` 上原生执行与 macOS arm64 相同的门槛；
- Release 附件为四个 wheel、sdist、候选结果 JSON 与 `SHA256SUMS`，共七个；候选结果记录冻结提交、五个正式附件（四个 wheel 与 sdist）的哈希与各验收阶段的计数，作为测试结果与附件之间的持久连接；`SHA256SUMS` 覆盖这五个附件与候选结果；
- 七个附件在一次签发中取得构建来源证明，写入公开透明日志；签发前由负责人保存完整候选证据集，经环境审批与保全回执核对后才签发（[0022](../decisions/0022-pre-signing-preservation-gate.md)）。

`0.3.0rc2` 的 JSON 写入优化、`0.3.0rc1` 的显式分区、partition key、请求前状态独立合并的非 key Upsert，以及更早版本的 nullable / 默认值、ARRAY、Query iterator、range search / Search iterator V1 均继续保留。行为与差异见 [0015](../decisions/0015-nullable-defaults-and-array.md)、[0016](../decisions/0016-query-iteration-and-range-search.md)、[0017](../decisions/0017-partitions.md)、[0018](../decisions/0018-json-write-normalization.md)。参照固定为官方 milvus-lite v3.2.1／`43d1257774e629bc9f66873977ab7c320d5bf5a7`。

## Upsert 行为（继承 0.3.0rc1）

旧行是 `{id:1,x:0,y:0}`，同一个请求对该主键做 partial Upsert：

```json
[{"id":1,"x":1},{"id":1,"y":2}]
```

已发布 `0.2.0rc1` 的结果是 `{id:1,x:1,y:2}`；`0.3.0rc1` 起为 `{id:1,x:0,y:2}`，本版保持不变，与参照 3.x 一致。每行独立从请求前的旧值合并；如果分成两个先后请求，仍依次合并，结果为 `{id:1,x:1,y:2}`。普通 Upsert 也按请求前状态独立合并，详见[修复与反证](../testing/0017-non-key-upsert-fix.md)。partition key 的重复主键胜者由实际分桶写入顺序决定，不能概括成输入最后一行总是获胜。

## 兼容性与已知限制

- 相对 `0.3.0rc2`，数据目录沿用相同的 schema.json、Arrow IPC WAL、Parquet 与 manifest format 2 编码，不增加私有数据格式或新 schema / 分区语义。已发布的 `0.3.0rc2` 读取本版写出的目录、本版再重开其追加，由候选验收在 Linux x86_64 上核验；这不扩大更早版本支持的 schema 或分区范围。
- **停服路径的一次段错误，根因未查明。** 持续集成试点中，Linux x86_64 的一次差分运行在停服路径上出现过一次进程段错误；此后 valgrind 检查与停服时序定向压力（三个时序变量合计 41568 轮）都没有再现。本版对当前产品源码与依赖谱系做显式发布级风险接受，不是修复；候选或后续运行再次出现即撤回这一接受，转回根因调查（[调查记录](../testing/shutdown-segfault-investigation.md)）。
- **降级到已发布 0.2.0rc1**：包含非默认分区的 manifest 或 partition key schema 会使对应 collection 在清理前被明确拒绝，不能降级后继续读写这些集合；拒绝不能改坏受保护文件，同库健康 collection 仍可打开。删除最后一个非默认分区且无 key 等旧版不支持属性时，仅剩 `_default` 的目录可能回到旧版能力范围，不能声称所有新版本目录永久拒绝。更早 0.1.0rc1–rc3 对 nullable / ARRAY 等 schema 属性的拒绝边界继续保留。具体回退用例见 [0017](../decisions/0017-partitions.md)、[0015](../decisions/0015-nullable-defaults-and-array.md)。
- 分区名称、实际目录身份及 snapshot pins 按 0017 的安全合同检查，路径越界、符号链接及物理目录别名被拒绝；Drop 保留其它分区仍需的全局删除记录，避免重开后已删除行复活。这些是相对参照缺陷的显式差异。
- partition key 的 B1 / B2 / B3 差异继续披露：生成 ID 取分桶后行 seq，按原输入顺序返回，可能为 `[1,3,2]`；所有桶的确定性校验 / 转换完成后才追加 WAL；自动 ID 将覆盖请求前可读旧行时整批拒绝。显式覆盖仍允许；真实 WAL I/O 故障仍按既有已校验前缀协议恢复，不承诺整批原子写入。
- 过滤继续按参照的整条表达式路线执行，缺失值、null、短路及类型错误依路线而异。算术、时间与几何谓词仍为范围外。
- JSON 顶层标量及相应默认值沿用 0004 已登记的任意 JSON 值规则，存在参照 Arrow 转换缺陷对应的差异；非有限数值与 binary 原始默认值暂不支持，超出参照默认数字位数限制的数值也明确拒绝，具体边界见 0015。
- 距离沿用 [0004](../decisions/0004-m1-scope.md) 的浮点误差预算；范围阈值落在误差带内时，两端可能有成员或数量差异。服务端仍作严格比较，不加 epsilon；带外结果不得以该规则豁免。
- Search iterator V1 依赖 SDK 的有限探测算法，部分批量和距离分布下会提前结束；不保证任意数据下完整遍历。服务端忽略 V2 探测参数，返回不含 V2 字段的普通结果，SDK 据此自动回退 V1，与参照一致；服务端 V2、token 和跨请求 MVCC 未实现。
- 手写 proto 中，被同名后列覆盖或被完整布局 valid_data 掩码遮住的坏 JSON 仍会被拒绝；相对 `0.1.0rc3` 的严格化边界及理由见 [0015](../decisions/0015-nullable-defaults-and-array.md)。普通 SDK 不构造这类请求。
- 两条 SDK 的端点 schema 缓存限制仍存在：同一进程中，显式释放后复用端口，或 CLI 在固定端口更换数据目录重启，可能使 SDK 沿用旧 schema。此问题在真实 3.x 上也存在；测试的跨用例隔离没有修改 SDK 或产品运行行为，见[调查与反证](../testing/0015-0016-cross-platform-acceptance.md#本轮发现两条-sdk-的跨用例-schema-缓存污染)。
- 向量仍仅以 FLAT 执行，已接受的 ANN 定义不意味着实际 ANN；新建 INVERTED 只接受 BOOL、INT8/16/32/64、FLOAT/DOUBLE、VARCHAR，执行仍为扫描；JSON／ARRAY 新定义被拒绝，存量 ARRAY 定义在需要构建时按参照报错。存量定义、DropIndex 及持久化未确认时的封锁／恢复沿用 [0014](../decisions/0014-index-definitions-and-filter-expressions.md) 和 [README](../../README.md)。
- LoadPartitions / ReleasePartitions、alias／rename、snapshot RPC、稀疏向量、BM25／function chain、nullable 向量、真实 ANN、TIMESTAMPTZ／GEOMETRY、AddCollectionField／AlterCollectionSchema 不在本版范围。
- JSON 写入优化的收益限于 [0018 已审同机工况](../testing/0018-json-write-acceptance.md)，不外推为任意 JSON、并发吞吐或全部写入路径的保证。原记录属于开发实施产物，不是本版候选重新测出的成绩；进程峰值资源差距尚未解决，继续单独跟进。

## 平台、解释器与证据边界

四个平台均为标准层，在发行工作流中执行相同的适用门槛（[0021](../decisions/0021-release-build-in-ci.md) 第 9、14–16 条）：Linux x86_64 与 arm64 在 GitHub 托管机器上固定的 manylinux_2_28 容器（glibc 2.28）中执行，macOS arm64 在 `macos-15`、macOS x86_64 在 `macos-15-intel` 上原生执行。各平台覆盖正式 wheel 的归档与二进制检查、Rust 默认与故障注入构建的单测、CPython 3.10 与 3.15 上两条 SDK（pymilvus 2.6.17／3.0.2）的端到端全套、3.11–3.14 联合冒烟、正式 wheel 上与官方 3.x 的差分及 Arrow 15/25 数据互通，以及故障注入测试包的恢复专项；Linux 另验 LOCK、strace 与容器 PID 1，Linux x86_64 另验已发布 `0.3.0rc2` 读取本版写出的目录。sdist 另验构建根、PEP 517 安装、Rust 1.89 MSRV 与各项构建期拒绝。

Windows、free-threaded 和非 CPython 在构建时明确拒绝。musl、其它架构及较低 glibc 的自行构建仅为实验性尝试。Linux 容器的宿主内核是托管机器的较新版本，托管机器没有 macOS 11；二进制的最低系统字段由检查核对，不等于真机最低系统、真实断电或任意文件系统持久化已经验证。

FI wheel 仅供隔离验收，不随发行分发。旧线是否继续发修复版按实际需求另定；本候选不承诺持续维护多个版本线，也不自动将 0.1 或 0.2 转正式版。

## 安装（对应 Release 发布后）

本包与官方 milvus-lite 共用 `milvus_lite` 模块，不可同时安装；不用 `pymilvus[milvus-lite]`。

```bash
python -m pip uninstall milvus-lite
python -m pip install pymilvus
python -m pip install --no-index --only-binary :all: --find-links https://github.com/GrittyChen/milvus-lite-rust/releases/expanded_assets/v0.3.0rc3 milvus-lite-rust==0.3.0rc3
```

也可从 [v0.3.0rc3 Release](https://github.com/GrittyChen/milvus-lite-rust/releases/tag/v0.3.0rc3) 下载本平台 wheel 与 SHA256SUMS，核对后安装：

```bash
shasum -a 256 -c --ignore-missing SHA256SUMS && python -m pip install --no-index ./milvus_lite_rust-0.3.0rc3-*.whl
```

Linux 可用 sha256sum 执行同样的校验。

sdist 的 Python 下限及 Rust 1.89 MSRV 沿用 [源码回退门槛](../../tests/packaging/README.md#源码与拒绝门槛)，不引导从 PyPI 按项目名解析本包。
