## 结论

0.5.0rc1 交付 `0.4.0rc1` 之后合入的 0027–0031 与 JSON 私有键修复（参照升级到 `1320d26`、按字节预算的自动 flush、多向量字段、`text_match` 与 analyzer 属性、稀疏向量、BM25 全文检索），是发行工作流第一次在这些产品代码上运行。冻结提交满足候选方案的四项冻结条件；前置 CI 与 Compare、演练和正式运行都在 attempt 1 一次全部成功，计数逐项与收集数一致，没有失败、忽略或意外跳过，也没有 `transport-retry` 注解。正式运行在签发前完成本地保全，以保全工具输出的审批行批准后，一次签发覆盖七个附件的来源证明；签发后补存与复核通过，回执不变。`main` 已普通快进到冻结提交，台账登记 `candidate` 并合入，发布准备工具核对通过。

停服路径段错误由负责人对本版谱系**再次做发布级风险接受**：根因仍未查明，不是修复，也不是继承（见下文）。老内核抽查与托管机器上的停服窗口诊断都没有执行。本记录不声明生产可用。

## 停服段错误：再次做发布级风险接受

本版 `crates/` 相对 `0.4.0rc1` 有变化，差异涉及服务生命周期（最终 flush、打开路径）与原生交界（新增一个导入时调用的 PyO3 函数），按调查记录「失效与继承」第二条不能继承。负责人于 2026-11-11 依据[候选方案](../releases/0.5.0rc1-candidate-plan.md#停服段错误再次做发布级风险接受)的只读核对，对本版谱系再次做发布级风险接受；适用范围以 D 的 `crates/` 树 `73fb12ff…` 与 `Cargo.lock`（相对 D 只差三个本项目 crate 的版本）、Rust 1.98.1 与 CI 固定的 grpcio 1.84.0 为准。上节四项冻结条件在 C1 上全部成立。

接受的残余风险与方案相同：最终 flush 与打开路径的新代码、停服窗口内的新在途处理体（稀疏与 BM25 检索、写入时生成输出字段、按字节预算的自动 flush）与新增 PyO3 函数，都没有托管机器上的定向压力证据。冻结前的本机停服窗口诊断（见「冻结前的本地检查」）只供诊断。

这是「根因未查明、再次显式风险接受」，不是修复。截至候选验收的九次运行（冻结分支的 CI 与 Compare、演练、正式运行、`main` 上 C1 与台账提交的两次 CI、台账分支的 CI 与 Compare、`main` 上台账提交的定时 Compare）中，两次发行工作流运行各自的 28 个「崩溃现场」步骤、冻结分支 CI 与 Compare 各自的 9 个「崩溃现场」步骤全部为 skipped；九次运行全部 165 个 job 的完整日志中没有 SIGSEGV、Segmentation fault、signal 11 或 core dumped 字样。本版已作为不可变预发布发布；今后任一运行再次出现停服路径 SIGSEGV，即撤回这一风险接受，停止对本版的后续使用与推广，按 [0013](../decisions/0013-first-release-platform-and-packaging.md) 的发布后失败处置在 Release 说明中标明该版本不可用，并按调查记录的停止条件处理，不重跑掩盖；台账保持 `released`，不替换 tag 或附件。
