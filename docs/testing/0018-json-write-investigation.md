普通 simple / mixed raw Insert 比 3.x 分别慢约 34.8% / 37.9%，mixed SDK 端到端慢约 29.6%；default Upsert 约慢 7.6%，key Upsert 本样本与 3.x 接近。现象不是所有操作同幅度退化，也不是分区新增代码才出现的问题。相对 2.5.1 的结果仅对普通模式成立；不把其不支持的 key 入口算作性能成绩。

两套原专项的工作负载不同：mixed 每批使用新 collection，准备、核验、Flush / Drop 均在计时外；simple 复用同一 collection，Insert 与全行 Upsert 各重复六次同键写入，每批后完整读回核验，保留真实活跃版本成本。不能把这两张语料的差值归因为某个单独函数。

### nullable 诊断

由原 key 专项派生，仅增加 nullable schema 和逐行 null 输入 / 真值；请求计时、状态、完整主键 / 成功位次、JSON 类型及读回断言不变。为仓库外运行显式保持原仓库路径保护根。这里使用 JSON `null` 文本、没有 valid_data；不与完整掩码组件的工作量混为一谈。只测 default，两实现顺序三轮为 Rust / 3.x、3.x / Rust、Rust / 3.x。

| 场景 / 操作（ms） | 0.3.0rc1 | 3.x |
| --- | --- | --- |
| nullable，0% null，Insert | 125.62 | 96.62 |
| nullable，0% null，Upsert | 144.50 | 138.19 |
| nullable，50% null，Insert | 65.06 | 60.04 |
| nullable，50% null，Upsert | 81.36 | 98.30 |

null 比例会改变有效 JSON 的实际体积和处理次数；50% null 比全有效快，不能据此声称优化或去掉一半固定成本。没有用 nullable 诊断替换普通正式数据。

## 原组件分项

从冻结归档在仓库外解包，只追加诊断函数和一个 example，原生产函数体未改。独立 release target、Rust 1.98.1、offline / locked 构建。组件只含一个 JSON 列，真实调用字段校验、可选列转换、规范化、WAL Arrow 构造与写入；六次逐批同步后读回，核对全部 JSON 和父有效位，预热一次后取五次，再取三轮中位数。

| 阶段（ms） | simple 非空 | mixed 非空 |
| --- | --- | --- |
| 请求 JSON 缓冲克隆 | 0.71 | 0.96 |
| 字段校验 | 13.05 | 27.30 |
| 列转换 | 0.75 | 0.77 |
| 列规范化 | 42.17 | 77.20 |
| WAL Arrow 构造 | 46.28 | 80.02 |
| WAL writer 创建 | 0.11 | 0.10 |
| WAL append | 7.20 | 7.65 |
| 额外观察：文件同步 | 10.14 | 14.87 |

额外文件同步不在普通 Insert 响应前强加；此表不包含 gRPC、PK / 向量、全库状态、分桶、Upsert 合并和 MemTable 发布。分项不可直接当作完整 RPC 的 CPU 占比，也不能相减预测已实现的提速。

逐行 codec 子诊断中，simple 的解析 / 有限浮点检查 / 输出约为 13.89 / 5.42 / 24.43 ms，mixed 为 26.20 / 4.42 / 44.69 ms；包含计时器开销，释放与循环开销另在墙钟中。输出也是显著成本，首片不应仅盯着校验解析。完整掩码的 50% 无效组件另保留三轮原始结果；它仍校验被掩码遮住的 JSON，不等同于直接传 null 的 nullable 诊断。

### 调用链支持的归因

- [逐行校验](../../crates/core/src/collection.rs)的 `check_value` 会解析 typed JSON；错误位置与优先级受 0015 保护。
- 同文件的持久化 Insert 在列转换后调用 `normalize_data_json`；[key 预构造](../../crates/core/src/collection/partition_key.rs)逐桶同样处理。
- [runtime](../../crates/core/src/storage/runtime.rs)普通路径调用 `wal_data_batch`；[Arrow 构造](../../crates/core/src/storage/arrow_data.rs)的 JSON / nullable JSON 分支又调用 `json_strings`，再次解析、检查有限浮点并输出规范文本。普通 Insert 的有效 JSON 因而经过一次业务校验和两次规范化过程。
- 非 key Upsert 先合并及逐行校验，再进入普通 Insert；其额外工作及临时列也不能因 raw Insert 结果就假定占比相同。
- 参照 translator 在原始协议解码时 `json.loads`，WAL 构造对 dict/list `json.dumps(..., ensure_ascii=False)`，其 Python 值校验不等同于 Rust 上述重复规范化；参照代码保持只读。

本轮据此推荐：复用首轮已规范化的 typed JSON 字节构建 WAL Arrow，保留通用存储入口的检查、逐行业务校验与首轮规范化。没有实施省略校验、替换解析库或 AST 缓存的优化原型，也没有测量“优化后”产物。

## 峰值资源拆分

原 key 专项的整进程峰值（同批输入、客户端、进程内服务及重复版本共同作用）三轮中位数为：

| 模式 / MiB | 0.3.0rc1 | 3.x |
| --- | --- | --- |
| default | 898.4 | 752.1 |
| key 单桶 | 911.0 | 753.3 |
| key 多桶 | 971.3 | 743.6 |

不能与 2.5.1 的控制进程峰值比较，因为 C++ 服务在外部子进程。另起 worker 只托管 Rust / 3.x 服务，SDK / 请求 / 核验留在控制进程，分别观察两进程，普通 / multi 各三轮：

| 模式 / MiB | Rust 服务 ready | 3.x 服务 ready | Rust 服务 Upsert 完整读回后峰值 | 3.x 同阶段峰值 | Rust 客户端峰值 | 3.x 客户端峰值 |
| --- | --- | --- | --- | --- | --- | --- |
| default | 28.5 | 153.8 | 521.3 | 452.9 | 310.3 | 325.1 |
| multi | 28.5 | 155.1 | 478.3 | 430.5 | 308.0 | 323.3 |

两进程峰值可能发生在不同时间，不相加当作同时峰值，也不把新进程布局的差值直接从原整进程结果扣除。服务端存在额外增长，客户端准备请求和完整读回也显著抬高高水位；原整进程差距不能全部归到请求预构造。Flush 后当前 RSS 与高水位分开保存，释放后高水位不回落不等于泄漏。

组件实际计数中，simple 原始 JSON 10,950,000 字节，WAL Arrow 数组占用约 18,496,016 字节；mixed 为 13,474,480 / 22,690,320 字节。Arrow 数字包含缓冲容量及系统列，不是纯 JSON 体积。组件预热后的 RSS 快照趋于平台，不能据此声称某阶段没有分配。

源码可见原始 InputValues、规范化列、Arrow / IPC 编码缓冲与 runtime 的 `columns.to_vec()` 克隆，此外还有 MemTable、读视图和存量版本。没有分配器栈 / 活数据总账来量化每项占比；RSS 变化只用于缩小问题范围。首片只处理重复 WAL 编码，列共享、所有权转移与分配器保留另行调查。

## 独立评审后的工具修复

首次独立评审发现 `memory.py` 只检查新数据库路径，却以覆盖模式打开派生的 `.server.log`。本轮独立复现：预置普通日志和指向旁证的符号链接时，两者的 36 字节内容均在 worker 启动前变为 0 字节；当时数据库尚未创建。该问题属于工具输出安全，不否定原 75 次运行、229 项原始证据或优化归因。

修复仅涉及完整输出集合的预检、日志排他新建与文件关闭，以及对应自检 / 说明。数据库和日志均须是仓库外的新路径，并拒绝解析后指向同一位置；已有文件、目录、链接、断链均在启动 worker 前拒绝。日志以 `open('x')` 创建，检查后才出现的同名文件也不会被截断。用文件上下文覆盖原诊断调用，启动失败同样关闭句柄并保留日志。采样、工作负载、计时及内容断言不变；产品实现、参照 checkout、原证据包与已发布附件不变。

补验为诊断自检 8 项通过（数据库 / 日志各四种已有路径另按子场景覆盖）、原基准工具自检 67 项通过；将修复前工具代入新增保护测试，6 个原先未保护的场景均被拦住，数据库已有路径的原保护继续通过。正式 macOS arm64 `0.3.0rc1` wheel 环境在全新路径上顺序执行 default / multi 两次原资源诊断，均完成 5000 行、Insert / Upsert 各六批、完整读回、Flush 及 17 个资源快照，并生成新的服务日志。这两次仅验证修复后工具可运行，不并入原 75 次样本，不更新性能汇总；无需重跑既有测量或产品矩阵。

补验证据与原证据包分开保存，包含修复前复现、修复后测试、旧实现反证、两次全新路径诊断及源码 / 产品输入指纹。首轮补验中纠正了一条对 `with_suffix` 的测试预期，改为真实可达的日志链接指向数据库场景；基准自检曾因正式 wheel 环境未装 pytest 而未启动，随后使用已有开发测试环境完成 67 项。旧实现反证计数按 6 个新缺陷场景统计，4 个数据库已有路径场景原本已受保护。准备失败日志单列保留，不计作通过。
