## 结论

第一次冻结提交 `fa7d278` 的演练只有 macOS x86_64 的 dump 差分一条用例断言失败（判定层），失败详情因失败记录上传被拒而丢失，根因只到「高度可能、未能确认」；按负责人的决定先把修复合入 `main`（`61221f5`），在其上重新冻结为 C，经单独授权开了第二次演练。C 满足候选方案的四项冻结条件；前置 CI 与 Compare、第二次演练与正式运行都在 attempt 1 一次全部成功，各阶段计数逐项与收集数一致，没有失败、忽略或意外跳过，也没有 `transport-retry` 注解；Intel Mac 的 dump 差分在两次运行中都 20/20 通过。正式运行在签发前完成本地保全，以保全工具输出的审批行批准后，一次签发覆盖七个附件的来源证明；签发后补存与复核通过，回执不变。`main` 已普通快进到 C 与台账提交，台账登记 `candidate`，发布准备工具核对两次通过。

## 停服段错误：再次做发布级风险接受

`0.6.0rc1` 继承的接受以 `crates/` 树 `c695221b…` 与当时的 `Cargo.lock` 为适用范围，本版两者都有变化。差异涉及原生交界（本仓 AVX2 分派的 `unsafe`、`bytecount` 带运行时 SIMD 的 `unsafe`）与服务生命周期的新用法（dump 在进程内启停服务，并在 atexit 前改信号处置），按调查记录「失效与继承」第二条**不能继承**，须由负责人再次做发布级风险接受。比较的提交是 `5f7c191` 与 C（`crates/` 与 D 相同），差异范围与结论见[候选方案](../releases/0.7.0rc1-candidate-plan.md#停服段错误再次做发布级风险接受)及上节冻结条件第 4 项：**停服顺序本身逐字未变，停服窗口内的在途处理体、原生交界与依赖都有新增**。

理由：崩溃现场位于停服顺序的前段（停止信号、宽限等待、runtime 关闭、`db.close()` 开始到 flush 写文件之前），这段代码与它依赖的原生库没有变化；新增的 `unsafe`（本仓的 AVX2 分派与 `bytecount` 的 SIMD）只在检索的叶子任务与 jieba 分词中执行，不在停服函数上。下面的运行统计只是辅助证据，不说明根因已排除。

适用范围：谱系以 D 的 `crates/` 树 `4126edbc…` 与 `Cargo.lock`（相对 D 只差三个本项目 crate 的版本）为准，Rust 1.98.1，同进程 grpcio 为 CI 固定的 1.84.0；dump 进程另有 `dump30.txt` / `dump26.txt` 固定的 BulkWriter 依赖。上节四项冻结条件在 C 上全部成立。下一个候选以此为基准比较。

接受的残余风险与方案相同：`0.6.0rc1` 继承的全部残余风险；加上 x86_64 上 AVX2 副本在停服窗口内执行、批量检索的新任务模型、jieba 分词与词典加载（含 `bytecount` 在各平台的 `unsafe` SIMD）、nullable 向量的编解码（写入、最终 flush 写出与打开、恢复时读入）、dump 的进程内启停与信号处置，都没有托管机器上的定向停服压力证据。dump 的端到端用例（含 SIGINT / SIGTERM 清理）在发行工作流的 `dump-3.10-<sdk>` 阶段于两次演练与正式运行中通过，降低了常规覆盖的不确定性，但不是定向压力。

这是「根因未查明、再次显式风险接受」，不是修复，也不是继承。截至本记录，候选准备期间的运行如下：

- 开发基线与第一次冻结（6 次）：第一次冻结提交 `fa7d278` 的 CI `44691268182` 与 Compare `44691268315`、第一次演练 `44695814187`、修复提交 `61221f5` 的 CI `44713303890` 与 Compare `44713303916`、`main` 的 CI `44717220055`；
- C 与台账提交（8 次）：冻结分支的 CI `44723620292` 与 Compare `44723620299`、第二次演练 `44728358779`、正式运行 `44741797152`、`main` 上 C 的 CI `44758539356`、台账分支的 CI `44758858373` 与 Compare `44758858394`（2 个 attempt）、`main` 上台账提交的 CI `44769524660`。

其中：

- 成功的两次发行工作流运行各自的 28 个「崩溃现场」步骤、十一次 CI 与 Compare 运行的「崩溃现场」步骤（每次 9 个；台账分支 Compare 的 attempt 1 有一个 job 未分配执行机，两个 attempt 共 17 个）全部为 skipped；
- 第一次演练中失败的 `tests (macos-x86_64, diff-3.0.2)` 运行了崩溃报告步骤，输出 `0 crash report(s) since the marker`，其余 27 个为 skipped；
- 十四次运行全部 270 份 job 日志（被取消、没有执行机的 job 没有日志）中没有 SIGSEGV、SIGBUS、SIGABRT、Segmentation fault、signal 11、core dumped、Fatal Python error 或 `panicked at` 字样。

候选准备之前、`0.6.0rc1` 冻结分支起至第一次冻结基线的运行统计见[候选方案](../releases/0.7.0rc1-candidate-plan.md#停服段错误再次做发布级风险接受)第 5 项：`CI` 33 次、`Compare` 27 次结论全部成功；11 个多 attempt 运行的早先 attempt 中没有以信号结束的 job（冻结前逐个核对，见「冻结前的本地检查」）。

今后任一运行再次出现停服路径 SIGSEGV，即撤回这一风险接受：发布前立即停止创建 tag 与发布（`main` 已快进、台账已登记 `candidate`，台账按结局另行更新）；发布后停止对本版的后续使用与推广，按 [0013](../decisions/0013-first-release-platform-and-packaging.md) 的发布后失败处置在 Release 说明中标明该版本不可用。两种情形都按调查记录的停止条件处理，不重跑掩盖。

## 负责人确认

候选方案要求以下各项由负责人在本记录中明确确认；方案评审中的同意不代替这里的确认。第 2–7 项的决定在方案评审中已由负责人作出并已执行，这里列出决定、理由与执行结果，由负责人连同第 1 项一并确认。

1. **停服段错误的再次接受**：依据「冻结条件」「Cargo.lock 与产品输入」「停服段错误」三节的只读核对，对 C（`crates/` 树 `4126edbc…`）再次做发布级风险接受，适用范围、残余风险与撤回条件如「停服段错误」一节所列。依据是「停服路径未变 + 现有运行没有反证」，不是根因查明；任何运行再现停服路径 SIGSEGV 即撤回。
2. **冒烟日志纳入失败收集**（方案待决定第 2 项）：纳入冻结提交。理由：`0.6.0rc1` 第一次正式运行 `43831366176` 的 `smoke-3.14` 因 uv 安装以退出码 2 失败，冒烟阶段的日志写在 `smoke-<python>/` 下而不在失败收集模式中，根因无法诊断；不纳入时本候选再遇冒烟失败仍无法诊断。C 的 `release.yml` 在「收集运行记录」步骤加入 `'smoke-*/*.log'`；冻结改动后以冻结分支中的实际参数在临时目录复跑 `collect_records.sh`，冒烟日志全部收集，wheel 不收集，名为 `a:b` 的目录被剔除并列出（见候选方案「冻结前的本地检查」）。本候选的运行没有失败的冒烟阶段，这一模式没有被实际触发。
3. **老内核抽查不执行**（第 3 项）：理由见「第二次演练」末段（持久化改动只有 nullable 向量的 Arrow null，启停、端口、网络与 LOCK 没有新路径，没有新的系统调用或原生依赖）。
4. **停服窗口诊断不执行**（第 4 项）：理由：停服顺序本身未变；调查记录阶段 2 的探针原样重跑约需 3 个托管 job、合计约 2.25 job·小时，只能顺带经过 Linux x86_64 的 AVX2 检索，要覆盖 jieba 与 dump 须改探针的在途负载，那是新的试验，不是原崩溃的复现；零崩溃也不改变「根因未查明」的结论。「新在途处理体没有定向压力证据」保留为残余风险，由第 1 项的接受覆盖。
5. **0020 第 2 条：0036–0038 的重新计数**（第 5 项）：CI 与 Compare 一侧在合入时完成，0036 的 CI 次数按 0037 的口径（5 次）由后续批次补齐；发行工作流一侧的新阶段由本候选的第二次演练与正式运行共 2 次承担（第一次演练失败，不计入）。映射见下表一；这是 0020 第 2 条「经评审约定」的替代，不是达到 10 / 5 次的门槛，不写成已完成稳定性计数。
