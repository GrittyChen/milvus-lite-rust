# 恢复内存与冷启动专项

日期：2026-10-08。基线为 `8782800`，参照为 v3.2.1 / `43d1257`。本切片处理已提交 segment 的恢复副本，不改变 M2 功能面或生产可用性声明；批量检索、compaction、动态过滤与其他首发功能继续分开推进。

## 所有权及不变量

原 `Collection::from_recovered` 借用每个已提交 `DecodedData`，将 columns / meta / seqs 全量克隆到现有 `Arc<ChunkData>`；所有原批直到整个恢复对象销毁才释放。百万行向量缓冲区本身为 512,000,000 字节，临时双份不能当成永久泄漏，也不能仅凭代码阅读断言它解释全部 RSS。

本轮在全部磁盘恢复判定成功之后，取出 `RecoveredCollection.segments`，按原 manifest/批次顺序消费每个批次，将 Vec 及其内层缓冲区直接移入原有的 `Arc<ChunkData>`。norms 仍由相同向量计算，保留全部物理行、失效位、源 ID、源内行号、位次及原主键建表顺序。

- 锁序、按名字恢复串行、collection 登记时间不变；没有新增共享状态，也没有改变快照的 Arc/有效位 CoW 边界。这里只转移登记前的局部独占所有权，不重新设计单写者或同步 flush。
- 活跃 WAL 的 `Arc<DecodedData>` 仍归 memtable，供冻结和 flush 使用；读块仍复制其列，不移走、不新增共享列类型。本轮不声称消除 WAL 副本或写入合并的复制。
- schema / manifest / Parquet / WAL 校验及错误分类不变，仍全部成功后才清理孤儿、登记句柄。构造中途出错只析构尚未登记的局部对象，不改磁盘。
- 旧快照、flush 发布、drop、关闭协议及 aliases 锁不变。共享磁盘格式和公开 RPC 不变，没有新增依赖或生产 unsafe。

## 定位证据：分配量与 RSS 分开看

仓库外诊断程序通过公开 core 入口分别执行 `load_committed` 和 `Db::collection`，以独立可执行程序的全局 System 分配器包装记录成功 alloc/dealloc/realloc 的请求字节与峰值；两版本两规模各三轮，顺序运行。它不注入到发布产物，分配计数不含 malloc 管理开销、Python、线程栈等，不等于 RSS。原始程序及记录保留在仓库外，诊断耗时包含原子计数开销，不作为服务延迟结论。

百万行的三轮中位数（MiB，字节除以 1024²）：

| 阶段 | 原版存活分配 | 原版峰值 | 移交后存活分配 | 移交后峰值 |
| --- | ---: | ---: | ---: | ---: |
| load_committed 返回 | 635.2 | 733.2 | 635.2 | 733.2 |
| collection 构造完成 | 744.955 | 1286.136 | 744.955 | 793.015 |

10 万行 collection 构造峰值为 120.880 → 69.746 MiB，存活分配均约 67.169 MiB。百万行构造峰值减少约 38.3%，最终存活分配基本不变。原对象和 Db 销毁后残余计数约 2 KiB / 21 KiB，不把该探针推广为所有路径的无泄漏证明。

这组诊断与下面的原生 wheel RSS 测量共同支持「移除临时副本可降低恢复峰值及加载后的 RSS」；没有完整堆归因，不把主键表、可见性表或分配器高水位的各自占比写成已知值。

## 第二轮：主键表存键与恢复临时开销

基线为已提交的 `7ae4f4c`（native `222c6436…`）。先拆解存活分配，再分别试验临时开销和键表示；以下新测量不覆盖或替换第一轮表。

### 占用拆解及方案边界

隔离源码副本中的诊断按实际 Vec 容量统计列缓冲区，以标准分配器记录两张表 clone 的新增请求字节（clone 的有效位 Arc 仍共享），原始诊断代码、日志和产物保存在仓库外，不进入生产引擎。Int64 主键、百万行、全部存活的数据下，三轮数值一致：

| 部分 | 请求分配 MiB |
| --- | ---: |
| 向量列 | 488.281 |
| Int64 标量列 | 15.259 |
| 字符串 Vec 及字符容量 | 25.654 |
| `_seq` / 位次 / norms | 7.629 / 7.629 / 3.815 |
| 读取主键表 | 98.000 |
| 可见性状态 clone 的新增字节 | 98.006 |
| 其他结构及诊断固定开销的差额 | 约 0.683 |

总存活分配约 744.955 MiB。clone 的新增分配不是原对象的逐字节堆普查（如有效位 Arc 不复制），差额也不是完整的 malloc 开销。一次独立服务的 `vmmap -summary` 另显示 `Malloc Large` 的 RESIDENT 为 `196.0M`、`Malloc Large (empty)` 为 `95.0M`。这是辅助定位，保留工具原单位，不与 RSS 三轮表混算；没有逐个追踪空块来源，不能将它们全部归因于某张表。

两个低风险局部改动先行试验：按最终活行数预留读取主键表；`scan_wal` 没有规范 WAL 文件时不复制提交态 Visibility。有 WAL 文件（包括只有 schema 的空流）仍在注册活跃源之前保留同一份提交态快照；真实扫描错误先返回，不被当作空目录。它们降低百万行构造分配峰值约 793.015 → 745.100 MiB，但同机三轮服务 RSS 没有降低，故不据此宣称常驻内存改善。试验 native 为 `c0ebbaa3…`，24 条记录与最终存键方案分开保留。

进一步的改动只压缩内存键表示：读取主键表和 Visibility.latest_data 使用同一个私有 `PkMap<V>`，内部为 `HashMap<i64,V>` 和 `HashMap<String,V>`。只做现有 get/get_mut/insert/remove/len/reserve 操作，不提供新的策略或扩展入口，不增加依赖、unsafe、锁、共享对象或磁盘格式。两类键可以并存；`Int64(7)` 和 `VarChar("7")` 仍是两个键。VARCHAR 原 String 在插入时移入，查询借用 str，不额外复制。标准 RandomState 哈希防护不变。

两张表的职责不合并：读取表定位稳定块；可见性表保留已失效行的最大序号以判断乱序回放。delete 最大序号表与 memtable 批索引仍保持原结构。对外 `Pk`、结果、诊断、源序/行号/位次、冻结/发布协议及快照 CoW 边界均不变；修改仍发生在原状态写锁内，读取任务仍不取锁。本轮没有改变同步 flush 或单 collection 单写者，不需要新的并发调度方案。

隔离原型的一次分配诊断中，每张百万行 Int64 数据表的新增 clone 分配约 98 → 66 MiB，最终构造存活分配约 745 → 681 MiB；这不是三轮服务 RSS 的统计。该结果限于 Int64 基准；不宣称 VARCHAR 或 tombstone-heavy 输入有同等内存下降。
