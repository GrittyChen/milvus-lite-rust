# 0015：JSON 写入回归修复

- 日期：2026-10-16
- 状态：负责人复审通过（2026-10-16），JSON 写入退化修复，切片 A 可收口
- 合同：[0015](../decisions/0015-nullable-defaults-and-array.md) 新增的“含 JSON 字段写入”条目；上轮两项阻断已由负责人复审通过
- 参照：milvus-lite 3.2.1 / `43d1257`；SDK 2.6.17 / 3.0.2

## 依据与范围

负责人复审指出：普通非空 JSON 的写入相较 rc3 稳定变慢，原冻结矩阵仅覆盖 S1、批量检索和恢复 RSS，遗漏了写入。此处是单独登记的合同修订，不追溯改判旧合同，也不扩展 ARRAY 或 0001 的跨实现写入优化。

独立使用 5000 行、每行 2694–2695 字节的普通非空 JSON、二维向量、无动态字段/nullable/default，预序列化 raw RPC 后计时。首组 rc3 的五次样本最小/中位为 271.18 / 289.92 ms，上轮 `b2166dbf…` 构建为 366.39 / 381.49 ms，分别增加约 35% / 32%。输入 JSON 形状与负责人探针不同，不把两者绝对耗时混合；本组的全部样本、输入和初版脚本指纹保留。

## 最小修复与语义边界

产品只改 `collection.rs` 的两个空值探测点：`input_is_null` 与 `convert_optional` 共用 `json_text_is_null`，识别首尾四种 JSON 空白包围的 `null`。普通 JSON 首字节不匹配时直接返回，不构造完整 JSON 值。

四种空白严格限定为 ASCII 空格、tab、LF、CR；仅忽略首尾，不删除内部字符。`n ull`、`null null`、换页符/垂直制表符、BOM、非 UTF-8 字节都保持非空探测结果，随后由原校验拒绝。不能使用会包含换页符的 trim_ascii。JSON 字符串 `"null"`、数组/对象中的 null、false 和数字均不是整值 null。

`check_value` 的语法校验、`json_strings` 的规范化/有限值检查和 `json_checks` 完全保留。转换函数仅在完成逐行校验后调用；移除整列探测中的解析不把坏 JSON 绕过到 WAL。Insert/Upsert、默认值/auto_id、掩码/覆盖和错误顺序保持上轮已通过的合同。

## 验证与二三阶影响

- Rust 新增以原 serde_json 解析结果为判据的组件差分，覆盖全部 65,536 种首尾字节组合和多空白、内部空白、引号/容器、BOM 等反例。不是以新 helper 自己计算期望值。
- 原始 gRPC 新增 24 项 Insert/Upsert 用例，验证有效 null/字符串/容器的读取结果；畸形文本必须 code 6、无新增行，之后合法写入仍可用。新用例在上轮构建上也有 24 passed，证明要保持的行为基线；修复后与既有 JSON 优先级/掩码反例合计 68 项通过。
- 写入前失败边界不变：形态/长度、逐行业务与 JSON、规范化和转换都在当前请求首次 WAL 追加、next_seq 发布之前。没有移动实际校验和任何存储提交动作。
- 扫描模式为 `InputValues::Json|input_is_null|contains_null|parse_json|convert_optional|json_strings|json_checks`，覆盖 grpc 解码 → Insert/Upsert 的所有空值探测、合并/默认值 → 转换与 Arrow 规范化。仅两处为判空新增的完整解析被替换；动态字段、类型名诊断和存储解析保留。

## 性能方法与结果

可复现工具见 [JSON 写入专项](../../benchmarks/json-write/README.md)。正式对照使用同机、独立 wheel/venv，rc3、上轮已通过构建、修复后构建、真实 3.x 顺序三轮轮换；raw RPC 与 SDK 端到端分开。预热一批后每轮五个样本，保留全部时延，同时报告最小值、中位数和轮间范围。

raw 时延包含本机传输及响应，不是单独的服务端 CPU 时间。SDK 输入与真值分离，逐批检查返回状态/主键/位次、总行数及全部 JSON 值和类型；验证、Flush/Drop/关闭在计时外。完整测试/构建退出后才开始计时，测量期间没有并行测试或诊断。

本机为 macOS 27.0.1 / arm64、10 个逻辑 CPU，四套环境均为 CPython 3.12.14 / pymilvus 3.0.2，参照使用 PyArrow 25.0.1。24 次独立进程运行共约 213 秒；每次均有一批预热、五批计时，合计 144 批、72 万行全部核验。所有 raw 输入/等价请求指纹、脚本、Python 与 SDK 版本一致；原生库按 rc3 / 上轮构建 / 最终构建分别绑定 `53b74ce7…` / `b2166dbf…` / `d1d8cdfa…`。原始五次样本、逐轮结果均保留。

### 另行跟进：rc3 与 3.x 的既有写入差距

状态为待后续分析。负责人提供的 raw 数据是 rc3 718 ms、3.x 385 ms，约 1.9 倍；这不是本轮独立复跑的数值。该差距在本切片之前已存在，不能靠恢复 rc3 基线关闭 0001“写入追平”的目标。本次只记录现象和独立对照结果，不改 JSON 校验/规范化或持久化策略来追赶参照；后续需要在单独范围内定位，并按规则 7 补齐同机 2.5.1 / 3.x 基线。

本轮独立负载中，rc3 / 3.x 的 raw 各轮最小值汇总约为 1.40 倍、中位数汇总约为 1.22 倍；JSON 形状与计时口径不同，不能替换负责人的 1.9 倍观察。两组都提示仍有后续分析空间，本轮不处理该历史目标。

冻结验收时变更未提交、未切版本或发布；ARRAY 随后完成并评审收口。已确认的切片现按逻辑边界作本地提交，不推送、不发布。
