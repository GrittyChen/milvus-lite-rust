# S1 过滤性能专项

日期：2026-10-08。功能范围与错误合同仍由 [0006](../decisions/0006-m2-scope.md) 和 [0007](../decisions/0007-m2-storage-engine.md#s1-过滤的当前实现与验收范围) 定义；此记录只验证已有 S1 的执行效率。下面两轮表保留各自的历史产物与脚本身份，复审修复后的校验及构建另列。

## 第一轮：列类型绑定与位图运算

先在 release 的内部临时计时模块中拆分百万行阶段，再以真实 pymilvus 对照。临时模块已移除，不在生产构建或测试套件内保留计时钩子。下面的单阶段平均值是定位证据，不能直接代替端到端表或相加成整体延迟。

| 阶段 | 优化前 ms |
| --- | ---: |
| `cat >= 0` 求值 | 5.62 |
| `cat == 5 and id > 1000` 求值 | 13.70 |
| `tag == 't7'` 求值 | 9.89 |
| 过滤 count 的掩码计数 | 0.57 |
| 两条件 Query 的引用收集 | 1.33 |
| 两条件 Query 的复制引用与排序 | 0.15 |
| 两条件 Query 的 100 行物化 | 0.004 |

定位场景使用既有 M2 的百万行库（删除/upsert 后 999000 行），优化前版本在独立进程中取得快照、各阶段 100 次循环；阶段结果受编译优化、缓存和采样顺序影响。它表明主要开销在求值；没有据此重写排序或分页。

- 比较操作由字符串分派改为枚举；按块绑定列类型和常量，循环内只访问相应的列。
- 整数转浮点保留 ±2^24/±2^53 的安全范围与原错误文本，验证全部原活行之后才产生该操作数的比较掩码；普通浮点 NaN/±0 语义保持不变。
- 位图按 u64 合并，写时复制仍保护旧快照；计数使用 popcount，Query 仅枚举置位行。源序、位次、稳定排序、limit/offset 及最终物化未变。
- 不改主键 in、parser、语法诊断、加载与错误优先级、并发模型、持久化格式、WAL/fsync 或提交协议。

## 第一轮端到端测量

命令与口径见 [benchmarks/s1](../../benchmarks/s1/README.md)。同机顺序运行两个规模、四个版本、轮换三轮，共 24 条正式记录。准备阶段的第 0 轮与初步探针未计入。场景是全部存活、显式 Flush 后的只读库；Rust 两版本顺序读取同一目录。每项计时前一次正确性调用、一次预热，结束后再检查；所有计时返回值在计时后校验。计数、Query 行序及过滤 Search 的 top10 与距离真值均通过。

## 第一轮正确性证据

- `eval` 保留独立的原逐行标量模型，与列特化对照八类标量、六种比较及两个方向、NaN/±0、宽整数、字面量越界、稀疏有效位和 63/64/65/129 行边界；额外固定掩码已为零时仍报告活行的转换错误。
- `SourceBits` 单测固定置位迭代、popcount、尾位、旧位图不变，以及第二个操作数仍访问原候选集合。
- 真实差分新增 130 行跨块场景，覆盖覆盖写/删除后的 count、分页、Search、关闭重开，以及 limit=1 和 false 前置谓词仍不能屏蔽末尾转换错误。复审时进一步在每次 Delete 转换失败后断言计数与完整 id/age/title 行内容、顺序均与调用前相同，直接固定这一错误族不生效。
- 默认与 fault-injection 的 Rust 全套、两套 Clippy、fmt/diff check 通过。两条 pymilvus 线各 `tests/python` 232、`tests/differential` 81、`tests/storage_interop` 60 passed；基准与平台自检 10 passed。

## 第二轮：稠密字连续扫描

只调整 `SourceBits::intersect_matching`：原有效位字为 `u64::MAX` 时，连续读取对应的 64 行并生成比较掩码；其他字继续逐个提取原置位，包括未填满的尾字。两条路径均访问原候选，不以累计掩码跳过操作数；仍只在结果不同的字上触发位图写时复制。没有增加表达式缓存、count 融合、分页算法、并行任务或平台专用代码。

新增 `dense_and_sparse_words_visit_original_live_rows_once_without_reading_padding`，覆盖同一位图中的完整活字、半密度字、空字、尾字、连续多次过滤及旧视图不变。原标量模型继续对照八类标量、六种比较、两个方向与数值错误。默认 Rust 全套（core lib 132）和故障注入全套（core lib 153）、两套 Clippy、fmt/diff check 通过；重新构建后两条 SDK 线各 Python 232、差分 81、互通 60 passed。

本轮使用与第一轮逐字节相同的测量脚本、schema、种子与已建库，配对轮换三轮比较上一轮 Rust、2.5.1 与本轮 Rust，共 18 条增量记录。3.x 使用第一轮同机同脚本同库的 6 条冻结参考记录，不声称本轮重跑了完整四版本矩阵；第一轮表与产物身份保留。测量期间没有并行构建或测试，机器与依赖版本不变，load average 为 6.74–7.88。

## 复审修复与证据身份

- 0001 与 M2 验收记录已链接本专项，同时保留原主表及当时的未达结论。
- S1 只允许字段与字面量比较，整数列遇到浮点常量只会提升到 float64，因此删去该列核中的 float32 死分支与多余参数；`value()` 中 FLOAT 列配整数字面量的 ±2^24 校验和转换保留。真实入口、全部比较方向、数值边界、空块与失效行仍由原标量模型和差分覆盖。
- 原历史测量脚本的距离门为 `np.allclose(rtol=1e-5, atol=1e-5)`，比 0004 的 `max(1e-5 * abs(d), 1e-6)` 宽松。当前脚本使用后者，拒绝非有限值及形状不匹配；三组阈值回归能抓住旧的宽松门。没有将旧计时样本冒充当时已按严格门逐次验证：旧返回值未保存，复审中重新用严格门检查了同一数据集和冻结产物的相同请求。
- 严格核验覆盖原 Rust、列绑定 Rust、稠密 Rust、修复构建、2.5.1、3.2.1 的两个规模，共 12 组，只校验结果、不采集延迟。全部 Query/计数和过滤 Search 的候选与距离通过；旧表时间未改，也未把核验输出混入性能表。
- 当前输出记录 NumPy 版本和可选的 pyarrow 版本；只有包确实未安装时省略 pyarrow，元数据读取错误仍传播。新脚本指纹为 `39d53deab2a5dceca2d41db983cd7b9dc4b6a5762fdd5cb92c3ae626385927cd`。历史源码恢复与完整旧指纹复算见 [S1 基准说明](../../benchmarks/s1/README.md#历史测量脚本)。
- 修复构建的扩展 SHA256 为 `f6657546ca9def90ba6591d216c426fe17170f908dcd7e2b8c8309eb69ceb6a3`；它不是第二轮表中的 `5577951d…`。本次重建后，两条 SDK 线各 Python 232、差分 81 passed，Rust workspace / core fault-injection、两套 Clippy、fmt/diff check 通过，基准与平台自检 16 passed。存储互通两线各 60 为上一轮稠密构建的验证，本次未改持久化/恢复协议，不重复将它写成修复构建的实跑结果。

## 边界

正式性能场景是全部存活、已 Flush 的只读数据，不能推广为任意位图密度、MemTable 布局、大范围输出或写入并发的收益。原 M2 基准是历史快照，继续保留原构建与脚本身份，不将此次结果覆盖进去。内存/恢复、批量检索、Windows 与真实断电不属于本次验证；M2 的性能目标是否全部达成仍按各指标判断。
