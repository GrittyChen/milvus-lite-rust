# 分配器保留内存专项

日期：2026-11-21。改动前的基线为 `48a3b3f`（`0.7.0rc1` 发布后的 `main`），改动随本记录所在的提交合入。目标是 [0001 约束 5](../decisions/0001-refactor-baseline.md#对-rust-实现的约束)：服务端内存不高于 2.5.1 的同规模水平。

## 结论

- 百万行写入并 flush 后，服务端 RSS 比关闭重开后多出约 250 MiB，多出的部分是 glibc 留在 arena 中、没有交还系统的空闲内存，不是存活数据，也不是后台合并。
- 改动：Linux（glibc）上后台维护每轮结束后调用一次 `malloc_trim(0)`。百万行 flush 后的服务端 RSS 由 1076 MiB 降至 742 MiB，同机 2.5.1 为 930 MiB；重开后由 833 MiB 降至 734 MiB。
- 代价：trim 逐个 arena 加锁整理，期间要在被锁 arena 上分配的线程等待。在测量规模（单个集合、至多 100 万行）下，每次 flush 或打开集合后正好在这时执行的请求最多多等约 10 ms；重开后的首次检索在百万行时由 12.2 ms 变为 20.8 ms，10 万行时由 3.2 ms 变为 7.8 ms（同机 11-18 复测中 2.5.1 的这一项为 82.4 ms 与 11.5 ms，该次复测的结果由负责人本地留存）。更大的数据量与多集合没有测量。稳态的延迟、吞吐与并发没有可辨的变化。负责人接受这一代价。
- macOS 上有同类现象，机制不同：系统分配器缓存已释放的块，flush 后比重开后多约 300 MiB（10 万行三轮与 100 万行一轮）；trim 类接口对它无效，本实现无法在进程内处理，README 写明了用户可用的环境变量。

## 定位

数据与 [benchmarks/baseline](../../benchmarks/baseline/README.md) 的 `memory` 阶段相同：主键 INT64、128 维 FLOAT_VECTOR、INT64 与短 VARCHAR 各一列，每批 1000 行写入，建 FLAT 索引、load、flush、检索一次后采样。服务在独立辅助进程中运行，采样只计辅助进程。另做了三项诊断：

- 在辅助进程中读 `mallinfo` 与 `malloc_stats`，并手动调用一次 `malloc_trim(0)`；
- 用计数分配器统计 Rust 堆的存活字节（只在隔离副本中替换全局分配器）；
- 设置 `MALLOC_ARENA_MAX=2` 作对照。

百万行三轮（`48a3b3f`）：

| 项 | flush 后 | 重开后 |
| --- | --- | --- |
| 服务端 RSS（MiB） | 1067–1093 | 829–835 |
| flush 后等待 30 秒的 RSS | 不变 | — |
| Rust 堆存活（MiB） | 680.8 | 681.3 |
| malloc 在用（MiB） | 约 713 | 约 713 |
| malloc 空闲保留（MiB） | 348–376 | 约 103 |
| 手动 `malloc_trim(0)` 后的 RSS（MiB） | 739–763 | 734–736 |
| `malloc_trim(0)` 耗时（ms） | 23–38 | 10–15 |

- 存活数据在两种状态下相同，写入路径没有多留数据；flush 后等待 30 秒 RSS 与 Parquet 文件数都不变，不是后台合并在进行。
- 空闲保留几乎都在一个 arena 中（`malloc_stats`：该 arena 向系统申请 462 MB，在用 109 MB），`MALLOC_ARENA_MAX=2` 的结果与默认相同。问题不在 arena 数量，而在单个 arena 中间的空闲块不会自动交还。
- 构建过程中 Rust 堆的峰值为 1579 MiB，是存活量的 2.3 倍；这些临时分配释放后形成上述空闲块。峰值来自哪些阶段没有拆分。
- 10 万行：flush 后 157–163 MiB，手动 trim 后约 105 MiB，耗时约 7 ms。

## 设计

- 新模块 [allocator.rs](../../crates/core/src/allocator.rs)：Linux glibc 上调用 `libc::malloc_trim(0)`，其他平台是空函数。不新增依赖；`unsafe` 只在这一处。
- 调用点在[维护线程](../../crates/core/src/maintenance.rs)一轮结束、登记完成状态之后，且只在这一轮之后队列已空、维护未停止、结果不是 `Closed` 时调用。flush 写入了行、打开集合与新建集合都会排一轮维护，合并也在这里执行，因此这是这些操作释放临时内存之后唯一的后台时机。多个集合同时排队时只在最后交还一次；关闭时的排空不交还，进程或 Db 随即释放全部内存。trim 不计入轮次耗时，也不延后等待维护完成的调用方。调用不在请求路径上，也不持有任何引擎锁。
- flush 发布后先释放冻结代，再排维护（[db.rs](../../crates/core/src/db.rs) 的 `flush_handle_with`），否则维护轮次可能先于冻结代释放而结束。仍在被检索快照引用的内存要到下一轮维护才交还。
- `malloc_trim` 作用于整个进程，宿主 Python 的空闲块也会交还。trim 逐个 arena 加锁并对空闲页执行 `madvise`，期间要在被锁 arena 上分配的线程等待，这就是「结论」中的代价。没有设阈值：百万行重开时空闲保留约 100 MiB，设阈值也避不开打开时的这一次。
- 不排维护、因而不触发 trim 的操作：清空等直接走 `flush_locked` 的操作、drop collection、release，以及没有 flush 的大批写入；它们释放的内存要等之后某次 flush 或打开集合排入维护时才交还，空闲时可能一直不交还。不改分配器，不在库内调用 `mallopt`（会改变宿主进程的全局分配策略）。

## 测量环境与方法

- x86_64：原生物理机（AMD EPYC 7702，CentOS 7，内核 3.10）上的 manylinux_2_28 容器（glibc 2.28），绑定 16 核与单个 NUMA 节点，host 网络；CPython 3.12，pymilvus 3.0.2，Rust 1.98.1 离线构建。测量期间一分钟负载低于 3 才开始每一项。
- native SHA256：改动前 `c71681969c56702d1833203c7c26ba05190b7eb6aa5c2965be9e73539fc67fba`，改动后 `0ff0cb776675acdf1a6e13a1d53a4e72ad89d0d72cffa1329c065ce446746f16`。改动后的这一版在每轮维护后都交还、且排在登记完成之前；评审后改为上文的调用条件，单集合场景下交还的时机相同，复核见「评审后的复核」。
- 2.5.1 只有一轮有效：后两轮的探针没有删掉 2.5.1 的单文件数据库，行数核对失败，结果未计入。这一轮与同机 11-18 的三轮（flush 后 924–941 MiB）一致。
- 仓库内可重跑的部分：服务端 RSS 用 [benchmarks/baseline](../../benchmarks/baseline/README.md) 的 `rs:FLAT:server:memory` 与 `m2` 阶段测量。本记录的 RSS 表来自仓库外的探针，它的数据与写入顺序与 `memory` 阶段相同，另外多采了等待后、重开后、`mallinfo` 与手动 trim 的样本；探针、计数分配器诊断与原始结果由负责人本地留存，依赖它们的结论（存活量、空闲保留、arena 分布）只由本地证据支撑。

## 验收测量

### 服务端 RSS

三轮轮换顺序，中位数（最小–最大），MiB：

| N | 状态 | 2.5.1 | `48a3b3f` | 本改动 |
| --- | --- | --- | --- | --- |
| 100000 | flush 后 | 234.1 | 167.3（156.8–207.4） | 98.8（94.2–100.7） |
| 100000 | 重开后 | 207.8 | 145.5（145.5–145.5） | 92.1（92.1–92.1） |
| 1000000 | flush 后 | 930.5 | 1076.2（1062.8–1096.2） | 742.3（742.2–742.9） |
| 1000000 | 重开后 | 955.1 | 833.1（832.9–833.1） | 734.4（734.3–734.4） |

flush 后的样本取在 flush 与一次检索返回之后；trim 在维护线程中异步执行，三轮中 flush 后立即采样与等待 5 秒后采样的值相同。

### 延迟与吞吐

[benchmarks/baseline](../../benchmarks/baseline/README.md) 的 `m2` 阶段（含 `reopen`），10 万与 100 万行，改动前后各三轮、轮换顺序。写入吞吐、单条与 nq100 检索、过滤检索、查询、`count(*)`、点查、upsert、写入中的检索，以及 1–8 路线程与进程并发，中位数差异都在各轮的波动范围内（各轮区间重叠）。区间只是部分重叠、方向偏慢的一项是百万行的 1% 字符串过滤检索：p50 改动前 5.60 ms（5.46–6.60），本改动 6.88 ms（6.00–6.97），复核一轮 7.15 ms；10 万行同一项改动后反而更快，原因未查明，记为弱信号。可辨的变化只有重开后的首次检索：

| N | 指标 | `48a3b3f` | 本改动 |
| --- | --- | --- | --- |
| 100000 | 重开后首次检索（ms） | 3.2（2.6–3.7） | 7.8（6.6–8.9） |
| 1000000 | 重开后首次检索（ms） | 12.2（11.6–12.7） | 20.8（20.4–22.3） |

打开集合会排一轮维护，首次检索与这一轮的 trim 同时执行。重开后的后续检索（p50 与 p99）不变。

### 反复写入、删除与 flush

先建 100 万行并 flush，再做 20 个周期：每个周期 upsert 5 万行（部分为新主键）、删除 1 万行、flush，随后检索 30 次。改动前后交替各两轮。

- 每个周期的耗时（中位数约 2.6 秒）与检索 p50（约 11.3 ms）两版相同。
- 每个周期 30 次检索中最慢的一次：改动前 11.4–15.6 ms，本改动 12.2–28.2 ms。flush 之后的那轮维护与检索重叠，最多一次检索多等约 10 ms。
- RSS 两版都随周期增长，活行数保持约 97.7 万：改动前 1084 → 1630 MiB，本改动 741 → 1328 MiB，全程低约 300 MiB。增长来自合并之前保留的旧版本行，与本改动无关，本记录不处理。

## 评审后的复核

独立评审后，调用条件改为「这一轮之后队列已空、维护未停止、结果不是 `Closed`」，并移到登记完成之后（见「设计」）；单测改为在关闭之前等待交还。修改后的 native SHA256 为 `559ae9e2af5b1a9674de1788c4acf0ab76f4bb3f408ccdce9ad5fe8690a97bfe`，在同一环境各跑一轮百万行：

| 项 | 验收中的本改动（三轮） | 复核 |
| --- | --- | --- |
| flush 后 RSS（MiB） | 742.3 | 741.7 |
| 重开后 RSS（MiB） | 734.4 | 734.5 |
| 反复写删：起止 RSS（MiB） | 741 → 1328 | 750 → 1339 |
| 反复写删：各周期最慢检索（ms） | 12.2–28.2 | 12.5–25.7 |
| 重开后首次检索（ms） | 20.8（20.4–22.3） | 23.5 |
| 写入吞吐（行/秒） | 23468 | 23583 |
| nq1 / nq100 检索 p50（ms） | 8.68 / 128.3 | 8.72 / 131.1 |

单集合场景下交还的时机与修改前相同，结果一致；多集合同时打开时只交还一次、关闭排空时不交还，这两点没有单独测量。

## macOS 观察

Apple M2 Pro、32 GiB、macOS（Darwin 27.2）开发机，桌面负载未隔离（一分钟负载最高 15），只观察 footprint（活动监视器显示的值），不作为性能结论；10 万行三轮、100 万行一轮，构建自 `48a3b3f`。

| 配置 | N | flush 后 | 重开后 |
| --- | --- | --- | --- |
| 默认 | 100000 | 433–437 | 138–142 |
| 默认 | 1000000 | 1247 | 932 |
| `MallocLargeCache=0` | 100000 | 78 | 75 |
| `MallocLargeCache=0` | 1000000 | 678 | 669 |
| `MallocSpaceEfficient=1` | 100000 | 74 | 71 |

- 默认配置下 flush 后比重开后多 295 MiB（10 万行）与 315 MiB（100 万行，一轮）；与设置了 `MallocLargeCache=0` 的同一状态相比，flush 后多约 355 MiB 与 569 MiB。`vmmap -summary` 显示多出的主要是 `Malloc Large (empty)`（10 万行时 259 MiB）与 `Malloc Small (empty)`，即系统分配器缓存的已释放块。
- `malloc_zone_pressure_relief(NULL, 0)` 返回 0，没有释放任何内存。
- 启动前设置 `MallocLargeCache=0` 可以消除这部分（`MallocSpaceEfficient=1` 只测了 10 万行一轮，结果相近）；这类变量只能在进程启动前设置，且作用于整个进程，本实现不代为设置。
- 减少 flush 与合并中的大块临时分配，可以同时改善两个平台，作为下一步单独调查。

## 正确性门

- [allocator.rs](../../crates/core/src/allocator.rs) 的单测在主线程与新线程中各调用一次；[db.rs](../../crates/core/src/db.rs) 的 `maintenance_rounds_release_free_memory` 确认维护轮次会调用它。
- macOS arm64（评审前）：`cargo test --workspace` 719 通过，`tests/python` 765 通过，clippy `-D warnings` 无告警。
- Linux x86_64（上述容器，评审前后两版各一次）：clippy `-D warnings` 无告警，`milvus-lite-core` 库单测 396 通过；wheel 的动态符号中有 `malloc_trim`。
- 评审后在 macOS arm64 上另跑：`milvus-lite-core` 库单测 395 通过（新增的两个单测连跑三次），开启 `fault-injection` 的 `milvus-lite-core` 849 通过，`tests/python` 765 通过；Windows 目标的 clippy 无告警。
- trim 不改变任何数据与持久化文件，没有新增差分或互通测试；完整矩阵以合入时的 CI 与 Compare 为准。
