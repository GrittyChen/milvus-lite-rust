## 结论

0.6.0rc1 交付 `0.5.0rc1` 之后合入的 0032–0035 与超出 f64 范围的 JSON 数字真值修正（过滤中的算术、hybrid 动态列类型推断、GEOMETRY 与几何谓词、公共 function chain），是发行工作流第一次在这些产品代码上运行。冻结提交满足候选方案的四项冻结条件；前置 CI 与 Compare、演练都在 attempt 1 一次全部成功。前四次正式运行都在签发前失败（三次是 macOS arm64 托管执行机未分配，一次是 macOS x86_64 上 CPython 3.14 冒烟阶段的依赖安装以退出码 2 失败、根因未查明），没有签发、没有消费版本，也没有重跑任何 attempt；第五次正式运行 attempt 1 全部 42 个 job 成功。各阶段计数逐项与收集数一致，没有失败、忽略或意外跳过，也没有 `transport-retry` 注解。正式运行在签发前完成本地保全，以保全工具输出的审批行批准后，一次签发覆盖七个附件的来源证明；签发后补存与复核通过，回执不变。`main` 已普通快进到冻结提交，台账登记 `candidate`，发布准备工具核对通过。

## 停服段错误：继承 0.5.0rc1 的发布级风险接受

`0.5.0rc1` 的接受以它的 `crates/` 树 `73fb12ff…` 为适用范围，本版 `crates/` 与 `Cargo.lock` 有变化，不自动适用。按调查记录「失效与继承」第二条，差异若不涉及停服、服务生命周期、原生交界或停服相关依赖，写明比较的提交与差异范围、经负责人明确确认后可以继承。比较的提交是 `fd70faf` 与 C1（`crates/` 与 D 相同），差异范围与结论见[候选方案](../releases/0.6.0rc1-candidate-plan.md#停服段错误继承-050rc1-的发布级风险接受)及上节冻结条件第 4 项：**停服路径逐字未变，残余风险集合扩大**。

适用范围：谱系以 D 的 `crates/` 树 `c695221b…` 与 `Cargo.lock`（相对 D 只差三个本项目 crate 的版本）为准，Rust 1.98.1，PyO3、tonic、tokio 等停服相关依赖相对 `0.5.0rc1` 逐字未变，同进程 grpcio 为 CI 固定的 1.84.0。上节四项冻结条件在 C1 上全部成立。

接受的残余风险与方案相同：`0.5.0rc1` 接受的全部残余风险（最终 flush 与打开路径的新代码、导入时调用的 PyO3 配置函数 `configure_flush_budgets`、稀疏与 BM25 检索、写入时生成输出字段、按字节预算的自动 flush 等在途处理体），加上本版新增的三类在途处理体（算术、几何、function chain），都没有托管机器上的定向停服压力证据。

这是「根因未查明、显式风险接受」，不是修复。截至本记录的十二次运行（冻结分支的 CI 与 Compare、演练、五次正式运行、`main` 上 C1 与台账提交的两次 CI、台账分支的 CI 与 Compare）中：

- 成功的两次发行工作流运行各自的 28 个「崩溃现场」步骤、六次 CI 与 Compare 运行各自的 9 个「崩溃现场」步骤全部为 skipped；
- 签发前失败的四次正式运行中，第一次的失败 job 运行了崩溃报告步骤，输出 `0 crash report(s) since the marker`，其余 27 个为 skipped；第三次的 27 个为 skipped；第二、四次在构建阶段停止，没有到达测试 job；
- 十二次运行全部 252 份 job 日志（被取消的 job 只有空日志）中没有 SIGSEGV、Segmentation fault、signal 11 或 core dumped 字样。

候选的任何运行再次出现停服路径 SIGSEGV，立即停止发布并撤回接受，按调查记录的停止条件处理，不重跑掩盖。

## 执行偏差

- **正式运行五次**：前四次在签发前失败（见「签发前失败的四次运行」），每次新开运行都由负责人单独决定。
- **第一次失败后未先查明根因即继续**：候选方案沿用的 0.4.0rc1「运行预算」要求判定层失败「先查明并写下根因，再决定是否继续」。第一次正式运行的冒烟安装失败属于判定层失败，根因没有查明；负责人在知情的情况下决定新开运行，这是对该条款的偏离。依据只有：同一步骤在演练、第三次与第五次正式运行中都成功。残余影响：不能排除正式 wheel 或固定约束在 macOS x86_64 / CPython 3.14 上存在间歇性的安装问题。根因无法查明的原因是冒烟安装日志不在失败时的收集范围内（[发行工作流](../../.github/workflows/release.yml)传给 `collect_records.sh` 的模式只有 `*-plan`、`*-run`、`*.log` 与 `acc-*/*.log`，不含冒烟的工作目录），这是一处诊断缺口，本候选不修改，发版后另行处理。
- 老内核抽查（检查点 5）与停服窗口诊断由负责人决定不执行（见「演练」与「冻结前的本地检查」）。
- 第四次正式运行触发前的第一遍核对（15:11:31）中，新写的核对命令查询 `release-signing` 部署时没有按冻结提交过滤，数到 6 个部署；逐个查看后都是 `0.3.0rc3`、`0.4.0rc1`、`0.5.0rc1` 与测试版本 `rc904` 的历史部署，没有 C1 的部署。这一遍作废并留档，改为按 C1 过滤后重新做两次核对（15:11:52、15:12:57）。第五次的核对同样按 C1 过滤；前三次的情况见「签发前失败的四次运行」。
- 冻结分支推送前核对与冻结确认、批准前核对、两次快进 `main` 前的核对与回读，以及第五次正式运行等待审批期间的扫描，当时只在执行会话中输出；起草本记录时按时间窗口从执行会话中逐字提取，补存到本地留存，内容与上文一致（其中两份夹有同一窗口内查阅 `0.5.0rc1` 命令记录的无关输出）。
- 第五次正式运行等待审批期间，第一次读取运行的 job 记录时网络连接中断（EOF）；这是只读查询，重新读取一次后完成比对。
- 首次发布准备核对在台账合入 `main` 之前执行，台账合入后补跑一次（见「签发后补存与发布准备」）。
