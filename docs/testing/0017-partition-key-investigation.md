## 范围与证据类型

本轮固定 34 个直接引擎场景，以及 65 个原始 gRPC / SDK 观察组，共 99 组；每组可含写入、查询、Flush、关闭、重开及后续写入的多个状态。这个数量是参照观察组，不是 Rust 差分用例或通过数。

直接引擎读取真实活跃位置、segment、WAL batch、运行时及磁盘 manifest、两个计数器；原始 gRPC 独立观察真实响应与可查询行，避免从内部状态推导协议结果。每轮包含 13 个实际子进程退出点，其中一个在 raw gRPC 已收到错误响应后直接退出。正常关闭后重开也有独立场景，不能用关闭替代进程退出。

`wal-late` 只对当前 collection 的第二次 WAL 追加前注入 OSError，`after-first` 在真实首桶 `_apply` 完成后退出；这些是诊断注入，既不修改参照文件，也不冒充真实 ENOSPC、部分字节写或断电。ARRAY 越界、普通批校验失败和 raw gRPC 报错后退出均不注入引擎故障。

工具只创建仓库外的新目录。内部恢复入口还要求同一脚本版本的场景所有权标记，拒绝错误场景、已有目录复用和符号链接；不安装依赖、不联网、不进入默认 pytest。核验保留列表次序、完整状态、错误原文、数字与布尔类型；不以 Python 的 `True == 1` 或 `1 == 1.0` 视为相同。

## 确认的行为

| 边界 | 参照实测 |
| --- | --- |
| schema / Describe | 至多一个 key；只能为非主键 INT64 / VARCHAR。nullable 和默认值允许；标志及默认值在 Describe 保留。非法 key 类型、多个 key、主键冲突的 code / reason 已逐项捕获 |
| 分桶数 | 固定 16 个 `_pk_0`…`_pk_15`，连同 `_default` 共 17 个名称；raw `num_partitions=-1/0/1/2/32` 都不改变这一结果 |
| 路由 | `MD5(str(value).encode()) mod 16`；INT64 十进制、VARCHAR 原字符串、None 为 `"None"`，不做 Unicode 归一化。0→`_pk_10`、1→`_pk_11`，空字符串→`_pk_14` |
| 默认值与缺失 | 缺失与显式 None 先按默认值填充；0 和空字符串同样生效。无默认且 nullable 时均路由到 `MD5("None")` 的桶；非 nullable 则先报业务校验错误 |
| 请求分区名 | key 集合的 Insert 忽略请求的 `partition_name`，包括不存在的名字；不能把 A 的显式分区存在性检查放到 key 路由之前 |
| 手动 Create / Drop | key 集合均报 code 6；Drop `_default` 和 Drop unknown 同样先报 key 禁止操作的错误，不沿用 A 的默认/未知分区分派优先级 |
| 处理顺序 | 以桶首次出现顺序处理，每桶内部保持输入顺序；按此分配 `_seq` 并写独立的 WAL batch。主键结果恢复到输入位置返回 |
| 跨桶重复主键 | 输入 key 为 `0,1,0`，同一个显式主键的 tag 为 `A1,B,A2` 时，最后生效的是 B；普通输入末行 A2 不决定结果。状态、Flush 及重开均固定 |
| 普通 / partial Upsert | 都进入引擎的“取旧行合并→Insert”。SDK 普通 Upsert 会预填遗漏的 nullable key 为 None，或预填默认值；partial 保留字段缺失，因此引擎合并后沿用旧 key。两种调用可路由到不同桶 |
| 更换 key | 全集见新桶版本；旧行已在 segment 时，单选旧桶仍可读旧值，继续继承 A 的选择集可见性 |
| 存量 WAL 的隐含桶 | 新建 key 集合尚未 Flush 时，磁盘可以没有 manifest，WAL 已含 `_pk_10` / `_pk_11`。3.x 重开恢复这些行，并重新建立 16 桶；B 的恢复不能只依赖磁盘已有分区键 |

### 普通成功请求中的 auto_id 顺序

三行输入 key 为 `0,1,0`：

| 输入位置 | tag | 参照 auto_id | `_seq` | 处理位次 |
| --- | --- | --- | --- | --- |
| 0 | A1 | 1 | 1 | 0 |
| 1 | B | 2 | 3 | 2 |
| 2 | A2 | 3 | 2 | 1 |

RPC 返回 `[1,2,3]`；物理批为 `[(id=1,seq=1),(id=3,seq=2)]` 和 `[(id=2,seq=3)]`。这说明已知的逐行 ID 上界问题在普通成功分桶请求中也存在，不只发生在失败之后。

### 不注入故障即可触发的部分写入

仍用 `0,1,0`，第二行 ARRAY(INT8) 元素为 128，其余两行合法：

1. 前置业务校验只检查数组形态和容量，三行通过。
2. 首桶 A 的两行完整写入 WAL 与 MemTable，auto_id 为 1、3，`_seq` 为 1、2。
3. 后桶 B 的 Arrow 转换失败，raw gRPC 返回 code 1，reason 为 `Value 128 too large to fit in C integer type`；返回 IDs、成功/失败位次均为空，Query 却能读到 A1、A2。两条 SDK 也实际收到同一错误并可读到这两行。
4. 同一会话立即再写，得到 ID 4。若报错后直接退出再重开，或者正常关闭后立即重开，计数器均从可恢复的最大 seq=2 继续，下一次得到 ID 3，全集覆盖原来的 A2。

相同坏值在首桶时没有前缀写入；落在同一个桶时也没有写入，因为该桶 Arrow 转换整体失败。超容量等前置业务校验失败则整批无写入，但仍消耗参照的 auto_id，沿用 0004 已登记问题。

## 已采纳的三项方案与合同边界

完整规范见 [0017 B 合同](../decisions/0017-partitions.md#b-合同设计已通过)。以下记录已采纳的方向及继承边界，不替代合同中的阶段、错误顺序和验收定义：

1. 保留首次出现桶的处理顺序、显式主键的去重与可见性；生成的 auto_id 取该行 `_seq`。上述普通请求返回 ID 将为 `[1,3,2]`，这是必须显式登记的兼容性影响，不能仍声称普通分桶请求的生成 ID 与 3.x 相同。
2. 在任何 WAL 追加前完成整批业务校验和全部桶的 Arrow 转换；确定性转换错误整批无写入、无编号消耗，保留错误码和信息。该行为相对 3.x 的部分写入属于已采纳的 B2 差异，仍须按完整合同接受评审。
3. 真正 WAL 追加故障仍按 0007 的已校验前缀、编号不回退及恢复保证处理；上面第 2 项不构成跨桶 I/O 事务。原有已确认数据须保留，任何报错不得伪装成功。
4. 已有 3.x 坏前缀另作保护：重开读取后，如果本次自动生成的主键将覆盖写入前已可读的行，按已采纳的 B3 方案，在首个 WAL 前以 code 1 拒绝整批，不消耗编号、不修改旧文件。仅以候选主键查询既有位置表；显式提供主键的覆盖语义保留。单纯 ID=seq 只能保护 Rust 新写出的行，不能消除存量 `(id=3,seq=2)` 的风险。这是已采纳的 B3 差异；不会声称旧目录已被修复，或保证它随后由 3.x 写入也安全。
5. 读入带 key 的 schema 时，在内存中将固定 16 桶加入逻辑注册集，再校验和回放 WAL；不为打开而重写旧 manifest。除 schema 推导出的精确桶集合及 manifest 已登记名称外，未知 WAL 标签仍拒绝。

合同交付时，三项方案已采纳但完整合同尚待评审，产品仍拒绝 partition key；该历史调查没有把方案采纳等同于实施授权。随后设计准入通过并进入实现，当前产品证据见 [B 验收](0017-partition-key-acceptance.md)，不将本页参照结果冒充 Rust 验收。
