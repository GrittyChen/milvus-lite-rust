# 过滤表达式性能专项

日期：2026-11-26 至 2026-11-27。改前为 `7278f63`。改动分四个提交：

| 提交 | 内容 |
| --- | --- |
| `fd4590b` | Query 有 limit 且各块已按序时直接取前 k 条，不对全部命中行排序 |
| `6267b58` | 只引用 schema 非 JSON 列与字面量的布尔树逐块在原列上求值，任一块出错回到整源路径 |
| `5ea261c` | 比较、`in`、`like` 与 and / or / not 等节点改用类型化内核 |
| `1fe1410` | 动态字段每个键只逐行查一遍 meta |

本记录的测量以 `c63b21f`（含上述四个提交）为改后。过滤的语法、语义与三条求值路线见 [0014](../decisions/0014-index-definitions-and-filter-expressions.md) 与 [0032](../decisions/0032-arithmetic-filters.md)；S1 路线此前的优化见 [S1 过滤性能](s1-performance.md)。

## 结论

- 100 万行（全部存活、已 Flush），count 的 p50：
  - **like**：前缀 364 → 12 ms（2.5.1 为 13 ms），后缀 328 → 14 ms（2.5.1 为 126 ms）。
  - **`in`**：50 项 87 → 21.5 ms（2.5.1 为 13–23 ms），5 项 82 → 8.0 ms（2.5.1 为 8–15 ms）。
  - **算术**：`tag * 3 + 1 > 1500` 87 → 17 ms，2.5.1 不支持。
  - **组合**：`(a and b) or c` 203 → 15 ms（2.5.1 为 7–9 ms）；含 `not (...)` 的组合 249 → 20 ms，2.5.1 不支持。
  - **JSON / 动态字段**：`$meta["k"] > 500` 272 → 128–135 ms（2.5.1 为 103 ms）；`s == "v7"` 231 → 160 ms（2.5.1 为 110 ms）。
- **Query limit 100**：宽命中的 `tag < 500` 6–10 → 4.7 ms，2.5.1 为 2.5–2.7 ms。
- **未经过改动路径的表达式**（整数等值与区间、varchar 等值、浮点区间）：
  - count 都在 2–7 ms。`tag < 500` 改前两轮为 1.93 与 3.49 ms、改后为 3.4 ms，测量区分不了时段漂移与小幅回退，比 2.5.1 慢约 1 ms；varchar 等值比 2.5.1 快约 5 ms。
  - 带过滤单条检索中，`tag < 500` 为 9.5 ms，2.5.1 为 38 ms。
- **3.x**：同一数据上比改后的本实现慢约 30 倍到近万倍。100 万行时：
  - 慢得最少的是动态字段：带过滤检索 `$meta["k"] > 500` 为 3.5 s（本实现 124 ms）。
  - 慢得最多的是整数与浮点区间：count 约 26 s（本实现 2.7–3.4 ms）。
- **结果一致**：本实现改前改后、2.5.1、3.x 的全部 count 相同（2.5.1 不支持的表达式除外）。Query 与检索的结果摘要，在本实现改前改后之间、以及与 2.5.1、3.x 在各自支持的表达式上也都相同；Query 的摘要按排序后的 id 计算，不比较行序。
- **仍落后于 2.5.1 的表达式**（100 万行）：
  - **JSON / 动态字段**：count 约为 2.5.1 的 1.25–1.45 倍；带过滤检索中 `$meta["k"] > 500` 反而更快（124 对 135–151 ms）。
  - **`(a and b) or c`**：count 与 Query 约为 2 倍；带过滤检索更快（20 对 28–33 ms）。
  - **`in` 50 项**：Query 约为 1.7 倍（23 对 13–14 ms）；count 为 21.5 ms，2.5.1 各轮 p50 为 13.2–22.6 ms。
  - **Query limit 100 宽命中**：约为 1.8 倍。

  10 万行时，动态字符串与组合表达式的 count 仍比 2.5.1 慢，见「10 万行」。

## 环境与方法

x86_64 服务器（AMD EPYC 7702），容器绑定 16 个核；Rust 1.98.1、Python 3.12、pymilvus 3.0.2、grpcio 1.85.1、protobuf 7.36.2、NumPy 2.5.5。2.5.1 为 `milvus-lite==2.5.1`；3.x 为 `milvus-lite==3.2.2`，pyarrow 26.0.1。

**数据**：每批 1 万行写入，最后 Flush 一次。字段与取值：

| 字段 | 类型 | 取值 |
| --- | --- | --- |
| `id` | INT64 主键 | `i`，0 起 |
| `vec` | 128 维 float 向量 | uniform，seed 42，FLAT L2 |
| `tag` | INT64 | `i % 1000` |
| `score` | DOUBLE | `[0, 100)` 均匀 |
| `name` | VARCHAR（max_length 64） | `n{i % 10000}` |
| 动态字段 `k` | 整数 | `i % 1000` |
| 动态字段 `s` | 字符串 | `v{i % 50}` |

三方各建一个 10 万行库与一个 100 万行库。本实现改前改后读取同一物理库。表中 `tag in [0, 17, …]` 为 0 到 833、公差 17 的 50 项。

**测量**：每个表达式测三种操作：
- `count(*)`；
- Query 输出 `id`、limit 100；
- 带过滤的单条检索，top 10。

每项先调用一次，记下结果或结果摘要，再计时至少 3 次、至多 20 次，单项累计超过 10 s 即停，取 p50。服务端在独立进程中运行，所用的 `server_process.py` 与 [benchmarks/baseline/server_process.py](../../benchmarks/baseline/server_process.py) 相同。

**轮次与时段**：各配置顺序执行、交替轮换。

| 时段 | 内容 |
| --- | --- |
| 2026-11-26 | 改前与 3.x 的数据。10 万行三方三轮；100 万行本实现与 2.5.1 两轮、3.x 一轮；补充四式只测本实现与 2.5.1 |
| 2026-11-27 | 改后与 2.5.1 交替：两个规模各按「改后、2.5.1、2.5.1、改后」的对称顺序各两轮，主表达式与补充四式都测 |

表中 2.5.1 的区间合并了两个时段；3.x 在 100 万行只有一轮。

**测量工具**：基准脚本与引擎层探针都在仓库外，性能数字只由负责人本地留存的证据支撑。结果表来自留存的原始 JSONL，证据还包括构建与环境清单，以及改后 wheel 的 SHA256 `0e55f1de17d7615a1bd86c53f9563a2eba3633a97feaee66ffd90c3f1d3fcf7d`。「根因与改法」中的 perf 占比与各步收益来自开发期的采样与引擎探针，同样由负责人本地留存，不在上述 JSONL 内，不能由结果表重算。正确性由仓库内的测试与差分保证，见「正确性」。

**代码布局与调频**：同机先后运行时，服务器的调频策略会制造与顺序有关的假差。可疑项都按两种先后顺序复测，结论按区间给出。改前与改后不在同一时段测量。时段漂移的参照有两个：
- **2.5.1 两个时段的同一批表达式**：基本一致，例如 100 万行 JSON 比较的 count 为 102.6–102.8 对 102.7 ms，`tag < 500` 的检索为 38.3–38.4 对 38.0–38.1 ms。
- **本实现未经过改动路径的表达式**：count 改后都落在改前的区间内。但 `tag < 500` 的改前区间宽达 1.5 ms，这一项区分不了漂移与小幅回退。

## 根因与改法

改前，布尔树路线（[filter/eval.rs](../../crates/core/src/filter/eval.rs) 的 `Predicate::from_parsed` 中不属于 AND 连接比较与根主键 `in` 的表达式）一律经整源路径：
1. 按 3.x 的遍历顺序收集存活行，逐行复制所引用的列；
2. 每个节点每行经 `Scalar` 枚举做通用求值；
3. 结果位图逐位写入，每次都经 `Arc::make_mut`。

宿主机 perf 采样（100 万行）显示：
- **like**：约 55% 在内存分配：每行一个码位向量，每个记号一个 DP 向量；
- **`in`**：约三成在 SipHash 集合；
- **JSON / 动态字段**：47%–62% 在逐行 `IndexMap` 查键；
- **Query limit**：约 57% 在收集全部命中行的引用并排序。

| 步骤 | 改法 | 100 万行主要变化（ms） |
| --- | --- | --- |
| `fd4590b` | 各块均为原始代且键区间按块序相接不重叠时，按收集顺序取前 `offset + limit` 条即停 | Query limit 100 `tag < 500` 6.4 → 3.1–5.0 |
| `6267b58` | 只引用 schema 非 JSON 列与字面量的树按块在借用列上求值；全部块成功才采用，否则回到整源路径以保持报错的行序与文案；存活行不足一半时直接走整源路径 | count：`tag in [0, 17, …]` 86 → 51、`tag * 3 + 1 > 1500` 88 → 51、含 `not` 的三项组合 250 → 143 |
| `5ea261c` | 比较按列类型单态化、标量绑成常量；`in` 在不需转换列类型时排序后二分查找（浮点按位）；`like` 不含 `_` 时按 `%` 切成字面段在 UTF-8 上匹配，含 `_` 时复用缓冲；and / or / not、is null 与算术的有效位按 64 位字计算 | count：`name like "n12%"` 276 → 11、`tag in [1, 2, 3, 4, 5]` 34 → 6.9、`(tag > 10 and tag < 300) or name == "n42"` 102 → 14 |
| `1fe1410` | 推断与物化共用一次逐行收集，推断的输入集合与顺序不变；键数不超过 4 的对象按序比较键名 | count：`$meta["k"] > 500` 380 → 154、`s == "v7"` 280 → 175 |

各列数字的口径：
- **前两步**：pymilvus 端到端，与结果表同一套脚本，都对比 `7278f63`（第 1 步不影响这些 count）。
- **后两步**：引擎层探针，对比前一个提交。探针不经 RPC，读取另一份按相同逻辑数据建的 100 万行库，物理布局不同，绝对值与端到端不可比（例如 JSON 比较在探针上比端到端还慢）。这些数字只用于说明各步的贡献，不能与结果表相加减。

各步都保留 3.x 的语义约束，并由测试守住：
- and / or 不短路；
- DFS 后序求值；
- 可回退与不可回退的错误之分；
- 整数转浮点的 ±2^53 与 float32 ±2^24 检查只看本侧有效位、按行序报第一个越界值；
- float32 列升 f64 比较；
- `in` 的浮点集合键按位区分 ±0 与 NaN；
- Kleene 三值逻辑，`not in` 对 null 为真；
- `like` 用 Arrow 的转义规则；
- 动态键推断与转换对行序的依赖。

## 正确性

- **新旧内核对拍**：优化前的列式内核原样保留为测试模型，见 [filter/columns/kernel_tests.rs](../../crates/core/src/filter/columns/kernel_tests.rs)，随机与确定性对拍结果、有效位、错误种类与文案。另有三组对照测试：
  - 根主键 `in`；
  - 按块路径与整源路径（[tree_tests.rs](../../crates/core/src/filter/tree_tests.rs) 的 `chunk_entry_agrees` 与多块随机对照）；
  - 小对象查键与 `Map::get`。
- **变异检查**：每一步都做了。非等价的变异都被测试抓到；未被抓到的都论证为等价变异，其中多余的分支已删除。
- **全量测试**：第 4 步提交前，`cargo test --workspace` 774、fault-injection 903、`tests/python` 767、与 3.x 的差分 874 全部通过；[fuzz_arith](../../tests/differential/fuzz_arith.py) 种子 32 / 33 各约 5 万条，0 不一致。
- **CI**：各提交经临时分支的 CI 与 Compare（各 12/12）后合入。

## 剩余差距与后续

- **JSON / 动态字段**：剩余开销在逐行访问百万个分散小对象的访存、字符串物化的逐行分配，以及数字在推断与物化中各解析一遍。
- **`(a and b) or c` 与 `in` 50 项**：仍比 2.5.1 慢，单线程内核已不是主要开销，剩余部分在整源与按块路径的固定开销上。
- **按块并行**：可能抹平上述差距。它需要先写并发设计并经负责人确认；动态键的类型推断依赖整个数据源的行序，并行时要拆成并行收集与按序推断。
- **未测量**：存活行稀疏（大量删除且尚未合并）时会走整源路径，本记录未测量该场景。
