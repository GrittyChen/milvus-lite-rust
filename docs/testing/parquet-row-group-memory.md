# Parquet 行组上限与写入峰值

日期：2026-11-21。改动前的基线为 `a93ba64`（其中 crates 与 `a82bc41` 相同，已含[分配器保留内存](allocator-retention.md)的 `malloc_trim`），改动随本记录所在的提交合入。证据的分类与复核范围见[证据的存放与复核范围](README.md)，本记录的划分见文末「证据范围」。

## 结论

- 百万行写入过程中，进程 RSS 的峰值来自自动 flush 写 Parquet 的那一步。ArrowWriter 默认每个行组上限 1048576 行，要把整个行组编码完才落盘；一次 flush 的整代数据（memtable 预算 128 MiB，128 维时约 25 万行）因此全部以编码形式缓存在内存里。
- 改动：每个行组上限 64Ki 行、32 MiB，批数据按 4096 行切片写入，使字节上限在第一个行组内也生效。百万行写入期间的服务端 RSS 峰值（`VmHWM`）由 1618–1622 MiB 降到 1229–1309 MiB，逐轮配对低 311–389 MiB。同机 2.5.1 约 940 MiB，仍高约 290–370 MiB，见「剩余的峰值」。
- flush 后与重开后的 RSS、写入耗时、反复写删的 RSS 在三轮或一轮测量中未见可辨变化；检索延迟只测了一轮，见「验收测量」。数据文件仍是标准 Parquet，只是行组更多；3.x 用 pyarrow 15 与 25 都能读，由存储互通用例证明。

## 定位

测量使用仓库外的诊断构建：替换全局分配器统计 Rust 堆的存活量与峰值，并在 flush、合并、打开集合、各 RPC 处理体上加阶段标记，记录每个阶段在本线程内相对起点的分配峰值、≥1 MiB 的分配次数与总量，以及全局峰值出现时所在线程的阶段。数据与 [benchmarks/baseline](../../benchmarks/baseline/README.md) 的 `memory` 阶段相同，x86_64 服务器容器（与[分配器保留内存](allocator-retention.md)同一环境），10 万与 100 万行各三轮，每轮结果完全相同。

百万行（MiB）：

| 时刻 | Rust 堆 |
| --- | --- |
| 进入第 4 次自动 flush 时的存活量（已发布的段与这一代 memtable） | 约 895 |
| memtable 物化为 Arrow 批 | +130 |
| Arrow 批解码为引擎的列数据 | +130 |
| 写 Parquet 的瞬时分配（约为 Arrow 批的 3.3 倍） | +424 |
| 全局峰值，出现在 `flush.write` | 1579 |
| 写完后的稳态存活量 | 681 |

- 10 万行时手动 flush 的峰值为 440 MiB，存活量 63 MiB，同样出在 `flush.write`。
- 重开集合时读取文件的瞬时分配约 64 MiB，不是峰值来源。
- 反复写删（每个周期 upsert 5 万行、删除 1 万行、flush）时，每次 flush 只有 5 万行，原本就只有一个行组；合并准备阶段的瞬时分配约 317 MiB，主要花在读取与合并，不在写文件。

## 设计

- [parquet_file.rs](../../crates/core/src/storage/parquet_file.rs) 的 `write_new` 设 `max_row_group_row_count = 65536` 与 `max_row_group_bytes = 32 MiB`。flush、合并与 delta 文件都经这一处写出。
- parquet 的字节上限只在行组已缓存数据之后按平均行宽判断；整批一次写入时，第一个行组会吞下整批。因此按 4096 行切片写入（`RecordBatch::slice` 零复制）。行数上限对窄行起作用，字节上限对宽向量起作用。
- 字节上限是软上限：第一个分片写入时行组还没有缓存行，parquet 不做字节检查，所以一个行组最多超出一个分片。例如 4096 维（每行 16 KiB）时一个行组约 64 MiB。flush 的批大小本来就受 memtable 预算（128 MiB）限制，宽向量下也不比改动前差。
- 不改变物理行顺序、列类型与压缩；读取端不依赖行组数量（本实现只在恢复时读取 Parquet，按批读出；3.x 用 `pq.read_table` 与 `ParquetFile(...).metadata.num_rows`）。写入参数登记在 [0002 约束 9](../decisions/0002-data-dir-compat.md)。

诊断构建上比较过另外一种设置：在行组上限之外，再关闭浮点向量列的字典编码。峰值 1274 MiB，与只设行组上限的 1275 MiB 相同，没有采用。

## 验收测量

正式构建（不含诊断代码），x86_64 服务器容器。基线环境与改动后的源码只有 `parquet_file.rs` 不同，Cargo.lock 相同。百万行三轮交替，反复写删与 m2 各一轮。服务端 RSS 单位为 MiB。

| 项 | 基线 | 改动后 |
| --- | --- | --- |
| 写入期间的 RSS 峰值（`VmHWM`），第 1 / 2 / 3 轮 | 1622 / 1618 / 1620 | 1237 / 1229 / 1309 |
| 写入结束时的 RSS | 785–808 | 797–812 |
| flush 后 | 746–770 | 742–771 |
| flush 后 30 秒 | 745–753 | 742–771 |
| 重开后 | 734 | 732–734 |
| 写入 100 万行耗时（s） | 40.6–42.2 | 41.5–42.3 |
| 重开 load（s） | 1.64–1.67 | 1.64–1.66 |

同机 2.5.1 一轮：写入结束时服务端子进程 695 MiB，flush 后峰值 940 MiB，写入耗时 75.6 s。

- 改动后峰值的三轮波动（1229–1309）大于基线，原因未查；逐轮配对低 311–389 MiB。
- 诊断构建上，4 次自动 flush 写文件的合计耗时由 3.0–3.3 s 变为 3.3–3.7 s，写入总耗时看不出差别。数据文件总大小由 502 MiB 变为 511 MiB。
- m2（百万行、128 维 FLAT，各一轮，客户端与服务端同进程）：写入 23645 → 23837 行/秒；单查询检索 p50 8.72 → 8.68 ms，100 个查询 130.8 → 128.7 ms，1% 字符串过滤 7.04 → 7.44 ms，查询 p50 5.40 → 4.87 ms，写入期间检索 113.5 → 113.9 QPS；重开后首次检索 18.9 → 23.1 ms。只有一轮，不足以判断这些差异，其中 1% 字符串过滤与重开后首次检索的方向偏慢。本改动只改变 Parquet 写入，不在这些读取路径上。
- 反复写删 20 个周期：两版 RSS 都从约 790 MiB 涨到约 1350 MiB，检索 p50 都是 11.3 ms。这一增长来自被覆盖的旧版本行没有回收，与本改动无关，另行处理。

## 剩余的峰值

改动后，百万行写入的峰值仍比 2.5.1 高约 300–370 MiB。按诊断数据，flush 时同一代数据同时有三份：memtable、Arrow 批、解码后的列数据，额外的两份约 260 MiB。去掉其中一份需要改变列数据的内部表示，没有在本改动中处理。

## 正确性门

- 单测 `row_group_limits_bound_each_group_and_round_trip`：行数上限与字节上限各自切分行组（字节上限用小值验证分片使它在第一个行组内生效）；`write_new` 以生产常量写 7 万窄行，行组为 65536 与 4464；读回的数据与原批逐段相同；空批不产生行组。
- 存储互通 `test_rust_multi_row_group_data_file_opens_in_reference`：本实现一次 flush 写出 7 万行（两个行组以上），pyarrow 15 与 25 完整校验、逐行核对 `_seq` 与主键，3.x 引擎按行组边界前后的主键读出相同的行。
- 本机（macOS arm64）：clippy 无告警，workspace 单测 720 项、fault-injection 单测 850 项、`tests/python` 765 项、存储互通 337 项全部通过。服务器容器（Linux x86_64）上 clippy 与 core 单测通过。存储互通的收集数随之由 336 改为 337（Compare 的分片计划与发行记分牌）。

## 证据范围

- 仓库内可重跑：单测与存储互通用例；m2 与重开数字可用 [benchmarks/baseline](../../benchmarks/baseline/README.md) 在同类机器上重测（绝对值随机器而变）。
- 只有本地证据：「定位」中的阶段分解来自仓库外的诊断构建（计数分配器与阶段标记，不入库）；写入期 `VmHWM`、反复写删与 2.5.1 的峰值来自仓库外的测量脚本。原始输出由负责人本地留存。验收所用正式构建的扩展 SHA256：基线 `559ae9e2af5b1a9674de1788c4acf0ab76f4bb3f408ccdce9ad5fe8690a97bfe`，改动后 `e9434dd1150c953dc0692e8ac5db9096dfaec30e6ea5d42f553088901d0129fd`（评审后的修改只涉及注释与测试）。
