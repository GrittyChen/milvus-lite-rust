## 执行方式与条件

每个平台依次执行 0019 试点表的各阶段：互通三条 Cargo 命令的预构建与 `fresh` 核对，差分两条 SDK 线与互通的串行基线（单片计划），P0（三条线同时、各单片），P1（三条线同时、各 N 片，按耗时均衡、单元顺序轮转、单元倒序轮转各一次；两个 Linux 平台另试一个 N），敏感用例在 P1 主 N 的平台总并发下各重复 10 次。差分敏感子集为 CLI、LOCK、compaction 与重开用例（24 项），互通为崩溃、ARRAY、nullable 与索引存储用例（77 项）。全程每 2 秒采样进程数、线程数、内存与负载。

| 平台 | 主机与运行方式 | N | 条件 |
| --- | --- | --- | --- |
| Linux x86_64 | 原生多人共享物理机（256 线程、约 2 TiB 内存）、glibc 2.28 容器、非 root | 4，另试 6 | 内核 3.10；负载为整机值，含其他用户 |
| Linux arm64 | 本机 Docker VM（10 CPU、7.75 GiB 内存）、glibc 2.28 容器、非 root | 2，另试 3 | 与 macOS 共用本机，依次运行 |
| macOS arm64 | 本机原生 | 4 | 桌面应用常驻，负载与内存峰值主要来自它们 |

各阶段时长按分片工具在 `processes.json` 中记录的进程起止计算，不使用驱动的顺序等待时间。本机运行期间持有防睡眠断言；10-21 17:00–23:40 的电源日志中，睡眠与唤醒只出现在 21:48–22:13，此时 arm64 试点已按中断记录停止、后续运行尚未开始；23:26 之后的 arm64 互通复验以运行时的系统日志为准，未另行导出。

x86 首轮串行基线的 pytest 自报时长为 42.8 / 42.6 / 33.9 分钟，与 0.3.0rc2 候选的 42.7 / 42.8 / 34.0 一致，测量条件可比。arm64 的串行基线慢于 rc2 扣除睡眠后的数值，同一会话内差分两条线也相差 6.7 分钟；运行区间无睡眠，推断来自宿主机桌面负载对 VM 的影响，因此 arm64 的收益只按同一会话内的相对值判断。

正确性：试点计划内完成的各次运行，插件执行记录与 JUnit 均与计划一致，执行并集等于收集全集，skip / xfail / xpass 为 0；被中断的运行与环境错误的复验首轮见下文「执行接续与证据边界」。收集集合的比较对象如下，均逐项相同：

- 首轮各阶段与敏感子集：同平台、同源码的串行基线（敏感子集为其按序子集）。
- x86 修复后：差分对照本轮 421 项串行基线，互通对照首轮串行基线。
- macOS 与 arm64 的修复后差分：本平台没有 421 项基线，对照 x86 修复后的串行基线。
- arm64 互通复验：对照 arm64 首轮的互通串行基线。

完成的运行中共出现两次失败，均定位为测试基础设施问题并修复（见下节），其余全部通过。修复后复验：

- Linux x86_64 以修复后的差分源码重做串行基线、P0、P1 三种分配、N = 6 与敏感用例，全部通过；首轮失败的 P1 单元顺序轮转此次通过。
- Linux arm64 单独运行修复后的完整互通 211 项（N = 3，3 个进程，争用低于失败时 9 个进程的平台总并发），通过；修复有效性由独立复审的确定性复现支撑。
- macOS（N = 4）与 Linux arm64（N = 2）以修复后的差分源码各运行一次两条 SDK 线同时的完整分片差分，均为 421 项通过，用时分别为 4.3 与 14.0 / 14.1 分钟。

资源峰值取同一 N 下各阶段的最大值，x86 合并两轮：

| 平台与范围 | 进程 | 线程 | 内存 |
| --- | --- | --- | --- |
| x86 P1 N = 4 / N = 6 | 35 / 45 | 6377 / 7118 | 进程常驻合计 7.9 / 8.9 GiB |
| x86 敏感用例（每批最多 18 个 pytest 进程） | 69 | 8658 | 4.5 GiB |
| arm64 P0 / P1 N = 2 / P1 N = 3 | 15 / 21 / 26 | 317 / 450 / 486 | cgroup 6.31 / 6.46 / 6.92 GiB |

x86 的线程数来自每个 Rust 服务按 256 个逻辑 CPU 创建线程池；进程数上限为 unlimited，未触及，主机内存余量充足。arm64 的 cgroup 计数含可回收的文件页缓存，但 N = 3 时与 7.75 GiB 的 VM 内存只余不到 1 GiB。macOS 的采样覆盖全部桌面应用，不用于判断测试资源。

## 试点发现

机制、修复与对既有证据的评估以 0019 为准，此处只记录本次的观测：

1. **参照服务端口复用**（x86 首轮 P1 单元顺序轮转，差分 3.0.2 一项失败），见 [0019](../decisions/0019-test-sharding.md#试点发现参照服务的端口复用)。50 个存活监听下 20000 次端口 0 自动分配，x86 撞上 29 次，arm64 与 macOS 为 0；同时运行 20 个真实参照服务时，修复前 16 次、修复后 0 次。此前一次同类探针观测为 38 次与 18 → 0 次，原始输出未保留。修复为 `b788a83`，差分收集与会话组变为 421 / 118。
2. **参照实现崩溃时的索引文件**（arm64 P1 N = 3，互通一项失败），见 [0019](../decisions/0019-test-sharding.md#试点发现参照实现崩溃时的索引文件)。独立复审只在写入子进程内放慢参照的索引保存：修复前写入留下 0 字节侧车，修复后侧车为 136 字节；参照随后报出原错误、修复后交叉打开通过的观测记录在复审报告中，其输出未单独留存。修复为 `1d70755`。

macOS 与 arm64 共用本机，仍依次运行；x86 与本机序列从开始即并行。按本次各阶段实测与 0.3.0rc2 候选中未变阶段的时长相加：本机两平台合计约 60 分钟；x86 约 30 分钟，其中假设预热后 PID 1 与 arm64 命中镜像缓存相当（约 0.2 分钟），若未命中则按 rc2 的 13.8 分钟计约 43 分钟。端到端约 60 分钟（rc2 为 296 分钟）。这是组合估计，下一候选采用后以实测为准。

## 执行接续与证据边界

- arm64 的 P1 N = 3 首次运行因负责人改用电池，按中断记录停止：三条线均写入 interrupted，各分片以 SIGTERM 结束，未产生汇总，不计入上文的运行结果。恢复交流供电后，在同一平台目录完整重跑该阶段及其后的敏感用例。
- arm64 互通修复复验的首轮未设置 `src/target` 指向 Cargo 输出目录的软链，依赖 Rust 工具二进制的 22 项在进入产品断言前报找不到文件；补设软链后在新目录完整重跑通过，首轮输出保留。
- 两次失败的测试数据目录已被首轮驱动在运行后清理，根因由内核探针、调用链与独立确定性复现确认。x86 修复后重跑保留了各分片的服务日志 3776 份：参照服务日志 3712 份，CLI 用例的参照与本实现日志各 32 份。会话级参照服务的工作目录由差分 conftest 在会话结束时删除，其日志不在保留范围内。
- macOS 与 arm64 的首轮试点基于修复前源码；二者内核不受端口复用影响，互通问题已在 arm64 以修复后源码复验。
- 本次未以 P0 / P1 运行完整候选矩阵，也未改变各阶段通过判据；Python 全套、Rust / FI、PID 1 等阶段的时长取自 0.3.0rc2 候选。
