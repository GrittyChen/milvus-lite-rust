# 代码审查规则

> 本文档是一套可验证的闭环评审协议，目标是：
> 1. 禁止牙膏式地反馈问题，推进工作尽快闭环收敛
> 2. 禁止过度设计，但保证不遗漏真有影响的问题
> 3. 禁止因修复引入新的二、三阶衍生问题
>
> 每个目标都有对应的操作规则兜底：
> - 目标 1 → 第 4 条；
> - 目标 2 → 第 5、6 条；
> - 目标 3 → 第 7、8 条。
>
> 规则不靠自觉，靠可复核的证据。

仅审查时保持只读；修复建议不等于修改代码的授权。检查深度按变更风险调整，不把局部审查扩展为全仓安全审计，也不因接触高风险代码而擅自扩大用户任务。

## 1. 先冻结评审合同

**优先使用已有合同；没有现成合同时，由评审方根据需求、现有行为和测试建立最小合同。** 评审开始前明确：

- 本次工作要保证哪些不变量。
- 哪些行为必须保持兼容。
- 哪些失败语义必须维持。
- 哪些内容明确不在本次范围。
- 达到什么条件才算通过。

后续问题和建议都必须能对应合同。无法对应实际合同、用户场景或明确风险的内容，不应列为问题。

从需求和代码推导的合同应注明依据；只有影响正确性或范围的歧义才需要询问用户，不要求每次审查都先举行确认流程。无法确认的内容标记为“待确认”，不要自行假定为已冻结的不变量。评审中若对合同本身有异议（范围划错、不变量缺失），单独提出并显式修订合同，不混入问题清单。

## 2. 按完整调用链评审，不只看修复函数

必须从真实入口一直检查到最终副作用：

```
外部入口 → 参数构造 → 调用方前置操作 → 核心实现 → 持久化/外部调用 → 失败处理 → 重试/清理 → 消费方
```

典型失败模式：安全原语本身修对了，但调用方在进入原语前还有一个旧的前置写入，绕过了修复。只审核心函数，无法证明系统行为闭环。

## 3. 发现一处问题后，按「问题类别」全域清扫

本节产物是扫描证据。发现问题后先提炼其共同不变量，在约定范围和直接关联调用链内搜索同类出口，再汇总反馈。“全域”指这一明确边界，不是无限扩展到整个仓库。

例如，发现“未经验证的路径写入”后，应同时清点：

- 所有 `mkdir`、`open`、`write_text`、`replace` 等写入。
- 所有调用者的前置写入。
- 实际存在的正常、重试、恢复等替代路径。
- 新建、复用、失效、部分失败等相关状态。
- 中间目录、最终目录、最终文件等不同攻击面。

同一根因、同一修复边界的问题合并列出相关出口；需要独立修复的问题分别报告，不因类别相同而掩盖不同影响。

**清扫必须留下扫描方法证据**：反馈中写明用了哪些搜索模式（grep 表达式 / 目录范围 / 排除项）、覆盖了哪些路径与状态组合。“已完成全域搜索”是一个可复核的过程记录，不是一句断言——没有方法证据的清扫不算完成。

## 4. 每轮反馈必须是完整清单

本节产物是问题清单。每轮评审输出的是**当前范围和证据下发现的全部问题**，按优先级排序，一次性给出，不以“完整”暗示证明不存在其他缺陷。后续轮次的新问题应说明来源：

1. 本轮修复引入的回归（属于第 7、8 条的检查产物）。
2. 此前确实漏掉的问题，且必须附带“为何上轮清扫没有覆盖到”的说明（哪个搜索模式缺失、哪条路径没枚举）。
3. 新增需求、范围变化或新证据揭示的问题，说明相对上一轮的变化。

第二类连续两轮出现同类漏项，说明清扫方法系统性失效，应停止逐条反馈，转入组件级收敛（冻结不变量 + 完整测试矩阵 + 只读评审）。

## 5. 问题必须达到证据门槛，并强制标注分级

阻断问题至少需要三个条件：

1. 存在真实可达路径。
2. 违反明确合同或产生可观察错误。
3. 有实质影响，而非纯理论上的“不够优雅”。

最好提供反证测试或最小复现。优先级由“影响 × 可达性 × 恢复难度”决定，而不是由代码是否漂亮决定。

**每条反馈必须落一个标签**，不允许无标签的问题进入清单：

| 标签 | 含义 | 处置 |
| --- | --- | --- |
| **阻断** | 满足三条件，违反当前合同或造成实质可观察错误 | 解决前不能宣布通过；是否实施修复由用户授权 |
| **建议** | 有实际收益但不违反当前合同，或属于低风险加固 | 变更方决定是否本轮处理 |
| **待确认** | 无法当场核实可达性或影响 | 标注核实方法，不冒充确定问题 |
| **单独记录** | 与本次变更无因果关系的历史问题 | 移出本轮，另开条目 |

以下情况按标准降级或过滤：

- 只对假设中的未来调用者有意义：通常不要求本轮处理。
- 现有上游已经保证，重复校验没有独立收益：通常不要求增加。
- 需要引入新框架或重构大片代码才能消除极小风险：优先接受残余风险。

## 6. 修复建议必须同时定义「改什么」和「不改什么」

修复建议说明最小改动、保留行为和验收方式；涉及所有权或跨组件边界时，再明确：

- 应删除、移动或统一到哪个所有权边界。
- 是否需要统一实现入口；已有边界足够时不新增抽象。
- 必须保留哪些既有行为。
- 哪些相邻模块不需要修改。
- 需要什么反证测试。
- 验收时观察什么外部结果。

通用形态示例（针对“未经验证的路径写入”类问题）：不是“全面改造文件系统写入”，而是：

- 有请求上下文的创建统一交给安全物化器；
- 合同明确不受影响的内部路径保持原行为；
- 增加运行器级“外部零新增文件”反证测试；
- 不扩展到普通产物写入。

明确边界的建议才能显著降低二、三阶问题。

## 7. 修复后必须做二、三阶影响矩阵

仅在复审修复结果时应用本节。不能只验证原问题消失，还要按实际涉及的路径和状态选择检查项，不为不存在的状态增加测试：

- 正常路径是否仍成功。
- 新建与复用状态是否分别符合合同。
- 失败路径是 fail-open 还是 fail-closed，是否符合原合同。
- 已有重试、恢复等旁路是否仍正常。
- 旧状态、残留文件、软链、非普通文件是否处理一致。
- 是否改变调用顺序、持久化顺序或可见性窗口。
- 是否新增另一条旁路。
- 是否破坏兼容调用者。

检查原缺陷的回归测试、正常路径及受影响的兼容路径。已有测试能覆盖时复用，没有相应兼容路径时不强凑测试类别；仅审查时指出测试缺口，不自动修改测试。

## 8. 终审必须重新审完整范围，而不是只验上一条问题

本节产物是复审结论。在用户请求终审或复审时同时检查：

1. 增量检查：确认本轮修复没有引入新问题。
2. 全范围检查：重新按冻结合同遍历全部入口和状态，确认没有同类残留。

只做第一轮，会漏掉此前未发现的问题；只做第二轮而不分析修复差异，又容易忽略修复引入的回归。

全范围检查的成本可按合同分级：冻结合同中标注哪些不变量属于**每轮必扫**（安全 / 数据完整性 / 失败语义类），哪些属于**触及即扫**（仅当本轮修复触及对应组件时重扫）。分级在冻结合同时定，不在终审时临时裁量。

## 9. 变更方自查：重排「检查 / 写入」顺序前，先列全部确定性失败

仅在变更涉及“检查 / 写入”顺序时应用本节：评审方核对清单；获得修复授权后，变更方在重排前列出清单。避免只移动当轮被指出的一条检查而留下同类旁路。

判据（一句话，可执行）：

> 调整"检查 / 写入"顺序前，先把该边界上**全部**确定性失败列成清单，逐条确认都排在第一个破坏性写入
> 之前。清单要分两族：**形态族**（类型不对、被异物占据、目标在托管集合之外）与**能力族**（本次实际
> 要写 / 要枚举的每个目录的权限）。只挪被点名的那一条 = 下一轮同族复发。

该原则适用于合同要求提前拒绝、且能在写入前判定的失败。权限预检不保证实际操作成功，不能替代操作时的错误处理；并发变化和检查后使用竞态需要单独分析，不能用预检宣称消除。

至少检查两个容易漏的位置：

- **注入的 callback**：代码可能位于别的模块，沿调用链正向查看时容易漏掉。
- **看似只读的下行**：路径遍历中的迁移、替换或清理分支可能产生破坏性副作用；排在该操作之后的检查已经太晚。

刻意**不**规定状态矩阵画法或测试格数——那属于第 7 节，且重流程会被跳过。

## 通过条件

只有同时满足以下条件才能宣布通过：

- 约定范围内的不变量有实现依据和必要的验证证据。
- 范围内相关的真实入口、替代路径和失败路径已枚举。
- 所有同类出口已完成全域搜索，**且留有扫描方法证据**。
- 确定问题有可核查的路径或复现证据、明确分级和最小修复建议；不把待确认项当成确定问题。
- 按仓库要求应执行的相关测试已通过；复审时同时验证原问题和受影响的兼容路径。
- 没有未验证假设被包装成结论。
- 剩余风险已明确说明且不构成当前合同违约。
- 若本次改动动过「检查 / 写入」的先后顺序：第 9 节那份确定性失败清单已列出并逐条确认。

## 评审证据与输出

评审结论必须区分“已验证”和“未验证”。能运行测试、构建或最小复现时，记录实际命令及结果；无法运行时，说明缺少的环境、权限或依赖，不得将未执行的检查写成通过。

存在阻断问题时结论为“不通过”；没有已证实的阻断但关键验证缺失时为“待确认”；满足通过条件时才写“通过”，且仅代表已声明范围内未发现阻断问题。

优先遵循用户或调用环境规定的输出格式。否则使用以下简式，按需合并字段，不必机械展开空项；扫描记录保持简短，不粘贴无关日志：

```
结论：通过 / 不通过 / 待确认

问题清单（按优先级）：
- [阻断] 文件:行号
  - 违反的合同：
  - 真实路径：
  - 影响：
  - 证据：
  - 最小修复：
  - 不改范围：
  - 验收方式：

扫描证据：
- 搜索模式：
- 覆盖路径与状态：
- 未执行检查及原因：
```

建议、待确认项和历史问题与阻断清单分开。没有问题时也要说明扫描范围、测试结果和剩余风险。
